# 2027 DevOps 로드맵

> 작성일: 2026-10-14 · 재직 중 학습 기준 · 코딩테스트는 매일 유지, 오픽 집중 후 GCP ACE 준비

## 목표와 출발점

목표는 GCP 서비스의 배포·관측·복구·인프라 구성을 설명하고 재현할 수 있는 DevOps 엔지니어다.
백엔드 개발과 클라우드 운영을 함께 맡는 포지션도 지원 대상으로 삼는다.
공기업 전산·금융 IT 지원은 병행하되, 각 공고의 시험 준비에 맞춰 학습 시간을 조정한다.
학습을 모두 끝내기 전에도 현재 경력과 맞는 공고에는 지원한다.

현재 자료에서 확인되는 경험과 다음에 확보할 증거를 구분한다.

| 현재 경험 | 다음에 확보할 증거 |
|---|---|
| Cloud Run·Cloud SQL·Secret Manager 구성, 홈페이지·CRM 운영 | 리소스와 권한 관계를 설명하는 구성도, 동일 환경을 재현하는 절차 |
| Dockerfile 오선택 분석, 이미지 빌드와 배포 분리, 응답 검증 및 롤백 | 실패한 빌드·검증이 배포를 막는 자동화, 이전 이미지로 복구한 기록 |
| DNS·인증서·로드밸런서, gzip·CDN 버퍼링 문제 대응 | Linux·네트워크 진단 명령과 근거로 원인을 좁히는 실습 기록 |
| 원격 DB 조회·조인 타입·동시 실행 문제 분석 | 부하 조건을 기록한 측정, 병목 분석, 변경 전후 비교 |
| Python·TypeScript 백엔드와 실시간 이벤트 전달 | 테스트 가능한 운영용 API, 구조화 로그와 지표·알림 |

기존 경험의 상세 근거는 [경력기술서 원문](../경력기술서/경력기술서_TMI.md)에 있다.
프로젝트 규모·성능 수치를 새 문서에 인용할 때는 [실측 지표](../portfolio/프로젝트_지표.md)를 먼저 확인한다.
Terraform·Kubernetes·관측 시스템은 아래 실습으로 증거를 확보할 항목이며, 기존 실무 경력으로 미리 기재하지 않는다.

현재 토스 DevOps 공고에는 배포 자동화, 모니터링·로깅, Kubernetes, 비용 최적화, 장애 복구와 IaC 경험이 제시돼 있다.
아래 학습 순서는 이 업무들과 현재 경험을 연결하기 위한 개인 계획이다. 전체 채용시장의 공통 기준으로 단정하지 않는다.

## 공부 시간을 배분하는 방법

오픽을 준비하는 동안은 주당 약 8시간을 시작 가정으로 둔다.

- **코테:** 매일 30분. 새 문제 풀이 또는 이전에 도움받은 문제를 코드 없이 재구현한다. 어려운 문제는 여러 날 이어서 풀어도 된다.
- **오픽:** 평일 25~30분. 목표 공고의 인정 기준을 확인해 목표 등급과 응시일을 정한다.
- **DevOps:** 주말 2시간. 한 번에 한 실습과 그 결과 기록까지 마친다.
- **업무 중:** 실제로 담당한 배포·장애·DB 문제에서 판단 근거를 기록한다. 사내 시스템 변경은 정상 업무 절차 안에서 진행한다.

오픽을 마친 뒤에는 해당 시간을 ACE와 DevOps 실습으로 옮긴다.
공기업·금융 IT 필기 일정이 생기면 ACE·실습 시간 일부를 전공·NCS·코테 모의시험으로 전환한다.
모든 과목을 기존 일정 위에 계속 추가하지 않는다.

코테 언어는 현재 익숙한 Python을 기본 후보로 두고, 실제 응시 공고의 허용 언어를 확인한다.
주말에는 틀린 문제를 복습하거나 시간 제한을 둔 풀이를 한다.

## 1단계: Linux·네트워크·Docker

**연결할 업무 경험:** 컨테이너 배포, 기존 Windows/IIS와 신규 GCP 환경 운영, DNS·CDN 문제 대응.

Linux에서 프로세스·권한·환경변수·포트·로그·디스크를 확인하고, 요청이 어디에서 실패했는지 설명한다.
WSL2 또는 기존 Linux 개발 환경에서 `ps`, `ss`, `curl`, `dig`, `df`, `du`를 사용한다.
HTTP 상태·헤더·본문, DNS 해석, TLS, 프록시·로드밸런서, 연결·응답 타임아웃을 실제 요청과 연결한다.

Docker는 이미지와 컨테이너의 차이, 빌드 컨텍스트·캐시, 멀티 스테이지 빌드, 포트·네트워크·볼륨,
환경변수, 종료 신호와 graceful shutdown을 점검한다.
직접 작성한 작은 FastAPI 앱과 PostgreSQL을 Docker Compose로 실행한다.

**완료 기준:**

- [ ] README만 보고 API와 DB를 실행하고 정상 종료할 수 있다.
- [ ] 포트 오류·DB 접속 오류·잘못된 환경변수를 각각 재현하고 로그와 명령으로 원인을 확인한다.
- [ ] 데이터가 컨테이너 재생성과 볼륨 삭제에서 어떻게 달라지는지 설명한다.
- [ ] 자신의 서비스에서 브라우저→DNS→TLS→애플리케이션→DB 경로를 그린다.

[Docker 공식 학습 자료](https://docs.docker.com/get-started/)

## 2단계: GCP ACE와 배포 자동화

ACE는 **취득을 목표로 준비**한다. 현재 경험을 공식 시험 가이드에 대조해서 부족한 영역을 채운다.
Google은 ACE에 GCP 실무 경험 6개월 이상을 권장하며, 환경 설정·솔루션 구현·운영·접근 및 보안을 평가한다.
자격증 공부와 실습을 함께 진행한다. [ACE 공식 안내와 최신 시험 가이드](https://cloud.google.com/learn/certification/cloud-engineer)

Cloud Run·Cloud SQL·Secret Manager는 실제 경험을 다시 설명하고,
IAM·서비스 계정·리소스 계층·Compute Engine·VPC·스토리지·GKE 등 시험 가이드에서 부족한 영역을 점검한다.
응시 예약 전에는 그때의 공식 시험 범위와 샘플 문제를 다시 확인한다.

실습 프로젝트의 CI/CD는 익숙한 Cloud Build를 먼저 사용한다.
테스트·이미지 빌드·Artifact Registry 저장·Cloud Run 배포·응답 검증을 단계별로 연결한다.
배포할 이미지 식별자를 기록하고, 상태 코드뿐 아니라 Content-Type과 필요한 응답 필드도 확인한다.
검증 실패 시 이후 단계를 중단하고 이전 정상 리비전으로 복구하는 절차를 만든다.

**완료 기준:**

- [ ] 테스트 실패가 배포를 막는 것을 직접 확인한다.
- [ ] 배포된 리비전과 이미지·소스 버전을 대조할 수 있다.
- [ ] 정상 상태 코드로 잘못된 본문을 반환하는 경우도 검증에서 잡는다.
- [ ] 실패한 배포를 이전 리비전으로 복구하고 탐지·복구 시각과 확인 근거를 남긴다.
- [ ] 애플리케이션 롤백과 DB 스키마 변경의 복구가 다른 문제임을 설명한다.
- [ ] ACE 취약 영역을 실습·정리하고, 공식 샘플의 정답 근거와 오답 이유를 설명한다.

[Cloud Build로 Cloud Run 배포](https://docs.cloud.google.com/build/docs/deploying-builds/deploy-cloud-run) · [Cloud Run 트래픽 전환과 롤백](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)

## 3단계: 관측·장애 대응·성능

처음에는 Cloud Logging·Cloud Monitoring으로 시작한다.
Cloud Run은 요청 수·지연·CPU·메모리 등의 지표를 제공하며, 모니터링과 알림을 연결할 수 있다.
[Cloud Run 관측 공식 문서](https://docs.cloud.google.com/run/docs/monitoring)

요청 ID와 배포 버전을 구조화 로그에 넣고, 오류율·p95 지연·리소스 사용을 함께 본다.
학습용 서비스에서 지연·오류·DB 연결 실패를 주입하고 알림→원인 확인→복구→재검증을 수행한다.
사용자가 겪는 실패와 내부 지표의 관계를 정리하고, 가용성·지연에 대한 SLI/SLO를 작게 설계한다.
부하 실습은 요청 패턴·동시성·실행 환경·측정 구간을 기록하고 변경 전후를 비교한다.

**완료 기준:**

- [ ] 대시보드와 알림에서 문제를 확인하고 관련 로그까지 추적한다.
- [ ] 지연 증가가 앱 처리·DB·리소스·네트워크 중 어디와 관련되는지 근거를 제시한다.
- [ ] 장애 보고서에 영향·시간순 경과·원인·복구·재발 방지를 정리한다.
- [ ] 성능 비교의 환경·조건·한계를 적고, 측정하지 않은 수치를 성과로 쓰지 않는다.

Prometheus·Grafana는 목표 공고에 필요하거나 Kubernetes 단계에 들어갈 때 추가한다.

## 4단계: Terraform으로 인프라 재현

실습용 Cloud Run·Artifact Registry·서비스 계정·권한 등의 구성을 Terraform으로 관리한다.
`init`, `fmt`, `validate`, `plan`, `apply`, state, drift, import를 이해한다.
기존 회사 리소스 대신 직접 만든 학습 환경에서 생성·변경·정리를 연습한다.
비밀값 원문과 state는 공개 저장소에 올리지 않고, 상태 저장소의 접근과 관리 방법을 문서화한다.

**완료 기준:**

- [ ] 새 실습 환경에서 문서와 코드로 필요한 리소스를 재현한다.
- [ ] plan에서 어떤 변경이 일어나는지 설명한 뒤 적용한다.
- [ ] 콘솔 변경으로 생긴 차이를 발견하고 코드와 실제 상태를 맞춘다.
- [ ] 리소스 재현과 state 관리의 역할을 구분한다.
- [ ] 실습 종료 후 리소스를 정리하고, 앱·DB·저장 데이터의 수명 차이를 설명한다.

[Google Cloud Terraform 공식 문서](https://docs.cloud.google.com/docs/terraform)

## 5단계: Kubernetes

앞선 앱과 이미지를 로컬 kind 또는 minikube에 배포한다.
Pod·Deployment·Service·ConfigMap·Secret·probe·requests/limits·rolling update·rollback을 실습한다.
`kubectl get`, `describe`, `logs`, 이벤트와 rollout 상태로 원인을 추적한다.
클러스터의 Secret 객체와 외부 비밀값 관리, readiness와 liveness의 역할도 구분한다.

**완료 기준:**

- [ ] 같은 이미지를 Cloud Run과 Kubernetes에 배포하고 각 환경이 담당하는 운영 범위를 설명한다.
- [ ] 잘못된 이미지·probe 실패·OOM 상황을 실습 환경에서 진단한다.
- [ ] 업데이트·롤백을 실행하고 요청 처리와 종료 동작을 확인한다.
- [ ] YAML이 실제로 만드는 리소스와 연결 관계를 설명한다.

GKE·Helm·Argo CD는 이 단계의 기본 동작을 설명한 후 필요한 것부터 확장한다.
AWS는 지원할 공고가 요구할 때 IAM·네트워크·컨테이너·관측 개념을 대응시켜 학습한다.
[Kubernetes 공식 기초 학습](https://kubernetes.io/docs/tutorials/kubernetes-basics/)

## 공개할 실습 프로젝트

가칭 **gcp-service-ops-lab**을 하나 만들고 단계마다 같은 앱을 발전시킨다.
직접 작성한 FastAPI와 간단한 샘플 업무 데이터로 구성한다. 현재는 계획이며, 아직 구현한 프로젝트가 아니다.

| 영역 | 저장할 자료 |
|---|---|
| 앱·로컬 실행 | 작은 CRUD API, 상태 확인 엔드포인트, 테스트, Dockerfile, Compose |
| 배포 | Cloud Build 설정, 이미지 식별, 응답 검증, 롤백 절차 |
| 관측 | 구조화 로그, 대시보드·알림 구성과 화면, 장애 실습 기록 |
| 인프라 | Terraform 구성, 상태 관리 안내, 재현·정리 절차 |
| Kubernetes | manifests, 실행·진단·업데이트·복구 기록 |
| 설명 | 구성도, 선택 이유, 한계, 장애 보고서와 부하 실습 결과 |

처음부터 모든 디렉터리를 채우지 않는다. 완료한 실습만 공개하고, 회사 경험은 담당 범위와 판단 과정으로 별도 정리한다.
실습에서 확인한 범위와 실제 운영 경험을 경력기술서에 구분해 적는다.
