## 1순위: Node.js Developer (Operations)

[공고](https://toss.im/career/job-detail?gh_jid=6679884003)

**하는 일**: 결제단말기 생애주기·물류 관리 플랫폼, 외부 물류 시스템 연동, 사내 업무 자동화와 Internal Product(어드민). TypeScript·Node.js·NestJS 기반 서버·배치·내부 제품.

법승에서 하는 일(사내 수작업을 시스템으로 바꾸기, 외부 API 연동, 어드민 직접 만들기)과 거의 같다.
공고가 말하는 "문제 정의부터 설계, 성과 측정까지 주도"는 1순위 포지셔닝(프로덕트 엔지니어)과도 맞는다.

| 공고 요구 | 근거 | 판정 |
|---|---|---|
| TypeScript · NestJS | 홈페이지 V2 백엔드 NestJS 1인 구축(엔드포인트 146개 · 16,254 LOC), 사내 포털 TypeScript | ✅ |
| MikroORM | 사용 경험 없음(Prisma · SQLAlchemy). SQLAlchemy 세션 훅(flush 전후 · 커밋 후)으로 감사로그와 실시간 이벤트를 전역 처리한 경험은 MikroORM의 Unit of Work · flush 이벤트와 같은 개념 | △ 연결 가능 |
| MySQL | CRM을 MySQL(Cloud SQL)로 운영하며 `GET_LOCK`으로 다중 인스턴스 스케줄러 중복 실행 차단. 이후 PostgreSQL로 이관 | ✅ |
| Redis | 실무 경험 없음. Redis 대신 LISTEN/NOTIFY · `GET_LOCK`을 고른 판단 근거는 있음 | ❌ 보강 필요 |
| REST · Open API로 데이터 수집 · 적재 · 가공 | Google Workspace API군, 공공데이터포털 특일정보 API, GA4 Data API, 레거시 → V2 동기화(HTTPS 밀어 넣기로 전환), SQL Server → PostgreSQL 731만 행(41개 테이블), 구글시트 → DB 9.8만 건 | ✅ 강함 |
| 자동화 · 시스템화로 일하는 방식 개선 | 구글시트 수기 관리 → CRM, Google Sites · 크롬 익스텐션 → 사내 포털, 열람등사 도과 자동 알림, 구성원 수정 시 수신 번호표 Job 즉시 재실행, 지점 사이트맵 자동 갱신 | ✅ 강함 |
| 우대: React로 어드민 직접 개발 | 사건관리 React 업무 화면(2인 팀), 홈페이지 V2 어드민 CMS 37화면, 사내 포털 | ✅ 강함 |
| 물류 · 운영 · 고객지원 흐름에 관심 | 10개 지사의 상담 접수 → 배정 → 예약 → 문자 안내 흐름을 CRM으로 구축 | ✅ (물류 도메인은 없음) |
| 가독성 · 유지보수 가능한 코드 | 사전과제에서 판정 | 과제 |

**부족한 것**

- Redis · MikroORM 실습이 없다. 과제가 공고 스택으로 나올 수 있다.
- 자동화 효과를 보여 줄 숫자가 약하다. 공고는 "프로젝트 전후 개선된 점"을 요구한다. 사용자 수, 하루 처리 건수, 없어진 수작업 같은 값을 재서 지표 파일에 먼저 기록한 뒤 인용한다.
- 사내 도구라 사용자 · 트래픽이 작다. 규모를 부풀리지 않고 "작은 조직에서 혼자 전 과정을 맡았다"로 쓴다.

**이력서에 앞세울 사례**

1. 구글시트 수기 관리 → CRM: 데이터 이관, 시트와 공존하는 과도기 동기화, 동시 접수 점유, 스케줄러 락
2. 레거시 → V2 동기화: "포트 차단" 오진을 재측정으로 바로잡고 HTTPS 밀어 넣기로 전환, 종료코드 0으로 숨은 실패 감시, 상담 305건 복구
3. 사내 포털: 크롬 익스텐션의 구성원 관리 흡수, fail-closed 권한, 로그인 직후 첫 화면 7.3초 → 1.5초

## 보류 · 해당 없음

- **Server Developer (Platform)**: SSE 서버, 분산 락, 인증 · 인가, 타임아웃 · 재시도 · 중복 처리 근거가 꽤 있다. 공고도 "언어 · 프레임워크에 관계없이 써도 된다"고 한다. 그러나 전사 공통 서비스와 Java · Kotlin 라이브러리를 맡고 여러 팀과의 조율을 본다. 이번엔 보류.
- **Frontend Platform Engineer**: Turborepo 모노레포와 빌드 개선 근거는 있다. 그러나 Electron · MFA · AWS · Terraform과 "여러 팀의 개발환경 변화까지 완수"를 본다. 보류.
- **SRE · DevOps**: 첫 SRE와 DevOps 리드 자리. 프로덕션 K8s 운영 경험이 필수다. [로드맵](../../roadmap/2027_DevOps_로드맵.md)의 장기 기준으로만 둔다.
- **Android · iOS · QA**: 직무가 다르다.
- Engineering 탭 밖: Technical Product Owner는 PO 챕터가 5~15년 차라 해당 없음. IT Operations Specialist는 3년 이하도 지원할 수 있지만 1년 계약직 사내 IT 지원이라 커리어 방향과 다르다.

## 공통 준비

- **이력서 형식**: 토스 공고들이 공통으로 요구하는 순서로 쓴다. 문제 → 왜 중요했고 어떤 제약 → 내 역할과 판단(검토한 대안) → 전후 변화. 포지션마다 앞세울 사례만 바꾼다.

- **2인 팀 표기**: 사건관리 앱은 2인 팀(내 커밋 23%)으로 쓴다.
- **레퍼런스 체크**: 모든 포지션 전형에 있다. 부탁할 사람을 미리 정해 둔다.

- 배송 상태 동기화 배치를 Redis 락으로 한 번만 실행 (`GET_LOCK` 경험과 비교)
- MikroORM 이벤트로 상태 이력 자동 기록 (SQLAlchemy 세션 훅 경험과 비교)
- README에 설계 판단과 트레이드오프
- 로드맵 트랙 C 1주차 앱을 이 프로젝트로 대신한다. 이력서에는 "개인 실습"으로만 쓴다.

기초 점검: 이벤트 루프, `Promise.all` 실패 처리, NestJS 요청 처리 순서(미들웨어 → 가드 → 인터셉터 → 파이프 → 핸들러 → 예외 필터), MySQL 격리 수준과 잠금, Redis 자료형과 TTL.
