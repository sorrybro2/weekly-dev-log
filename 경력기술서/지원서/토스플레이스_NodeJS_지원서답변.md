## 5. Node.js Developer 사전질문 1 — 기술적 난제 해결 사례 (최소 2개)

**넣는 순서** 사례 A(외부 시스템 연동, 데이터 복구) → 사례 B(측정으로 원인 찾기) → 칸을 더 붙일 수 있으면 사례 C(NestJS 장애 격리).
세 사례 모두 이력서와 포트폴리오에 같은 내용이 있어, 2차 인터뷰에서 어디를 물어도 같은 이야기로 이어진다.
칸이 사례마다 따로가 아니라 **700자 칸 하나**라면 아래 압축본 하나만 넣는다.

#### 사례 A. 성공으로 표시되던 연동 배치 재설계 (622자 / 700)

```text
[성공으로 표시되던 연동 배치를 다시 설계하다]
레거시 홈페이지의 게시물과 상담을 신규 홈페이지로 옮기는 배치가 2주간 스케줄러에는 성공으로 표시됐지만 실제로는 멈춰 있었습니다. 처음에는 레거시 DB 포트 차단으로 기록했지만, 설정 파일과 실제 접속을 다시 측정하니 레거시가 실제로 쓰는 포트는 열려 있었고 끊긴 곳은 클라우드 DB의 접속 허용목록이었습니다.
진짜 문제는 두 가지였습니다. 배치가 두 DB에 직접 붙어 끊길 곳이 두 군데였고, 마지막 명령이 echo라 실패해도 종료코드가 0이었습니다. 고정 IP용 NAT(연 약 60만 원)도 검토했지만, 레거시 쪽이 자기 DB를 읽어 신규 NestJS 백엔드의 HTTPS API로 밀어 넣는 방식으로 바꿔 DB 외부 개방과 허용목록 의존을 없앴습니다.
복구 중에는 두 시스템이 같은 상담 번호를 서로 다른 접수에 발급한 것도 발견했습니다. 접수 고유키로 대조하고 저장할 때 새 번호를 발급해 상담 305건과 게시물 61건을 복구했고, 재실행해도 중복 저장되지 않는 것을 확인했습니다. 실패 즉시 알림과 별도로, 26시간 동안 성공 기록이 없으면 다른 기계에서 알리는 감시를 두었습니다. 배치는 실패뿐 아니라 아예 돌지 않은 것도 잡아야 한다는 것을 배웠습니다.
```

#### 사례 B. 같은 함정을 두 번 찾아낸 첫 화면 개선 (597자 / 700)

```text
[같은 함정을 두 번 찾아낸 첫 화면 개선]
사내 포털이 느리다는 의견이 나왔습니다. 운영 요청 로그 일주일치를 나눠 보니 첫 화면의 약 30%가 콜드스타트였고, 켜져 있을 때도 구성원 명부가 중간값 5.7초였습니다.
먼저 캐시를 의심했습니다. CRM 응답에 Next.js의 fetch 캐시를 걸어 두었는데, 캐시 키를 만드는 소스를 확인하니 요청 헤더까지 키에 들어갔습니다. 토큰의 발급 시각이 매번 달라 캐시는 한 번도 적중하지 않았습니다. 응답이 보는 사람과 무관하다는 것을 CRM 코드로 확인한 뒤 인스턴스 메모리 캐시로 바꿨습니다.
그다음 로그인 직후 첫 화면이 7.3초인 것을 확인했습니다. 지사별 내선을 약 20명분 모두 받을 때까지 기다린 탓이라, 기억해 둔 값으로 먼저 그리고 뒤에서 갱신하게 해 4.48초가 됐습니다. 남은 시간은 구글 디렉터리 조회에 있던 같은 함정이었습니다. 새 access token이 키에 섞여 로그인마다 캐시가 비었고, 이를 고쳐 1.50초가 됐습니다.
콜드스타트는 최소 인스턴스 1대로 막고, 화면이 더 이상 기다리지 않게 된 연결 서비스는 0대로 되돌렸습니다. 이후 캐시를 둘 때는 적중 여부를 응답 시간으로 확인합니다.
```

#### 사례 C. DB 순간 장애가 전체 장애로 번지던 구조 (609자 / 700)

```text
[DB의 순간 장애가 서비스 전체 장애로 번지던 구조를 끊다]
홈페이지 백엔드(NestJS)가 6분 39초 동안 모든 요청에 500을 반환했습니다. 로그를 따라가 보니 Cloud SQL 커넥터가 잠깐 타임아웃된 순간, Prisma 연결을 맡은 서비스의 onModuleInit이 재시도 없이 예외를 던졌습니다. Nest 부팅이 실패하자 Cloud Run이 인스턴스를 종료했고, 시작 검사(startup probe)를 통과하지 못하는 상태가 이어졌습니다. DB가 잠깐 흔들린 것이 서비스 전체 중단으로 커진 것입니다.
기동 시 DB 연결을 0.5초에서 8초까지 간격을 늘려 가며 5회 재시도하게 했습니다. 재시도를 모두 소진해도 예외로 죽지 않고 기동을 이어가, DB가 돌아오면 자동으로 다시 연결되도록 바꿨습니다. 순간 장애에는 재시도로 버티고, 긴 장애에도 프로세스가 죽지 않게 해 복구를 사람의 재배포에 의존하지 않게 한 것입니다.
같은 서비스의 상담 접수에서는 CRM으로 넘기는 요청을 응답을 기다리지 않는 경로로 두어, 다른 시스템의 장애가 고객의 상담 접수를 막지 않게 했습니다. 이 일 이후 외부 의존성을 붙일 때마다 이것이 실패하면 무엇이 같이 멈추는지를 먼저 따지고 있습니다.
```

레거시에서 신규 홈페이지로 데이터를 옮기는 배치가 2주간 성공으로 표시됐지만 실제로는 멈춰 있었습니다. 마지막 명령이 echo라 종료코드가 늘 0이었고, 포트 차단으로 기록했던 원인도 재측정하니 클라우드 DB 허용목록이었습니다. DB에 직접 붙는 구조를 NestJS 백엔드의 HTTPS API로 밀어 넣는 방식으로 바꿔 허용목록 의존을 없앴고, 번호 충돌을 접수 고유키로 대조해 상담 305건과 게시물 61건을 복구했습니다. 실행 기록이 26시간 없으면 알리는 감시도 다른 기계에 두었습니다.

## 6. Node.js Developer 사전질문 2 — 코드 철학 및 품질 관리

#### 코드 철학 (624자 / 700)

```text
[다음 사람이 틀리기 어렵게 만드는 코드]
제가 생각하는 좋은 코드는 읽기 쉬운 것을 넘어, 다음에 고치는 사람이 실수하기 어렵게 만드는 코드입니다. 그래서 세 가지를 지킵니다.
첫째, 실패를 조용히 덮지 않습니다. 권한 연동이 실패하면 DB 권한으로 넘어가는 폴백 때문에 직원 109명의 역할을 몇 달간 한 번도 읽지 못했는데도 화면은 정상으로 보였습니다. 이후 권한 판정은 원본을 못 읽으면 막고, 어떤 경로로 판정했는지 로그에 남깁니다.
둘째, 사람의 기억에 기대는 규칙을 구조로 옮깁니다. API 키가 배포 과정에서 두 번 빠진 뒤로 비밀값은 빠지면 배포 자체가 실패하게 했고, 마이그레이션은 적용됐는데 모델 컬럼이 빠져 500이 난 뒤로 스키마와 모델의 정합성을 자동으로 검사합니다. 실제로 새어 나온 오류는 회귀 테스트로 고정합니다.
셋째, 값마다 원본을 한 곳에 둡니다. 이름과 내선은 CRM, 조직도 배치는 포털처럼 바뀌는 주체가 다른 데이터를 나눠야 서로 어긋나지 않습니다.
지속 가능한 소프트웨어는 왜 이렇게 만들었는지가 남아 있는 소프트웨어라고 생각합니다. 커밋마다 이유를 본문에 적고 원인 분석과 설계 판단은 이슈에 남겨, 몇 달 뒤의 저나 동료가 같은 고민을 처음부터 다시 하지 않게 합니다.
```
