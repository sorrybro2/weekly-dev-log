### ❌ 반드시 수정해야 하는 항목

`경력기술서_TMI.md`의 KOGAS 항목에 본인이 직접 남긴 문장:

> **분석한 배포 구조**: Docker 멀티스테이지 빌드로 생성한 Go 바이너리를 Linux systemd 서비스로 운영.
> 아래 항목은 **기존 시스템을 읽고 파악한 내용이며 본인의 신규 구현 범위와 구분합니다.**

`경력기술서.md`의 해당 항목 제목도 **"KOGAS — 신규 개발을 위한 기존 시스템 코드 분석"**이다.
Gorilla WebSocket 허브도 Docker/systemd도 **읽고 분석한 기존 코드**이지 본인 구현물이 아니다.

**위험도가 특히 높은 이유**: 지원처가 ETRI이고, 리얼타임테크는 ETRI 과제 수행사다.
2번 문항에서 본인이 "ETRI CCTV 시스템 유지보수 경험"을 직접 언급했으므로 레퍼런스 체크가 실제로 가능하다.
여기서 "구현"이 "분석"으로 드러나면 검증된 다른 성과(160배, 730만 건)까지 함께 의심받는다.

# 제출 형식 주의 — 특수문자

공고 원문: **"자기소개서 작성 시 특수문자나 특수기호 등을 입력할 경우 에러 발생의 요인이 될 수 있음"**

작성해 둔 답변을 스캔한 결과다. ASCII 문자(`[`, `]`, `&`)는 대체로 안전하나, **비ASCII 기호는 치환할 것.**

| 문항 | 검출된 기호 | 조치 |
| --- | --- | --- |
| 1번 수정안 | `·` x2 | 공백 또는 쉼표로 |
| 2번 원안 | `·` x2 | 공백 또는 쉼표로 |
| 3번 원안 | `→` x1 | `에서`로 풀어쓰기 |
| 3번 수정안 | `→` x2 | `에서`로 풀어쓰기 |
| 4번 수정안 A/B | 없음 | 안전 |
| 5번 원안 | `•` x3 | 줄바꿈 또는 `-` |
| 5번 수정안 | `•` x3, `·` x3 | 위와 동일 |

**치환 규칙**

- `→` 는 `8초에서 0.05초로`, `1695ms에서 109ms로` 처럼 풀어쓴다
- `·` 는 공백 또는 쉼표로 (`학과-학생`의 하이픈은 ASCII라 안전)
- `•` 는 줄바꿈으로 항목을 구분하거나 ASCII 하이픈 `-` 로
- `[`, `]`, `&`, `%`, `(`, `)` 는 유지 가능

입력 후 **저장을 한 번 눌러 에러 여부를 확인**할 것. 에러가 나지 않으면 그대로 두어도 된다.

## 3-2. 개척인 (Pioneer) — 300~1000자

> 적극적 진취적 자세로 성취를 이루어낸 경험, **기존과 다른 방식으로 어려움을 극복 개선한 경험**, 사명감과 열정을 바탕으로 공동 성장 및 발전에 기여한 경험

**추천 소재 — SQLAlchemy 세션 훅으로 감사로그와 실시간 이벤트를 전역 구현**

"기존과 다른 방식"에 가장 정확히 부합한다. 통상적 방법은 엔드포인트마다 로그 코드를 넣는 것인데,
`before_flush`와 `after_flush`, `after_commit` 훅을 써서 **엔드포인트를 하나도 고치지 않고** 전역 적용했다.

**함께 쓸 수 있는 소재**

- **Cloud Run 다중 인스턴스 스케줄러 중복 실행** — 통상적 해법은 별도 분산 락 인프라 도입. 추가 인프라 없이 MySQL Named Lock(`GET_LOCK`)으로 해결
- **LISTEN/NOTIFY 기반 SSE** — 폴링 대비 추가 인프라 비용 0으로 실시간 동기화
- **외주 유지보수의 사내 전환** — 진취성 측면. 비용 절감과 대응 리드타임 단축

**서사 구조** 통상적 방법의 한계를 먼저 제시하고, 다른 경로를 택한 근거를 설명한 뒤, 결과를 수치로 마무리

```
제보를 듣는 방식도 협업입니다. 홈페이지가 6분간 전면 오류를 낸 적이 있는데, 대행사와 사내 홍보 담당자 양쪽에서 특정 버튼이 오류를 낸다는 제보가 왔습니다. 확인해 보니 버튼과 무관했고 그 시각 서버가 통째로 기동에 실패하고 있었습니다. 제보 내용은 정확하지 않았지만 제보가 없었다면 그 시각을 특정하지 못했을 것입니다. 개발을 모르는 분의 말은 원인이 아니라 증상으로 듣고, 그 증상이 언제 어디서 나왔는지를 단서로 씁니다.
```

## 4. 기타사항 (0~1000)

```
[만든 것을 버리는 판단]
요즘 가장 자주 생각하는 주제는 무엇을 만들지가 아니라 무엇을 만들지 않을지입니다.

업무 시스템에 실행취소 기능을 만든 적이 있습니다. 작업 단위로 되돌리는 동작을 쌓아 두는 구조였고, 적용 범위와 중복 실행 차단까지 검토해 완성했습니다. 그런데 실제 업무 흐름에 놓고 보니 되돌릴 일이 생기는 지점과 사용자가 되돌리고 싶어 하는 지점이 어긋나 있었습니다. 기능은 정상인데 쓸 자리가 없었습니다. 며칠을 들였고 검토까지 마쳤지만 폐기하기로 했습니다.

동작하는 코드를 지우는 일은 아깝습니다. 다만 쓰이지 않는 기능도 남아 있는 한 이후의 모든 변경에서 함께 고려해야 할 대상이 됩니다. 만드는 비용은 이미 지불됐고 유지 비용은 계속 나가는 것이라면 접는 편이 낫습니다. 대신 폐기한 이유는 남겨야 합니다. 기록이 없으면 다음에 같은 아이디어가 나왔을 때 같은 검토를 처음부터 반복하게 됩니다.

관심사는 일 밖에도 있습니다. 올해 봄부터 주짓수를 시작했습니다. 그동안 달리기와 웨이트, 수영처럼 혼자 하는 운동만 해 왔는데 그래플링은 상대가 있어야 성립한다는 점이 달랐습니다. 여기서 뜻밖의 것을 두 가지 얻었습니다.

하나는 이것이 또 하나의 사회생활이더라는 점입니다. 몸을 맞대고 연습하다 보면 말보다 빨리 가까워지고, 동시에 상대가 어디까지 괜찮은지를 계속 살피게 됩니다. 힘을 더 써도 되는 사람과 조심해야 하는 사람이 다르고, 그 조절을 못 하면 다음에 같이 할 사람이 없어집니다. 잘 지내는 일과 조심하는 일이 반대가 아니라 같은 것임을 도장에서 배웠습니다.

다른 하나는 오랜만에 아무것도 모르는 상태로 배우는 입장이 되어 본 것입니다. 시작한 지 얼마 안 돼 매번 지지만, 그 자리에 서 보니 익숙한 일에서는 보이지 않던 것이 보입니다. 처음 접하는 사람에게 설명할 때 무엇을 생략하면 안 되는지 같은 것들입니다. 제가 만든 화면을 처음 쓰는 사람도 같은 자리에 서 있을 것이라고 생각합니다.
```
