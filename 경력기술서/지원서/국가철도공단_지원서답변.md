### 1. 새로운 과제를 스스로 학습하고 적용한 경험

```
[처음 다루는 클라우드로 업무시스템을 처음부터 세운 경험]
입사 후 첫 과제는 전국 지사가 함께 쓸 고객관리 시스템을 만드는 일이었습니다. 업무는 스프레드시트로 돌아가고 있었고 서버도 데이터베이스도 배포 경로도 없었습니다. 클라우드는 실무에서 다뤄 본 적이 없었기에 공식 문서를 기준으로 관리형 데이터베이스, 컨테이너 실행 환경, 비밀값 저장소를 하나씩 익혀 구성했고, 스키마 설계부터 배포 파이프라인까지 직접 올렸습니다. 기존 데이터 약 9만 8천 건의 이관도 단독으로 수행했습니다.
운영 중 사용이 몰려 서버가 여러 대 뜨자 정해진 시각에 한 번만 돌아야 할 작업이 중복 실행됐습니다. 잠금 전용 저장소를 새로 두는 대신, 이미 쓰던 데이터베이스의 잠금 기능으로 같은 결과를 얻을 수 있음을 확인해 적용했습니다. 관리 대상을 늘리지 않는 해법이었습니다.
모르는 영역은 1차 자료로 원리를 먼저 확인하고, 작은 단위로 검증하며 적용한다는 제 학습 방식은 이때 만들어졌습니다.
```

### 2. 정보를 수집 분석해 개선 아이디어를 실행한 경험

```
[느린 화면의 원인을 쿼리가 아니라 데이터의 이동 경로에서 찾은 경험]
사내 업무시스템에서 상담료 처리 대기 목록을 여는 데 8초 이상 걸렸습니다. 먼저 실제로 어디서 시간이 쓰이는지부터 확인했습니다.
원인은 다른 데이터베이스의 데이터를 원격 테이블로 연결해 로컬 테이블과 조인하는 구조에 있었습니다. 이런 원격 조인은 조건이 원격 쪽으로 전달되지 않아, 조회할 때마다 원격 테이블 전체를 가져온 뒤 로컬에서 다시 거르고 있었습니다. 쿼리를 다듬는 것으로는 풀 수 없는 문제였습니다.
그래서 조인을 없애는 쪽으로 방향을 바꿨습니다. 필요한 일정을 먼저 조회하고, 그 결과에 필요한 이름과 사무소 정보만 묶어서 한 번에 가져오도록 재설계했습니다. 응답은 0.05초로 약 160배 빨라졌습니다.
같은 관점으로 다른 화면도 점검해, 비교하는 두 컬럼의 타입이 달라 인덱스를 쓰지 못하던 조회를 찾아 1695ms에서 109ms로 줄였습니다. 이후 성능 문제는 측정으로 원인을 먼저 좁힙니다.
```

### 3. 본인의 실수를 책임 있게 해결한 경험

```
[배포 실수를 덮지 않고 절차로 바꾼 경험]
업무시스템 배포 중 제 실수로 서비스가 9분간 멈췄습니다. 화면 빌드를 확인하려 이동한 폴더에서 그대로 배포 명령을 실행해, 서버가 빠진 이미지가 올라갔습니다. 더 큰 실수는 그다음이었습니다. 상태 확인 주소가 정상 코드를 돌려주는 것만 보고 정상이라 보고했는데, 그 응답은 서버 대신 화면 파일이 돌려준 것이었습니다.
원인 확인 즉시 올바른 경로로 재배포해 복구했고, 경위와 제가 잘못 판단한 근거까지 기록으로 남겼습니다. 그때는 경로만 바로잡고 절차는 그대로 두었고, 열흘 뒤 같은 유형의 배포 오류가 다시 발생해 27분간 서비스가 멈췄습니다.
이번에는 즉시 이전 버전으로 되돌린 뒤 폴더 기준 배포를 금지하고 빌드와 배포를 두 단계로 나눴으며, 배포 후에는 상태 코드가 아니라 응답 내용까지 확인하는 절차로 고정했습니다. 이 절차는 다른 시스템에도 적용했습니다. 실수를 고치는 것과 다시 일어나지 않게 하는 것은 다른 일임을 배웠습니다.
```

### 4. 역할이 크지 않더라도 공동체 목표에 자발적으로 기여한 경험

```
[맡은 범위 밖의 데이터까지 들여다본 경험]
미수금 관리 화면의 8월 미납액이 기존 장부와 1천만 원 넘게 차이 났습니다. 차액을 1원 단위까지 원인별로 나눠 보니, 장부에서 고친 값을 시스템이 다시 읽어 오지 못하는 동기화 결함으로 전액이 설명됐고, 관련 결함 3건을 이슈로 정리했습니다.
여기서 멈추지 않고 조사 범위를 8월에서 전 기간으로 넓혔습니다. 그 결과 장부가 아니라 데이터베이스 안에 같은 사무소, 같은 입금인, 같은 금액과 날짜로 이중 등록된 미수금 27쌍, 43,818,000원이 있었습니다. 자동 생성 경로는 원인이 아님을 먼저 확인했고, 전부 수기 입력 건임을 밝혔습니다.
운영 중인 회계 데이터였기에 제가 판단해 고치지 않았습니다. 조회만으로 조사를 마치고, 건별 근거를 정리해 승인 후 정리하도록 이슈로 넘겼습니다. 제 역할은 화면 개발이었지만, 그 숫자가 업무 판단에 쓰이는 이상 맞는지 확인하는 것도 만든 사람의 몫이라고 생각합니다.
```

### 5. 주어진 절차를 따르는 데 그치지 않고 개선한 경험

```
[기존 방식을 그대로 옮기지 않고 위험부터 걷어낸 경험]
홈페이지를 새 시스템으로 옮긴 직후, 광고 성과를 측정하는 태그가 빠져 전환 추적이 끊긴 상태였습니다. 가장 빠른 방법은 기존 시스템처럼 관리자 화면에 태그 스크립트를 통째로 붙여 넣는 칸을 만드는 것이었습니다.
그러나 그 방식은 관리자 화면에서 누구든 임의의 스크립트를 사이트 전체에 심을 수 있다는 뜻이었습니다. 그래서 스크립트 대신 태그 컨테이너의 식별값만 저장하고, 실제 스크립트는 코드가 생성하도록 바꿨습니다. 식별값은 화면과 서버 양쪽에서 형식을 검증해 잘못된 값이 들어가지 않게 했습니다.
경로별로 어느 지사의 태그를 쓸지 정하는 규칙은 기존 동작과 똑같이 재현했고, 페이지당 컨테이너를 하나만 불러 화면 전환 중 태그가 뒤섞이는 문제도 피했습니다.
결과적으로 마케팅 담당자는 개발자를 거치지 않고 관리자 화면에서 태그를 지정할 수 있게 되었고, 임의 스크립트가 들어갈 경로는 구조적으로 막혔습니다.
```

- [ ] 이전 직장 인턴 기간(일학습병행)이 건강보험자격득실확인서에 잡혀 있는지 — 없으면 그 기간은 경력에서 빠진다

- [ ] 사이트에서 글자수 재확인(공백·줄바꿈 계산 방식이 다를 수 있음)
