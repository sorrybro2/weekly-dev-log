## Q1. 높은 목표를 달성하기 위하여 다각도로 노력했던 경험 (602자 / 700)

```
[전국 10개 지사의 업무를 멈추지 않고 CRM으로 옮기다]
입사 직후 맡은 일은 전국 10개 지사가 구글시트에 손으로 기록하던 고객 접수, 상담 예약, 문자 기록을 사내 CRM으로 옮기는 것이었습니다. 저는 목표를 "CRM을 만드는 것"이 아니라 "현업이 멈추지 않고 넘어오는 것"으로 잡았습니다. 시트를 한 번에 끊으면 그날의 상담 예약이 멈추기 때문입니다.
그래서 세 갈래로 접근했습니다. 첫째, 당사자·상담·문자 기록 9.8만 건을 이관하고, Apps Script 트리거와 웹훅으로 시트와 DB를 양방향 동기화해 과도기에 두 방식이 공존하게 했습니다. 둘째, 목록 조회가 무한 로딩되자 원인을 페이지당 최대 480개의 서브쿼리에서 찾아 JOIN과 복합 인덱스로 다시 짰습니다. 셋째, 서버가 여러 대로 늘자 스케줄러가 중복 실행되고 직원들이 같은 접수 건을 동시에 덮어쓰는 문제가 생겼습니다. 추가 인프라 없이 DB Named Lock으로 실행을 하나로 묶고, 처리를 시작하면 점유했다가 10분 뒤 자동 회수하는 방식으로 충돌을 막았습니다.
그 결과 5월 정식 오픈 이후 전국 지사가 CRM으로 업무를 처리하고 있고, 저는 지금도 1인으로 개발과 운영을 맡고 있습니다.
```

## Q2. 현재에 안주하지 않고 기존과 다른 방식을 자발적으로 시도하여 문제를 해결한 경험 (619자 / 700)

```
[성공으로 보고되던 배치를 의심하고, 데이터 흐름의 방향을 뒤집다]
레거시 홈페이지의 글과 상담을 신규 홈페이지로 옮기는 동기화 배치가 있었습니다. 스케줄러에는 매일 성공으로 떠 있었지만, 직접 건수를 대조해 보니 2주치가 빠져 있었습니다. 배치의 마지막 명령이 늘 성공 코드를 남겨 실패가 가려져 있었습니다.
기존 구조는 사무실 PC가 레거시 DB와 클라우드 DB 양쪽에 접속해 데이터를 당겨오는 방식이라, 방화벽이나 허용목록 중 하나만 바뀌어도 끊겼습니다. 고정 IP를 둔 클라우드 작업으로 옮기는 안은 연 60만 원이 들었습니다. 저는 방향을 뒤집어 레거시 데이터를 신규 백엔드의 HTTPS API로 밀어 넣고 백엔드가 저장하게 바꿨습니다. 열어 둘 인바운드 포트와 허용목록이 사라졌고, 추가 비용은 0원이었습니다.
옮기는 과정에서 두 시스템이 같은 번호대로 상담 번호를 각자 발급해 42개 번호가 서로 다른 사람에게 배정된 것도 발견했습니다. 번호 대신 접수 고유키로 대조해 상담 305건과 게시물 61건을 복구했습니다. 끝으로 실패 알림과 별도로, 26시간 동안 실행 기록이 없으면 울리는 감시를 다른 기계에 두었습니다. 이제 "실패한 것"뿐 아니라 "아예 돌지 않은 것"도 그날 안에 드러납니다.
```

## Q3. 본인에게 낯설었던 것 혹은 다양한 것을 마주하고 포용했던 경험 (656자 / 700)

```
[처음 보는 법 조문을 설계 조건으로 받아들이다]
법무법인에 개발자로 들어와 가장 낯설었던 것은 코드가 아니라 법이었습니다. 홈페이지 문구 하나, 상담봇 답변 한 줄도 변호사 광고 규정의 적용을 받는다는 것을 개발하면서 알게 됐습니다.
2025년 개정 규정을 기준으로 사이트를 전수 점검했습니다. 소스와 DB, 게시물 4,452건을 대조해 금지된 '무료 상담' 표기 두 곳은 바로 걷어내고, 상담봇이 같은 표현을 내보내지 못하게 출력 필터에도 넣었습니다. 반면 회생 사례 제목의 감면 비율이나 '지점' 호칭처럼 해석이 필요한 세 건은 제가 판단하지 않고 근거를 정리해 광고책임변호사에게 넘겼습니다. 조문을 읽는 일과 해석하는 일은 다르다고 봤기 때문입니다.
며칠 뒤 AI 조항을 다시 읽다가 규정이 두 겹이라는 점을 놓쳤음을 알았습니다. 상위 규칙의 한 조항은 삭제됐지만, 소비자가 AI를 직접 쓰게 하는 광고를 금지하는 조항은 남아 있었습니다. 이 차이로 설계가 갈렸습니다. 사례 요약은 AI 표기 없이 실제로 검토한 변호사만 표시하는 방식으로 공개했고, 방문자가 직접 쓰는 상담봇은 외부 공개에 변호사 판단을 조건으로 추가했습니다.
낯선 분야일수록 제가 아는 범위와 모르는 범위를 먼저 나누고, 모르는 부분은 그 분야 사람에게 묻는 것이 협업의 출발점이라고 생각합니다.
```

## Q4. 업무 혹은 일상에서 AI를 활용하여 문제를 해결하거나 생산성을 향상시킨 경험 (690자 / 700)

```
[AI로 사례 3,358건의 FAQ를 만들되, AI를 그대로 믿지 않는 장치를 함께 만들다]
AI 답변엔진은 요약과 문답이 정리된 글을 잘 인용합니다. 홈페이지의 공개 사례 3,358건에 이를 붙이고 싶었지만, 사람이 한 건씩 쓰기에는 너무 많은 양이었습니다.
그래서 Gemini로 초안을 만들되 백엔드 파이프라인으로 설계했습니다. 조회수 높은 사례부터 30건씩 생성하고, 입력은 그 글의 공개 본문만 쓰며, 응답은 정해진 JSON 형식으로만 받게 했습니다. 상담봇을 만들며 이미 백엔드에 붙여 둔 Vertex AI를 재사용할 수 있었고, 실측 토큰으로 계산하니 건당 약 2.4원, 전체 약 8천 원이면 충분해 이 도구를 택했습니다.
가장 신경 쓴 것은 AI가 지어내는 내용이었습니다. 법률 광고에서 "60% 감액" 같은 비율이나 "보장" 표현은 규정 위반이 됩니다. 그래서 생성된 글을 원문과 대조해 원문에 없는 숫자, 비율, 보장·최고·무료 상담 표현, 그 사건에 한정되지 않는 일반론이 있으면 자동으로 비공개 처리하는 검사기를 만들었습니다. 첫 배치에서 "혈중알코올농도 0.260%"를 비율로 오인한 오탐은 규칙을 고쳐 바로 해결했습니다.
그 결과 하루 만에 3,038건을 공개했고, 검사에 걸린 303건은 비공개로 남겼습니다. 이후 사례 본문이 바뀌면 FAQ를 다시 만들어 재검사하게 해, 옛 결과가 남는 위험까지 막았습니다.
```

## Q5. 지원 직군에 필요한 역량을 향상시키기 위해 노력했던 경험 (914자 / 1,200)

```
[RAG 검색을 감이 아니라 숫자로 다루다]
AI 상담봇을 만들며 처음 다룬 검색 시스템을 숫자로 평가하려 했습니다. 실제 상담 접수에서 말투를 뽑은 골든셋 50문항을 직접 만들어 정답률을 쟀고, 의미 검색과 글자 검색의 순위를 합산(RRF)해 Recall@5를 93.8%에서 95.8%로 올렸습니다. 일반 기법이 늘 맞지는 않는다는 것도 배웠습니다. 흔한 단어를 빼면 잡음이 준다는 방식이 법률 문서에서는 거꾸로 작동해 핵심 법률 용어를 버릴 뻔했고, 질문 7개로 정한 판정 기준은 50문항에서 틀렸습니다. 이후 기준을 정할 때는 표본 크기부터 확인합니다.

[DB 지식을 실제 실행 구조로 확인하다]
정보처리기사를 준비하며 익힌 데이터베이스 지식은 쿼리의 실행 구조를 직접 확인하는 습관으로 이어졌습니다. 2인 팀으로 개발한 사건관리 앱에서 화면 하나가 8초씩 걸리던 원인을 추적하니, 원격 DB 테이블과의 조인이 원격에서 처리되지 않고 데이터를 통째로 가져와 걸러내는 구조였습니다. 필요한 일정을 먼저 조회한 뒤 이름 정보를 묶어 가져오도록 바꿔 0.05초로 줄였고, 컬럼 타입이 달라 인덱스를 타지 못하던 목록 조회도 1,695ms에서 109ms로 개선했습니다.

[남이 만든 시스템을 읽어 설계 근거로 만들다]
이전 회사에서는 일학습병행제로 근무하며 월 단위 평가를 받고 SW개발 L5 자격을 취득했습니다. 사원 시기에는 가스 점검 앱 신규 개발에 앞서 기존 Go 백엔드와 JavaScript 프런트엔드를 분석했습니다. 직접 구현한 코드는 아니지만 REST API 흐름, JWT·API Key·토큰 화이트리스트로 이뤄진 인증 구조, WebSocket 브로드캐스트 구조를 읽어 설계 근거 자료로 정리했습니다. 남의 코드를 빠르게 읽고 구조를 문서로 남기는 이 경험은 지금 레거시 시스템을 이관할 때 가장 먼저 쓰는 역량입니다.
```
