## 1. 평가 기준부터 바로잡기

**쪽수가 줄었다는 사실만으로 문서가 개선되지는 않는다.** 처음 읽는 사람이 역할을 이해하고, 필요한 곳에서 설계·구현·검증의 깊이를 확인할 수 있어야 한다. 짧아졌어도 맥락과 업무 범위가 사라지면 나빠진 결과다. 상세본은 필요한 만큼 유지하고, 소개와 근거 사이의 읽기 순서를 설계해야 한다.

이전안은 같은 성과를 재강조하고 분량을 줄이는 데 치우쳤다. **CRM 업무와 외부 연동, 포털 구성원 관리, CMS와 레거시 병행을 실제 일일 기록에서 다시 선정했다.**

### 현재 문서가 입증하는 범위

현재 자료는 업무 흐름을 화면·API·DB·클라우드에 연결하고 운영 문제를 해결한 경험을 보여준다. 민간 풀스택 이직에 쓸 소재는 있다. 다만 업무 종류가 많다는 것만으로 시니어 설계·팀 리딩·대규모 트래픽 운영을 입증할 수는 없다. 이는 실제 능력의 단정이 아니라 **서류에 제시된 증거의 범위에 대한 판단**이다.

첫 소개는 “얼마나 많이 만들었는가”보다 “어떤 업무를 맡았고, 계층 사이의 어떤 문제를 해결했는가”를 설명해야 한다. 이어지는 프로젝트는 화면만 나열하지 말고 데이터의 원본, 변경 경로, 외부 연동, 실패 처리와 검증을 연결해야 한다. 함께 일한 사람의 의견이 설계에 반영된 과정도 필요하다.

### 이번에 직접 확인한 자료

사람인 문안, 경력기술서와 TMI, 포트폴리오 원본·출력 코드, 프로젝트 지표, 사실 정정 기록을 비교했다. 대표 소재는 해당 날짜의 daily에서 구현·운영 조치·보류 사항을 직접 확인했다. 공공기관 지원서는 사실관계 대조에만 사용했다. 마지막의 선정 근거에 날짜·파일·기록 범위를 연결했다.

협업 검토에서는 BS_MAINBOARD의 HEAD 75a6233을 기준으로 계정 생성·퇴사 예약·권한·GCS 조건부 저장·원본 분리와 초안 처리의 일부 소스를 대조했다. 운영 계정 변경, 실행 테스트, 배포 상태, 개별 코드 작성자까지 확인한 것은 아니다. 전체 코드·운영 환경을 감사한 결과로 해석하지 않는다.

숫자는 [프로젝트 지표](../../portfolio/프로젝트_지표.md)를 기준으로 확인하고, 구성의 오류를 설명할 때만 남겼다. 수치가 없으면 성과를 추정하지 않았다.

## 2. 개인 책임과 집계 범위를 먼저 고쳐야 한다

### 팀 전체 규모를 본인 설계량으로 표현했다

포트폴리오 첫 화면은 API 423개를 “직접 설계한 엔드포인트”라고 한다. DB 85개도 “스키마 설계와 쿼리 튜닝을 직접”이라고 설명한다. 이 합계에는 사건관리 공동 개발의 전체 API·테이블이 포함된다. 따라서 전체 규모를 본인 설계량처럼 읽히게 하는 문구다.

규모를 유지하면 “담당 시스템 전체, 팀 개발 포함”이라고 명시한다. 본인 성과는 상담·문서·전자결재·정산과 배포 등 맡은 범위로 설명한다. 개인 API 설계량은 별도 확인이 필요하다. 커밋 비중을 기능 기여나 업무 가치의 비율처럼 쓰지도 않는다. 책임을 좁혀 적는 것은 실제 수행한 역할을 검증 가능하게 만드는 작업이다.

근거: [포트폴리오 원본](../../portfolio/content.json) 19–21행·36행, [지표](../../portfolio/프로젝트_지표.md) 전체 합계·사건관리.

### “시스템 5종”의 대상이 페이지마다 다르다

실제 PDF의 대표 프로젝트 페이지는 나머지 시스템을 “사내 포털과 AI 상담봇”이라고 한다. 사람인의 5종에는 AI 대신 연동 서비스가 들어간다. 지표는 RAG를 V2 내부 모듈로 분류하고 레거시까지 별도로 집계한다. 같은 숫자에 연결된 대상이 문서마다 달라진다.

“CRM·홈페이지 V2·포털을 단독 구축하고, 사건관리는 공동 개발하며 연동 서비스와 레거시를 운영”처럼 대상을 직접 쓰면 명확하다. RAG를 내부 모듈로 설명하면서 독립 제품 개수에도 넣는 방식은 피한다. 개수보다 각 프로젝트의 책임·범위·상태가 판단에 도움이 된다.

근거: [출력 코드](../../scripts/render-portfolio.cjs) 78–79행, [사람인](../지원서/사람인_이력서.md) 49행, [지표](../../portfolio/프로젝트_지표.md) 제품 수·AI 상담봇.

### 현재 스택과 과거 구현의 연결을 설명해야 한다

요약본은 CRM 스택을 PostgreSQL로 제시하면서 MySQL GET_LOCK을 해결책으로 적는다. TMI에는 Google Sheets → MySQL → PostgreSQL 전환이 있다. 현재 스택과 과거 운영 단계의 구현을 구분하지 않은 문제다.

“MySQL 운영 단계의 중복 실행 제어”로 표시하고 PostgreSQL 전환 후 방식은 현재 코드로 확인한다. “DB Named Lock”으로 용어를 넓히면 독자가 확인할 단서를 없애게 된다. 이관 단계와 현재 구조를 같은 도식 안에서도 구별해야 한다.

CRM 규모 역시 정식 오픈 당시와 현재 측정값이 섞여 있다. 과거 값은 기준 시점을 적고 현재 소개는 최신 측정으로 맞춘다. 기술 태그도 React·Next.js·Node.js·PostgreSQL·GCP의 실무와 Go 코드 분석 경험을 같은 숙련도로 나열하지 않는다.

## 3. 현재 운영 상태와 미확정 사실을 구분해야 한다

### 홈페이지 완전 대체로 읽히는 문구

상단 소개는 레거시 홈페이지를 Next.js로 “대체했다”고 한다. 실제 일일 기록에는 롤백 이후 두 도메인 병행, 서로 다른 광고 계측, 공개 상태 동기화, 레거시 파일 폴백이 있다. 신규 사이트·CMS 구축을 설명할 수 있지만 레거시 폐기까지 완료한 것으로 확대하면 안 된다.

“신규 홈페이지와 CMS를 구축하고 기존 사이트와 병행 운영하며 콘텐츠를 동기화”라고 쓴다. 운영자가 어느 시스템에서 무엇을 수정하는지, 신규 시스템에서만 관리하는 값은 어떻게 보존하는지, 아직 기존 서버가 필요한 이유를 설명하면 전환의 실제 난도를 보여줄 수 있다.

## 4. 실제 업무를 어떤 소재로 보여줄 것인가

### CRM — 업무 전환과 예약·달력·문자 연동

CRM을 “데이터 이관과 API 구축”으로만 설명하면 실제 구현 범위를 놓친다. daily에는 시트 수정의 DB 반영과 삭제 동기화, 예약 문자 시간대, 지사 공용 연락처 저장, 발송번호 기준의 양식, 상담사 변경에 따른 달력 참석자 갱신이 있다.

좋은 대표 프로젝트는 **고객 정보를 어디서 받아 누가 상담을 맡고, 일정과 메시지가 어디에 반영되는가**를 연결한다. 외부 참석자와 회의실 보존, 초대 메일을 보내지 않는 정책, 문자 양식의 소유 기준처럼 업무 규칙이 UI·API·데이터 모델에 어떻게 구현됐는지 보여준다. 업무 시간 절감이나 오류 감소는 별도 측정 없이는 주장하지 않는다.

### 포털 — 조직도와 계정의 관리 흐름

권한 버그 한 건으로 요약하면 계정 생성·수정·정지, 퇴사 예약, 조직도 편집, 내선과 명부, 관련 서비스의 갱신을 맡은 범위가 사라진다. 특히 이름·내선·직위의 원본은 CRM의 동기화본으로, 배치·배지·순서는 포털 파일로 나눈 판단이 설명할 만하다.

계정 생성부터 퇴사 예약까지 운영자의 업무 흐름을 보여주고, 각 변경이 Google Admin·CRM·GCS·연동 Job 중 어디에 쓰이는지 표시한다. 조건부 저장과 실패 시 권한 거절, 관리자 계정 보호, 밀린 예약의 재시도를 연결한다. 예약 처리는 포털 요청이 들어올 때 기한이 지난 작업을 실행하므로 지정 시각의 실행을 보장하는 구조로 쓰지 않는다. 관리자 키 사용의 잔여 위험과 전용 계정 분리 후속도 남긴다.

### 홈페이지 — 운영자 편집과 레거시 병행

공개 홈페이지의 화면 개수만 보여주면 CMS를 만든 이유가 드러나지 않는다. 운영자가 지사·센터별 GTM 식별값을 편집하고 FAQ를 공개 화면과 구조화 데이터에 함께 반영하도록 만든 사례가 있다. 레거시의 예약 공개 상태와 파일 의존을 유지하면서 V2의 값을 보존한 과정도 풀스택의 연결 문제다.

**운영자가 변경할 수 있는 값, 코드가 통제하는 실행 경로, 양쪽 시스템의 원본과 동기화 규칙**을 같은 사례로 설명한다. GTM 식별값 편집 기능을 만들었다고 광고 전환 설정 전체가 완료됐다고 쓰지 않는다. 콘솔 작업과 대행사 결정, 비활성화한 경로는 상태를 나눠 표시한다.

## 5. 재작성은 짧게 만드는 것보다 판단을 드러내야 한다

### 민간 풀스택용 상단 소개

> 고객·상담 업무와 사내 운영 절차를 웹 시스템으로 구현하는 풀스택 개발자입니다. CRM의 예약·달력·문자 연동, 포털의 조직도·계정 관리, 홈페이지의 공개 화면과 CMS를 개발하고 데이터·클라우드 운영을 담당했습니다. 사건관리는 공동 개발하며 상담·문서·전자결재·정산과 배포를 맡았습니다. 화면의 동작을 외부 서비스와 데이터의 변경까지 연결하고, 권한·동기화·실패 처리의 운영 조건을 확인하며 개선해 왔습니다.

개수와 단독 비율 대신 맡은 업무와 연결 문제를 드러낸다. 회사·팀 전체의 수치는 본인 성과와 분리하고, RAG는 직원 시범 운영으로 별도 설명한다.

### 대표 프로젝트 문안 예시

**CRM — 상담 처리와 외부 업무의 연결**

> 스프레드시트와 공존하던 고객·상담 업무를 CRM으로 옮기며 시트 변경과 DB 반영, 지사 공용 연락처 저장을 구현했습니다. 예약 문자의 시간대와 발송번호별 양식을 정리하고, 상담 등록·상담사 변경이 달력 참석자에 반영되도록 연결했습니다. 회의실과 외부 참석자는 보존해 CRM 변경이 다른 일정 정보를 덮어쓰지 않도록 했습니다.

이후 설명은 예약·수정·취소가 화면에서 서버와 외부 서비스까지 이동하는 흐름으로 이어간다. 일부 기능이 철회되거나 비활성화됐다면 구현 이력과 현재 경로를 구분한다.

**포털 — 조직도와 구성원 계정의 관리**

> 조직도 편집과 계정 생성·수정·정지·퇴사 예약을 포털의 관리 화면으로 옮겼습니다. 사람 정보와 배치 정보의 원본을 분리하고, 요청별 권한 판정과 GCS 조건부 저장으로 변경을 통제했습니다. 주요 조작의 확인 창과 관리자 계정 보호를 적용했고, 요청 시 기한이 지난 퇴사 예약의 처리·실패 재시도와 관련 서비스 갱신을 연결했습니다.

정책 결정과 상태 전이를 보여줄 사례다. 구현한 보호 장치가 모든 운영 위험을 제거했다고 주장하지 않는다. 변경 후 다른 앱에 미치는 영향과 남은 권한 구조를 함께 설명한다.

**홈페이지 — CMS 편집과 병행 운영**

> 지사·센터별 GTM 식별값을 관리자 화면에서 편집하고 서버와 화면에서 검증하도록 구성했습니다. FAQ는 운영자 편집 내용이 공개 본문과 구조화 데이터에 함께 반영되게 했습니다. 기존 홈페이지와 V2를 병행하며 예약 글의 공개 상태와 파일 참조를 동기화하고, 신규 사이트에서 관리하는 값은 보존하도록 변경했습니다.

공개 화면, 관리 화면, 데이터 저장, 동기화 배치, 외부 콘솔의 책임을 한 도식으로 연결한다. 운영자가 실제로 어디까지 직접 처리하는지는 사용자 확인 자료를 붙인다.

### 캡처와 상세 자료의 역할

작은 전체 화면과 검은 가림만으로는 무엇을 맡았는지 알기 어렵다. 테스트 데이터로 실제 담당 화면을 보여주고 변경 지점·사용자 행동·서버 처리와 연결한다. 사건관리 전체 목록을 넣더라도 본인 담당과 대표 기능의 관계를 설명해야 한다.

상세본은 삭제 대상이 아니다. 프로젝트의 목적·현재 상태·본인 역할을 먼저 안내하고, 선택한 사례의 설계·코드·검증을 찾아갈 수 있게 한다. 분량은 그 설명에 필요한 만큼 사용한다.

## 6. 보강 순서와 면접에서 확인할 내용

### 먼저 필요한 작업

**사실과 책임 정리:** 개인·팀 규모, 시스템 집계, 현재 운영 상태, DB 단계, 비용 시점, 이전 경력을 맞춘다. 사실 정정을 제출용 본문에도 반영한다.

**대표 프로젝트의 깊이:** CRM의 업무 전환·외부 연동, 포털의 계정·조직도, CMS와 병행 운영을 연결된 프로젝트로 작성한다. 기능 목록만 늘리지 말고 무엇을 원본으로 삼았는지, 어떤 대안을 버렸는지, 실패가 업무에 어떻게 나타나는지 설명한다.

**증거 보강:** 시나리오별 확인 결과, 주요 코드·도식, 실제 변경 합의와 리뷰를 붙인다. 없던 협업이나 검증을 만들어 쓰지 않는다. 새로 작성한 테스트·재현 예제는 보강 자료임을 밝히고 당시 이미 존재했던 성과로 표현하지 않는다.

성능이나 비용의 수치를 유지할 경우 측정 범위·환경·시점과 반복 여부를 적는다. 테스트는 개수보다 어떤 실패를 막는지 설명한다. RAG도 검색의 Recall@5와 답변의 정확성·근거·허위 사실·개인정보 대응을 분리한다. 검색 평가가 답변 품질 전체를 보장하지 않는다.

### 면접 질문도 실제 업무 흐름에 맞춰야 한다

- 고객·상담 정보를 CRM으로 옮길 때 기존 시트와 공존한 규칙은 무엇이었나?
- 문자 양식의 기준을 지사에서 발송번호로 바꾼 이유와 기존 데이터 처리 방법은?
- 예약 시각의 저장·표시·발송은 어떤 시간대를 사용하며 취소·재시도는 어떻게 처리하나?
- 상담사가 바뀌면 달력의 무엇을 변경하고 외부 참석자와 회의실은 어떻게 보존하나?
- 포털의 이름·직위와 조직 배치 정보를 다른 원본에 둔 이유는 무엇인가?
- 계정 생성·정지·퇴사 예약의 부분 실패는 어떻게 복구하며 예약과 실제 처리 시점의 차이는?
- 조직도 저장이 충돌했을 때 사용자 변경을 어떻게 다시 적용할 수 있나?
- 권한 정보를 읽지 못했을 때 왜 거절하며, 관리자 계정 보호의 범위는 어디까지인가?
- GTM 식별값만 편집하게 한 이유와 실제 태그·전환 설정의 책임 분담은?
- 레거시의 공개 상태와 V2 전용 값이 충돌하면 무엇을 보존하나?
- 본문 파일의 원본 의존이 남은 이유와 자동 동기화의 미완료 범위는?
- 팀·현업·대행사의 의견으로 본인의 설계나 운영 순서가 달라진 사례는?

핵심은 답변에 큰 숫자를 넣는 일이 아니다. 확인한 조건과 자료, 선택한 범위, 구현과 검증, 남은 한계를 설명해야 한다. 새 HTML·PDF 역시 이 기준으로 평가한다. 쪽수가 같거나 늘어나도 역할과 근거가 더 분명해졌다면 그 변화가 개선이다.
