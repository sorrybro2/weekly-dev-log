### 1. BS_CRM — 목록 자동 갱신(폴링)과 새 행 강조 (`bs_crm#7`)

- **폴링 공통 계층 신설** — 상담·당사자 목록이 15초마다 스스로 재조회해 다른 사용자의 등록·수정이 새로고침 없이 올라옴. 화면마다 타이머를 두면 `dispose()` 누락이 남으므로 `common/utils/list_auto_refresh.dart`의 `ListAutoRefreshMixin`에 모아 화면 쪽 추가 코드는 사실상 두 줄. 탭 이탈 시 정지 → 복귀 시 다음 주기를 기다리지 않고 즉시 1회 조회, 다이얼로그·상담 폼이 열려 있으면 입력값이 갈리지 않게 정지. (`b6f4e0c`)
- **새 행 강조** — 폴링만 붙이면 목록이 소리 없이 바뀌어 변화를 인지하지 못한다. 자동 갱신으로 들어온 행만 옅은 파란 배경 + 왼쪽 바로 약 2초 표시하고 되돌림. 첫 로드·페이지 이동·검색은 대상에서 제외(안 거르면 진입할 때마다 전체가 물든다). 모바일 카드는 흰 배경이라 배경색이 안 보여 테두리 색으로 대체. `new_row_tracker.dart` / `new_row_highlight.dart`로 분리. (`76c29b8`)
- **🔴 표 행이 통째로 안 보이던 잠복 버그** — 가로 스크롤이 표에 무한 폭을 내려주는데 안쪽 `Column`이 `CrossAxisAlignment.stretch`로 그 무한을 물려받아 행 크기가 정해지지 않았다. 디버그는 assert로 걸리지만 **릴리즈는 검사를 건너뛰어 여태 드러나지 않다가**, 강조용 `Stack`을 넣자 행 높이가 0이 되며 표면화. 컬럼 폭 합계와 가용 폭 중 큰 값으로 표 폭을 확정해 무한을 제거하고, 강조는 레이아웃에 참여하지 않는 덧그리기 방식으로 변경. 회귀 테스트 추가. (`9e91ce6`)
- **강조 깜빡임 수정** — 강조 없는 상태의 색을 지정하지 않아 중간 색을 만들 수 없어 배경이 켜졌다 꺼졌다 했다. 투명색을 명시하고 켜짐 0.18초 / 빠짐 0.9초로 시간을 나눠, 눈에는 띄되 어지럽지 않게. 전이 색과 시간 비율을 고정하는 테스트 추가. (`cc1f815`)
- **회생 상담관리에도 동일 적용** — 15초 자동 갱신·새 행 강조·수동 새로고침. 자동 갱신 때 목록을 비우지 않고 도착 시 한 번에 교체(기존 구조라면 주기마다 표가 잠깐 비었다), 조회 성공 시 이전 오류 안내를 지우도록 처리. (`9bf2c50`)
- **정리** — `flutter create`가 만든 기본 테스트가 존재하지 않는 카운터 화면을 검사해 항상 실패하던 것을 삭제, `flutter test` 결과에 실제 실패만 남게 함. (`f9b9fe7`)

### 2. BS_CRM — 회생 현재상태 재정의와 상태 필터 UI

- **상태 이름 9개로 변경 + 목록 단일화** — 신규상담 / 상담완료(재통화예정·콜백예정·보류·방문상담예정·불가예상·불가) / 계약완료 / 부재. 목록 필터·등록 폼·배지 색·엑셀 색이 **각자 상태 목록을 들고 있어** 실제로 "수임"이 필터엔 있고 폼엔 없는 어긋남이 있었고, 이를 `constants/recovery_status_options.dart` 한 파일로 모음. 저장된 값이 목록에 없어도 살려서 보여주도록 고쳐 **다른 항목만 수정해도 상태가 조용히 덮어써지던 문제**를 제거. 일괄 변경 스크립트는 기본이 건수 집계이고 `--apply`를 붙일 때만 실제 변경. (`95a4ef4`)
- **필터를 건수 중심 배치로** — 18개로 늘어 가로로 밀리던 필터를 줄바꿈 배치로 바꾸고, `상담완료(...)` 6개는 공통 접두어를 떼어 묶음 아래로 모음(항목마다 반복하면 앞 네 글자가 같아 구분이 안 된다). 상태명은 작게·건수는 크게, 단일 선택인데 알약이 여러 개 켜진 듯 보이던 표시를 밑줄로 변경, 정리 대상 옛 상태는 접어둠. (`54c852c`)
- **상담관리와 같은 카드로 통일** — 상담관리의 상태 카드를 공통 위젯(`status_filter_card.dart`)으로 승격해 회생관리도 같은 모양을 사용. 선택 항목 배경이 아래만 각져 잘려 보이던 것 해결, 필터 높이 고정으로 표가 밀리지 않게, 카드 폭을 화면 폭에서 계산해 가로 스크롤 없이 한 줄에 수용. 아이콘은 제거(상담완료 6개가 같은 아이콘이라 구분에 도움이 안 되면서 폭만 차지), 건수 0인 항목은 흐리게. (`5ed62ab`)

### 3. BS_CRM — 구글 연락처 저장 대상 확대 (`bs_crm#9`)

- **조직 → 이메일 1개 구조를 여러 개로** — 당사자 저장 시 대표연락처가 구글 연락처로 자동 저장되는데, 회생팀은 공용 모바일 계정이 없어 폴백(담당자 개인 계정)으로 떨어진다. 여기에 오용문 주임을 추가하려면 매핑 구조 자체를 바꿔야 했다(`WHERE email = ? LIMIT 1` → `IN (...)`). 지정 순서를 유지하도록 처리해 DB 반환 순서에 좌우되지 않게 했고, 퇴사·오타로 한 명을 못 찾아도 나머지는 정상 저장되게 함. 이슈에 **공용 계정을 만들면 코드 수정 없이 1단계에서 잡히는 조건**까지 적어 폴백 제거 경로를 남김. (`2ed0cb7`)

### 4. 사건관리 앱 — 변경 강조 + 폴링 확대, 웹소켓 보류 (`#186` / 브랜치 `feat/list-row-change-highlight`, 머지 전)

- **웹소켓(C안) 보류 결정** — Cloud Run은 연결이 열려 있는 동안 인스턴스를 "활성"으로 보고 계속 과금한다. 사건앱은 이미 `--min-instances 1`로 유휴 단가를 내는 중인데 웹소켓을 붙이면 업무시간이 활성 단가로 전환된다(증분 월 ~$21, 탭 상시 개방 시 ~$96 / 폴링 ~$5). 여기에 인스턴스 간 신호 전파용 중계(Redis pub/sub 또는 Postgres `LISTEN/NOTIFY`)와 60분 타임아웃 재접속 처리가 더 붙는데, 얻는 것은 타인 화면 반영 15초 → 1초뿐. 20명 규모에서 14초를 사는 값으로 과하다고 판단해 보류하고, 재검토 조건("폴링으로도 체감 지연이 있다"는 실사용 피드백)을 이슈에 명시. (`#186` 코멘트)
- **행 비교 공용 훅** — 직전 응답과 비교해 새 행/바뀐 행을 찾아내는 `useRowChangeHighlight.ts` + 색·지속시간을 모은 `lib/rowHighlight.ts` 신설. 왼쪽 강조 바는 `border`가 아니라 **inset box-shadow**로 그림 — border는 박스 크기를 바꿔 rowSpan 병합 셀의 내용을 밀고, `border-collapse` 표는 `<tr>`의 box-shadow를 안 그려 첫 `<td>`에 건다. 여기서 **호출부의 `= []` 기본값이 매 렌더마다 새 빈 배열을 만들어 무한 렌더로 사건상세를 죽이던 문제**를 잡아, 내용이 같으면 상태를 갱신하지 않도록 처리. (`a346600`)
- **사건목록·계약목록 적용** — 사건목록 15초 / 계약목록 20초, 새 행 초록·변경 행 주황으로 1.8초 표시. 선택·기일충돌·종결 행은 상태색이 더 중요한 정보라 배경을 덮지 않고 강조 바만 올림. 모바일 카드도 같은 강조 값을 받아 폭이 바뀌어도 같은 행이 같은 색으로 뜨게 함. 사건목록 툴바에 수동 새로고침 추가. (`d9606cd`, `6b8fd9f`)
- **사건상세 하위 항목까지 폴링 확대** — 연결사건·열람/등사·수발신 문서·수납·타임라인이 자동 갱신 대상에 없어 다른 사용자가 등록해도 화면을 다시 열기 전엔 반영되지 않던 것(`#170`에서 범위 밖으로 뒀던 항목)을 15초로 통일. `staleTime`은 건드리지 않음 — `refetchInterval`은 그와 무관하게 발화한다. (`9ccaf81`)
- **사건상세 강조는 약하게** — 한 화면에 목록이 여럿이라 목록 화면과 같은 강도로 주면 동시에 물들어 번쩍인다(바 2px·옅은 배경). 풀페이지와 사이드패널이 마크업을 각자 들고 있어(`#337`) 비교 기준을 `useCaseSectionHighlights` 한 파일에 모아 한쪽만 고치는 사고를 차단, 카드 컴포넌트 4개가 `className`을 받도록 열어 양쪽에서 재사용. (`1124aaf`)

### 5. 사건관리 앱 — 드라이브 중복 복사 수정과 배포 (`#491`)

- **중복 사본 차단** — 수발신문서에서 PC 업로드한 파일을 이어서 수기일정 "드라이브에서 선택"으로 고르면 같은 파일이 사건 폴더에 하나 더 생겼다. `copy_file_to_folder`에서 원본의 부모 폴더를 확인해 이미 그 폴더에 있으면 복사 없이 원본 링크를 사용하도록 하고, 호출부(수기일정·계약)마다 넣는 대신 **한 곳에 모아 앞으로 추가될 호출부까지 보호**. 판정은 파일 ID 기준 — 같은 이름을 재사용하면 내용이 수정된 새 문서를 올렸을 때 건너뛰어 옛 문서가 남는다. 이름이 다른 사본을 원하는 호출(`new_name`)은 그대로 복사. (`a5326a8`, 머지 `262a783`)
- **본문 정정** — 이슈에 "`document_logs_api.py`도 같은 문제"라고 적었으나 확인 결과 수발신문서는 `#101`에서 같은 방어를 이미 갖고 있었다. pull 이전 코드의 줄번호만 보고 맥락을 읽지 않은 실수여서 코멘트로 정정하고 실제 영향 범위(수기일정·계약)를 표로 정리.
- **배포·후속** — 리비전 `lawwin-case-00212-5kh` 트래픽 100%, `/health`·`/api/notifications` 검증 통과. 백엔드 테스트 프레임워크가 없어 **다른 위치 파일은 여전히 정상 복사되는지**(조건이 잘못 걸리면 파일이 사건 폴더 밖에 남는 새 문제가 된다)를 실사용 확인 항목으로 남김. 제보된 중복 파일은 사본이 일정·캘린더에 연결돼 있어 **원본으로 재지정 후 삭제** 순서를 안내.
