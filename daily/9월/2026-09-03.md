## 📝 상세 업무 내역

### 1. BS_CASE_MANAGEMENT — 예약금·상담료 레코드 분리 (`#457`)

#### 스키마 — 행 분리와 이중계상 방지

- **한 행에 두 입금을 담던 구조를 행 2개로 나눴다** — `reservation_*` 컬럼 세트로 예약금을 얹어 두던 `consultation_fees` 를 `fee_kind`('예약금'/'상담료') + `fee_group_id` 로 재구성했다. 회계상 서로 다른 시점의 별개 입금이고 영수증도 2장 끊기므로 **"행 1개 = 영수증 1장"** 이 성립해야 한다. `029` 에서 컬럼 추가 + 기존 행 그룹키 백필, `030` 에서 예약금 분리. (`39e9779`)
- **`reservation_*` 원본 값을 지우지 않았다** — 롤백 여지를 남기기 위함이고, 대신 실행 순서를 `029 → 신규코드 배포 → 030` 으로 못박았다. 구코드가 원본 컬럼과 새 행을 **둘 다 세면 시트 금액이 2배**가 되기 때문이다. 검증 후 별도 마이그레이션에서 DROP 예정.
- **분리된 예약금 행도 분류상으로는 '상담료'** — 예약금은 상담료의 선입금일 뿐이고 `receivables.reward_type` enum 에 '예약금' 이 없다.

#### API — DB는 행 단위, 화면은 상담 단위

- **두 단위를 의도적으로 다르게 뒀다** — DB 는 영수증 단위 행이지만 API·화면은 "상담 1건 = 1행" 을 유지한다. 직원이 상담료 입력창에서 예약금과 추가 상담료를 **한 번에** 처리하기 때문이다. 조회는 상담료 행만 뽑고 같은 그룹의 예약금을 `.reservation` 중첩 객체로 붙여, 목록 건수·페이지네이션이 계속 상담 수와 일치한다(53건이 72건이 되지 않는다). 스키마는 `reservation_*` 접두어 11필드 → `PaymentFields` 한 세트 + 중첩 객체로 정리. (`68a13a0`)
- **생성·수정은 상담 단위 payload 하나로 두 행을 한 트랜잭션에서 upsert**, 처리 취소는 그룹 전체를 함께 비활성화한다. 공제 수납(`receivables`)만 **행 단위 1:1** 로 두어 영수증 2장이면 수납도 2건이 된다.
- **필터가 새던 버그를 함께 잡았다** — 입금상태·결제방법을 상담료 쪽만 보고 판정하고 있어서 **예약금만 미입금이거나 예약금만 계좌결제인 건이 필터에서 빠져나갔다.** 상담 단위 판정으로 교체.
- **`PATCH` 에 `reservation` 이 없으면 예약금 행을 건드리지 않게 했다** — 수임 전환처럼 상담료 행만 바꾸는 요청이 예약금 결제정보를 지워버리는 사고를 막기 위함.
- 파일: `backend/app/crud/consultation_fees_crud.py`, `schemas/consultation_fees_schema.py`, `api/consultation_fees_api.py`

#### CRM 동기화 — 상담(그룹) 단위 유지

- **레코드는 나눴지만 CRM 은 상담 단위로 주고받는다** — `sync_fee_to_crm` 이 fee 1건만 읽던 것을 `fee_group_id` 로 두 행을 함께 읽도록 바꿨다. 캘린더 제목에는 여전히 예약금·상담료가 한 벌로 찍혀야 하는데, 단건으로 두면 **예약금 행만 저장했을 때 제목이 반쪽만 갱신**된다. `consultation_fee_amount` write-back 은 상담료 행 값만 보내고, 예약금 금액은 종전대로 CRM 소유값을 읽는다. (`5387773`, `consultation_crm_sync_service.py`)

#### 시트 내보내기 — 행 단위로 각각

- **합치기 로직을 전부 제거했다** — AR_DB 가 한 행에 결제 한 세트만 담는 구조여서, 앱이 합쳐 갖고 있던 값 중 한쪽의 입금일·결제방법이 내보낼 때 사라지고 있었다(이 작업의 최초 계기). 레코드가 나뉘었으므로 시트에도 각각 한 행씩 내보내고, `_fmt_total`·`_has_reservation`·`_fully_paid`·`_paid_amounts` 와 필드 빌더의 `A or B` 폴백을 걷어냈다. (`9ab4429`, `consultation_fee_sync_service.py` 91+/99-)
- **이중계상이 나지 않는 이유를 확인해 뒀다** — 새 예약금 행의 `OS_key` 는 기존 `_backfill_legacy_keys` 가 발급하고 원본 행은 기존 키를 유지하므로, 시트의 그 행은 상담료 금액으로 덮어써지고 예약금이 새 행으로 추가된다(합계 불변). 단건 푸시도 그룹의 두 행을 각각 upsert 해 연달아 append 할 때 행 번호가 겹치지 않게 했다.

#### 프론트 · 후속 정리

- **`item.reservation` 중첩 객체로 전환** — `reservation_*` 11필드를 읽던 자리를 하위 객체로 바꿨다. 화면 구성은 그대로 유지(목록은 상담 1행, 금액만 그룹 합산). 저장 시 예약금 금액이 없으면 `{ fee_amount: null }` 을 보내 기존 행이 비활성화되게 했다. 폼 상태(`FeeForm`)의 `reservation_fee_amount` 는 **일부러 그대로 뒀다** — 입력 UI 는 여전히 상담 단위 한 화면이라 로컬 상태 모양을 바꿀 이유가 없었다. (`dc98cfb`, `api/consultationFees.ts`)
- **공제 수납행 재동기화 스크립트 (1회성·멱등)** — `030` 실행 뒤 수임 전환된 건의 `receivables` 공제행이 분리 전 상태(상담료 행에 합산 1건, 예약금 행 없음)로 남아 앱과 어긋났다. 총액은 상쇄되어 변하지 않지만 **"영수증 1장 = 수납 1건" 이 깨진다.** 앱과 동일 로직으로 재정렬. (`1e669a0`)
- **Windows 콘솔에서 스크립트가 거짓 실패로 끝나던 문제** — 완료 로그의 체크 이모지가 cp949 에서 `UnicodeEncodeError` 로 터져, **DB 작업은 커밋됐는데 스크립트는 실패한 것처럼 종료**됐다. 순수 ASCII 라벨로 교체. (`200443c`)
- 판단 근거는 `#457` 코멘트에 남겼다 — "왜 컬럼 추가가 아니라 행 분리인가" 는 앱 DB 사정이 아니라 **내보낼 곳(AR_DB) 사정**이라는 점.

### 2. BS_CASE_MANAGEMENT — 목록 예약금 하위 행 표시 후 되돌림 (`#463`)

- **분리 후에도 화면에서는 예약금이 안 보였다** — `#457` 시점에는 목록을 "상담 1건 = 1행" 으로 유지하고 예약금은 부기만 했다. 그런데 **입금일·결제방법이 화면에 전혀 없어** 시트에는 2행으로 남는 정보를 앱에서는 수정 모달을 열어야 알 수 있었다. 이슈를 직접 생성해 요구사항을 정리했다(건수·페이지네이션·합계·버튼은 상담 단위 유지, 대안인 완전 독립 2행은 기각). (`#463`)
- **결제 관련 셀마다 둘째 줄을 그리는 방식으로 구현** — `DataTable` 의 `renderExpandedRow` 는 `colSpan` 전체 폭이라 컬럼 정렬이 되지 않아 쓰지 않았다(공유 컴포넌트 변경도 피함). 셀 안 두 줄의 높이를 맞춰 컬럼 정렬된 하위 행처럼 읽히게 했고, 결제방법 컬럼이 `mobileHidden` 이라 **모바일 카드에서는 아예 안 보였던 값**도 총액 아래 두 줄로 분리했다. 예약금 결제방법은 상담료와 같아도 항상 표시 — 방법이 같고 입금일만 다른 경우를 숨기지 않기 위함. 백엔드 변경 없음(목록 API 가 이미 중첩 객체로 전체 결제정보를 내려주고 있었다). (`ffbdac7`)
- **⚠️ 같은 날 28분 뒤 되돌렸다** (`14aae1a`) — **되돌린 사유가 커밋 본문·이슈 코멘트 어디에도 남지 않았다.** 재작업할 때 판단 근거가 없으므로 `#463` 에 사유를 보강해 두는 것이 좋다.

### 3. BS_MAIN_HOMEPAGE_V2 — Cloud SQL 보안 경고 전수 검토 (`#107`)

- **운영 조치 ① 삭제 보호 활성화 (커밋 없음)** — `lawwin-pg` 가 삭제 방지 없이 돌고 있었다. 인스턴스를 지우면 **자동 백업 7일치도 함께 사라지는데**(별도 GCS export 없음) 콘솔 클릭 한 번으로 가능한 상태였다. 비용·다운타임 0 이라 즉시 적용.
- **운영 조치 ② 평문 접속 차단 (커밋 없음)** — `sslMode` 가 `ALLOW_UNENCRYPTED_AND_ENCRYPTED` 여서 암호화 없는 접속을 받아주고 있었고, 실제로 그렇게 붙는 클라이언트가 있었다. 그 구간으로 쿼리문·상담자 PII·**DB 비밀번호 본체**가 평문으로 흘렀다. 클라이언트 쪽에 SSL 을 먼저 켠 뒤 서버에서 `ENCRYPTED_ONLY` 로 전환하는 순서로 진행(역순이면 접속이 끊긴다). 적용 후 평문 연결이 `pg_hba.conf ... no encryption` 으로 실제 거부되는 것과, 운영 백엔드 health·공개 사이트가 정상인 것까지 확인했다.
- **사전 확증이 결정적이었다** — Cloud Run 이 `run.googleapis.com/cloudsql-instances` 커넥터(유닉스 소켓) 경유임을 먼저 확인해 **운영 무영향을 판정한 뒤** 실행했다. 승인 네트워크가 단일 IP 뿐이고 `privateNetwork` 도 없는데 사이트가 정상인 점으로도 교차 검증됐다.
- **🔴 SSL 강제가 마이그레이션 스크립트 12개를 깨뜨린 것을 같은 날 발견·수정** — `migration/scripts/` 의 `pg`(node-postgres) 사용 스크립트에 SSL 처리가 0건인데, 런북의 원격 실행 절차가 `backend/.env` 를 그대로 읽어 `sslmode=require` 를 물려받았다. **`pg` 는 이 값을 `verify-full` 로 해석**해 Google 내부 CA 검증에서 죽는다(`unable to verify the first certificate`) — Prisma 는 암호화만 하고 검증하지 않아 앱은 무사했고, 그래서 "앱은 Prisma 만 쓰니 무관" 이라고 판단했던 것이 **마이그레이션 도구 경로를 놓친 오판**이었다. 레거시 증분 재최신화가 다음 실행에서 전부 실패할 상태였다. REMOTE 추출에 libpq 호환 플래그를 붙여 암호화는 유지하고 CA 검증만 끄도록 고치고, 재발 방지용으로 경위를 주석에 남겼다. `pg_dump` 단계는 libpq 기본값 `prefer` 라 무영향. (`2d9b5d7`, `migration/REFRESH-MANUAL.md`)
- **운영 조치 ③ 비밀번호 정책 적용 (커밋 없음)** — 인스턴스 단위 정책을 켰다(`minLength: 12`·복잡도·계정명 포함금지·재사용금지 5). 이 정책은 **비밀번호를 바꾸는 순간에만** 발동하는 가드레일이어서 오늘의 위험을 직접 줄이지는 않지만, 보안 체크리스트의 "시크릿 일괄 로테이션" 때 실제로 작동한다. 사용자별 정책도 `lawwin`·`postgres` 에 `allowedFailedAttempts: 100` 으로 들어갔다.
- **사용자별 정책의 위험 여부를 실측했다** — 사전 검토에서 "사용자 단위 정책은 만료·실패잠금이 있어 `lawwin` 단일 계정 구조에서는 사이트 전면 정지 위험" 이라고 판단했으므로 그 두 필드를 직접 확인했다. **`passwordExpirationDuration` 미설정 · `enableFailedAttemptsCheck` 미설정** — 임계값 100 만 저장돼 있고 잠금 로직은 켜지지 않았다. 만료도 없다. 즉 **위험 없이 들어갔다**(운영 `/health` 정상 확인). 잠금을 실제로 작동시키려면 `--password-policy-enable-failed-attempts-check` 를 함께 켜야 하는데, 단일 계정 구조에서는 켜지 않는 것이 맞다.
- **경고 3건은 미실행·보류 판단 (커밋 없음)** — SCC 는 ISO 27001·NIST 800-53·PCI DSS 벤치마크로 모든 프로젝트에 같은 잣대를 대며 **당사는 인증 대상이 아니다.** 항목별 근거:
  - **멀티리전 → 하면 안 됨.** 한국에는 GCP 리전이 서울 하나뿐이라 복제본이 반드시 일본(도쿄·오사카)에 놓인다. 상담자 성명·연락처·사건 내용이 든 DB 를 국외로 복제하는 것이므로 **개인정보 국외이전** 사안이고, 법무법인에서는 기술 결정이 아니라 법무 검토 대상이다. 경고를 없애려다 법적 리스크가 새로 생기는 경우.
  - **HA(REGIONAL) → 경영 판단.** 요금이 약 2배가 되고 사는 것은 가용성뿐이다. 데이터 유실은 백업·PITR(7개 보관, 트랜잭션로그 7일)로 이미 막혀 있다.
  - **pgaudit → 후순위.** 재시작이 필요한 플래그(계획 다운타임) + 상시 로그 비용.
- **집계 주의 — 콘솔은 한 번에 6건씩 보여주지만 검토한 것은 7개 항목이다.** 항목이 닫히면 목록이 교체된다(삭제 보호가 닫히면서 `비밀번호 정책이 없음` 이 새로 올라왔다). **7건 중 4건 조치 · 1건 미실행 확정 · 2건 보류.**
- **SCC 가 지적하지 않은 실질 약점 2건을 기록** — ① DB 비밀번호가 사람에 묶이지 않은 **공용 비밀**이라는 구조(승인 네트워크의 IP 는 사람이 아니라 네트워크이고, 같은 비밀번호가 복수 `.env` 에 복사돼 접속 주체 구분·이탈자 차단이 안 된다 → 근본 해법은 Cloud SQL IAM 인증, 별도 과제) ② 기본 컴퓨트 서비스 계정에 `roles/editor` 과다부여(필요한 것은 `cloudsql.client` 뿐. 선조사 없이 떼면 파이프라인이 깨진다).
- **IAM 변경 (커밋 없음)** — 박준수 실장에 `roles/owner` 부여, **프로젝트 소유자 2명** 구성. 그전까지 사람 IAM 계정은 1개였고 실장님은 사무실 IP + 공용 비밀번호로만 DB 에 접근하는 경로였다.
- **별건 확인** — 방문자 구간은 이미 TLS 1.3·HSTS·`http→https` 리다이렉트가 적용돼 안전하다. 단 **CSP 헤더가 없다** — XSS 폭발 반경을 줄이는 안전망이며, GTM·외부 스크립트가 많아 잘못 걸면 전환 추적이 조용히 죽으므로 리포트 모드 관찰 후 적용해야 한다(`#101` 사안).

**금일 종합:** 오늘의 축은 **"구조를 회계 단위에 맞추는 일"** 과 **"경고를 판단하는 일"** 두 갈래였다. 사건관리 앱에서는 예약금·상담료를 한 행에 합쳐 두던 구조가 구글시트로 내보낼 때 한쪽 결제정보를 잃는 실제 사고로 드러났고, 이를 행 분리로 해결하면서 **DB 는 영수증 단위, API·화면은 상담 단위**라는 이원 구조를 의도적으로 세웠다 — 직원의 입력 동선과 회계의 기록 단위가 애초에 다르기 때문이다. 마이그레이션 실행 순서를 못박고 원본 컬럼을 남긴 것, 필터가 새던 버그를 함께 잡은 것이 이 작업의 실질이었다. 홈페이지 쪽에서는 Cloud SQL 경고 7개 항목 중 4건을 조치하고 3건은 근거를 남겨 미실행·보류로 정리했다 — 특히 멀티리전이 국외이전 문제로 이어진다는 점은 경고 문구만 보고 실행했다면 되돌리기 어려운 판단이었다. 다만 SSL 강제 직후 마이그레이션 도구 12개가 깨진 것은 사전 판단의 누락이었고, 같은 날 실측으로 잡아 런북에 반영했다. `#463` 되돌림 사유가 기록되지 않은 것은 보완이 필요하다. 금일 2개 repo 에 걸쳐 커밋 10건.
