## 📝 상세 업무 내역

### 1. 홈페이지 V2 — 레거시→V2 동기화 복구와 자동화 (이슈 #131)

#### 진단 — 9/17 기록의 오진을 바로잡았다

- **막힌 곳은 한 군데였다** — 9/17 기록에는 "레거시 MSSQL `1433` TCP 실패"와 "Cloud SQL 허용목록 빈 상태"가 **양쪽 다 끊겼다**고 적혀 있었다. 다시 재보니 레거시가 실제로 쓰는 포트는 `appsettings.json`이 가리키는 **49752**였고 그 포트는 열려 있었다. 1433은 애초에 쓰지 않아 막혀 있는 게 정상이다. **레거시 방화벽은 손댈 필요가 없었고, 진짜 원인은 Cloud SQL 한 곳**이었다.
- **밀린 양을 먼저 쟀다** — 레거시 8,119건 / V2 8,060건. 라이브 사이트에 최근 60건을 조회해 8436~8496 구간이 통째로 빠진 것을 확인했다.

#### 구조 — 당겨오지 않고 밀어 넣는다

- **방향을 뒤집어 방화벽 의존을 제거했다** — PC가 양쪽을 당겨오던 구조라 끊길 곳이 두 군데였다. 레거시가 자기 DB를 읽어 **HTTPS로 V2 백엔드에 밀어 넣고 백엔드가 Cloud SQL 커넥터로 저장**하게 바꾸니, 레거시는 `localhost` 접속이라 인바운드 구멍이 필요 없고 Cloud SQL은 허용목록이 필요 없다. (`7a800e0`·`dc481b0`)
- **비용으로 대안을 기각했다** — Cloud Run Job + Cloud NAT은 월 $35(연 60만원)이고 전액이 "고정 egress IP를 켜 두는 값"이다. 레거시에 Node를 얹는 안도 그 서버가 .NET/IIS 운영 서버라 제외했다. **채택안은 설치할 런타임이 없다.** (이슈 `#131`)
- **접속 정보를 이중관리하지 않는다** — 스크립트가 레거시 웹앱 `appsettings.json`의 접속 문자열을 직접 읽어, DB 비번을 바꾸면 따라간다. 다만 그 파일은 **쉼표가 남은 형태**라 표준 JSON 파서가 죽어 정규식으로 뽑도록 했다. (`dc481b0`)
- **3겹으로 잠갔다** — 공유 열쇠 + IP 허용목록 + 속도 제한. **열쇠가 없으면 전부 거절**한다 — 설정을 깜빡한 채 DB 쓰기 경로가 열려 있는 쪽이 더 나쁘다. (`7a800e0`)

#### 게시물 61건 복구 + 후처리 자동화

- **BACKFILL_PK 전략을 유지했다** — "레거시에 있는데 V2에 없는 번호만" 넣는다. V2 어드민으로도 글을 써서 V2 최대 번호가 레거시보다 크기 때문에, `APPEND`(최대 번호 초과분)로 바꾸면 새 글이 영원히 0건으로 나온다. (`7a800e0`)
- **손으로 돌려야 했던 후처리를 편입했다** — 지역키(`companyindex`) 채우기는 별도 스크립트라 자주 잊혔고, 그러려면 운영 DB를 공인 IP에 열어야 했다. 백엔드 경로로 옮겨 동기화 뒤 자동으로 이어지게 하고 **컬럼·인덱스 생성(DDL)은 빼서** 앱이 실행 중에 스키마를 바꾸지 않도록 했다. 3,786행이 채워졌다. (`6a7b281`)

#### 상담 305건 — 번호로 옮기면 사람이 사라지는 상태였다

- **충돌이 실재했다** — V2 6,243건(최대 27,249) / 레거시 6,521건(최대 27,529). 이관 스냅샷은 27,207까지 같고, 그 뒤로 **V2가 27,208~27,249(42건)**, **레거시가 27,208~27,529(322건)** 을 각자 발급했다. 즉 **42개 번호가 서로 다른 사람에게 배정**돼 있었다. 번호로 맞추고 `ON CONFLICT DO NOTHING`을 썼다면 그 42건이 로그도 없이 사라진다. 글 하나가 빠지는 것과 전화를 기다리는 사람이 사라지는 것은 무게가 다르다. (이슈 `#131`)
- **접수 고유키로 맞췄다** — `listkey`는 접수 시 생성되는 8자 키로 레거시 6,521건 중 **중복 0건**, 2026-06 이후 750건은 **100% 존재**한다(빈 374건은 이미 이관된 구간). 두 시스템이 같은 키를 우연히 만들 일이 없다. (`3b63439`)
- **넣을 때 V2가 새 번호를 발급한다** — 원래 번호는 `legacy_listindex`에 보관하고 UNIQUE로 재실행 중복을 막는다. 재실행 "0건"으로 멱등 확인. 지나간 접수라 **알림은 쏘지 않는다** — 305번 울리면 진짜 신규가 묻힌다. 자동증가 시퀀스가 최대 번호보다 뒤에 있으면 새 접수 저장이 실패하므로 보정도 함께 넣었다. (`3b63439`)

#### 알림 — 실패만으로는 또 놓친다

- **침묵 감시를 별도로 만들었다** — 9/11~17 구간은 **실패한 것이 아니라 아예 실행되지 않았다.** 실패 알림만 걸면 그 7일은 여전히 조용히 지나간다. 마지막 성공이 26시간을 넘기면 알리는 경로를 두고, **감시자를 대상과 다른 기계(Cloud Run)** 에 뒀다 — 죽은 쪽이 스스로 죽었다고 말할 수는 없다. (`7a800e0`)
- **수신처를 분리했다** — 운영 알림은 `ops_notify_webhooks`(정보실)로, 상담 접수 알림(`consult_notify_webhooks`)과 다른 설정 키에 뒀다. 같은 배열에 넣으면 정보실이 모든 상담 접수 알림까지 받는다. (`7a800e0`)
- **조용한 실패 버그가 원인째 사라졌다** — 기존 `.cmd`는 마지막 명령이 `echo`라 **종료코드가 항상 0**이었다. 스케줄러에는 성공으로 뜨는데 로그에는 실패가 찍혀 2주간 아무도 몰랐다. `.cmd` 래퍼를 쓰지 않으므로 이 구멍이 없어진다. (`dc481b0`)

#### 실행 중 밟은 함정 6건

전부 "새벽에 조용히 실패했을" 종류라 기록해 둔다.

- **`$PSScriptRoot`가 param 기본값에서 빈다** — 상대 경로로 `-File` 실행 시 즉사. 본문에서 재계산 + 폴백. (`99cc0d5`)
- **BOM 없는 UTF-8을 PowerShell 5.1이 ANSI로 읽는다** — 한글이 깨지는 데서 끝나지 않고 **파싱까지 어긋나** 동작이 엉켰다. (`99cc0d5`)
- **`--update-env-vars`가 쉼표를 자기 구분자로 먼저 먹는다** — IP 목록이 쪼개져 구분자를 넓혔다. (`26b8a20`)
- **Cloud Scheduler는 출발지 IP가 고정이 아니다** — 감시 호출 403. 감시 경로만 IP 검사를 면제(열쇠 유지, DB 쓰기 없음). (`99cc0d5`)
- **`--update-headers`가 기존 헤더를 통째로 교체한다** — 열쇠 헤더가 소실돼 또 403.
- **PowerShell이 `$inserted건`을 통째로 변수명으로 읽는다** — 한글도 변수명이라 **로그·알림의 건수가 빈칸**이었다. 알림이 없었으면 계속 몰랐을 버그다. (`900d806`)

#### 운영 설정

- **매일 09:15 실행 / 12:15 감시** — 새벽이 아닌 이유는 이 배치가 사무실 PC 작업 스케줄러라 **PC가 켜져 있어야 돌기** 때문이다. 26시간 기준이 이 조합의 정확한 경계다 — 정상이면 3.0시간, 하루 거르면 27.0시간이라 그날 점심에 잡힌다. 창 숨김·놓친 실행 따라잡기·중복 방지·1시간 제한을 함께 걸었다. 305건을 넣은 실행이 3초였다. (이슈 `#131`)

### 2. 홈페이지 V2 — 구글 권한 연동이 운영에서 한 번도 동작하지 않은 이유 (이슈 #74)

- **맞춤정보 묶음 이름이 달랐다** — 구글에 저장된 스키마 이름이 코드가 찾던 것과 달라 역할을 **한 건도 읽지 못했다.** 직원 109명 전원이 권한 없음으로 보였고, 값은 멀쩡히 들어 있었다. 실제 이름으로 읽도록 바로잡고 또 바뀔 경우를 대비해 환경변수로 열었다. (`208b8e3`)
- **이 실패가 침묵이었다** — 한 건도 못 읽으면 아무 말 없이 DB 권한으로 넘어가, **화면은 멀쩡해 보이고 구글에 넣은 권한만 조용히 무시**됐다. 그래서 몇 달간 몰랐다. 이제 어느 이름으로 찾았는지까지 로그로 남긴다. (`247a76e`)
- **옛 이름 `main-homepage`도 인정** — 정식 이름과 나뉘어 적혀 있으면 합쳐 인정하고 중복은 한 번만 센다. 어드민에서 바꾸면 정식 이름 한 곳에만 남겨 **해제한 권한이 되살아나는 것**을 막았다. 테스트 6건. (`484ac4c`)
- **복수 권한 지원** — 계정 관리를 단일 선택에서 토글로 바꾸고, 구글 역할을 첫 개만 읽던 것을 전부 읽도록 고쳤다(두 번째부터 사라지던 문제). 메뉴·화면·개인정보 열람 판정을 **가진 권한의 합집합**으로 바꿔 상담관리자+업무분야관리자면 두 메뉴가 모두 열린다. 전 지사 열람은 종전대로 슈퍼어드민만. 회귀 테스트 19건. (`b93d94a`)
- **지사를 못 잡아도 구글 권한을 적용한다** — 관리 지사를 한 곳도 못 정하면 구글 권한을 버리고 DB의 옛 권한으로 되돌아가, **구글에 상담·업무분야를 넣어 둔 사람이 오히려 DB 최고관리자로 로그인**되는 경우가 있었다. 이제 권한은 그대로 적용하고 지사로 나뉜 자료만 가린다. (`5d93d3a`)
- **권한 변경이 재로그인 없이 반영된다** — 로그인 시 1회 → 화면 전환마다 재확인(늦어도 30초). 계정 관리에서 저장하면 캐시를 즉시 버려 다음 클릭에 반영된다. **조회 실패와 권한 없음을 구분**해 백엔드가 잠시 불안정해도 로그인한 사람을 내보내지 않는다. (`b4f98f4`)
- **코드에 박힌 최고관리자 2계정 제거** — 그 계정은 구글에서 권한을 바꿔도 반영되지 않아 **연동 검증 자체가 막혀 있었다.** 운영 환경변수로만 지정. (`4884555`)
- **업무분야관리자 업로드 권한 누락** — 메뉴는 열리는데 사진만 안 올라가던 상태. (`e5948bb`)

### 3. 홈페이지 V2 — 가사 업무분야 페이지 재구성 (배포 `00121-c49`)

- **첫 화면을 사건 이름으로** — '가사 업무분야'라는 분야 이름표 대신 '이혼·재산분할 등 가사 사건'을 걸고, 아래에 취급 사건 키워드 줄을 신설했다. 어느 분야에나 붙을 수 있는 배경 건물 사진은 걷어내고 빛과 미세 격자로 대체했다. `family-hero.tsx`·`center-data.ts` (`a985ae0`)
- **인트로 문단 자리에 담당 변호사 띠** — 첫 화면과 같은 말을 반복하던 문단을 걷어내고, 대한변협에 가사·이혼을 등록한 4명이 굴러가는 띠를 넣었다. 지사 큐레이션 순서를 먼저 쓰고 빠진 사람은 전국 목록으로 채워 **부산처럼 큐레이션에 1명뿐인 지사에서도 4명이 보인다.** 사진이 상반신에서 잘려 있어 하단을 흐리게 처리했다. `family-lawyer-band.tsx` (`240a3cb`)
- **절차와 상담 폼을 한 면에** — 절차 4단계를 왼쪽, 폼을 오른쪽에. 읽는 자리와 남기는 자리가 스크롤만큼 떨어져 있으면 그 사이에 마음이 식는다. 폼이 자기 섹션을 통째로 들고 있어 2단에 못 넣던 것을 **카드만 꺼낼 수 있게 분리**했고 폼 로직은 건드리지 않았다. (`8629dc5`)
- **가사 성공사례를 되살렸다** — DB에 가사 단독 분류가 없어 '민사, 가사' 전체를 부르면 부동산·대여금이 쏟아진다. 그 안에서 가사 키워드로 한 번 더 좁혀 조회한다(합집합 49건). 조회 조건이 한 번에 하나뿐이라 키워드별로 나눠 부른 뒤 합쳐 정렬. `family-cases.ts` (`240a3cb`)
- **지역별 문답 + 사무소 구조화 데이터** — 어드민 문답의 `{지역}` 토큰을 치환하고, **지사마다 연락처·담당 변호사가 실제로 다른 문답**을 맨 앞에 세웠다. 지역 URL은 self-canonical이라 답이 같으면 같은 페이지 여러 장으로 읽힌다. 구조화 데이터에는 사무소 10곳의 NAP과 네이버 플레이스를 실었다. `center-jsonld.tsx` (`3044cac`)
- **모바일 높이 축소** — 분야 2열 격자, 사례 3건 목록, 절차 2×2 격자. 긴 문단은 모바일에서만 접어 **본문은 DOM에 두고 화면만** 줄였다. 마크업을 두 벌 그리지 않은 것은 한쪽을 숨겨도 브라우저가 양쪽을 다 내려받기 때문이다. 문장은 마침표에서, 폼 제목은 쉼표에서 끊어 법인명·낱말이 갈리지 않게 했다. (`8629dc5`·`f1cf625`)

### 4. 홈페이지 V2 — AI 상담봇 Phase 2 착수 (이슈 #125)

- **설계 분기점이 해소됐다 (커밋 없음, 실측)** — 스펙 §9-1은 "서울 리전 Gemini 가용성"을 **설계 분기점**으로 못 박아 뒀다. 못 쓰면 국외이전 고지 검토가 되살아나 Vertex AI 채택 근거 자체가 흔들리는 자리였다. `chat-preflight.mjs`로 실호출한 결과 `gemini-2.5-flash` 생성·`gemini-embedding-001` 임베딩 모두 `asia-northeast3`에서 성공했다. 9/2 실측의 "비활성"이 뒤집혔다. Vertex AI API 활성 확인, 서비스계정은 `roles/editor` 보유라 별도 권한 부여도 불필요했다.
- **다만 상위 모델 에스컬레이션은 서울에서 불가** — `gemini-2.5-pro`·`flash-lite`·`3-*`가 전부 404다. §9-6의 "2단 구성"은 선택지가 아니라 애초에 불가능하며, **Flash 단일**로 확정된다.
- **답변 검사층을 백엔드로 이식** — 시험 도구에만 있던 출력 검사와 질문 키워드 추출을 `backend/src/chat/`으로 옮겼다. 처분 결과를 옮겨 적는 표현, 결과 예측·보장, 광고규정 저촉 표현을 차단하고, 허용 목록에 없는 전화번호·주소가 나오면 잡는다. **걸렸을 때 빈 화면 대신 상담 접수로 이어지는 문구**를 돌려주도록 했다 — 오류 문구를 주면 이용자는 그냥 나간다. 실제로 새어 나왔던 문장(`집행유예 성공 사례`·`혐의없음 처분`·`1577-3031`)을 그대로 회귀 테스트 27건으로 고정했다. (`3fc931c`)
- **범위는 검색+답변까지로 정했다** — 툴콜(`submit_consult`)은 Phase 4로 미룬다. 답변 품질이 검증되기 전에 실제 고객 접수를 붙이는 것은 순서가 아니다.
