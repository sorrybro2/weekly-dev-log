## 📝 상세 업무 내역

### 1. 메인보드 — Vercel → Cloud Run 이관 (이슈 #11, #13)

#### 이관 판단의 근거

- **비용 구조를 실측으로 비교** — Vercel Pro $20/월은 트래픽과 무관한 고정비였고, 그중 실제 컴퓨트는 $0.84였다. 나머지는 회사가 이미 GCP에 내고 있는 것을 한 번 더 사는 플랫폼 요금이었다. Hobby 요금제는 상업적 이용이 금지라 사내 포털에는 더 싼 등급이 없었다. Cloud Run 서울 리전에서는 84명 × 하루 8회 조회가 월 200만 요청의 3%, 450,000 GiB-초의 16%에 들어와 무료 한도를 넘지 않는다. (`4a33434`, 이슈 `#11`)
- **DB가 없다는 점이 전제** — 세션은 JWT 쿠키이고 조직도는 30KB JSON 객체 하나라 상시 켜진 인스턴스가 필요 없다. 사건관리앱은 Cloud SQL을 상시 물고 있어 같은 계산이 성립하지 않는다. 이 차이를 이슈에 근거로 남겨 다음에 "사건관리는 왜 안 되나"를 다시 따지지 않게 했다. (이슈 `#11`)
- **프로젝트 배치** — 서비스를 `flutter-crm-e44f5`에 올렸다. 다른 웹 서비스가 있는 프로젝트가 아니라 이쪽인 이유는 셋이 이미 거기 있기 때문이다 — OAuth 클라이언트(ID 접두사 `384202909785`가 그 프로젝트 번호), Firebase Hosting, 그리고 조직도가 대조하는 CRM API. CRM 호출이 리전 안에 머문다. (`4a33434`)

#### 저장소 계층 재작성

- **3중 어댑터로 백엔드 차이를 한 곳에 가둠** — `src/lib/org/storage.ts`를 `Store` 인터페이스(`read`/`write`/`keys`) 하나로 정리하고 `ORG_BUCKET` → Cloud Storage, `BLOB_READ_WRITE_TOKEN` → Vercel Blob, 없으면 로컬 파일로 갈리게 했다. 기존에는 읽기·쓰기·목록 로직이 백엔드마다 통째로 중복돼 있었는데 이번 재작성으로 함께 접혔다. Vercel 경로는 걷어내지 않고 남겨 되돌릴 여지를 뒀다. (`4a33434`)
- **GCS 쓰기 옵션을 의도적으로 지정** — 30KB JSON이라 `resumable: false`(재개 업로드는 왕복만 늘림), 조직도는 저장 즉시 반영돼야 하므로 `cacheControl: "no-store"`. 읽기 실패는 404와 권한·네트워크 오류를 구분하지 않고 모두 "저장본 없음"으로 처리해 호출부를 단순하게 뒀다. (`4a33434`)

#### 배포 경로 구성

- **도메인 우회 경로가 필요했던 이유** — `portal.lawwin.co.kr`을 `lawwin-mainboard.web.app`에 CNAME으로 걸고 Firebase Hosting이 Cloud Run으로 rewrite한다. Cloud Run 도메인 매핑이 `asia-northeast3`를 지원하지 않고, 글로벌 로드밸런서는 고정 요금이라 무료로 만든 의미가 사라지기 때문이다. (`4a33434`)
- **사건관리앱의 사고 규칙을 그대로 이식** — 빌드와 배포를 명시적 2단계로 분리하고 `run deploy --source .`를 금지했다(그쪽에서 잘못된 Dockerfile을 집어 27분 장애가 두 번 재현됨). `--update-secrets`는 매번 전체를 명시(부분 갱신이 안 돼 하나라도 빠지면 그 리비전에서 통째로 사라짐), `--project`도 항상 명시(이 repo의 활성 gcloud 프로젝트가 다름). `scripts/deploy/deploy_lawwin_mainboard.sh`에 근거 주석과 함께 고정했다. (`4a33434`)
- **`min-instances`를 일부러 비워둠** — 업무시간만 1대를 켜도 메모리 무료 한도를 넘겨 과금이 시작된다. 콜드스타트는 `--cpu-boost`로 먼저 대응하도록 두고, 예열이 필요해지면 사건관리앱처럼 별도 창을 붙이는 쪽으로 남겼다. (`4a33434`)

#### 배포 후 발견한 결함 3건 — 전부 같은 원인

- **`AUTH_URL` 누락 (첫 배포)** — 이 값이 없으면 next-auth가 요청에서 origin을 유추하는데, standalone 서버는 Cloud Run 헬스체크를 받으려고 `HOSTNAME=0.0.0.0`에 바인딩하므로 그 값이 새어나가 `redirect_uri`가 `https://0.0.0.0:8080/...`으로 나갔다. **앱은 정상으로 뜨고 로그인만 전부 실패**하는 형태라 발견이 늦기 쉽다. `lawwin-mainboard.env.yaml`에 근거 주석과 함께 고정했다. (`4a33434`, 이슈 `#13`)
- **콜백 가로채기 코드에 같은 결함 2개** — 인증서 발급 후 다시 훑어보니 내가 쓴 `route.ts`에 동일 원인이 두 개 더 있었다. ① `new URL(request.url).origin`으로 절대 URL을 만들어 브라우저를 `https://0.0.0.0:8080/signin`으로 보냈다 → `Location`을 **상대 경로**로 바꿔 origin을 알 필요 자체를 없앴다. ② 같은 origin이 `callbackUrl` 검증에도 쓰여, 진짜 쿠키 값을 `0.0.0.0:8080`과 비교해 정상 값을 전부 기각했다 → next-auth가 이미 공개 origin으로 취급하는 `AUTH_URL`을 신뢰하고, `AUTH_URL`이 없는 로컬 개발에서만 요청으로 폴백하게 했다. 페이지 로드가 아니라 **배포된 서비스에서 인증 URL을 직접 뽑아** 찾은 결함이다. (`240d733`, 이슈 `#13`)
- **공개 주소 3개 중 1개만 로그인이 완결됨** — `lawwin-mainboard.web.app`이나 run.app 주소로 로그인하면 `InvalidCheck: pkceCodeVerifier value could not be parsed` 500이 났다. `AUTH_URL`이 origin을 하나로 고정하니 구글은 어디서 시작했든 `portal.lawwin.co.kr`로 돌아오는데, PKCE 쿠키는 시작한 호스트에 남아 있었다. `src/proxy.ts`를 추가해 나머지를 308로 정규 호스트에 보낸다. 판단 근거를 `x-forwarded-host`로 잡은 이유는 공개 호스트가 살아남는 유일한 자리이기 때문이다 — Firebase Hosting은 Host를 run.app 주소로 바꾸고, `request.url`은 위에서 본 `0.0.0.0:8080`이다. **추론하지 않고 진입점 3곳을 실측한 뒤** 작성했다(같은 `0.0.0.0` 가정으로 이미 세 번 깨졌으므로). 헬스체크처럼 `x-forwarded-host`가 없는 요청과 로컬 개발은 건드리지 않는다. (`d3d8b55`, 이슈 `#13`)

### 2. 메인보드 — 사일런트 인증 (커밋 `c1c0cbf`)

- **진입 시도를 `prompt=none`으로 교체** — `/signin`이 곧장 구글로 넘겨서 세션 없는 사람은 우리 카드를 한 번도 못 보고 구글 로그인 페이지에 떨어졌다. 이제 구글이 아무 화면도 그리지 않고 즉답한다 — 세션 있으면 code, 없으면 `error=login_required`. 둘 다 리다이렉트라 왕복이 보이지 않는다. (`c1c0cbf`)
- **Auth.js가 정상 응답을 실패로 처리하던 것을 가로챔** — Auth.js는 이 거절을 `OAuthCallbackError`로 접어 `/signin?error=OAuthCallbackError`로 보내면서 사유를 버리고 실패 문구를 띄운다. 콜백 라우트가 `SILENT_DECLINED`에 열거한 거절만 가로채 사유를 넘기고, `authjs.callback-url` 쿠키에서 복귀 경로를 되살린다. **쿠키는 심어질 수 있으므로 동일 출처 경로만** 허용했다. 표에 없는 값은 기존대로 Auth.js를 그대로 통과한다. (`c1c0cbf`)
- **사유가 버튼 동작까지 결정** — `login_required`/`consent_required`/`interaction_required`는 계정 선택을 생략한다(이 카드를 보는 사람은 계정이 이미 정해져 있으므로 군더더기). `account_selection_required`·`access_denied`와 명시적 로그아웃은 유지한다 — 생략하면 같은 계정에 다시 붙어 로그아웃과 계정 전환이 둘 다 불가능해진다. 판정 규칙은 `src/lib/signin-attempt.ts`로 빼고 `tests/signin.test.mjs`로 고정했다. (`c1c0cbf`)

### 3. 메인보드 — Firebase Hosting 쿠키 제거로 로그인 실패 (커밋 `eb980c0`, 이슈 #14)

- **정규 호스트로 모아도 로그인이 끝나지 않았다** — `d3d8b55`로 진입점을 하나로 모은 뒤에도 운영 리비전 `lawwin-mainboard-00007-2tj` 로그에 `InvalidCheck: pkceCodeVerifier value could not be parsed`가 남았고(2026-09-11 08:53 UTC), 그 이전 리비전에는 `MissingCSRF`도 있었다. 앞선 커밋에서 세웠던 **"쿠키가 시작한 호스트에 남는다"는 설명으로는 이게 안 풀린다**. 운영 `/api/auth/csrf` 응답 쿠키를 다음 요청에 그대로 재전송해도 CSRF 토큰이 바뀌고 signin POST가 `MissingCSRF`로 거절되는 것을 재현해, 원인이 호스트가 아니라 **Firebase Hosting이 `__session` 외의 요청 쿠키를 제거하는 것**임을 확정했다(공식 문서에 명시된 동작). 작업 기록에 적어뒀던 Safari 쿠키 저장 경합 추정은 입증되지 않아 폐기했다. (이슈 `#14`)
- **쿠키를 서버에 두고 브라우저에는 손잡이만 보냄** — `src/lib/auth-cookie-bridge.ts`를 추가해 Auth.js 쿠키 묶음을 비공개 GCS `auth/cookies/`에 불변 스냅샷으로 저장하고, Firebase가 유일하게 통과시키는 Secure·HttpOnly·SameSite=Lax `__session`에는 **256비트 임의 식별자만** 싣는다. 객체 키는 그 식별자의 SHA-256이라 저장소 이름만 봐서는 손잡이를 역산할 수 없고, 인증 응답마다 식별자를 회전한다. 저장을 **완료한 뒤** 리다이렉트한다. 브라우저 4KB 한도를 넘겨 분할되는 세션 JWT도 스냅샷에는 그대로 담긴다. (`eb980c0`)
- **복원은 프록시에서, 반영은 인증 응답에서** — `src/proxy.ts`가 들어오는 요청의 `__session`을 원래 쿠키 묶음으로 되돌리고, `/api/auth/*` 응답에서 생성·갱신·삭제를 스냅샷에 반영한다(`persist`). 로그인 시작은 `src/app/api/auth/start/route.ts`로 분리해 **CSRF 발급과 검증을 서버 안에서 끝낸다** — 그 구간에는 Firebase가 끼어들 자리가 없다. PKCE 검증은 손대지 않았다. (`eb980c0`)
- **실패를 조용한 로그아웃으로 만들지 않음** — 저장소 읽기에서 404만 "없음"으로 처리하고 나머지 오류는 던진다. 여기서 뭉뚱그리면 GCS 장애가 인증된 요청을 익명으로 바꿔버린다. 반대로 **서버 측 세션 강제 폐기는 제공하지 않는다** — 이전 스냅샷도 만료 전까지 재사용 가능해 기존 JWT와 성질이 같고, 그 한계를 `scripts/deploy/AUTH.md`에 명시했다. 스냅샷 유효기간은 로그인 전 15분, 로그인 후 Auth.js 만료(최대 30일)까지다. (`eb980c0`)
- **검증을 코드로 고정** — 실제 Auth.js 엔진과 모의 OAuth 제공자로 CSRF → PKCE 코드 교환 → 분할 세션 읽기 → 로그아웃까지 태우고, 변조·만료 식별자·PKCE 만료·저장소 오류·외부 복귀 URL 차단을 함께 검증했다(`tests/auth-cookie-bridge.test.mjs`, 전체 41건 통과). 배포 후 확인용으로 `scripts/deploy/check-auth.mjs`를 따로 뒀다 — Firebase를 실제로 경유하는 CSRF 왕복과 사일런트 거절 복귀 경로를 찍어본다. **쿠키 형식이 기존 리비전과 달라 전환 시 트래픽을 한 리비전으로 모아야 한다**는 점도 문서에 남겼다. (`eb980c0`)

### 4. 사건관리 — 사일런트 인증 (이슈 #524)

- **백엔드에 `?silent` 추가** — `/auth/google/login?silent`로 `prompt=none`을 붙인다. 콜백도 code 없이 error만 오는 경우를 받도록 고쳤다 — 기존엔 code가 필수라 422가 났는데, 이건 장애가 아니라 정상 응답이므로 사유를 그대로 프론트 `/login`으로 넘긴다. 사용자가 인증을 취소한 경우(`access_denied`)도 같은 경로로 들어온다. (`7f4d92d`)
- **프론트 진입을 사일런트로 전환** — `/login` 진입 시 무조건 구글로 풀 리다이렉트하던 것을 `prompt=none`으로 바꿔, 세션이 있으면 지금처럼 무클릭 통과하고 없으면 우리 로그인 화면이 뜬다. 사일런트 거절은 실패가 아니므로 에러 문구를 띄우지 않고, `SILENT_DECLINED` 표로 사유를 구분해 버튼이 계정 선택을 거칠지 함께 정한다. `getGoogleLoginUrl`은 인자가 둘로 늘어 옵션 객체로 바꿨다. (`8f8a010`)
- **탭 복귀 재시도 — 채택했다가 같은 날 철회** — 자동 로그인이 불발되면 카드가 뜬 채 멈추고, `auto_login_attempted`가 sessionStorage에 있어 새로고침으로도 안 풀린다. 브라우저에는 "방금 구글에 로그인했다"를 알려주는 이벤트가 없어 `visibilitychange`를 트리거로 삼고 가드 3개(탭당 1회·3초 이상 숨었을 때만·"이미 시도함" 분기에서만)를 뒀다. (`d1e6385`) **그러나 띄워놓고 확인한 뒤 철회했다** — 탭을 옮겼다 왔다는 이유만으로 화면이 구글로 날아가고, 세션이 없으면 사용자는 아무것도 누른 적 없이 구글 페이지에 남겨진다. 대신 진짜 군더더기였던 **버튼의 계정 선택 화면**을 걷어내 `forceAccountOnClick` 한 필드로 버튼 동작을 정하게 했다. 클릭 0회가 아니라 1회지만 사용자가 의도한 1회다. (`4839051`, 이슈 `#524`)

### 5. CRM — 사일런트 인증 (이슈 #12)

- **첫 방문자 보호를 먼저 넣고, 곧 사일런트로 대체** — 우선 "이 브라우저에서 로그인한 적이 없으면 자동 로그인을 걸지 않는다"로 막았다. 브라우저에 구글 세션이 있는지는 넘겨보기 전에는 알 수 없어 첫 방문을 버튼으로 받는 방식이었다. (`c7ca257`) 이후 `prompt=none`이 들어오면서 그 전제가 사라져 **첫 방문이라 무조건 로그인 화면을 띄우던 조건을 제거**했다 — 세션이 있으면 첫 방문도 바로 통과한다. 백엔드에 `silent` 파라미터를 추가하고 재동의(`force_consent`)와 동시 사용 시 재동의를 우선하게 했다. (`2c83ada`)
- **버튼에서 계정 선택 생략** — 자동 로그인이 불발돼 카드가 뜬 경우 로그인 버튼에 `login_hint`를 붙여 계정 선택창을 건너뛴다. 진입 판정을 `AutoLoginDecision`으로 바꿔 버튼 동작이 사유에 따라 갈리게 했다. 함께, **인증 실패 차단을 탭 단위로 변경** — 기존에는 브라우저에 영구히 남아 한 번 실패하면 자동 로그인이 영영 안 됐다. 직접 로그아웃한 차단은 기존대로 유지해 새로고침으로 풀리지 않게 했다. 판정 규칙 10건을 테스트로 고정. (`9c7155b`)

### 6. CRM — 목록 폴링 비용 절감 (이슈 #13)

- **gzip 압축으로 응답 88% 감소** — 백엔드에 압축 미들웨어를 추가해 목록 응답이 실측 27KB → 3.2KB가 됐다. 컬럼 별칭이 한글이라 UTF-8에서 키가 행마다 3바이트씩 반복돼 압축 효과가 특히 컸다. 갱신 주기도 15초 → 20초로 늘려(상담·당사자·회생 3화면 공통) 60명 기준 월 $22 → $10으로 내려갔다. (`70b3a27`)
- **SSE 전환은 기각** — 연결을 계속 열어두면 Cloud Run 활성 단가 구간이 34%에서 100%로 올라가 오히려 비싸진다. 폴링을 줄이는 쪽이 이 구조에서 맞다고 판단하고 근거를 이슈에 남겼다. (이슈 `#13`)

### 7. 운영·보안 조치 (커밋 없음)

- **운영 조치 — KISA 보안권고 1048·1049 영향도 점검** — PostgreSQL CVE 6건과 Linux Kernel CVE 1건에 대해 우리 인프라를 점검했다. 운영 Cloud SQL `lawwin-pg`가 `POSTGRES_16_14`로 실측돼 "16.14 미만" 조건에 해당하지 않아 CVE 5건 영향 없음, `CVE-2026-6476`은 18.4/17.10 대상이라 16.x 라인이 애초에 비대상. Linux Kernel은 직접 운영하는 리눅스 호스트가 없어(프론트·백엔드 Cloud Run, DB Cloud SQL, 레거시 Windows+IIS) 대상 없음. **결론: 조치 불필요.** 근거를 양쪽 repo 이슈에 남겼다. (이슈 `#133`, `#540`)
- **운영 조치 — 사건관리 SSE 운영 로그 점검** — 리비전 `lawwin-case-00229-b26` 기준 최근 24시간 `GET /api/events` 620건 중 5분 미만 조기종료가 **0건**, 553건이 Cloud Run timeout(3600초)을 꽉 채웠다. 리비전 00221의 즉시끊김 패턴이 사라진 것으로 `is_disconnected` 검사 제거(`fd87359`)가 운영에서 확인됐다. 응답 바이트 min 2176 / avg 3196으로 keepalive 바닥값을 웃돌아 실제 이벤트가 실려나간 것도 확인. 7일간 에러 1건은 Cloud SQL 인스턴스 전체의 일시적 네트워크 리셋이었고 백오프 루프가 1초 뒤 자동 복구했다. **조치 불필요** — 설계된 복구 경로가 설계대로 동작한 사례. (이슈 `#518`)

**금일 종합:** 오늘의 축은 두 개였다. 하나는 **세 앱에 흩어져 있던 같은 결함을 같은 날 정리한 것** — 메인보드·사건관리·CRM이 각각 다른 언어와 프레임워크로 짜여 있으면서도 "세션 유무를 모르는 채 구글로 넘긴다"는 동일한 전제를 공유하고 있었고, 그 대가로 세션 없는 사용자는 우리 로그인 화면을 한 번도 보지 못했다. `prompt=none`이라는 같은 해법을 세 코드베이스에 각각 맞춰 넣으면서, 거절 사유별로 계정 선택을 생략할지까지 세 곳 모두 같은 표로 통일했다. 사건관리에서는 탭 복귀 재시도를 채택했다가 실제로 띄워보고 **같은 날 철회**했는데, 사용자가 누르지 않은 화면 전환을 만들지 않는 편이 낫다는 판단이었다. 다른 하나는 **사내 포털의 Cloud Run 이관**으로, 월 $20 고정비를 무료 한도 안으로 옮겼다. 다만 배포 후 `0.0.0.0:8080`이 원인인 결함이 세 번 연달아 나왔고 — 앱은 멀쩡히 뜨고 로그인만 깨지는 형태라 전부 발견이 늦었다 — 진입점 3곳을 실측한 뒤 프록시로 모았지만 그것으로도 로그인은 끝나지 않았고, 마지막에 가서야 진짜 원인이 **Firebase Hosting의 쿠키 제거**라는 것이 재현으로 드러났다. 앞선 설명이 틀렸음을 인정하고 다시 판 셈인데, 오늘 배운 것을 하나만 꼽으면 이쪽이다 — **증상이 남아 있으면 앞의 설명이 맞았다는 근거가 아니다.** 그 외 KISA 보안권고 2건과 사건관리 SSE 운영 로그를 점검해 양쪽 다 조치 불필요를 근거와 함께 확정했다. 금일 3개 repo에 걸쳐 커밋 13건.
