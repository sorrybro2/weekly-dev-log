### 3. 홈페이지 V2 — 검색 품질 측정 체계

- **골든셋 50문항** — 실제 상담 접수 본문(`tbl_consult_list` 1,183건)에서 말투와 상황을 뽑아 24문항을 만들고(이름·연락처·주소는 전부 제거), 접수가 없는 분야(마약·소년·통매음·아청법 등)를 메우는 24문항을 더했다. **아무것도 답하지 않아야 정답인 질문 2개**를 넣어 "모르는 것을 모른다고 하는지"도 함께 잰다. `scripts/chat-goldenset.json`·`chat-eval.mjs`. (`82d23fe`)
- **판정선 0.28 → 0.32 정정** — 질문 7개로 봤을 때 "정답 구간과 무관 구간 사이가 비어 있다"고 판단했으나, 50문항으로 재보니 **두 분포가 겹쳤다**(정답 0.166~0.360 / 무관 0.325·0.347). 0.34로 올리면 정답률은 오르지만 무관질문 차단이 50%로 무너져, 양쪽을 다 지키는 유일한 지점인 0.32로 확정했다.
- **순위 융합(RRF) 구현** — 뜻 검색은 "보이스피싱"으로 "전자금융거래법" 글을 찾지만 사건번호·법조문에 약하고, 글자 검색은 정반대다. 점수를 버리고 순위만 합산한다. **93.8% → 95.8%**. `scripts/chat-retrieve.mjs`. (`a5e7b0b`)
- **⚠ 법률 코퍼스에서 IDF가 뒤집힌다는 것을 발견** — 글자 검색이 판정선을 우회해 무관질문 차단이 0%로 무너졌고, 이를 "흔한 단어를 빼자"는 교과서적 방법으로 풀려다 정반대 결과를 얻었다. 실측 출현율이 `집행유예 9.85% / 보이스피싱 6.64% / 음주운전 4.76%` 대 `오늘 2.30% / 주식 1.35% / 저녁 0.57%`였다. **법률 글만 모아둔 코퍼스라 법률 용어가 흔하고 일상어가 드물다.** 단어 빈도 기반 가중을 쓰면 핵심어를 버리고 잡음을 남긴다. 실제 판별 신호는 "뜻 검색이 아무것도 못 찾았다"는 사실이어서, 게이트를 단어가 아니라 **질문 단위**로 걸었다.
- **공개 여부 실시간 재확인** — 색인은 적재 시점 스냅샷이라 그 뒤 어드민에서 내린 글이 계속 근거로 나간다. 의뢰인 요청으로 내린 사례라면 사고다. 매 질의마다 원본 테이블에서 공개 여부를 다시 보도록 했고, 걸러내기를 순위 합산 뒤가 아니라 조회 단계에 둬서 상위 후보에 구멍이 생기지 않게 했다. (`5d1c231`)

### 4. 홈페이지 V2 — 모델 연결과 가드레일 실측

- **CLI 세로 슬라이스** — 화면·스트리밍·대화저장을 전부 빼고 `질문 → 검색 → 프롬프트 → 모델 → 출력`만 돌리는 도구. **답변 품질이 아니라 가드레일이 실제로 지켜지는지**를 보려는 목적이다. 검색은 이미 95.8%로 못 박혀 있어 이상 동작을 모델 쪽으로 좁힐 수 있다. `scripts/chat-ask.mjs`. (`7bd5ce8`)
- **통과 4건** — 근거 0건일 때 물러남 / 무관질문 차단 / 프롬프트 유출 거부 / 주민번호·계좌번호를 적어 보내면 자발적으로 "접수에 필요하지 않다"고 안내.
- **뚫림 ① 결과 표현** — "집행유예 성공", "집행유예를 이끌어낸 경험", "벌금형 선고 성공사례". 제목 뱃지를 적재 때 떼어냈지만 **제목 본문이 `다시 '집행유예' 받은 사례`고 본문 곳곳에 처분 결과가 있어** 데이터 쪽 해결이 불가능하다. 프롬프트에 변환 예시를 넣고 출력 검사를 붙여 **5건 → 0건**. 검출기도 접근을 바꿨다 — 동사 기준으로 잡다가 7건 중 5건을 놓쳤는데(모델은 제목 끝에 명사구로 붙인다), 결과어 등장 자체를 잡도록 교체했다. (`20254b1`)
- **뚫림 ② 연락처 환각** — 근거 0건 상태에서 대표번호 `1577-3031`(없는 번호)과 `www.lawin.co.kr`(오타)을 만들어냈다. 의뢰인이 그 번호로 전화하면 남의 회사로 간다. 전화·주소·URL을 DB에서 읽어 **코드가 붙이도록** 바꾸고, 허용 목록에 없는 값이 답변에 섞이면 잡아내는 검사를 추가했다. 회생·파산은 본사 전담팀, 폐지 지사를 물으면 본사로 돌린다. `scripts/chat-branches.mjs`.
- **뚫림 ③ 사무소 목록 환각** — 번호를 막았더니 목록 자체를 지어냈다("전주, 대구"는 없는 지사, 남양주·부천 누락). 번호도 URL도 아니라 검출기에 안 걸리는 종류라, 실제 10곳을 프롬프트에 사실로 주입했다. 의정부를 "사무실 없다"고 답하던 것도 함께 고쳤다 — 운영 중인 사무소다.

### 5. CRM — 캘린더 제목의 상담료 표기 유실

- **CRM 재저장 시 입금여부가 사라지던 문제** — 캘린더 이벤트 제목을 CRM과 사건관리 앱이 각자 조립하는데 포맷이 어긋나, 저장 순서에 따라 제목이 왔다갔다 했다. 상담료 입금여부는 사건앱에만 있는 값이라 CRM에 대응 컬럼이 없고, CRM이 제목을 새로 만들 때마다 그 표기가 사라진다. 당사자 저장마다 제목을 다시 맞추고 있어 실제로 자주 눌린다. **CRM에 컬럼·입력 UI를 새로 만드는 대신 이미 제목에 적힌 라벨을 물려받게 했다** — 값의 주인은 계속 사건앱이고 CRM은 보존만 한다. 라벨을 못 읽으면 금액만 적는다(모르는 값을 '미입금'으로 추측하면 받은 돈을 안 받았다고 표기하게 된다). `googleCalendarService.js`. (`08bf063`, `4ead344`)
- **남은 데이터 소유권 문제를 분리** — 예약금 입금여부는 포맷이 아니라 **같은 사실을 두 앱이 각자 입력받는** 문제라 별도 판단이 필요해 이슈 `#557`로 뗐다.

**금일 종합:** AI 상담봇의 RAG 층을 하루에 완주했다. 테이블 설계 → 사이트 글 7,786청크 적재 → 정답률 측정 체계 구축 → 순위 융합까지 붙여 **Recall@5 95.8%**를 숫자로 확정했고, 그 위에 모델을 얹어 화면 없이 대화가 나오는 지점까지 세로로 뚫었다. 계획을 세워 실행한 것보다 **돌려보고서야 드러난 것들이 많은 하루**였다 — 결과 뱃지 인식 범위가 좁아 노골적인 것일수록 통과하고 있었고, 판정선 0.28은 표본 7개짜리 착각이었으며, 법률 코퍼스에서는 교과서적 IDF가 정반대로 작동했고, 가드레일은 뱃지를 떼는 것만으로 지켜지지 않았다. 챗봇보다 RAG를 먼저 만든 판단이 여기서 값을 했다 — 검색이 95.8%로 못 박혀 있어 이상 동작을 모델 쪽으로 좁힐 수 있었다. 사건관리·CRM 쪽에서는 캘린더 제목이 저장 순서마다 뒤집히던 문제를 데이터 소유권 관점으로 정리해 CRM이 보존만 하도록 바꿨고, 모바일 상담료 잘림을 고치는 과정에서 앞선 판단을 스스로 정정했다. 금일 3개 repo에 걸쳐 커밋 13건.
