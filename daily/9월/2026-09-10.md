### 1. CRM — 회생 상담 채권자수·진행내역 컬럼 (이슈 #10)

#### 요구와 설계 판단

- **진행내역을 별도 필드로 분리** — 회생 상담관리 목록에는 이미 `진행` 컬럼이 있었지만 이건 총채무·소득·변제예상을 문자열로 조합한 **파생값**이라 사람이 경과를 적을 자리가 없었다. 상담·서류접수·후속연락 이력을 직접 쓰는 `progress_history`를 신설해 기존 파생 요약과 상담 메모 양쪽과 구분했다. (`47c477f`)
- **PDF 출력 항목 전수 조사** — "채권자수는 PDF에 나오고 진행내역은 나오지 말아야 한다"는 요구를 확인하기 위해 화면·PDF·PNG 세 렌더러의 항목을 대조했다. 채권자수는 이미 출력 항목에 포함돼 있어 변경이 불필요했고, 진행내역은 내부 관리 항목이라 처음부터 제외하도록 폼 안내문에 명시했다. 조사 결과(현재 미출력 항목 전체 목록)를 이슈 본문에 남겨 다음에 같은 질문이 나올 때 코드를 다시 뒤지지 않게 했다. (이슈 `#10`)

### 2. CRM — 크롬 구글 세션으로 자동 로그인 (이슈 #11)

#### 원인 규명

- **두 지점이 겹쳐 있었음** — `authController.js`의 `redirectToGoogle()`에 `prompt: 'consent'`가 박혀 있어 이미 스코프를 승인한 사용자에게도 동의화면을 무조건 노출했고, `login_page.dart`의 `_checkForLogoutOrCode()`는 JWT가 없을 때 아무것도 하지 않고 버튼 클릭을 기다렸다. 둘 중 하나만 고쳐도 클릭이나 동의화면 한쪽이 남는 구조였다. (이슈 `#11`)
- **리프레시 토큰(B안)을 버린 근거** — 프론트가 `*.web.app`, 백엔드가 `*.run.app`으로 크로스 사이트라 httpOnly 리프레시 쿠키가 `SameSite=None`을 요구하고 브라우저 3rd-party 쿠키 정책에 취약하다. 재인증을 눈에 안 보이게 만드는 A안이 이 구조에서 가성비가 높다고 판단. (이슈 `#11`)

#### 구현

- **백엔드 — `prompt` 제거, 파라미터 2개 신설** — `prompt`를 지정하지 않으면 동의 이력 + 브라우저 세션이 있는 사용자는 구글 화면 없이 콜백으로 되돌아온다. `login_hint`는 이메일 형식만 가볍게 검증(`normalizeLoginHint`)해 전달하고, `force_consent=true`일 때만 `prompt: 'consent'`를 붙여 재동의 경로를 남겼다. (`c7be844`)
- **프론트 — 자동 리다이렉트와 3중 가드** — JWT가 없으면 즉시 구글로 보내되, 콜백이 `?error=`로 돌아온 경우와 로그인 교환이 실패한 경우 자동 로그인을 차단한다. 재시도에 30초 쿨다운을 둬서 코드도 에러도 없이 돌아오는 예외 상황에서 왕복이 반복되지 않게 했다. (`c7be844`)
- **로그아웃 차단은 선택이 아니라 필수** — `main_layout._handleLogout()`에 차단 플래그를 세우지 않으면 로그아웃 직후 로그인 화면이 곧바로 재인증을 걸어 **로그아웃이 영구히 불가능**해진다. 수동 로그인 버튼은 차단을 풀고 `login_hint` 없이 보내 계정 전환이 가능하게 남겼다. (`c7be844`)
- **`prompt` 제거의 부작용을 함께 처리** — `prompt=consent`는 refresh_token을 매 로그인 재발급받던 유일한 경로였다. 이걸 빼면 기존 안내문("로그아웃 후 다시 로그인")이 더 이상 드라이브 권한을 복구하지 못하므로, `google_reconsent.dart`를 신설해 412 `GOOGLE_REAUTH_REQUIRED` 응답 시 스낵바의 **권한 동의** 액션으로 `force_consent` 흐름을 바로 실행하고 완료 후 원래 화면으로 복귀시켰다. 회생·상담 추출 다이얼로그 양쪽에 적용. (`c7be844`)

#### 자체 구현 버그 — 기존 브라우저에서 자동 로그인 차단

- **증상과 원인** — 배포 후 "한 번 로그인해둔 환경인데 자동 로그인이 안 된다"는 확인을 받았다. `canStartAutoLogin()`의 첫 조건이 `lastLoginEmail != ''`였는데, 이 키는 `saveLoginResponse()`에서만 기록되므로 **이 기능 배포 이후의 로그인에서만** 생긴다. 배포 전에 로그인해둔 브라우저는 키가 없고, 세션이 만료되면 `clearSession()`이 기존 `userEmail`까지 지워서 자동 로그인이 영구히 막혔다. (`c997877`)
- **수정** — 게이트에서 이메일 필수 조건을 제거했다(이메일은 계정 선택창을 건너뛰는 **힌트**일 뿐이고, 차단 조건은 로그아웃·실패 차단과 30초 쿨다운 두 가지로 충분). 추가로 `clearSession()`이 세션을 비우기 전에 `userEmail`을 `lastLoginEmail`로 이어받게 해, 이후 만료되는 기존 세션은 힌트를 자동으로 물려받는다. 건너뛴 사유를 `developer.log`로 남겨 브라우저 콘솔에서 원인을 바로 볼 수 있게 했다. (`c997877`)

#### 8시간 세션아웃 유지 확인

- **세션아웃은 그대로 있고 서버가 강제한다** — 자동 로그인이 8시간 경계를 무력화하는지 확인 요청을 받아 검증했다. JWT `exp - iat = 8시간`이고 `authMiddleware`의 `jwt.verify`가 만료 토큰을 `TokenExpiredError`로 거부해 403을 반환하므로, 만료 토큰으로는 API를 한 건도 호출할 수 없다. JWT를 발급·저장하는 지점이 각각 한 곳뿐이고 **토큰 갱신 엔드포인트가 존재하지 않아** 8시간마다 반드시 구글 인증 엔드포인트를 왕복한다. 즉 실질 재인증 주기는 우리 8시간이 아니라 **구글 워크스페이스의 4시간 세션 정책**이 결정하며, 세션이 죽어 있으면 구글이 비밀번호를 다시 묻는다. (이슈 `#11`)
- **부수 확인** — `session_manager.dart`의 8시간 유휴 타임아웃은 `_lastActivityTime`이 메모리에만 있어 새로고침마다 초기화되고 `null`이면 만료로 보지 않아, 실제로는 동작하지 않는 중복 체크였다(금일 변경 이전부터). 세션아웃은 JWT 만료가 담당하므로 실질 영향이 없어 손대지 않았다.

### 3. 사건관리 — 크롬 구글 세션으로 자동 로그인 (이슈 #524)

- **같은 증상의 다른 파라미터** — `backend/app/api/auth_api.py`의 인증 URL에 `prompt=select_account`가 박혀 있었다. CRM의 `prompt=consent`와 값은 다르지만 "기존 구글 세션을 무시하고 화면을 띄워라"는 같은 지시다. 제거하니 동의 이력이 있는 사용자는 화면 없이 즉시 되돌아온다. (`f835fa8`)
- **`hd` 도메인 힌트로 오선택 차단** — 업무 도메인 계정만 후보로 좁혀 개인 구글 계정을 잘못 고르는 경우를 막았다. 도메인 값은 `core/config.py`에 `GOOGLE_WORKSPACE_DOMAIN` 설정으로 분리해 하드코딩을 피했다. `force_account=true`일 때만 `prompt=select_account`를 붙여 계정 전환·공용 PC 경로를 남겼다. (`f835fa8`)
- **`access_type=offline` 유지 근거** — 드라이브 `refresh_token`이 이 값에 의존한다. `prompt`를 뺐으므로 refresh_token은 최초 동의 때만 내려오지만, 콜백이 "없으면 기존 토큰 유지"로 처리하므로 기존 사용자는 영향받지 않는다. (`f835fa8`)
- **프론트 자동 이동 + 가드 3중** — `LoginPage.tsx` 진입 시 자동으로 인증 URL로 이동시켜 `401 → /login → 구글 왕복 → 원래 화면 복귀`가 화면 깜빡임 수준으로만 보이게 했다. 복귀 경로는 기존 `POST_LOGIN_REDIRECT_KEY`가 그대로 처리한다. 콜백 `?error=` : 직접 로그아웃 : 이미 시도함 세 경우엔 자동 이동을 멈추고 기존 버튼 UI를 보여주며, 시도 플래그는 로그인 성공 시 해제해 다음 만료 때 다시 동작한다. (`94f62f1`)
- **StrictMode 이중 실행 회피** — 진입 판단은 세션 플래그를 읽고 지우는 부수효과라 effect에 두면 개발 모드 이중 실행과 set-state-in-effect 문제가 생긴다. 렌더 전 모듈 스코프에서 한 번만 판단하도록 `lib/authRedirect.ts`로 분리했다. (`94f62f1`)
- **엔드포인트 응답으로 검증** — 파라미터 없음 → `prompt` 없음 : `hd` 부착 : 200, `force_account=true` → `prompt=select_account` : 200, `force_account=oops` → 422. 기존 scope 4종과 `access_type=offline` 유지 확인. 프론트는 타입 검사와 변경 파일 ESLint 통과. (이슈 `#524`)

### 4. 운영 조치·이슈 정리

- **CRM 운영 배포 3회** — 백엔드는 `lawwin-crm-00227-4zj`(회생 컬럼)과 `lawwin-crm-00228-6n8`(자동 로그인) 2개 리비전, 프론트는 3회. 배포 전 기준 리비전을 먼저 기록해 롤백 지점을 남겼고, 배포 후 인증 URL의 `prompt` 부재 : `login_hint`·`hd` 부착 : `force_consent` 동작을 실제 302 응답으로 확인했다. 프론트는 배포본 `main.dart.js`의 SHA-256을 로컬 릴리스 빌드와 대조해 반영을 확정했다. (이슈 `#11`)
- **배포 반영 지연 발견(후속 과제)** — Firebase Hosting이 `index.html`·`main.dart.js`에 `Cache-Control: max-age=3600`을 내려 배포가 사용자 브라우저에 **최대 1시간 늦게** 도달한다. 금일 검증에서도 강력 새로고침이 필요했다. `firebase.json`의 headers로 index.html만 no-cache로 분리하는 정리를 후속 과제로 이슈에 남겼다. (이슈 `#11`)
- **미해결로 남긴 것** — 회생 컬럼 배포 직후 운영 로그인 요청 1건에서 구글 인증코드 교환 `invalid_grant` → HTTP 500이 확인됐다. 리비전 간 환경변수는 동일했고 이후 로그인은 정상이었으나, 반복 여부는 추가 관찰이 필요하다. (이슈 `#10`)
- **롤백 명령 오류 정정** — 프론트 롤백으로 안내했던 `firebase hosting:rollback`이 실제로는 존재하지 않는 명령임을 확인했다. 프론트 롤백은 콘솔의 릴리스 목록 또는 이전 커밋 재빌드로 해야 하며, 백엔드의 `gcloud run services update-traffic`만 유효하다. 배포 문서 메모에 반영했다.
- **이슈 종료 처리 2건** — `#522`(수납내역 착수금·성공보수 납입 진행률 분리)와 `#360`(VAPID 시크릿 버전 고정)의 구현 완료를 확인해 종료 처리했다. 두 건의 구현 커밋은 동료(`bs-jsPark`) 작업이며, 금일 내 몫은 검증과 종료 정리다.
