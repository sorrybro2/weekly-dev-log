어제 "폴링 유지"로 닫았던 결론을 오늘 다시 계산해 뒤집었습니다. 60명 기준으로는 폴링도 이미 인스턴스를 활성 단가로 태우고 있어서, 웹소켓을 보류시킨 근거가 성립하지 않았습니다. 20초 폴링을 SSE 실시간 신호로 전면 교체했고, 그 과정에서 로컬에서는 전혀 재현되지 않는 운영 전용 장애 3건을 순차로 규명했습니다. 금일 커밋 14건(2개 repo), 이슈 2건 생성 : 코멘트 5건.

⚡ *〔사건관리 앱 : 폴링에서 SSE 실시간 전환 (#518)〕*

•  *보류 결정을 비용 근거로 뒤집음* — #186이 웹소켓을 보류한 근거는 "연결 유지가 활성 단가"였는데, 60명이 20초마다 조회하면 초당 12요청이라 폴링도 같은 단가를 내고 있었음
•  *단가 자체가 틀려 있었음* — 주석의 egress $0.12/GB가 실제로는 $0.19/GiB. 폴링 비용이 1.6배 과소평가. 서울 리전이 Cloud Run Tier 2임도 문서로 확정
•  *팬아웃은 Postgres LISTEN : NOTIFY* — 이미 쓰는 Cloud SQL이라 추가 비용 0. Pub/Sub은 구독 생명주기 관리 부담, Redis는 월 $35로 절감액을 상쇄해 배제 (6123e90)
•  *엔드포인트 50곳을 안 고쳤음* — 감사로그와 같은 세션 훅으로 ORM 변경을 통째로 잡아, 새 엔드포인트가 생겨도 빠뜨릴 여지가 없음. 크롤러가 채우는 법원진행상황도 포함
•  *EventSource 대신 fetch* — EventSource는 헤더를 못 붙여 JWT를 쿼리스트링에 실어야 하고 그러면 액세스 로그에 토큰이 남음 (a2088a1)
•  *폴링 27곳 전면 제거* — lib:polling.ts까지 삭제. 주기 재조회에서 변경 신호 기반으로 전환 (5bcd062)

🔴 *〔로컬에서는 안 보이던 운영 전용 장애 3건〕*

•  *gzip이 SSE를 압축 대기* — minimum_size 1000B를 채우려 첫 청크를 물고 기다리는데 신호가 12~60바이트라 응답 헤더조차 안 나감. 클라이언트 헤더는 Cloud Run 프론트엔드가 정규화해 무력화, 서버가 경로로 판정하게 수정 (8550f58)
•  *is_disconnected가 첫 호출부터 True* — 스트림이 한 줄만 남기고 200으로 즉시 종료. 액세스 로그만 봤을 땐 "매달렸다"로 오해했고, 애플리케이션 로그의 200 OK를 보고서야 "끝난 것"임이 드러남 (fd87359)
•  *Firebase Hosting이 스트리밍을 버퍼링* — 도메인 경유는 응답 없음, run.app 직접은 정상. SSE만 Cloud Run에 직접 붙이고 REST는 도메인 유지해 CDN 캐싱을 잃지 않게 처리 (6e7f659)
•  *셋 다 로컬에 없는 계층에서 발생* — 로컬 검증은 필요했지만 충분하지 않았고, 진단 순서 자체가 관건이었음
