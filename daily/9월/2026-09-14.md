## 📝 상세 업무 내역

### 1. 사건관리 — PC 업로드 4개 기능을 브라우저 → Drive 직접 업로드로 전환 (이슈 #548, #549)

#### 전제 — 스코프 확대

- **`drive.readonly`로는 성립하지 않는다** — 이슈 본문은 기존 Drive Picker용 `fetchDriveAccessToken()`을 재사용하면 된다고 봤지만, 그 토큰은 읽기 전용이라 업로드가 403이다. `SCOPES`의 `drive.readonly`를 `drive`로 교체하고 `/auth/drive-token` 응답에 `scope`·`can_upload`를 실었다. 백엔드는 이미 DWD로 같은 `drive` 스코프를 써서 사용자를 가장해 파일을 쓰고 있었으므로 실질 권한 확대는 아니다. (`ae4e4c0`)
- **전원 재동의를 기다리지 않는 구조** — 저장된 refresh_token은 옛 스코프 그대로라 사용자가 재동의해야 새 토큰이 나온다. `can_upload`를 내려 불가한 사용자는 프론트가 기존 서버 경유로 폴백하게 해, 배포와 재동의를 분리했다. (`ae4e4c0`, `backend/app/api/auth_api.py`)

#### 공용 유틸과 전환기 스위치

- **`frontend/src/lib/driveUpload.ts` 신설** — Drive v3 resumable 업로드로 세션을 만들고 XHR PUT으로 바이트를 보낸다(진행률 이벤트 때문에 fetch가 아니라 XHR). 다중 파일 순차 업로드까지 여기서 처리한다. (`88bca99`)
- **대상 폴더를 필수 인자로 뒀다** — 빠뜨리면 에러가 아니라 업로더의 **내 드라이브 최상단에 조용히 저장**돼, 사건 폴더에 있어야 할 문서가 개인 드라이브로 흩어진다. 타입으로 막는 편이 안전하다. (`88bca99`)
- **`shouldUploadDirectly()`는 전환기 스위치** — 합계 25MB 이하이거나 재동의 전 사용자면 검증된 서버 경유 경로를 그대로 쓴다. 운영 검증 후 임계값을 0으로 내리고 서버 경유 코드를 걷어내는 순서로 설계했다. (`88bca99`, `googlePicker.ts` 토큰 캐시가 `can_upload`를 함께 들도록 변경)

#### 기능별 전환 — 서버 역할을 조회와 기록 둘로 분리

- **수발신문서** — `GET /document-logs/{id}/upload-target`(폴더 ID·URL 반환)과 `POST /document-logs/{id}/attach-uploaded`(검증 후 기록)로 나눴다. UUID 파일명 폴백(#405)·결재배지 동기화 등 기존 `attach-file`의 후처리를 그대로 유지해 두 경로의 결과가 같게 했고, 이름을 고칠 때는 이미 올라간 Drive 파일도 함께 변경한다. (`3755c88`, `ba39e56`)
- **사건 Drive 패널** — DB에 따로 기록하지 않고 Drive 폴더 자체가 목록이라 서버는 대상 폴더만 정해주면 된다. 다중 파일이라 32MB가 파일 하나가 아니라 **합계**로 걸려 임계값 판정도 합계 기준이며, 한 파일이 실패해도 나머지를 계속 올리고 `uploaded`/`failed`로 나눠 돌려주는 기존 동작을 맞췄다. (`d7c3873`)
- **계약** — 폴더를 사무소 설정(`contract_file_folders`)이 정해서 프론트가 알 수 없으므로 조회가 반드시 선행된다. Drive 링크 첨부(`driveUrl`)는 바이트가 서버를 거치지 않아 32MB와 무관하므로 기존 경로를 그대로 뒀다. (`008b76f`)
- **수기일정** — 기존 `/file` 경로와 결과가 같아야 하므로 **캘린더 이벤트 파일 첨부까지** 동일하게 수행한다. 이걸 빠뜨리면 일정에는 파일이 보이는데 캘린더 이벤트에는 안 붙는 반쪽 상태가 된다. 이로써 #549가 지목한 4개 기능 전부 전환 완료. (`da1989c`)
- **기록 전 부모 폴더 재검증** — `attach-uploaded`는 클라이언트가 이미 올린 결과를 받는 구조라, 검증이 없으면 파일이 엉뚱한 곳에 있는데도 대장만 정상으로 보인다. 또 폴더 조회가 업로드보다 먼저라 폴더가 없으면 **업로드 시작 전에** 422로 막힌다 — 다 올린 뒤 실패하던 기존 동작(#229)보다 낫다. (`3755c88`)

#### 업로드 진행률 표시

- **API 계층까지 콜백 연결** — 4개 기능의 첨부 API가 `onProgress`를 받아 `uploadFileToDrive`로 넘긴다. 사건 Drive 패널은 다중 파일이라 "3개 중 2번째 · 45%"를 만들 수 있게 `DriveUploadProgress(index/total/fileName/ratio)`로 넘겼다. (`abfdb3a`)
- **화면 배치** — 사건 Drive 패널은 드롭 오버레이에 진행바를 두고, 나머지 3곳(수발신문서 등록·상세, 계약, 수기일정)은 제출 흐름 한가운데 루프에서 업로드가 일어나 진행바를 놓을 자리가 없어 같은 id의 토스트를 갱신하는 공용 헬퍼(`uploadProgressToast.ts`)로 처리했다. 호출부는 `try/finally` 두 줄만 늘었다. (`8009dba`)
- **서버 경유 경로에는 일부러 붙이지 않았다** — 측정 가능한 건 브라우저→백엔드 구간뿐이라 전송이 끝나는 순간 100%가 찍히고, 정작 남은 백엔드→Drive 구간 내내 100%로 멈춰 있어 오히려 거짓말이 된다. (`abfdb3a`)
- **99%에서 멈춘다** — 100%는 전송이 끝난 것일 뿐 서버 기록이 남아 있다. 100%를 보고 다 된 줄 알고 창을 닫으면 안 되기 때문이다. 토스트는 첫 진행률이 올라올 때만 떠 작은 파일에서 깜빡이는 것도 막는다. (`8009dba`)

#### 배포 전에 잡은 결함 — 재동의가 먹지 않는 문제

- **로그아웃·재로그인으로도 해결되지 않는 상태였다** — 구글은 **새 동의를 받을 때만** refresh_token을 재발급한다. 사용자가 `drive`에 동의해도(콜백 응답 `scope`에 실제로 들어온다) 동의 이력이 있으면 동의 화면을 건너뛰어 refresh_token이 안 내려오고, 콜백은 "없으면 기존 토큰 유지"라 옛 `drive.readonly` 토큰이 그대로 남는다. 그 토큰으로 갱신하면 계속 `can_upload=false`다. (`cf4ed75`)
- **로컬 실측으로 확정** — 저장된 토큰(발급 2026-07-15)으로 직접 갱신해보니 `scope`에 `drive.readonly`가 그대로였고, 재동의 뒤에도 직접 업로드 경로가 한 번도 실행되지 않았다. 이대로 배포했으면 전 직원이 재로그인을 반복해도 새 경로를 못 탔을 것이다. (이슈 `#549` 코멘트)
- **조치** — `/auth/google/login`에 `force_consent`(→ `prompt=consent`)를 추가하고, 큰 파일인데 권한이 모자라면 "Drive 권한 갱신" 안내 토스트를 세션당 1회 띄워 버튼으로 재동의에 진입하게 했다. 강제 리다이렉트는 하지 않는다 — 폴백이 동작하므로 안내를 무시해도 파일은 올라가고, 업로드 흐름을 끊지 않는 편이 낫다. (`cf4ed75`)
- **검증과 그 한계** — 재동의 후 `upload-target` 200 → `attach-uploaded` 200으로 직접 업로드 경로 동작을 확인했다. 다만 **32MB 한계 자체는 로컬에서 검증할 수 없다**(Cloud Run 제약이라 로컬 uvicorn은 큰 파일도 그냥 받는다). 실제 검증은 배포 + 재동의 후에 가능하다는 점을 이슈에 남겼다. (이슈 `#549` 코멘트)
- **정정해 둔 것 2가지** — 이슈 본문 비교표의 "속도 개선"은 기대보다 작다. 어느 경로든 사용자 회선으로 구글에 한 번 올리는 시간이 지배적이라 사라지지 않고, 줄어드는 건 릴레이 한 단계뿐이다. **이 작업의 실질 이득은 속도가 아니라 32MB 한계 제거**다. 또 진행률 토스트가 직접 업로드 경로에서도 실제로 뜨지 않는 것을 확인해, 원인 미확인 상태로 후속 과제에 남겼다. (이슈 `#549` 코멘트)
- **브랜치 병합** — 기능별 7개 + 후속 3개 커밋을 `feat/549-direct-drive-upload`에서 정리해 병합. (`58ae1f5`)

### 2. CRM — 로그인 진입 차단 복구·문구 정정·운영 조회 도구

- **로그아웃 이력이 있는 브라우저는 영영 못 들어갔다** — 로그아웃 차단 플래그가 localStorage(영구)에 있어, 한 번이라도 로그아웃한 브라우저는 진입 시 구글에 세션을 물어보지도 않았다. 주소만 쳐서는 자동 로그인이 성립하지 않는 상태. sessionStorage(탭 수명)로 옮겨, 로그아웃한 탭에서는 카드가 유지돼 계정 전환은 그대로 가능하게 했다. (`481d982`, 이슈 `#14`)
- **이미 각인된 플래그까지 처리** — 판정할 때 예전 localStorage 플래그를 발견하면 지우고 무시한다. 사용자가 캐시를 비우는 등의 조치를 할 필요가 없다. 운영 로그에서 프로브 없이 버튼 클릭만으로 1초 만에 로그인된 사례를 확인해 복구를 검증했다. (`481d982`)
- **테스트가 통과하고 있던 이유** — 모바일 세션 저장소 스텁이 항상 빈 값을 돌려줘 차단 로직이 동작하지도, 검증되지도 않고 있었다. 메모리 저장소로 교체하고 "차단이 브라우저에 남지 않는지 · 예전 플래그가 지워지는지"를 테스트로 고정했다. (`481d982`, `login_auto_login_decision_test.dart`)
- **회생 채권자 수 안내 문구 오기** — 보증보험을 포함해 계산하라는 안내가 '별도 채무자'로 잘못 적혀 있었다. 같은 문구가 입력 화면·결과 화면·PDF·이미지 4곳에 복사돼 있어 전부 함께 고쳤다. 회생팀 요청 건. (`2d6caf2`)
- **운영 DB 읽기 전용 조회 스크립트** — 조회 진입점을 파일 하나로 고정해 허용 규칙(`permissions.allow`)을 걸 수 있게 하고, `SELECT`/`WITH`로 시작하지 않는 SQL·세미콜론으로 이어 붙인 다중 문장·쓰기 키워드를 거부한다. DB 비밀번호는 Secret Manager에서 그때그때 읽어 레포에 남지 않는다. (`e13d7b9`, `backend/scripts/query-readonly.js`)

### 3. 메인보드 — 정적 이미지를 호스트 정규화에서 제외 (이슈 #15, #16)

- **운영에서 아이콘 2개만 깨졌다** — 사건앱(`vv-yellow.png`)·CRM(`vv-blue.png`)만 PNG를 쓰고 나머지는 인라인 SVG라 최적화기를 거치지 않아 멀쩡했다. 증상이 좁아 원인 추적이 늦어지기 쉬운 형태. (`c6c55ea`)
- **원인은 프록시와 `next/image`의 내부 요청** — 최적화기는 `/_next/image` 요청을 받으면 원본을 자기 자신에게 다시 요청하는데, 그 내부 요청은 `createRequestResponseMocks`로 만들어져 헤더가 비어 있어 Host가 없다. matcher가 `/_next/image`는 제외했지만 `/brand/*.png`는 제외하지 않아 내부 요청이 프록시에 걸렸고, `x-forwarded-host`가 `AUTH_URL` 호스트와 달라 308로 튕겨 최적화기가 이미지 대신 리다이렉트를 받고 400을 냈다. (`c6c55ea`, `src/proxy.ts`)
- **범위만 좁히고 동작은 유지** — matcher에서 정적 이미지 확장자를 제외했다. `_next/static`을 빼둔 것과 같은 근거로 정적 산출물은 어느 호스트에서 받아도 무해하다. 호스트 정규화 자체는 로그인 완주에 필요하므로 그대로 뒀다. standalone 빌드로 재현·검증(두 아이콘 400 → 200, 다른 호스트 `/org`는 그대로 308), 테스트 41개·lint 통과. (`c6c55ea`)

### 4. 홈페이지 V2 — 상담봇 연결 점검 도구

- **실제로 호출해 확인한다** — 서울 리전에서 생성·임베딩 모델을 각 1회 호출해 응답을 확인하고, 로컬 PostgreSQL의 `vector`·`pg_trgm`·`unaccent` 설치와 코사인 거리 계산을 읽기 전용으로 확인한다. `--db-only`/`--vertex-only`로 나눠 실행할 수 있다. (`9924417`, `scripts/chat-preflight.mjs`)
- **비밀은 출력하지 않는다** — 토큰·DB 비밀번호·임베딩 값은 찍지 않고, 실패하면 종료 코드 1을 반환해 자동화에 붙일 수 있게 했다. 점검 결과와 재실행 방법, 남은 확인 항목은 `docs/ai-chat-preflight.md`에 남겼다. (`9924417`)

### 5. 운영 판단 — SCC 경고 재확인 (커밋 없음, 이슈 #107)

- **재출현했지만 오탐이었다** — 콘솔에서 `lawwin-pg`에 "암호화되지 않은 직접 연결 허용" 경고가 다시 보여 실측했다. `sslMode: ENCRYPTED_ONLY`는 9/3 조치 그대로 살아 있고 `authorizedNetworks`도 비어 있어 공인 IP로 붙을 수 있는 클라이언트가 0개다. Cloud Run은 유닉스 소켓 경유라 이 경고와 무관하다. (이슈 `#107`)
- **왜 또 떴나** — 경고 패널의 '마지막 새로고침'이 2026-08-03으로 조치보다 앞선 캐시된 판정이고, 디텍터가 폐기 필드 `requireSsl`(여전히 false)을 볼 가능성이 있다. `sslMode`를 적용해도 `requireSsl`은 true가 되지 않으므로 그 필드만 보면 계속 오판한다. (이슈 `#107`)
- **음소거는 하지 않기로 선회** — 처음엔 음소거를 권고했으나, 리스크가 0인 항목을 숨기려다 다른 경고까지 가릴 여지를 만들 이유가 없다고 판단해 철회했다. 대신 실측 로그를 이슈에 남겨 다음에 같은 확인 비용이 들지 않게 했다. (이슈 `#107`)
- **원복 1건 남음** — 음소거를 CLI로 시도하며 `lawwin-homepage`에 `securitycenter.googleapis.com`을 켰고 직후 취소해 불필요하게 켜진 상태다(요금·동작 영향 없음, 위생 차원). 감사로그로 이번에 켠 것이 1개뿐임을 확인했다. 이 비활성화 명령은 자동승인 분류기가 막아 수동 실행이 필요하다. **'보안 수정' 버튼은 누르지 말 것** — `TRUSTED_CLIENT_CERTIFICATE_REQUIRED`로 유도되면 마이그레이션 스크립트 12개와 Prisma가 전부 깨지고 얻는 보안 이득은 없다. (이슈 `#107`)
