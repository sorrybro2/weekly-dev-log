📨 *1. 사건관리 : 수발신 문서 결재 흐름 재설계*

배경: 어제 AMP 인이메일 결재를 DKIM:DMARC 미설정으로 롤백한 뒤, 남은 것은 메일 안의 승인 반려 링크 방식이었다. 이것도 걷어내고 메일은 결재할 문서가 등록됐다는 알림, 실제 처리는 앱으로 역할을 갈랐다. 동시에 결재자를 사용자가 정할 수 없던 근본 문제(자동 매핑 결과가 실무와 다르면 막힘)를 풀었다.

 •  *결재자 참조를 등록 폼에서 직접 지정* — 사건을 고르면 결재자(주담당 변호사):참조(나머지 관계자)가 자동 매핑되지만 표시만 되고 고칠 수 없었다. 열람등사와 동일하게 편집 가능하게 바꾸고 document_logs.notify_emails JSONB를 신설했다(NULL은 자동 매핑 폴백으로 레거시 문서 보호, 빈 배열은 참조 없음). 자동 매핑은 사건과 담당자가 바뀔 때 한 번만 적용해 사용자 편집을 덮어쓰지 않게 하고, 미리보기가 도착하기 전 저장하면 빈 배열이 참조 없음으로 굳는 문제를 막기 위해 미반영 상태에서는 null을 보내 백엔드 폴백에 맡겼다. 함께 resolve_approval_recipients를 재작성해 자동 매핑 대상을 재직자로 한정. 퇴직한 주담당 변호사가 결재자로 잡히거나 참조에 퇴직자 메일이 들어가던 문제로, 등록 폼 드롭다운과 같은 기준을 적용했고 저장된 결재자가 그새 퇴직한 경우 재요청 시에도 다음 재직자로 내려간다. (c032891)
 •  *상세에서 결재자 지정 후 결재요청* — 결재자를 바꿀 방법이 앱 어디에도 없었다(등록 폼은 자동 매핑값만 저장, 상세는 읽기 전용, 수정 모드 편집 필드에도 없음). 결재 정보의 결재자를 셀렉트로 전환해(미요청 보류일 때만, 대기 완료는 읽기 전용) 결재요청 시 approver_key 오버라이드로 넘긴다. 또 결재 정보 섹션이 결재자와 참조가 모두 있을 때만 렌더되던 게이트를 제거. 등록이 결재자:참조를 저장하지 않게 바뀐 뒤로 새 문서에서는 섹션 자체가 사라져 결재요청 버튼조차 없었다. 메일 발송 실패를 성공 토스트로 표시하던 문제도 수정해, 상태는 대기로 바뀌고 인앱 알림은 갔지만 메일만 못 나간 상황을 구분해 알린다. (5001206)
 •  *결재 메일을 알림 전용으로* — 메일 본문의 승인 반려 코멘트 후 결재 3버튼을 제거하고 URL 자체를 싣지 않게 했다. _build_approval_email_body에서 approve_url reject_url comment_url 파라미터를 삭제하고 서명 토큰 발급도 걷어냈다. 제목은 결재요청에서 결재확인으로. 토큰 결재 페이지와 approval info submit 엔드포인트는 이미 발송된 메일이 깨지지 않도록 레거시로 남겼다. (54b5fc8)
 •  *등록 결재요청 안내메일을 API에서 분리* — 등록이 곧 결재 메일 발송이던 구조를 셋으로 나눴다. 등록은 send_approval 기본값을 True에서 False로 바꾸고, 결재자가 지정돼 있으면 메일 없이 인앱 알림 + 상태(대기) + Drive 배지만 적용(_apply_approval_state). 알림이 메일 발송 경로에만 묶여 있어 기본값을 끄는 순간 알림까지 함께 꺼지던 문제를 이 분기로 해소했다. 결재요청은 request-approval이 body로 approver_key notify_emails 오버라이드를 받는다. 안내메일은 send-email을 신설해 고른 문서를 한 통에 표로 묶어 보내고, 결재와 무관하므로 문서 상태:알림을 건드리지 않는다. 부수로 목록 응답에 case_number를 추가하고, _label_delegates로 Drive 라벨 위임 계정 후보를 산출해 호출 4곳에 연결했다. (25d164d)
 •  *다건 안내 메일 본문 + 수신자 override* — _build_document_list_email_body로 고른 문서 여러 건을 표로 나열하는 안내 메일 본문을 만들었다(결재 문구가 없는 중립 본문). effective_recipients는 APPROVAL_EMAIL_OVERRIDE가 설정되면 수신자를 그 주소 하나로 대체하는데, send_approval_email이 발송 직전 이걸 거치므로 모든 발송 경로가 자동으로 보호되고 API 응답도 실제 발송 수신자를 돌려줄 수 있다. (6456c09)
 •  *프론트 API 훅 확장* — ApprovalOverride로 결재요청 시 그 자리에서 정한 결재자:참조를 넘기도록 requestDocumentApproval 시그니처를 확장하고 useRequestApproval도 id와 override 형태로 바꿨다. sendDocumentEmail과 useSendDocumentEmail을 추가했고, 문서 상태가 바뀌지 않으므로 목록 쿼리를 무효화하지 않는다. (eb81a40)
 •  *등록 폼에서 결재 발송 UI 제거, 결재자 칸만 남김* — 등록이 메일을 보내지 않게 되면서 폼에 남은 발송 관련 UI가 채웠는데 왜 안 가지라는 오해를 만든다. 참조 입력:발송 토글:결재 메일 미리보기 pane을 제거하고 2단 레이아웃을 단일 컬럼으로 축소(마이너스 212줄). 결재자 칸은 남겨 사건을 고르면 자동으로 채워지고 저장 시 기록되며, 저장 시 결재자에게 앱 알림이 갑니다 확인 메일은 문서 상세에서 발송을 문구로 명시해 발송과 구분했다. 자동 매핑을 이펙트 대신 파생값으로 처리해 사용자 편집이 항상 우선한다. (de333b8)
 •  *목록 체크박스 선택 + 메일 발송 창* — 표 맨 앞에 체크박스 열과 페이지 전체선택 헤더를 추가하고 툴바에 선택 건수:해제와 메일 발송 버튼을 뒀다(선택이 있을 때만 노출). 체크박스 셀은 행 클릭과 겹치지 않게 전파를 차단하고, 선택은 필터가 바뀌어 목록에서 사라진 건을 제외해 유지한다. DocumentSendPopover는 화면 중앙 고정 카드에 좌 받는 사람 우 메일 미리보기 2단 구성이고, 받는 사람은 이름 검색:이메일 직접 입력으로 여러 명 추가할 수 있다. (89ab706)
 •  *등록 시 파일 첨부 필수* — 결재할 문서가 없으면 결재 자체가 성립하지 않으므로 Drive 선택 또는 PC 업로드 중 하나를 반드시 첨부하도록 막았다. FRONTEND_REQUIREMENTS 섹션도 실제 구현에 맞춰 갱신(기존 Drive 링크 URL 입력 서술은 이미 어긋나 있었다). 상세 드로어 수정과 결재 재요청은 파일 없는 레거시 문서 2114건(전체 16210건의 13퍼센트)이 잠기므로 제외. (1c5c2c5)
 •  *Drive 라벨 위임 계정 라우팅* — 결재상태 배지가 개인 내 드라이브 파일에 붙지 않던 문제. modifyLabels는 파일 쓰기 권한이 있는 계정으로 호출해야 하는데 GWS 관리자 하나로 고정돼 있었다. 정상 업로드 파일은 공유 드라이브에 있어 관리자가 organizer로 커버되지만, Drive Picker로 본인 개인 파일을 고른 경우 관리자에게는 파일이 보이지 않아 404 403으로 조용히 실패했다(best-effort라 예외를 먹고 로그만 남김). 위임 계정을 후보 목록으로 받아 관리자에서 기안자:요청자 순으로 시도하게 바꿨고 각 시도의 성공:실패 계정을 로그에 남긴다. (a50d313)
 •  *APPROVAL_EMAIL_OVERRIDE 설정 배선* — .env에는 있었지만 Settings에 정의되지 않아 값이 무시됐다. 그래서 로컬에서 결재:안내 메일을 보내면 실제 변호사에게 그대로 나갔다. 값이 있으면 수신자를 전부 그 주소로 대체하고 비워두면 원래 수신자에게 발송한다. (1446da6)

🗂 *2. 사건관리 : 표 목록 UX*

배경: 표가 페이지당 행 수를 상수로 고정하고 있어 큰 모니터에서는 표 아래가 통째로 비고 작은 화면에서는 스크롤이 생겼다. 사건목록의 종결 사건은 필터 팝오버의 체크박스로만 볼 수 있었고, 그 체크박스를 켜야만 보이는 보류 상태는 사실상 접근 경로가 없었다.

 •  *뷰포트 높이에 맞춘 자동 페이지 크기* — 공용 DataTable의 pageSize에 auto를 추가하고 계약 미수금 열람등사를 전환했다(PAGE_SIZE 상수 제거). 스크롤 컨테이너 높이에서 sticky 헤더 높이를 빼고 실제 렌더된 행 높이로 나눠 행 수를 정하며 ResizeObserver로 추적한다. 수발신문서의 기존 구현을 그대로 옮기지 않고 세 곳을 고쳤다. ①행 높이를 상수가 아니라 실측해 표마다 행 높이가 달라도 맞게, ②offsetHeight 대신 getBoundingClientRect로 소수까지 재서 행 높이가 41.5px일 때 오차가 쌓여 마지막 행이 잘리는 것을 방지, ③상한 50행을 둬 세로형 4K에서 100행을 넘겨 페이지네이션이 무의미해지는 것을 막고 여백 확보용 0.8 계수는 제거. pageSize가 줄어 현재 페이지가 범위를 벗어나면 상태를 되감지 않고 렌더 시점에만 보정해, 창을 다시 키우면 보던 페이지로 복귀한다. (0ce1505)
 •  *사건목록 진행상태 탭 분리에서 복수선택 전환* — 먼저 상단에 진행 보류 종결 세그먼트 탭(단일선택)으로 분리하고 필터 팝오버의 종결 사건 표시를 제거했다. 이후 필터 박스 안으로 옮기고 복수선택 체크박스로 바꿨다. 여러 개 고르면 OR 합집합으로 progress_status를 콤마 전달해 백엔드가 IN 절로 처리하고, 하나도 안 고르면 전체를 보여준다. 이슈는 종결 탭 추가만 요구했지만 3분할로 확장했다. 상태값이 3개인데 종결만 떼면 보류 35건이 앱 어디서도 접근 불가해지고, 기존에도 보류는 종결 사건 표시를 켜야만 보이는 값이었다. 검증은 진행 3193 더하기 보류 35는 진행보류 3228, 진행보류종결 9987은 전체와 동일. 부수 효과로 종결 6759건을 매번 내려받지 않게 됐다. 함께 변호사 탭 높이를 고정했다. 변호사 탭은 현재 목록에서 추출되므로 상태를 바꾸면 변호사 수가 달라져 탭 줄바꿈이 변하고 그만큼 아래 표가 위아래로 튀었다. 한 번 커진 높이를 유지하고 컨테이너 폭이 바뀔 때만 다시 측정한다. (1da5fbf, 80f5003)

🔄 *3. 사건관리 : 실행취소 1단계 (이슈 77)*

배경: 사건 연결사건 일정을 잘못 고치거나 지웠을 때 되돌릴 수단이 없었다. 이슈는 구현 지시가 아니라 범위:UX를 결정해달라는 설계 이슈였고, 그 결정까지 함께 진행했다. 전제로 SQL 레벨 되돌리기는 불가능하다. 백엔드가 요청당 트랜잭션을 바로 커밋하므로 ROLLBACK 대상이 없다. 그래서 역동작을 클로저로 쌓아 실행하는 애플리케이션 레벨 undo로 갔다.

 •  *undo 스택 + 헤더 버튼 Ctrl Z* — stores undoStore에 스택(최근 3건) push undo를 두고, 역동작이 실패하면 이력에 되돌려 재시도할 수 있게 했다. running 플래그로 버튼 연타:단축키 중복 실행을 차단한다. 단축키는 input textarea select contenteditable 안에서는 무시해 브라우저 기본 텍스트 되돌리기를 빼앗지 않는다. (1a925f6)
 •  *연결사건 일정 목록 인라인수정 배선* — 되돌리기는 전용 역-API를 만들지 않고 정식 엔드포인트를 역호출한다. 그래야 서버가 처리하는 사이드이펙트가 일관되게 따라온다. 일정 삭제 API는 구글 캘린더 이벤트도 지우고 생성 API는 새 이벤트를 만들기 때문에, 외부 API 역호출을 직접 구현하지 않고도 캘린더 정합성이 유지된다(이슈가 난이도 높음으로 제외했던 항목이 불필요해진 셈). 이전 값은 onMutate에서 해당 쿼리 캐시에서 떠두는 방식이라 연결사건:일정은 호출부를 하나도 고치지 않았다. (dc5da64)
 •  *범위 UX 확정 수정 삭제만, 되돌릴 내용 표시* — 아이콘만 있는 헤더 버튼은 무엇이 되돌아가는지 모르고 누르게 되는 문제가 있었다. 범위를 수정:삭제로 좁히고 추가 계열은 제외했다(잘못 넣었으면 지우면 되고, 보관이 3건이라 사소한 항목이 정작 되돌려야 할 삭제를 밀어냄). 사건 삭제를 추가했는데 삭제 직후 목록으로 이동하므로 route를 cases로 지정해야 도착 화면에서 버튼이 보인다. 기일 court_hearings는 추가:삭제 API 자체가 없어 대상 불가임을 확인했다(크롤링 데이터, get patch만 존재). UI는 헤더 아이콘에서 드롭다운으로 바꿔 수정은 되돌아갈 값, 삭제는 되살아날 내용을 펼쳐 보여주고 항목별 버튼으로 처리한다. 표시 방향은 바꾼 내역이 아니라 되돌리면 일어날 일 기준이다. 알림 벨과 달리 강조색:빨간 뱃지를 쓰지 않고 되돌릴 게 없으면 버튼 자체를 렌더하지 않는다. 안전장치로 ①기록 당시 경로만 노출(다른 화면 항목을 되돌리면 결과를 눈으로 확인할 수 없는 채로 DB가 바뀌고, 사건 A에서 사건 B 것을 되돌리는 사고도 막힘), ②targetKey로 이후에 같은 대상이 또 변경된 항목을 잠금(그대로 되돌리면 나중 변경이 조용히 덮여 값이 엉킴)을 넣었다. (ff01498)

✅ *〔금일 종합〕*

어제 AMP 인이메일 결재를 롤백하며 메일에서 결재한다는 방향에 제동이 걸렸고, 오늘은 그 방향을 정리해 결재의 무게중심을 앱으로 옮긴 날이었다. 메일에서 링크:버튼을 전부 걷어내 알림 역할만 남기고, 대신 그동안 자동 매핑에 맡겨져 있던 결재자를 사용자가 등록 폼과 상세 양쪽에서 직접 정할 수 있게 만들었다. 여기서 등록 결재요청 메일발송이 한 덩어리였던 구조가 걸림돌로 드러나 셋으로 분리했고, 그 과정에서 자동 매핑이 퇴직자를 결재자로 잡던 문제와 개인 드라이브 파일에 결재상태 배지가 조용히 실패하던 문제도 함께 잡혔다. 오후에는 표 페이지당 행 수를 뷰포트에 맞추고 사건목록 진행상태를 복수선택으로 바꿨으며, 실행취소 기능은 이슈가 요구한 범위:UX 결정부터 확정해 1단계를 붙였다. 되돌리기가 정말 필요한 지점(내용을 기억해야 복구되는 삭제, 여러 필드를 한 번에 덮는 수정)에 한정하고, 되돌리면 무엇이 어떻게 바뀌는지를 누르기 전에 보여주는 형태로 정리했다. 금일 1개 repo에 걸쳐 커밋 17건.
