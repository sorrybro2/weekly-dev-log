### 3. 사건관리 — 사건목록 기본 정렬 재정의 (이슈 #134)

> 배경: 기존 기본 정렬은 사건유형 1순위만 잡혀 있어 목록을 통으로 훑어도 배치 규칙이 읽히지 않았다. "사건유형 → 접수기관 → 등록일"로 3단을 정의하는 과정에서, 그 규칙을 **깨뜨리고 있던 두 층**(보류 별도 섹션, 그룹 순서)이 드러나 함께 정리했다.

- **기본 정렬 3단 적용** — `sortByCaseType`(1순위만) → `sortByDefaultOrder`(3단 복합)로 교체. 기관 구분은 문자열 매칭 대신 **`cases.stage` ENUM을 그대로** 썼다 — 법원/검찰/경찰/예정/기타 값이 이슈 요구 구분과 일치하고 목록 셀도 이미 `stage`로 법원사건을 판정하고 있었다('예정'은 미접수 자리, 기타·미지정은 맨 뒤). 3순위 등록일은 **최신순** — 목록 조회가 이미 `id` 내림차순으로 페이지를 떠오므로 같은 방향이라 사용자가 보던 순서가 뒤집히지 않는다. 모바일 목록도 동일 적용. (frontend `CaseListTable.tsx`·`CaseListMobile.tsx`) (`d7d1963`, 명세 `b267378`)
- **보류 별도 섹션 폐지** — 보류 사건을 구분선 아래 별도 섹션으로 내리던 처리가 **"사건유형 → 기관 → 등록일" 배치를 보류/비보류로 두 번 반복**하게 만들어 방금 정의한 규칙을 깨고 있었다. 변호사 그룹당 한 번만 정렬·렌더하도록 이중 렌더를 제거하고 `HoldSectionRow`를 삭제했다(보류 여부는 새로 붙인 진행상황 칩으로 확인). 렌더가 하나로 합쳐지면서 **보류 행만 `onCaseSelect`를 무시하고 항상 라우팅해 사이드패널 모드에서 동작이 달랐던 문제**도 같이 해소됐다. (`1a934be`, 명세 `b3622ac`)
- **그룹 사이에도 정렬 적용** — 정렬이 그룹 "안"에서만 걸려서 위의 두 층(변호사 그룹 순서 = 서버 응답 등장 순, 당사자 병합 그룹 순서 = 최소 `case_type` → 당사자명 가나다)이 규칙을 덮고 있었다. 두 층 모두 **그룹 대표 행(그룹을 기본 정렬했을 때 맨 앞 행)의 정렬 키**로 비교하도록 바꾸고, 동률일 때만 이름 가나다로 tie-break, 담당 없음 그룹은 뒤로 보냈다. `extractLawyerGroups`를 모바일이 공유하므로 표·모바일이 함께 맞는다. (`3f5eee6`, 명세 `82e45c3`)
- **등록일 컬럼 + 새 컬럼 삽입 위치 수정** — 정렬 3순위가 `created_at`인데 목록에 없어 눈으로 검증할 수 없었다. 종결일과 같은 형식으로 진행상황 다음·비고 앞에 노출. 이때 **컬럼 순서를 localStorage에 저장한 사용자는 나중에 추가된 컬럼이 항상 맨 뒤에 붙어** 코드가 정한 위치가 보이지 않는 문제가 드러나, 정의 순서상 앞 컬럼 뒤에 **제자리 삽입**하도록 공용 훅을 고쳤다. (frontend `CaseListTable.tsx`, `hooks/useColumnResize.ts`) (`4e88a2e`, `d786ba8`)
- **접수기관 필터** — 필터 패널에 `stage` 기준 복수선택 체크박스(법원·검찰·경찰·기타·예정)를 추가했다. 기본값은 5종 전부 체크라 설정을 건드리지 않은 사용자에겐 기존과 동일하고, 전부 해제는 바로 위 진행상태 필터와 같은 규칙으로 '전체 표시'로 처리한다. 기존 `case-list-filter-state` 키에 `stages`로 함께 저장하되 **키가 없던 설정은 전체 체크로 마이그레이션**해 기존 사용자 목록이 갑자기 줄지 않게 했고, ENUM 5종을 벗어난 값은 '기타'로 묶어 조용히 사라지지 않게 방어했다. ### 8. 사건관리 — 결재 참조자 신설 (이슈 #136)

> 배경: 결재자(`approver_key`)는 승인/보류를 누르는 **한 사람**이지만, 실무에서는 그 결재를 **같이 알고 있어야 하는 사람들**이 있다. 이들에게 결재 버튼을 주면 안 되고(권한), 메일 Cc(`notify_emails`)로 대신할 수도 없다(앱에서 봐야 한다). 열람 전용 참조자를 별도 개념으로 세웠다.

- **컬럼·마이그레이션** — `document_logs.cc_approver_keys` JSONB(마이그레이션 019). 별도 테이블 대신 JSONB를 택한 이유는 기존 `notify_emails`와 같은 방식이고, **"내가 참조자인 문서" 조회(`@>` 연산자)가 GIN 인덱스를 타게** 인덱스를 함께 만들면 되기 때문. **참조자용 상태는 두지 않는다** — `approval_status` 하나를 그대로 미러링해 대기/완료/보류를 표시한다(별도 상태를 두면 동기화가 어긋난다). (backend `document_logs_model.py`, `migrations/019_document_logs_cc_approvers.sql`) (`485706a`)
- **백엔드 조회·알림·자동 매핑** — `GET /document-logs?cc_approver_key=`로 내가 참조자인 문서를 조회하고, 결재요청 발송 시 참조자를 저장한다(**결재자와 중복되면 제외** — 안 그러면 수신함에 같은 문서가 두 번 뜬다). 참조자 알림은 타입을 **`document_approval_cc`로 갈랐다** — 기존 타입은 결재 대기 탭으로 보내는데 참조자에겐 그 문서가 없어 빈 화면이 된다. 결재가 완료/보류로 처리되면 **참조자 알림도 읽음으로 내린다**(엔드포인트 2곳) — 참조자는 할 일이 없어 뱃지가 안 지워지면 영구 미읽음이 되기 때문. 여기에 **자동 매핑**을 붙였다: 결재자·기안자를 뺀 사건 관계자(주담당·배당변호사·담당직원·수발신담당자)에 **사건 지사의 고정 수신자 중 재직 직원**을 더해 채우고(지사 공용 메일함처럼 직원이 아닌 주소는 메일 참조로만), 사용자가 손대지 않았으면(`null`) 요청 시점에 자동으로 채우되 `[]`(참조 없음)은 사용자의 선택이라 덮어쓰지 않는다. 지사 설정 읽기를 api → crud로 옮겨 **메일 발송과 결재 참조자가 같은 설정을 보게** 했다. 목록 응답의 직원 이름 배치 조회를 담당자·결재자·기안자·참조자로 확장하면서 **결재 수신함의 결재자/기안자 칸이 계속 비어 있던 것**도 함께 해소됐다. (backend `document_logs_api.py`·`document_logs_crud.py`·`document_logs_schema.py`) (`f61fd4e`, 타입 `939db87`)
- **참조함 탭 + 지정 UI** — 결재 관리에 「참조함」 탭을 신설하고 기안함처럼 **대기/완료/보류 3종을 한 탭에** 담았다. 결재자 탭처럼 대기/완료로 가르지 않은 이유는 두 가지 — 참조자는 결재 액션이 없어 "내가 처리한 것"이라는 구분이 성립하지 않고, **참조자가 정작 알고 싶은 건 결과인데 완료되는 순간 목록에서 사라지면 그걸 못 본다**. 결재자가 승인·반려하면 상태 뱃지만 바뀌고 문서는 참조함에 남는다. 참조자 지정은 `EmployeeMultiSelect`(신규 — `RecipientSearchInput`과 달리 이메일이 아니라 `employee_key`를 담는다)로 결재요청 발송 창·상세 드로어·등록 모달에서 하고, **자동 매핑값이 채워진 상태로 열려** 빼거나 더할 수 있다(결재자로 잡힌 사람은 목록에서 제외). 상세 드로어에는 참조자(열람) 칸을 위의 참조(Cc, 메일)와 **갈라서** 뒀고, 알림 라우팅은 `document_approval_cc`를 대기 탭이 아니라 참조함으로 보낸다. (frontend `ApprovalInboxPage.tsx`·`pickers.tsx`·`DocumentApprovalPopover.tsx`·`DocumentLogDetailDrawer.tsx`·`NotificationCenter.tsx`) (`4d0ccad`)

### 9. 사건관리 — 안내 메일 재구성 (이슈 #135)

> 배경: 받는 사람이 메일만 보고 **어느 의뢰인·당사자 사건인지 알 수 없다**는 피드백. 기존 본문은 "문서 N건을 안내드립니다" + 7컬럼 표였는데, 실무에서 실제로 쓰는 메일은 제목에 당사자명이 있고 본문 첫 줄에 사건이 정리된 뒤 하고 싶은 말이 오는 형태였다.

- **제목·사건 정리 자동 매핑 + 내용 입력란** — 제목은 `[분류태그] 당사자명 자료`(수신→자료수령 / 발신→자료송부 / 섞이면 자료수발신, 당사자 여럿이면 "박재경 외 2명"), 본문 첫 줄은 `당사자명(법원명 사건번호 사건명)`을 **문서에서 자동 조립**하고, 표 나열을 없앤 자리에 **사용자가 쓰는 내용 입력란**을 뒀다(비우면 고른 문서명을 번호 목록으로 대체해 메일이 텅 비지 않게). 조립 규칙은 백엔드 `gmail.py`의 `build_document_email_subject`·`build_document_case_lines`로 분리하고 프론트는 **같은 규칙을 `mailFormat.ts`로 복제**해 미리보기가 실제 발송 본문과 어긋나지 않게 했다(한쪽을 바꾸면 다른 쪽도 맞춰야 한다는 주의를 양쪽 주석에 남겼다). 사용자 입력은 HTML 이스케이프 후 줄바꿈만 살린다. **금일 종합:** 오전은 **사건목록을 실무 표로 만드는 작업**이었다. 컬럼을 다섯 개 늘리고(담당직원·종결일·진행상황·등록일) 셀 표기를 정리한 뒤, 기본 정렬을 사건유형 → 접수기관 → 등록일로 재정의했다. 이 과정이 흥미로웠던 건 **정렬 규칙을 정하자 그 규칙을 덮고 있던 층들이 차례로 드러났다**는 점이다 — 보류 별도 섹션이 배치를 두 번 반복시키고 있었고, 변호사·당사자 그룹의 순서가 위에서 규칙을 가리고 있었다. 둘을 걷어내면서 사이드패널 동작 불일치와 새 컬럼이 항상 맨 뒤에 붙던 저장 순서 버그까지 함께 정리됐다. 오후는 **조직 개념을 앱에 반영**했다. 대전/청주가 하나의 사무소처럼 움직이는데 필터만 두 칸이던 것을, 새 개념을 만들지 않고 **이미 있는 「지사 그룹 관리」 설정을 읽는 공용 훅**으로 6개 화면에 일괄 적용했다 — 설정이 한 곳에 남고, 부수적으로 권한 없는 사용자에게 탭 라벨이 내부 키로 노출되던 문제도 사라졌다. 저녁은 **수발신 문서의 사람 배선**이었다. 지사별 고정 수신자를 서버가 강제로 붙이고 지사별로 분할 발송하게 만든 뒤, 결재에 **열람 전용 참조자**를 세우고(JSONB + GIN, 알림 타입 분리, 참조함 탭) 사건 관계자와 지사 담당자를 자동 매핑해 **"누가 받아야 하는지 사람이 매번 고르지 않아도 되는"** 상태로 만들었다. 마지막으로 안내 메일 본문을 표 나열에서 실무 포맷(제목·사건 정리 자동 + 내용 직접 작성)으로 바꿨는데, 이때 의뢰인이 당사자와 갈리는 사건에서 의뢰인이 드러나지 않는다는 사실이 나와 별도 조회를 신설했다. 금일 1개 repo에 걸쳐 커밋 39건.
