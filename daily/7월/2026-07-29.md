# 일일 업무 보고 (2026. 07. 29)

> **어제 앱으로 옮긴 결재를 "결재자가 실제로 처리할 수 있는 화면"까지 이어붙이고, 수발신 문서의 파일 취급을 대장 수준으로 끌어올린 날.** 어제 결재 요청이 인앱 알림만 남게 되면서 **알림을 지나치면 처리할 건을 찾아갈 데가 없다**는 구멍이 드러났다 — 기안함·결재 대기·결재 완료 3탭의 **결재 관리 화면**을 만들고 대시보드 위젯·알림 토스트까지 같은 동선으로 묶었다. 파일 쪽은 ①**첨부 다중화**(문서 1건 = 파일 N개, 마이그레이션 017), ②**Drive에서 고른 파일을 사건 폴더로 복사**해 "대장에는 있는데 사건 폴더엔 없는" 상태 제거, ③**폴더 링크 저장**(018)으로 상세 진입 시 Drive 되짚기 제거, ④**Picker dispose 누락**으로 팝업을 닫아도 화면이 어둡게 남던 버그 수정. 그 밖에 **사건검색 결과를 기초사실 트리뷰로**, **사건목록 진행/종결 탭 분리**, **열람등사 목록 컬럼 보강**, **공용 표의 컬럼 리사이즈 버그**까지 — 금일 커밋 12건(1개 repo)

## 📝 상세 업무 내역

### 1. 사건관리 — 수발신 문서 첨부·파일 배치

> 배경: 지금까지 수발신 문서는 파일을 **한 개만** 걸 수 있었고, Drive에서 고른 파일은 **링크만** 대장에 남아 정작 사건 폴더에 가보면 그 문서가 없었다. 대장(臺帳)이라면 "문서가 어디 있는지"까지 책임져야 한다는 판단으로 세 가지를 한 번에 정리했다.

- **첨부 다중화 + 사건 폴더 편입 + 폴더 링크 저장** — 문서 1건에 파일 N개를 담도록 `document_log_files` 테이블로 분리하고(마이그레이션 017, 기존 `drive_url` 14,176건 백필), `document_logs.drive_url`은 **첫 번째 파일 링크로 계속 유지**해 목록 표시·Drive 결재 배지·메일 등 단일 링크를 전제하던 기존 경로를 건드리지 않았다. `attach-file`은 교체가 아니라 **추가**로 동작하도록 바꿔 PC 다중 업로드를 받는다. Drive에서 고른 파일은 저장 시 `사건폴더/수발신문서/{수신|발신}`으로 **복사**하고 대장이 사본을 가리키게 했다 — 부모 폴더를 먼저 확인해 **이미 그 폴더에 있으면 복사하지 않고**(중복 방지), 원본은 제자리에 둔다. 실패해도 등록 자체는 유지되는 best-effort 경로다. 여기에 상세 화면이 부모 폴더를 매번 Drive API로 되짚던 비용을 없애기 위해 **복사·업로드 시점에 폴더 링크를 함께 저장**(마이그레이션 018)하고, 값이 없는 옛 문서만 브라우저 조회로 폴백하게 했다. (backend `document_logs_api.py`·`document_logs_crud.py`·`document_logs_model.py`·`google_drive.py`, `migrations/017_document_log_files.sql`·`018_document_log_files_folder_url.sql`, frontend `api/documentLogs.ts`) (`771d833`)
- **Picker 잔여 오버레이 정리 + 파일 선택 방식 되돌림** — 파일 선택을 사건 폴더 브라우저로 바꿨던 것을 **「구글 드라이브에서 선택」(Picker)으로 되돌렸다**(첨부 다중화는 유지 — Picker는 한 번에 1개라 고른 파일을 목록에 계속 더한다). 되돌리는 김에 **팝업을 닫아도 화면이 어둡게 남고 클릭이 막히던 버그**를 잡았다 — 원인은 Picker를 만들고 `dispose()`를 한 번도 부르지 않아 body에 붙은 `.picker-dialog-bg`가 그대로 남는 것이었고, 선택·취소 시 `setVisible(false)` + `dispose()` 후 잔여 노드를 직접 제거하도록 했다(계약서용·폴더 선택용 Picker도 같은 버그를 공유해 함께 수정). 폴더 링크 조회가 호출마다 **서버→Google refresh_token 교환**을 유발해 체감 지연이 크던 것도 **access token 45분 캐싱 + 동시 호출 병합**으로 줄였다. 상세는 첨부를 **파일/폴더로 갈라** 표시한다 — 옛 데이터 14,165건이 파일이 아니라 사건 폴더 URL이라 "파일 열기"가 폴더를 열던 상태였다. (frontend `DocumentLogDetailDrawer.tsx`, `lib/googlePicker.ts`) (`f1df842`)

### 2. 사건관리 — 등록 시 발송 옵션·목록 버튼 분리

- **저장과 동시에 메일 발송·결재 요청** — 추가 직후 발송하려면 모달을 닫고 목록에서 그 문서를 다시 찾아 체크해야 했다. 등록 모달에 **체크박스 2개**(메일 발송 / 결재 요청, 둘 다 가능)를 두고, 메일을 켜면 모달이 2단으로 넓어지며 **우측에 실제 나갈 메일 미리보기**가 뜬다. 수신자는 사건 관계자로 자동 매핑하되 **사용자가 지운 주소는 되살리지 않는다**. 결재자 칸은 결재 요청 체크박스 아래로 옮겨 켰을 때만 변경 가능하게 했다. 목록에서는 메일 발송·결재 요청 버튼을 **항상 노출**하고(체크 없이 누르면 안내만), 문서별로 결재자가 다르므로 **결재 요청 창은 행마다 결재자를 수정**할 수 있게 만들어 한 건씩 발송 후 성공·실패를 나눠 보고한다. 체크 시 행 스냅샷을 함께 담아 년월·필터를 바꿔도 선택이 유지된다. 메일 미리보기는 `DocumentMailPreview`로 공용화해 발송 팝오버의 중복 마크업을 없애고 백엔드 본문 생성기를 한 곳에서만 따라가게 했다. (frontend `DocumentLogAddModal.tsx`·`DocumentLogListPage.tsx`·`DocumentApprovalPopover.tsx`·`DocumentMailPreview.tsx`·`DocumentSendPopover.tsx`) (`212ca8f`)

### 3. 사건관리 — 결재 관리 화면 (이슈 #106)

> 배경: 어제 결재를 "메일 링크"에서 "앱"으로 옮기면서 결재 요청이 **인앱 알림만** 남게 됐다. 그 결과 결재자는 알림을 지나치면 처리할 건을 찾아갈 데가 없고, 기안자도 자기가 올린 건이 어떻게 됐는지 볼 곳이 없었다. 알림은 흘러가는 신호일 뿐 목록이 아니라는 게 드러난 셈이다.

- **결재 관리 화면 신설** — `/document-logs/approvals`에 탭 3개(각 건수 표시). **결재 대기**(`approver_key=나` + 대기)는 목록에서 바로 승인할 수 있고 **반려는 사유를 남겨야 하므로 상세 드로어로 유도**한다. **결재 완료**(완료/보류), **기안함**(`created_by=나`, 전체 상태 — 결재자를 함께 표시). 조회는 **기존 `GET /document-logs`의 `approver_key`·`created_by`·`approval_status` 필터를 그대로 조합**해 백엔드는 손대지 않았고, 행 클릭 시 기존 상세 드로어를 재사용한다. `?tab=`으로 특정 탭을 열 수 있고 탭 전환 시 주소도 같이 바뀌어 새로고침·뒤로가기에도 유지된다. 사이드바는 「수발신 문서」 아래 **한 단계 들여써서** 하위 화면임을 드러냈고, 하위 경로가 생기며 상위 메뉴가 같이 활성화되던 문제도 `end` 매칭으로 고쳤다. (frontend `ApprovalInboxPage.tsx`, `Sidebar.tsx`, `routes/index.tsx`) (`7f9eb8a`)
- **대시보드 결재 위젯을 같은 분류로** — 승인/요청 2탭을 **대기·완료·기안 3탭**으로 바꿔 결재 관리 화면과 어휘를 맞췄다. 바로가기 버튼은 **보고 있던 탭 그대로** `/document-logs/approvals?tab=…`으로 넘어간다. 목록은 이미 받아둔 두 쿼리(내가 올린 / 나에게 온)를 상태로 나눠 써서 **추가 요청이 없다**. (frontend `ApprovalWidget.tsx`) (`143d69a`)
- **결재 알림 클릭 동선** — 지금까지는 보던 화면 위에 상세 드로어만 떠서, 처리하고 닫으면 남은 결재가 보이지 않았다. 결재 알림(`document_approval`)이면 **결재 관리(결재 대기 탭)로 이동한 뒤** 그 위에 상세를 띄우도록 바꿔, 닫으면 남은 대기 목록이 이어진다. 토스트의 「결재하기」와 벨 드롭다운 항목 모두 같은 동선이고 다른 알림은 종전대로다. (frontend `NotificationCenter.tsx`) (`7fdaea7`)

### 4. 사건관리 — 사건검색 트리뷰 (이슈 #117)

- **사건 목록 응답에 기초사실 정보 추가** — 수발신 문서등록의 사건검색 결과를 기초사실별로 묶으려면 사건이 속한 기초사실의 이름과 폴더가 필요한데, `CaseListItem`에는 `matter_id`만 있고 매터 정보가 없었다. `LEFT JOIN matters`로 `matter_title`·`matter_drive_folder_url`을 쿼리·스키마·TS 타입에 실었다. (backend `cases_api.py`·`cases_crud.py`·`cases_schema.py`, frontend `api/cases.ts`·`features/cases/types.ts`) (`2c8ec4d`)
- **검색 결과를 기초사실 트리뷰로** — 평평한 목록이라 같은 의뢰인 아래 사건이 여러 건이면 **어느 기초사실 소속인지 구분되지 않았다**. Drive 폴더 계층을 그대로 렌더해 위치를 구조로 보여준다 — 기초사실은 선택 불가한 그룹 헤더(폴더 아이콘 + 사무소 배지 + Drive 폴더 열기), 사건은 들여쓰기 + 왼쪽 세로선으로 소속을 표시하는 선택 대상. 떨어져 나온 같은 기초사실은 한 그룹으로 합쳐 헤더 중복을 막고(첫 등장 순 유지), 키보드 ↑↓는 헤더를 건너뛰고 사건만 순회한다. (frontend `features/document-logs/components/pickers.tsx`) (`17cba6f`)

### 5. 사건관리 — 사건목록 진행/종결 분리 (이슈 #90)

- **진행/종결 탭 분리** — 진행상태 필터에서 '종결'을 빼고 **엑셀 시트 탭처럼 목록 자체를 갈랐다**. 진행 중 탭은 진행·보류만 다루고 종결 사건은 「종결」 탭에서 본다(종결 탭에서는 상태가 고정이라 필터 패널의 진행상태 섹션을 감춘다). 탭 분리 전에 저장된 필터에 '종결'이 남아 있으면 정규화 과정에서 떨어내고, 남는 값이 없으면 '진행'으로 되돌린다. (frontend `CaseListPage.tsx`) (`f3fd6ea`)
- **종결 탭 시각 구분** — 종결 목록을 보고 있다는 걸 배경으로 읽히게 했다. 활성 종결 탭에 옅은 회색을 깔되 **글자·굵기는 진행 중 탭과 같게** 둬서 비활성 탭으로 오인되지 않게 하고, 행 배경은 `bg-slate-100`(다크 `slate-800/40`). 처음엔 `bg-muted/40`을 썼는데 이 테마의 `--muted`가 `oklch(0.97)`이라 **흰 배경과 3% 차이밖에 안 나 사실상 보이지 않아** 값을 올렸다. 선택 행(파랑)·기일 충돌 행(분홍)이 회색보다 우선이라 종결 탭에서도 묻히지 않는다. (frontend `CaseListPage.tsx`·`CaseListTable.tsx`) (`f7314f6`)

### 6. 사건관리 — 열람/등사 목록 + 공용 표 (이슈 #108, #107)

- **의뢰인·신청서류 컬럼 추가 + 발송 이력 hover** — 목록에 항상 보여야 할 네 값(의뢰인·사건명·신청서류·관할) 중 **빠져 있던 두 개**를 추가하고 목록 응답에 `email_client_name`·`request_documents`를 실었다. 발송 이력은 행을 펼쳐 표 아래에 두 줄을 여는 방식이 자리를 너무 차지해, **이력이 있는 행에만** 재알림 예정일 셀에 종 아이콘+건수를 붙이고 hover 시 도과알림·재알림 시각만 보여주도록 바꿨다(`portal + fixed`라 표 스크롤에 잘리지 않고 `pointer-events-none`이라 행 클릭을 막지 않는다). (backend `record_request_schema.py`, frontend `RecordRequestListPage.tsx`·`SendHistoryTip.tsx`·`features/cases/types.ts`) (`a2eb3ce`)
- **공용 표 컬럼 리사이즈 버그** — 한 컬럼을 줄이면 **옆 컬럼까지 같이 움직이는** 문제. `table-layout:fixed`에 `min-w-full`이 함께 걸려 있어 컬럼 폭 합이 화면보다 좁아지면 남는 폭이 모든 컬럼에 비례 배분된 것이 원인이었다(리사이즈 자체는 해당 컬럼만 바꾸고 있었다). 표 끝에 **폭을 지정하지 않은 여백 칼럼**을 두어 남는 공간을 그 칸이 흡수하게 하고, 로딩·빈 목록·펼침 행의 `colSpan`도 +1 했다. 공용 컴포넌트라 이를 쓰는 다른 목록도 함께 고쳐진다. (frontend `components/common/data-table/DataTable.tsx`) (`2ebe040`)
