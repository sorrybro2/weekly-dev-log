## ⏱️ 10초 핵심 요약

**[사건관리 — 감사 로그 신설]**
- **왜 앱이 직접 남기나**: Cloud Run 로그에는 **사용자와 요청 본문이 안 남고** 보관도 30일. "누가 무엇을 바꿨나"를 답할 수 없어 DB에 직접 적재(#171, 저장소 비교는 #173)
- **누락 없는 적재**: `before_flush`에서 변경 내역 수집(flush 후엔 history가 비어 있음) → `after_flush`에서 PK 확인 후 **같은 트랜잭션에** 기록. 유령 기록·누락 둘 다 방지
- **사람 행위만**: 컨텍스트 없는 크롤러·스케줄러 변경은 제외 — 기일 일일 갱신이 월 5천여 건이라 넣으면 사람 행위가 묻힌다
- **조회 화면**: 기간·행위자·대상·동작·지사 필터, 행 펼치면 **필드별 이전값 → 이후값 diff**, 행위자 지사 ≠ 대상 지사면 「타 지사」 경고 배지

**[사건관리 — 시스템 설정 UX]**
- **공용 네비 셸**: 계약 매핑·목표/달성율로 가면 좌측 메뉴가 통째로 사라져 **돌아갈 길이 없던** 것을 중첩 라우트로 묶음. 하위 화면에서 섹션을 눌러도 설정 본문으로 돌아가 해당 위치로 스크롤
- **설정 행 아코디언**: 지사마다 입력창이 항상 펼쳐져 세로로 늘어지던 것을 요약 한 줄 + 클릭 시 펼침으로. **저장 안 하고 접으면 저장된 값으로 되돌아간다**
- **고정 수신 이메일 개별 관리**: 쉼표 한 줄 입력이라 **실수로 전체를 지우면 복구 불가**였던 것을 주소별 행 + 개별 삭제로. 추가 시점에 형식·중복 검사
- **저장/삭제 피드백**: 저장 버튼이 저장 중 → 저장됨으로 바뀌고, 계약 설정 삭제에는 확인 다이얼로그와 결과 토스트를 붙임(기존엔 확인도 알림도 없었음)

**[사건관리 — CRM 연결]**
- **CRM 딥링크 교체**(#126): 'CRM으로 이동'이 `/cases?keyword=`로 **제자리 새로고침**만 하던 죽은 기능 → 사건상세와 동일한 `{CRM_URL}#/parties/{key}` 새 탭. 목록·상세가 **다른 의뢰인으로 갈 수 있던 문제**까지 키 해석 통일로 해소
- **타임라인 CRM 상담**(#127): `crm.*`가 이미 FDW로 마운트돼 있어 **미러 테이블 없이** 상담 일정 + 접촉 원장을 새 소스로 추가. FDW는 조인이 원격에 푸시다운되지 않아 배치 해소 방식으로 우회
- **중복 제거 결함 수정**: 실데이터로 검증하다 같은 날 방문상담이 예약돼 있으면 **그날 전화상담이 통째로 사라지는** 것을 발견 → 판정 키를 (날짜) → (날짜, 유형)으로

**[사건관리 — 기일·열람등사]**
- **기일 충돌 해소**(#130): 표시만 하고 끝이던 충돌을 **출석비고를 채우면(참석자 지정 또는 불출석) 해제**되게. 신규 컬럼 없이 기존 `attendee_keys`를 해소 신호로 재사용
- **참석자 ↔ 불출석 배타**: 둘이 독립이라 `['EMP0001','불출석']` 같은 모순 값이 저장될 수 있던 것을 서로 배타로
- **완료 = 등사일자 기준**: 등사일자 없는 완료 건이 생길 수 있던 것을 정리 — 완료 선택 시 등사일자 입력 팝업, 진행중 건에 날짜 넣으면 자동 완료, 날짜 없으면 저장 차단

**[운영 — 배포 사고]**
- **프로덕션 API 9분 중단**(#156): 배포 명령의 소스 경로가 잘못돼 **백엔드 없는 프론트 전용 이미지**가 올라감. 모든 요청이 SPA로 폴백돼 로그인·API 전멸. 루트 경로로 재배포해 복구, 경위와 주의사항을 기록용 이슈로 남김

## 📝 상세 업무 내역

### 1. 사건관리 — 사용자 활동 감사 로그 (이슈 #171, #173)

> 배경: 사건·계약·미수금 데이터가 바뀌었을 때 **누가 언제 어디서 무엇을 어떻게 바꿨는지** 확인할 방법이 없었다. GCP(Cloud Run) 로그에는 요청 URL과 상태코드만 남고 **사용자와 요청 본문은 남지 않으며** 기본 보관도 30일이다. 저장소를 Postgres 테이블로 갈지 BigQuery로 갈지 비교한 뒤(#173) 앱이 직접 DB에 남기는 쪽으로 결정했다.

- **적재 파이프라인** — `audit_logs` 테이블 + 인덱스 5개(마이그레이션 020). 요청 컨텍스트(행위자·IP·엔드포인트·trace_id)를 **ContextVar로 심는 미들웨어**를 두고, IP는 `X-Forwarded-For`의 **첫 값**을 취한다(그대로 쓰면 Cloud Run 내부 프록시 IP가 찍힌다). 핵심은 SQLAlchemy 세션 훅을 **두 단계로 나눈 것** — `before_flush`에서 변경 내역을 수집하고(flush 이후에는 attribute history가 비어 무엇이 바뀌었는지 알 수 없다), `after_flush`에서 PK를 확인한 뒤 **같은 트랜잭션에** 적재한다. 이렇게 해야 롤백된 변경이 로그로 남는 유령 기록도, 신규 레코드의 PK 누락도 생기지 않는다. 대상은 6개 테이블(cases/contracts/receivables/record_requests/document_logs/system_settings)이고 update는 **바뀐 필드만**, insert·delete는 스냅샷을 남긴다. (backend `core/audit.py`·`main.py`·`models/audit_log_model.py`·`migrations/020_audit_logs.sql`) (`9b37d82`)
- **사람 행위만 기록** — 요청 컨텍스트가 없는 변경, 즉 크롤러·스케줄러의 자동 갱신은 제외했다. 기일 일일 갱신만 월 5천여 건이라 함께 쌓으면 정작 찾아야 할 사람의 행위가 묻힌다. 반대로 **권한 거부(403)는 데이터가 안 바뀌어 세션 훅이 잡지 못하므로** 별도 세션으로 따로 기록한다 — "시도했으나 막힌 행위"야말로 감사에서 봐야 할 기록이기 때문. 조회 API는 super_admin 전용이며, 지사명·사건번호는 **저장하지 않고 조회 시 조인**해 얻는다(로그에 파생값을 박아두면 원본이 바뀌었을 때 어긋난다). (backend `api/audit_logs_api.py`) (`9b37d82`)
- **조회 화면** — 시스템 설정에 「감사 로그」를 신설했다. 누가·어디서·무엇을·어떻게를 그대로 컬럼으로 두고, **행을 펼치면 필드별 이전값 → 이후값 diff**(등록·삭제는 스냅샷)를 보여준다. 필터는 기간·행위자·대상 테이블·동작·지사·검색어에 25건 페이지네이션. **행위자의 지사와 대상 데이터의 지사가 다르면 「타 지사」 경고 배지**를 띄운다 — 지사 간 데이터 접근이 감사에서 가장 먼저 봐야 할 신호라서다. super_admin 전용이라 네비에서 숨기고 페이지 단에서도 차단했다(직접 URL 접근 대비). (frontend `AuditLogPage.tsx`·`api/auditLogs.ts`·`hooks/useAuditLogs.ts`·`AdminLayout.tsx`·`routes/index.tsx`) (`c38535c`)
- **기간 필터 500 버그 수정** — `text()` 안에서 `:date_to::date`로 쓰면 SQLAlchemy가 `::`를 **캐스트가 아니라 바인드 파라미터 구분자로 읽어** 파라미터가 그대로 SQL에 남아 syntax error가 났다. 화면 기본값이 최근 7일이라 **감사 로그 페이지가 항상 500**이던 상태. `CAST(:date_to AS date)`로 교체했다. (backend `audit_logs_api.py`) (`776ada7`)

### 2. 사건관리 — 시스템 설정 화면 정비

> 배경: 설정 화면을 실제로 써 보니 세 가지가 걸렸다 — 하위 화면으로 가면 메뉴가 사라져 돌아올 수 없고, 지사가 늘수록 입력창이 세로로 끝없이 늘어지고, 저장을 눌러도 됐는지 안 됐는지 알 수 없었다.

- **공용 네비 셸** — 계약 매핑·목표/달성율로 이동하면 좌측 설정 네비가 통째로 사라져 **브라우저 뒤로가기 말고는 돌아갈 길이 없었다.** `/admin` 이하를 `AdminLayout` 중첩 라우트로 묶어 세 화면이 같은 네비를 공유하고 우측 본문만 바뀌게 했다. 하위 화면에서 섹션 메뉴를 누르면 `navigate` state로 설정 본문에 돌아가 **해당 섹션까지 스크롤**한다. 같은 셸 안이 됐으므로 "별도 창"을 뜻하던 ExternalLink 아이콘은 제거. (frontend `AdminLayout.tsx`·`AdminPage.tsx`·`ContractMappingPage.tsx`·`AchievementPage.tsx`·`routes/index.tsx`) (`d6aaf3b`)
- **설정 행 아코디언 + 저장 상태** — 지사마다 입력창이 항상 펼쳐져 있어 화면이 세로로 늘어지고, 무엇이 설정된 상태인지도 드러나지 않았다. 평소엔 **지사명 + 요약 한 줄**(예: `7영업일 · 웹훅 설정됨`)만 보이고 클릭한 행만 펼쳐지게 했다(한 번에 하나). 저장 버튼은 **저장 중 → 저장됨**으로 바뀌어 결과가 눈에 보이고, 미저장 변경은 주황 점으로 표시한 뒤 **접으면 저장된 값으로 되돌린다** — 아코디언은 접으면 안 보이므로 편집값이 유령처럼 남으면 위험하다는 판단. `직접 설정`/`기본값` 배지는 키 존재 여부가 아니라 **실제 값 유무**로 판정하게 고쳤다(빈 설정이 저장돼 있어도 「직접 설정」으로 보이던 문제). 「초기화」 버튼은 제거했다 — 값을 비우고 저장하면 같은 결과라 불필요한 파괴적 버튼이었다. (frontend `settingsControls.tsx`·`RecordRequestSettingsSection.tsx`) (`c0fce92`)
- **고정 수신 이메일 개별 추가·삭제** — 쉼표로 구분한 **한 줄짜리 입력**이라 실수로 전체를 지우고 저장하면 복구할 수 없었다. 주소마다 개별 행 + `×` 삭제로 바꾸고, 추가는 Enter 또는 버튼으로 한 건씩 받으며 **그 시점에 형식·중복을 검사**한다(저장할 때까지 기다렸다 에러 내지 않음). 추가·삭제는 화면상 변경이고 저장을 눌러야 반영되므로, 실수로 지워도 저장 전에 접으면 되돌아간다. (frontend `DocumentLogSettingsSection.tsx`) (`6d1e7e7`)
- **계약 설정 삭제 확인 + 결과 토스트** — 웹훅·저장폴더 휴지통을 누르면 **확인 없이 즉시 삭제**되고 추가·삭제 결과 알림도 없어 됐는지 알 수 없었다. 공용 `ConfirmDialog`(danger 톤)를 만들어 대상과 영향("이후 이 사무소의 계약 보고가 발송되지 않습니다")을 문구로 확인하게 하고, 성공/실패 토스트를 붙였다. 버튼에 `cursor-pointer`·호버 색도 함께 적용. (frontend `ConfirmDialog.tsx`·`ContractSettingsSection.tsx`) (`cf795cc`)
- **권한 범위 점검** — super_admin은 전 지사, admin은 본인 소속 지사만 보이는지 확인했다. 프론트 필터링뿐 아니라 **백엔드도 `get_office_scope()`로 서버측 강제**하고 있어(남의 지사 키를 직접 요청하면 403) 손댈 것이 없었다.

### 3. 사건관리 — 사건목록 CRM 이동 + 호버 반응성 (이슈 #126)

- **CRM 딥링크로 교체** — 당사자 셀 `+` 메뉴의 「CRM으로 이동」이 CRM이 아니라 `/cases?keyword=당사자이름`으로 **같은 사건목록을 다시 띄우고** 있었고, 도착한 `CaseListPage`가 `keyword` 파라미터를 읽지도 않아 검색도 안 걸리는 **완전히 죽은 기능**이었다. 이름대로 CRM 사이트를 새 탭으로 여는 쪽으로 방향을 정하고 사건상세 위임인 딥링크와 동일한 `{VITE_CRM_URL}#/parties/{key}` 형식을 썼다. 이때 `party_key`를 그냥 쓰지 않고 **`delegator_party_key`를 신설**한 이유가 있다 — 사건상세는 `matters.party_key` → `cases.party_key` 순으로 위임인을 찾는데 목록에는 후자밖에 없어, 그대로 쓰면 **같은 사건인데 목록과 상세가 서로 다른 의뢰인으로 갈 수 있었다.** 기존 `pd_m`/`pd_c` LATERAL에 컬럼만 추가해 조인 비용은 그대로다. CRM 의뢰인이 없거나 URL 미설정이면 비활성 표시 + 사유 툴팁을 띄운다(눌렀는데 아무 일도 안 일어나는 이번 상황의 재발 방지). (backend `cases_crud.py`·`cases_schema.py`, frontend `CaseListTable.tsx`·`types.ts`) (`f802fac`)
- **호버가 굼뜨던 원인 두 가지** — 눈에 보이는 원인은 `transition-colors`의 150ms 페이드였지만(`tr`·당사자셀·`+`버튼에서 제거), **진짜 원인은 리렌더**였다. 행에 마우스를 올릴 때마다 `setHoveredGroup`이 돌고 `CaseRow`가 memo도 가상화도 안 돼 있어 **커서가 행을 지날 때마다 화면의 모든 행이 다시 렌더**됐다(목록을 1000건으로 늘리면 색이 커서를 따라오지 못한다). 이 상태는 원래 **rowSpan으로 병합된 당사자 셀** 하나를 강조하려고 있는 것인데, 병합이 아닌 행은 `tr`의 CSS hover 배경이 셀까지 그대로 비쳐 상태가 애초에 필요 없었다. `partySpan === 1`(병합 아님)이면 상태를 건드리지 않게 해 **당사자 병합을 끈 상태에서는 호버 리렌더가 0**이 된다. (`f802fac`)

### 4. 사건관리 — 사건상세 타임라인에 CRM 상담 이력 (이슈 #127)

> 배경: 타임라인이 법원·수발신·열람등사·수기일정·연결사건·사건이벤트·계약수납 7개 소스만 보여줘 **선임 이전의 맥락(상담 → 계약 → 사건)이 끊겨** 있었다. 이슈에 미결로 남아 있던 4개 항목(무엇을 넣을지·FDW냐 미러냐·필드·시각 구분)을 먼저 확정하고 착수했다.

- **데이터 출처 결정** — 조사해 보니 `crm.*`가 **이미 postgres_fdw로 마운트**돼 있었다(`crm.party_detail`·`employee_info`·`organization`·`consultation_schedule`·`party_consultation`). 미러 테이블을 새로 만들 필요가 없어 FDW를 그대로 쓰기로 했다. 다만 기존 코드에 기록돼 있던 함정이 그대로 적용된다 — **FDW는 인라인 JOIN이 원격에 푸시다운되지 않아** 원격 테이블을 반복 스캔한다. 그래서 상담만 먼저 뽑고 상담자명·사무소명은 **배치로 따로 해소**하는 방식으로 짰다. (실제로 이 함정을 검증 단계에서 한 번 밟았다 — 사건 전체를 돌며 FDW 서브쿼리를 거는 조회를 짰다가 5분을 넘겨 중단하고, CRM 쪽에서 거꾸로 집계하는 방식으로 다시 짰다.)
- **엔드포인트** — `GET /api/cases/{id}/consultations`(`cases:read`). party_key 해석은 사건상세 위임인과 동일한 순서. `consultation_schedule`(예약 상담 — 유형·상태·상담자·**내용 본문**)과 `party_consultation`(접촉 원장 — 날짜·유형·상태)을 **둘 다** 조회하고 중복을 접는다. CRM 조회 실패가 사건상세 전체를 죽이지 않도록 예외를 삼키되, **party_key 부재 / 각 테이블 쿼리 실패를 구분해 로그로 남긴다** — 조용히 빈 배열을 주면 "상담이 없음"과 "쿼리가 터짐"이 구분되지 않아 원인 추적이 불가능하다(실제로 처음엔 이 로그가 없어 진단이 막혔다). (backend `cases_api.py`·`cases_schema.py`) (`901cda2`)
- **타임라인 소스 추가** — `consult` 소스를 신설하고 필터에 「CRM상담」을 **기본 체크 상태로** 넣었다. 색은 기존 6색(파랑·주황·보라·자주·하늘·청록)과 겹치지 않는 앰버 계열. 배지=상담유형, 본문=상담내용(없으면 사건명), 보조=상담자·사무소·상태·시각이며 **상태는 「완료」면 생략하고 예약·취소·노쇼일 때만** 표시한다. 풀페이지·사이드패널 양쪽에 적용. (frontend `caseTimelineUtils.ts`·`CaseDetailPage.tsx`·`CaseSidePanel.tsx`·`useCaseDetail.ts`·`api/cases.ts`·`types.ts`) (`901cda2`)
- **중복 제거 규칙 결함 발견·수정** — 처음엔 "같은 날짜에 예약 상담이 있으면 원장 기록은 접는다"로 짰는데, **실데이터로 검증하다 결함이 드러났다.** 한 사건(2026-05-26)에 방문상담 예약 2건과 방문상담 원장 2건 + **전화상담(직원) 3건**이 함께 있었고, 날짜만 보는 규칙이 그날의 전화상담 3건까지 중복으로 오인해 통째로 지웠다. 판정 키를 **(날짜) → (날짜, 상담유형)**으로 바꿔 같은 유형만 접고 다른 유형은 별개 접촉으로 남긴다. (backend `cases_api.py`) (`5ef0d6c`)
- **알려진 특성** — 상담은 사건이 아니라 **의뢰인(party_key)에 달려 있어** 같은 의뢰인의 다른 사건 상담도 함께 나온다. 맥락을 보기 위한 의도된 동작이며, 사건 단위로 좁히려면 `consultation_schedule.case_name` 매칭이 필요한데 CRM 입력이 부실하면 대부분 누락되므로 채택하지 않았다.

### 5. 사건관리 — 기일 충돌 사용자 해소 + 참석자/불출석 (이슈 #130)

- **출석비고를 채우면 충돌 해제** — 같은 변호사의 기일이 1시간 이내로 겹치면 행이 분홍으로 표시되는데, 지금까지는 **표시만 하고 끝이라 사용자가 어떻게 정리했는지 앱이 알 수 없었다.** 이슈에는 해소 상태를 담을 신규 컬럼이 필요할 것으로 적혀 있었으나, **출석비고(`attendee_keys`)가 채워졌다는 것 자체가 "누가 들어갈지 정해졌다 = 조율 끝"**을 뜻하므로 그것을 해소 신호로 재사용했다 — 마이그레이션 없이 해결됐고, 이슈의 또 다른 요구사항인 "불출석 기일은 충돌에서 제외"도 `불출석`이 같은 배열에 문자열로 담기는 구조라 **"배열이 비어있지 않다" 하나로 함께** 걸린다. 판정 쿼리에 `jsonb_typeof`로 방어한 길이 검사를 넣고(`NULL`·`[]`·JSON `null`은 미처리로 유지), 사건상세·사이드패널에서 출석비고를 채워도 목록 표시가 즉시 갱신되도록 `conflict-ids` 무효화를 추가했다. 행 툴팁에 해제 방법을 안내한다. (backend `cases_api.py`, frontend `CaseListTable.tsx`·`useCaseDetail.ts`) (`955da2f`)
- **참석자 ↔ 불출석 배타 처리** — 불출석은 "아무도 출석하지 않는다"는 뜻인데 참석자 선택과 독립이라 `['EMP0001','불출석']` 같은 **모순된 값이 저장될 수 있었다.** 참석자를 고르면 불출석이 해제되고, 불출석을 켜면 선택된 참석자가 비워지게 했다. 사건목록 팝업·사건상세·사이드패널 세 곳이 같은 팝업 구조라 **화면별로 규칙이 갈리지 않도록 함께** 적용했다. 이미 저장된 모순 데이터는 그대로 남지만 해당 기일을 한 번 건드리면 정리되며, 충돌 판정에는 영향이 없다(배열이 비었는지만 본다). (frontend `CaseListTable.tsx`·`CaseDetailPage.tsx`·`CaseSidePanel.tsx`) (`cace1ff`)

### 6. 사건관리 — 열람/등사 완료 상태 정리·팝업 잘림

- **완료 = 등사일자 기준으로 통일** — 완료 처리와 등사일자가 따로 놀아 **등사일자 없는 완료 건**이 생길 수 있었다. 목록에서 완료를 고르면 등사일자 입력 팝업이 뜨고(기존 재신청 팝업과 `StatusPopup`으로 통합), 상세 드로어에서는 등사일자를 상시 노출해 **진행중(신청·재신청) 건에 날짜를 넣으면 상태가 자동으로 완료**로 넘어간다. 반대로 완료인데 등사일자가 없으면 저장을 막는다. 상태 선택 목록에서는 '신청'을 뺐다 — 등록 시 초기값이라 사람이 되돌릴 이유가 없어 현재값일 때만 표시용으로 남긴다. (frontend `RecordRequestListPage.tsx`·`RecordRequestDetailDrawer.tsx`·`constants.ts`) (`70b1f66`)
- **수신자 이메일 드롭다운 잘림** — 목록이 `absolute`라 등록 팝업의 스크롤 컨테이너(`overflow-y-auto`)와 `DialogContent`(`overflow-hidden`)에 잘렸다. DatePicker·EmployeeComboBox와 동일하게 **`createPortal` + fixed 좌표로 body에 띄운다.** 포털로 나가면 바깥클릭 감지가 목록 자체를 "바깥"으로 취급하므로 `listRef`도 함께 검사하고, 열린 동안 스크롤·리사이즈 시 좌표를 다시 계산한다. (frontend `record-requests/pickers.tsx`) (`24a1bbc`)

### 7. 운영 — 배포 중 프로덕션 API 9분 중단 (이슈 #156)

- **사고 경위** — 09:08~09:17(KST) 프로덕션(`lawwin-case`)의 **백엔드 API가 전면 중단**됐다. 모든 요청이 SPA `index.html`(503바이트)로 폴백되어 로그인·API 호출이 전부 실패했고, GET은 200처럼 보이는데 POST/PUT은 404가 나는 형태였다. **코드 문제가 아니라 배포 명령의 소스 경로 실수** — 프론트 빌드를 확인하려고 이동한 디렉터리가 셸에 남은 상태로 `--source=.`을 실행해 Dockerfile이 없는 `frontend/`만 buildpack으로 빌드됐고, **백엔드가 통째로 빠진 이미지**가 배포됐다. 루트 절대경로로 재배포해 복구(리비전 00081).
- **되짚어 볼 점** — 배포 직후 `/api/health` 200 응답을 근거로 "정상"이라 보고했으나, 그 200은 SPA 폴백이 돌려준 HTML이었다. **헬스체크는 상태코드가 아니라 응답 본문·Content-Type까지 봐야** 이런 형태의 장애를 잡는다. 경위와 타임라인을 기록용 이슈로 남겼다.

**금일 종합:** 오늘의 축은 **"기록"과 "실수 방지"** 두 가지였다. 가장 큰 작업인 감사 로그는 단순한 로깅이 아니라 **어디서 잡아야 누락도 유령도 없는가**를 정하는 일이었다 — `before_flush`에서 변경 내역을 수집하고 `after_flush`에서 PK를 확인해 같은 트랜잭션에 적재하는 구조, 컨텍스트 없는 크롤러 변경은 빼되 데이터가 안 바뀌는 403은 오히려 따로 남기는 선택이 그것이다. 시스템 설정 정비는 전부 **"사용자가 실수하거나 결과를 모르는 지점"**을 없애는 작업이었다 — 돌아갈 길 없는 네비, 통째로 날아갈 수 있는 이메일 입력, 눌러도 반응 없는 저장 버튼, 확인 없이 지워지는 웹훅. CRM 연결 2건에서는 각각 **겉으로 보이는 문제 뒤에 진짜 문제가 하나씩** 있었다 — 'CRM으로 이동'은 링크만 고치면 될 줄 알았으나 목록과 상세가 서로 다른 의뢰인으로 갈 수 있는 키 해석 불일치가 있었고, 호버가 느린 건 CSS 페이드인 줄 알았으나 행마다 표 전체가 리렌더되고 있었다. 타임라인 CRM 연동은 FDW가 이미 깔려 있어 인프라 없이 붙였지만, **실데이터로 검증하지 않았으면 그냥 넘어갔을 결함**(같은 날 전화상담이 통째로 사라지는 중복 제거 규칙)을 검증 단계에서 잡은 것이 수확이다. 마지막으로 배포 사고는 뼈아팠다 — 9분간 프로덕션 API가 죽었고, 무엇보다 **200 응답을 보고 정상이라 판단한 것**이 문제였다. postmortem으로 남겼다. 금일 1개 repo에 걸쳐 커밋 16건.
