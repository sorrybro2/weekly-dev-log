# 일일 업무 보고 (2026. 10. 07)

> 어제 FAQ를 붙인 사례 3천 건이 검색엔진과 AI에게는 "안 바뀐 글"이었다. 바뀐 글을 빙·네이버(IndexNow)와 구글(사이트맵 수정일)에 알리는 장치를 만들어 첫 통지 7,227건을 보냈다. 사내 포털은 로그인 직후 첫 화면 7.3초를 원인별로 쪼개 1.5초까지 줄였다 — 금일 커밋 29건(3개 repo), 이슈 1건 생성 · 코멘트 16건.

## ⏱️ 10초 핵심 요약

**[홈페이지 V2 — 바뀐 글 알리기 (이슈 #145, #140)]**

- **IndexNow 통지**: 공개 글·변호사마다 내용 지문을 저장해 10분마다 비교하고, 새 글·바뀐 글·내려간 글을 빙과 네이버에 바로 알린다. 빙은 ChatGPT 검색이 쓰는 색인이다.
- **사이트맵 수정일**: 늘 작성일이던 `lastmod`·`dateModified`를 내용이 마지막으로 바뀐 날로 바꿨다. IndexNow를 받지 않는 구글(Gemini)에 알리는 길은 이것뿐이다.
- **FAQ 재생성**: 사례 본문이 바뀌면 그 글의 FAQ를 다시 만들어 검사를 다시 거친다. 옛 결과·형량이 FAQ에 남는 광고 리스크를 막는다.
- **배포**: 마이그레이션 → 백엔드 → 프론트 → 스케줄러 순서로 올렸다. 네이버는 7,227건 접수(200), 빙은 첫 요청 403 뒤 재전송해 200.
- **AI 유입 기준선**: 수집 / 답변 중 열람 / 클릭 방문 3단계로 나눠 통지 직전 값을 남겼다(ChatGPT 클릭 30일 125회).

**[사내 포털 — 첫 화면 속도 (이슈 #29)]**

- **콜드스타트**: 포털을 상시 1대 띄우기로 했다(월 약 $14 추정). 연결 서비스는 0으로 되돌렸다.

- **내선 통화 확인창**: 순차 조회를 동시 조회로 바꾸고 경유 서비스를 뺐다(2.2초 → 평소 1.36초).

**[사내 포털 — 조직도·구성원 관리 (이슈 #28, #30)]**

- **연락처 카드**: 정보실이 아닌 사람도 조직도 사람 칸을 누르면 연락처 카드가 뜬다.
- **대외비 워터마크 · 배율 고정**: 어디를 잘라 캡처해도 워터마크가 찍히게 하고, 확대·축소 없이 가로 폭에 맞춘 배율 하나로 고정했다.

## 📝 상세 업무 내역

### 1. 홈페이지 V2 — 바뀐 글을 검색엔진·AI에 알리기 (이슈 #145, #140)

- **배경** — `tbl_bbs`·`tbl_lawyer`에는 수정일 칸이 없다. 그래서 어제 사례 3,038건에 FAQ를 공개했어도 크롤러에게는 안 바뀐 글이라 다시 읽으러 올 이유가 없었다. 최근 7일 크롤러 요청을 보면 수집은 이미 들어오고 있어서, 다음 단계는 "바뀐 것을 빨리 다시 읽게" 하는 것이었다. AI 3사가 쓰는 색인을 정리하면 ChatGPT = 빙(IndexNow), Gemini = 구글(사이트맵 lastmod), Claude = Brave(따로 알릴 길 없음)다. (이슈 `#145`)
- **`content-change` 모듈** — 공개 게시물과 변호사마다 내용 지문(md5)을 `tbl_content_change`에 저장하고 10분마다 비교한다. 새 글·바뀐 글·내려간 글을 IndexNow로 빙·네이버에 보낸다. 어드민에서 고친 글, 레거시 동기화로 들어온 글, FAQ가 승인된 사례가 모두 같은 길로 잡히고, 바뀐 시각은 사이트맵 수정일의 근거가 된다. 로컬에서는 보내지 않고 Cloud Run에서만 보낸다. (`content-change.service.ts`, `migration/sql/20261007_content_change.sql`) (`52ea024`)
- **사이트맵·구조화 데이터 수정일** — 사이트맵 `lastmod`와 Article `dateModified`를 내용이 마지막으로 바뀐 때(사례는 FAQ 공개 포함)로 낸다. 상세글은 새 엔드포인트 `GET /api/bbs/sitemap` 한 번으로 받고, 실패하면 예전 방식으로 내려간다. (`sitemap.xml/route.ts`, `article-jsonld.tsx`) (`0fd9f05`)
- **본문이 바뀌면 FAQ도 다시** — FAQ를 만들 때 읽은 원문(제목·소개·단계 본문·소제목)의 지문을 `source_hash`에 저장하고, 지금 원문과 다르면 다시 만들어 자동 검사를 다시 거친다. 사람이 반려한 FAQ는 되살리지 않는다. 기존 FAQ는 첫 회차에 지금 원문을 기준으로 잡고, 한 회차에 바뀐 글이 200건을 넘으면 일괄 작업으로 보고 멈춘다. (`case-faq.service.ts`) (`57d7986`)
- **배포 순서와 첫 통지** — 마이그레이션을 먼저 하지 않으면 FAQ 조회가 실패해 사례 페이지에서 FAQ가 사라진다. 그래서 Cloud SQL Studio로 SQL을 먼저 적용했다(로컬 `prisma db execute`는 비밀번호 특수문자로 주소가 깨졌다). 이어 백엔드 `00089`(사이트맵 7,189건 중 사례 3,039건이 lastmod 10/6), 프론트, 스케줄러 `content-change-sync`(10분) 순서로 올렸다. 첫 실행에서 네이버는 7,227건을 200으로 받았고 빙은 403이었다. 키 파일을 아직 확인하지 않은 상태였던 것으로 보고, 빙에만 같은 7,227건을 다시 보내 200을 받았다. (이슈 `#145`)
- **알려진 한계** — 한쪽 엔진만 실패하면 그 회차 주소는 그 엔진에 다시 가지 않는다(다른 쪽 중복 전송을 피하려는 설계). "IndexNow 일부 실패" 로그가 반복되면 엔진별 통지 시각을 따로 두는 쪽으로 고치기로 했다. (이슈 `#145`)
- **AI 유입 기준선** — IndexNow 첫 통지 직전 값을 비교 기준으로 남겼다. 숫자를 ① 수집(크롤러) ② 답변 중 열람(`*-User` 에이전트) ③ 클릭 방문 세 단계로 나눠 "수집됨"과 "답변에 노출됨"을 섞지 않게 했다. 30일 ChatGPT 클릭 방문은 125회 · 91 IP이고 다른 AI는 0이었다. 메타·바이트댄스 봇이 수집 요청의 대부분인데 유입 기여는 없어 robots 차단 검토 대상으로 적었다. 방문별 검색어는 받을 수 없고 서치콘솔 합계로만 볼 수 있다는 점도 정리했다. (이슈 `#145`, 커밋 없음)
- **문서** — README에 운영 구성 그림, 콘솔 주소, Cloud Scheduler 8개 작업, 테이블 요약, 검색·AI 노출 장치 표를 넣었다. `docs/architecture.md`·`docs/db-schema.md`는 초기 계획 문서였던 것을 실제 운영 구성으로 다시 썼다. (`decd7cb`)

### 2. BS_MAINBOARD(사내 포털) — 로그인 직후 첫 화면 속도 (이슈 #29)

- **콜드스타트 결정** — 어제 측정에서 첫 화면의 약 30%가 콜드스타트(중간값 8.3초)였다. 포털 최소 인스턴스를 0 → 1로 올리고 배포 스크립트에 고정했다(월 약 $14 추정, 결제 보고서로 확인 예정). `gws-centrex-api`도 1로 올렸다가, 아래 수정으로 화면이 이 서비스를 기다리지 않게 되자 0으로 되돌렸다. (`bca1605`)
- **7.3초: 지사별 내선 대기** — "로그인이 5초쯤"이라는 체감을 로그로 나누니 로그인 자체는 1초 안쪽이었다. 느린 것은 로그인 직후 `GET /` 7.3초였다. 명부가 지사별 내선을 약 20명분(한 사람 1.5~4.9초) 다 받을 때까지 기다린 탓이다. 이제 명부와 조직도는 기억해 둔 값만 쓰고, 없거나 30분 지난 값은 뒤에서 새로 읽는다. 발신은 그대로 매번 새로 읽는다. (`branch-extension.ts`) (`deca640`)
- **4.48초: People API 캐시** — 그 뒤에도 4.48초가 남았다. 원인은 어제와 같은 함정이었다. People API 디렉터리 캐시가 `Authorization` 헤더(새 access token)까지 열쇠에 넣어 로그인할 때마다 비었다. 도메인 프로필은 누가 읽어도 같으므로 인스턴스 메모리에 하나만 두고 같이 쓴다. 이후 1.50초로 줄었다. (`directory.ts`) (`3cabf38`)

- **프로필 사진** — 카드를 열 때 처음 사진을 요청했고, 그 요청이 포털 이미지 최적화기를 거쳐 한 장에 0.8초쯤 걸렸다. 구글이 이미 작게 주므로 최적화기를 끄고 구글 CDN에서 바로 받으며, 명부가 뜬 뒤 브라우저가 한가할 때 미리 받아 둔다. (`261bbc0`)

### 3. BS_MAINBOARD — 조직도·구성원 관리 (이슈 #28, #30)

- **연락처 카드** — 정보실이 아닌 사람이 조직도 사람 칸을 누르면 구성원 찾기와 같은 카드(사진·직위·내선 통화·휴대폰·구글챗·이메일)가 뜬다. 정보실은 지금처럼 편집 패널이 뜬다. 박스 전체에 선택 테두리가 생기던 것은 React Flow 노드 선택을 꺼서 막았다. (`person-card.tsx`) (`fef9959`, `b77c58c`)

- **퇴직 탭** — 퇴직 + 계정 정지인 사람은 "정지"로만 보여 퇴직 탭에서 빠졌다. 이제 "퇴직 · 정지"로 퇴직 탭에 나온다. 구글 계정이 지워진 퇴직자를 CRM 기록으로 붙이는 것도 넣었다가, 구성원 관리는 구글 계정을 고치는 화면이라는 결정에 따라 그 절반은 되돌렸다. (`f8c6650`, `f183449`)

**운영 조치** — 구성원 찾기 89명과 관리 화면 "재직" 83명의 차이를 실데이터로 맞댔다(`83 + 4 + 1 + 2 − 1 = 89`). 휴직 4명은 정상이다. 직위 누락 1명은 직위 입력이 필요하다. CRM은 재직인데 구글 계정이 없는 2명은 재직 여부 확인이 필요하다. 구글 계정은 있지만 CRM 소속이 비어 조직도에 없는 통역사 1명도 확인 대상이다. 고문 진상덕 추가는 조직도 저장으로 처리했다. (이슈 `#30`)

### 4. BS_CRM — 로그인 경로·회생 입력폼

- **로그인 후 원래 화면으로** — 로그인 안 된 상태로 상세 링크를 열면 로그인 뒤 목록으로 갔다. 해시 URL이라 주소창 쿼리에서 돌아갈 경로를 읽으면 늘 비어 있었고, 구글 인증에서 돌아올 때 미리 저장해 둔 경로도 지워졌다. 라우터에서 경로를 읽고 저장값을 지키게 고쳤다. 구글 드라이브 재동의 후 복귀와 로그아웃 안내 미표시도 함께 해결했다. (`login_page.dart`, `login_session_storage.dart`) (`9e8387a`, 머지 `d3e13cf`)
- **개인워크아웃 자동차 기준** — 신청 기준 6번 항목을 시세 4,200만 원, 청산가치 2,000만 원, 월 할부금 70만 원 이상 기준으로 바꾸고 2000cc·친환경 차량 조건은 지웠다. 입력폼, 결과 화면, PNG, PDF 문구를 같이 맞췄다. (`recovery_intake_*`) (`c6b4a9c`, 머지 `ec7bbec`)
