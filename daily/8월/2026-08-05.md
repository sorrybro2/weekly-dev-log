# 일일 업무 보고 (2026. 08. 05)

> **컷오버 D-1 — 홈페이지 V2를 실서버로 넘기기 위한 마지막 정리와, 레거시 색인을 지키는 작업에 하루를 쓴 날.** 가장 큰 신규 기능은 **상담 접수 알림**이다. 홈페이지 상담이 접수돼도 담당자가 알 방법이 없다는 지사 제보(이슈 #5)에 대해, 지사별 구글챗 스페이스로 알림을 쏘고 **그 URL을 어드민에서 직접 관리**하게 만들었다 — env가 아니라 DB에 둬서 재배포 없이 켜고 끌 수 있다. 이후 담당자 피드백을 받아 카드에서 **일반 텍스트로 형식을 바꾸고** 회생·파산 전담 수신 대상을 추가했다. 두 번째 축은 **SEO**다. 레거시 URL을 전수 점검해 404 나던 **11개 패턴**(전문센터 `*contact` 6개, 변제금 예측, `/Center` 인덱스, 지역 민사, 상담 비밀번호·상세)을 301에 채우고, 구 sitemap에 색인된 `?tk=N` 뉴스 탭 32건이 전부 미디어 탭으로 뭉개지던 것을 탭 경로로 승격했다. 이미지 로딩 제보(#4)는 **DB 참조 자산 7,797개를 전수 대조**해 깨진 건 0건임을 확인하고 닫았다. 그 밖에 고문·전문위원에게 변호사 직함이 붙던 표기, 상담 전화번호가 본사로만 연결되던 문제(#6), 회신 불가능한 입력값 차단, 집계 수치 표기 정책(보류 → 복원 → 반올림+`+`)을 정리했다. **Cloud Run 스펙도 실서비스 기준으로 올렸다** — 프론트가 256Mi 한도를 넘겨 OOM 로그가 하루 198건 찍히고 있었다. 배포 4회(프론트 3·백엔드 1), 이슈 13건 정리 — 금일 커밋 33건(1개 repo)

## 📝 상세 업무 내역

### 1. 홈페이지 V2 — 상담 접수 알림 (이슈 #5)

> 배경: 「홈페이지 상담 신청시 상담알림 채팅에 발송되지 않음」(대전지사 제보). 레거시 코드를 확인해보니 `chat.googleapis.com` 호출이 없다 — **레거시 홈페이지 자체에 이 기능이 없었다.** 사건관리 앱의 계약 보고 카드와 같은 방식으로 새로 만들었다.

#### 1-1. 기능 신설

- **지사별 구글챗 알림 + 어드민 관리 화면** — 상담이 접수되면 해당 지사 스페이스로 접수 내용을 보낸다. 핵심 설계는 **웹훅 목록을 env가 아니라 DB에 두는 것** — Cloud Run 환경변수는 변경 시 새 리비전 롤아웃이라 운영자가 켜고 끌 수 없다. 사건관리 앱의 `system_settings`(key/value JSON) 방식을 그대로 이식해 어드민 `상담 관리 > 접수 알림 웹훅`(슈퍼어드민 전용)에서 등록·수정·활성 토글·테스트 전송을 한다. 보안 두 가지 — 등록 가능 주소를 **`chat.googleapis.com`으로 고정**해 임의 URL로 요청이 나가지 못하게 막고(어드민이 URL을 입력하는 구조라 내부망·메타데이터 엔드포인트가 열릴 수 있다), 구글챗 웹훅 URL은 **그 자체가 크리덴셜**이라 조회 시 `key`·`token`을 마스킹한다(수정 시 비워두면 기존 값 유지). 지사 미지정 훅은 모든 접수를 받아 미등록 지사도 알림이 유실되지 않는다. CRM 전달과 알림을 **순차로** 실행해 알림 링크를 눌렀을 때 그 건이 CRM 요청함에 이미 있도록 보장했다(병렬이면 알림이 먼저 도착할 수 있다). (backend `src/notify/*`·`admin-webhooks.controller.ts`·`consult.service.ts`, frontend `admin/webhook/*`, `backend/migrations/001_create_system_settings.sql`) (`846f0c4`)

#### 1-2. 담당자 피드백 반영

- **형식 전환 + 회생 전담 대상** — 카드(cardsV2)는 모바일에서 접히고 연락처를 복사하기 번거로워, 담당자 요청으로 **일반 텍스트**로 바꿨다(레거시 알림과 같은 형식). 텍스트라 버튼 위젯을 못 쓰므로 CRM 요청함 링크와 당사자 추가 딥링크는 URL을 본문에 그대로 적어 자동 링크되게 했다. 회생·파산 분야 접수는 지사와 별개로 회생팀이 전담해야 하므로 **접수 지사 훅과 회생·파산센터 훅이 모두 수신**한다 — 저장 스키마를 바꾸지 않고 대상 필드에 음수 센티넬(-2)을 써서 표현했다. 대상 선택 목록에서는 공개하지 않는 지사(의정부·목포·제주)를 제외해 노출 지사 10곳 + 회생·파산센터 11개만 남겼다. (backend `notify-targets.ts`·`google-chat.service.ts`) (`f5beb14`)

### 2. 홈페이지 V2 — 레거시 URL 301 보완 (SEO)

> 배경: 컷오버 시 구 URL로 들어오는 트래픽이 404가 나면 색인과 백링크가 죽는다. 레거시 뷰 폴더(`Views/Region`·`Views/Center`)에서 **액션을 전수 추출해** 현재 V2 응답을 하나하나 확인했다.

- **뉴스 탭 색인 보존** — 레거시는 뉴스 탭을 쿼리(`?tk=N`)로 갈랐고 V2는 경로(`/news/{slug}`)로 가른다. 구 sitemap에 `/{지사}/news?tk=4~7`가 **지사 8곳 × 4탭 = 32건** 색인돼 있어, `tk`를 무시하면 전부 미디어 탭으로 뭉개지며 동영상·사회공헌·공지 색인이 소실된다. tk 4/5/6/7을 media/video/social/notice로 승격하고, 없거나 모르는 값은 미디어 탭으로 폴백했다. (frontend `lib/legacy-redirects.ts`·`middleware.ts`) (`ea26287`)
- **404 나던 11개 패턴 채움** — 전문센터는 레거시만 유일하게 2단 경로(`/Center/{Action}`)를 쓴다. 필요한 일이 세 가지였다 — ① **대소문자 정규화**(레거시 IIS는 대소문자를 무시했지만 Next는 구분해서 `/Center/Recovery`가 404) ② 상담 액션(`*contact` 6개) → `/center/{slug}/consult` ③ 변제금 예측 → 회생 상담 페이지. 여기에 `/Center` 인덱스(레거시가 Recovery로 리다이렉트했음), 지역 민사 안내(`/{지사}/civil` → 민사센터), 상담 비밀번호·상세를 추가했다. **상담 상세는 레거시 `listindex`와 V2 `listkey`가 호환되지 않아** 상세 직결이 불가능하다 — 본인확인이 필요한 비공개 글이라 딥링크 자체가 부적절해 게시판 목록으로 보냈다. 대소문자 정규화를 하다 보면 목적지가 요청 경로와 같아질 수 있으므로 **무한 리다이렉트 방어**를 미들웨어에 넣었다. (`688c3a6`)

### 3. 홈페이지 V2 — 이미지 로딩 전수 검증 (이슈 #4)

> 배경: 「성공사례 처분지 이미지 안 보임 / 부산지사 윤재은 변호사님 이미지 안 보임 / 변호사 소개 일부 액박」 제보. 눈으로 확인하는 대신 **DB가 참조하는 자산을 전수 대조**했다.

- **전수 검사 결과 깨짐 0건** — 변호사 프로필 78건(노출중 39명 × profileimg·profileminimg), 성공사례 썸네일 857건, 전 게시물 본문·첨부 **고유 URL 7,797건**을 GCS와 대조했고 깨진 건이 없었다. 노출중인 변호사 중 프로필이 빈 경우도 0건. 제보된 개별 케이스(윤재은 변호사 192KB·김범선 변호사 288KB)는 GCS 직접 조회와 **라이브 사이트 rewrite 경유 양쪽** 모두 200이었다. 검사 과정에서 알게 된 것 — 성공사례 본문은 `desc`가 아니라 **`step1~6`·`fileupload`에 저장**된다(첫 쿼리가 0건으로 나온 이유). 원인은 두 개였고 당일 마이그레이션 작업으로 둘 다 해소됐다 — ① 6/22 GCS 이관 **이후** 레거시에 올라온 파일이 버킷에 없었음(736개·393.4MB 복구) ② CKEditor가 삽입한 대문자 `/Uploads`가 소문자만 매칭하는 rewrite를 못 타 404. **둘 다 증분 동기화마다 재발**하므로 재발 방지 절차를 매뉴얼에 정리했다. 이슈에 근거를 남기고 닫았다.
- **동기화 도구 보강** — 기존 전략(APPEND·BACKFILL_PK)은 **기존 행을 절대 건드리지 않아** 레거시 수정을 영원히 놓친다. 실측 결과 숨김 처리(`useflag`)가 반영되지 않아 **526건이 V2에서 계속 노출**되고 있었고, 담당 변호사 배정 51건·전문분야 플래그 63건 등이 누락돼 있었다. `FULL_UPSERT` 전략(PK 기준 전량 업서트)을 추가하고 `--strategy`로 실행 시점에 테이블별로 지정할 수 있게 했다 — TRUNCATE하지 않으므로 **V2 전용 컬럼은 보존**된다. 후처리 스크립트가 `TARGET_DATABASE_URL`을 보게 해 원격 Cloud SQL을 직접 타깃으로 지정할 수 있고, 조사 도구(덮여 사라질 값 프리플라이트·레거시에 없는 V2 행 조회·타깃 스냅샷)와 자산 복구 도구(GCS 누락 전수 대조 → 레거시 원본 다운로드 → 스테이징)를 함께 넣었다. - **Cloud Run 스펙 상향** — 프론트 메모리 로그를 확인하니 `Memory limit of 256 MiB exceeded with 285 MiB used`가 **하루 198건** 찍혀 있었다. 요청이 약 1,000건(대부분 검증용)인 **무트래픽 상태에서 이미 259~285Mi**를 쓰고 있었다 — Next.js standalone의 기본 상주 메모리가 256Mi에 맞지 않는다. 512Mi로 올려 OOM이 0건이 된 것을 확인한 뒤, 실서비스를 감안해 **1Gi + 동시성 80 → 40**으로 조정했다(1 vCPU에 동시 80 SSR은 메모리보다 응답 지연이 먼저 터진다). 백엔드는 OOM 0건이었지만 같은 여유를 두려고 512Mi로 올렸다. 프론트 `00060-zdz` / 백엔드 `00029-m8q`.

**금일 종합:** 컷오버 하루 전날, 남은 구멍을 메우는 데 하루를 썼다. 가장 값이 컸던 건 **레거시 URL 전수 점검**이다 — 레거시 뷰 폴더에서 액션을 뽑아 하나씩 두드려보니 404가 11개 패턴 있었고, 그중 전문센터 상담 URL 6개와 대소문자 정규화는 컷오버 직후 바로 색인 손실로 이어질 것들이었다. 이미지 제보(#4)도 눈으로 확인하는 대신 DB 참조 자산 7,797개를 전수 대조해 "지금은 0건이지만 **동기화마다 재발한다**"는 조건까지 규명한 게 실질이다. 기능 쪽 축은 접수 알림 — 레거시에 아예 없던 기능을 만들면서 웹훅 URL을 DB에 둬 **운영자가 재배포 없이 관리**하게 한 것, 그리고 담당자 피드백을 받아 카드에서 텍스트로 형식을 되돌린 것이 남는다. 인프라에서는 프론트가 조용히 OOM을 치고 있던 것을 로그로 잡아 1Gi·동시성 40으로 정리했다. 배포 빌드가 두 번 깨졌는데 둘 다 **로컬 환경이 오염돼 가려져 있던 문제**였다 — pnpm 락파일과 타입 증강. 앞으로는 CI와 같은 조건으로 `next build`를 돌려 확인한 뒤 푸시한다. 금일 1개 repo에 걸쳐 커밋 33건, 배포 4회, 이슈 13건 정리.
