- **`vh` → `dvh` 전환**: 실기기 모바일은 주소창이 뷰포트를 먹어 `90vh`가 실제 표시 영역보다 크다. 데스크톱 반응형 모드에선 재현되지 않던 종류
- **드롭다운 좌표 공통화**: 포털 드롭다운 12곳이 전부 트리거 밑에 붙이기만 해서, 폼이 긴 화면 아래쪽에선 목록이 화면 밖에 그려져 선택 자체가 불가능. `dropdownCoords()`로 모아 아래가 모자라면 위로 뒤집도록
- **팝오버 상수 높이 제거**: 참석자 팝업이 높이를 상수로 못 박아(`innerHeight - 660`) 실제 높이가 커지면 저장 줄이 화면 밖으로, 브라우저가 상수보다 작으면 값이 음수가 되어 위로 밀려났다. `ResizeObserver`로 실측

**[CRM / 구글 어드민 연동·문자]**
- **개명 미반영 수정**: 어드민에서 `진솔 주임 → 진솔 대리`로 바꿔도 DB가 그대로였다. 변경 감지 로직이 실제 UPDATE문과 어긋나 **이름만 바뀌면 '변경 없음'으로 걸러져 UPDATE가 스킵**되던 것
- **데이터 손상 동시 차단**: 기존 SQL이 `COALESCE(?, 기존값)`이라 UPDATE가 실행되는 순간 근무형태가 `전속 → 정규`, 입사일이 계정생성일로 덮여 썼다. 이름만 고치면 오히려 손상이 늘어나는 구조
- **문자 발신 지역 초기값**: 로그인 직원 지사 고정 → 당사자의 지역지사로. 운영 데이터 실측 **40,210 / 40,972건(98.1%)** 자동 지정
- **403 회피 설계**: 허용된 발신번호 목록 안에서만 매칭해, 스코프 밖 값이 초기값으로 들어가 발송 시점에 막히는 일이 구조적으로 없게

### 11. CRM — 구글 어드민 개명이 DB에 반영되지 않던 문제

- **원인: 변경 감지 로직이 UPDATE문과 어긋나 있었다** — `googleDirectorySyncService.js`의 UPDATE문은 `employee_name = COALESCE(?, employee_name)` 즉 **구글 값이 이기는** 형태인데, "쓸 필요 없음" 판정 함수 `isDirectoryEmployeeUnchanged`는 이 컬럼을 `COALESCE(기존값, ?)`로 착각해 *"DB가 비어 있을 때만 써야 함"*으로 판정했다. 그래서 기존 이름이 있는 상태에서 **이름만** 바뀌면 '변경 없음'으로 걸러져 UPDATE 자체가 스킵됐다. 휴대폰 등 다른 컬럼이 같이 바뀔 때만 우연히 반영되던 상태. (`7d1b60a`)
- **운영 데이터로 재현** — 프록시로 운영 PG(`db=crm`)에 붙어 구글 디렉터리 실시간 값과 대조했다. 디렉터리 108명 / `employee_info` 377행 / 이메일 매칭 108명 중 **이름 불일치 1건**(`임정민 주임` → 구글 `임정민 대리`, 재직). 그 실제 행으로 판정을 돌려 수정 전 `변경없음=true`(스킵), 수정 후 `false`(반영)를 확인했다.
- **컬럼별 소유권 분리** — 구글 소유(`employee_name`·`email`·`gws_id`)는 유입값이 비어있지 않고 DB와 다르면 UPDATE, CRM 소유(`organization_key`·`employee_type_key`·`employment_type`·`hire_date`)는 `COALESCE(기존값, ?)`로 뒤집어 비어 있을 때만 채우게 했다.
- **동시에 막은 데이터 손상** — 기존 SQL은 `COALESCE(?, employment_type)`이라 **UPDATE가 실행되는 순간** CRM 값이 구글 기본값으로 덮여 썼다. 같은 행에서 `employment_type` DB=`전속` / 구글 기본값=`정규`, `hire_date` DB=`2023-06-25` / 구글 계정생성일=`2023-08-08`이었다. 이름만 고치면 UPDATE 빈도가 늘어난 만큼 근무형태·입사일이 조용히 깨지는 구조였다.
- **비정규화 사본 갱신** — `consulting_manager.employee_name`이 이름 사본을 들고 있어 상담담당자 화면에 옛 이름이 남는다. 동기화 후 `employee_key` 기준으로 다른 행만 갱신하는 단계를 추가하고, 테이블이 없거나 실패하면 warn만 남기고 본 동기화는 계속되게 했다. 자동 동기화 로그에 `denormalizedNamesRefreshed` 카운터 추가.
- **반영 경로 확인 및 배포 후 검증** — 웹훅 채널 5종이 계속 갱신 중이고 알림 POST가 200으로 수신되며 실시간 웹훅 + 1시간 폴링이 모두 켜져 있음을 확인했다(`GOOGLE_ADMIN_PUSH_SYNC_ENABLED` / `GOOGLE_ADMIN_AUTO_SYNC_ENABLED`, Cloud Run `minScale=1`이라 폴링 타이머가 유지된다). 배포 후 새 리비전의 폴링이 `updated=27 → 28`로 1건 더 갱신 — 배포 전 스캔의 불일치 1건과 일치. 리비전 `lawwin-crm-00221-qrv`. 이슈 `#2`.

### 12. CRM — 문자 발송 시 발신 지역 초기값을 당사자 지사로

- **원인** — `buildAllowedSmsSenderOptions()`가 발신번호 추천(`isRecommended`)을 **로그인 직원의 `organization_key`**로만 계산하고 당사자는 전혀 보지 않았다. 게다가 당사자 드롭다운(`GET /api/party/consultation/dropdown-party-list`)이 `party_key`·`label`만 반환해 **프론트에 당사자 지사 정보가 아예 없었다**(지사명은 `label` 문자열에 섞여 있을 뿐). (`66dc063`)
- **작업** — 드롭다운 응답에 `source_office`를 추가하고, `sms_form_service.dart`에서 `sourceOffice`를 보존, `sms_form_screen.dart`에 `_senderKeyForOrganization()`·`_applyPartySenderDefault()`를 두어 당사자 선택 시점과 옵션 로딩 시점에 초기값을 맞춘다. 발신 지사가 바뀌면 지사별 문자 양식 목록도 재조회한다.
- **덮어쓰지 않는 경우를 명시** — 사용자가 발신번호를 직접 고른 뒤에는 당사자를 바꿔도 유지(`_senderManuallySelected`), 편집·재발송으로 이미 발신번호가 정해진 문자도 유지, 해당 지사 발신번호가 허용 목록에 없으면 기존 로직으로 폴백.
- **403 회피 설계** — `resolveAllowedSmsSenderKey()`가 사용자 조직 스코프 밖 발신번호를 403으로 막으므로, 매칭을 프론트가 이미 들고 있는 `_senderOptions`(서버가 스코프 필터링해 내려준 목록) **안에서만** 수행했다. 스코프 밖 값이 초기값으로 들어가 발송 시점에 막히는 일이 구조적으로 없다.
- **운영 커버리지 실측** — 발신번호 11개 기준 **40,210 / 40,972건(98.1%)** 자동 지정. 폴백 762건 중 694건이 제주지사(`SMS_SENDER_CONFIG`에 `jeju` 항목·`NCP_JEJU_*` env 부재), 나머지 68건은 마케팅팀·경영지원실 등 내부 조직. 우려했던 `source_office`가 `organization_key`가 아닌 케이스는 `party_detail`에 없었다(빈값 1건). `flutter analyze` 전체 통과. 이슈 `#3`.
- **부수 발견 — 피커 키 공급 경로가 전환됐다** — 프론트 배포에 현행 `docs/cloud-run-build-rule.md`대로 `--dart-define` 없이 빌드했더니, 배포 번들에 빌드타임 API 키가 없어 **본 서버도 서버 폴백이 유일한 경로**가 됐다. 이슈 `#1`이 "테스트에서 확인 후 전환"으로 계획했던 순서가 뒤바뀐 상태라, 실사용 확인을 우선 항목으로 올리고 롤백 절차를 함께 기록했다(운영 백엔드에 `GOOGLE_PICKER_API_KEY`는 설정돼 있어 조건 자체는 충족). 이슈 `#1` 갱신.
