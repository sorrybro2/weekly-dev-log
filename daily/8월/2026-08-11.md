### 1. 홈페이지 V2 — 도메인 롤백 및 `bslawwin.co.kr` 이전 (이슈 `#104`)

- **롤백 수행** — 8/6 컷오버로 `www.lawwin.co.kr`이 V2(Cloud Run)를 서빙하고 있었으나, **SEO 노출과 AI 인용이 끊겼다는 광고대행사 보고와 경영 판단으로 레거시로 되돌렸다.** 가비아 A 레코드(`www`, `@`)를 `35.186.226.100`(GCP ALB) → `139.150.69.177`(레거시 IIS)로 변경하고, 공개 DNS(8.8.8.8) 반영과 **레거시 IP 직접 호출 시 Next.js 흔적 0건**으로 레거시 정상 서빙을 확인했다. 넘기기 전에 레거시 서버 상태를 실측했다 — HTTPS 200, 응답 0.12~0.17초, 인증서 `CN=lawwin.co.kr`(Sectigo) 2027-03-06까지 유효, robots.txt 전면 허용 + 지사별 사이트맵 10개. **Cloud Run·ALB·Certificate Manager·GCS는 전부 유지**했다. V2를 별도 도메인에 올릴 예정이라 그대로 재사용하기 위한 판단이었고, 실제로 이후 새 도메인이 그 자원을 그대로 물려받았다.
- **새 도메인 구축** — Certificate Manager에 DNS authorization `bslawwin-auth`를 만들고 인증서 `bslawwin-cert`(`bslawwin.co.kr` + `*.bslawwin.co.kr`)를 발급해 기존 인증서 맵 `lawwin-cert-map`에 항목 2개를 추가했다. DNS는 A 레코드 `@`/`www` → `35.186.226.100`, `_acme-challenge` CNAME은 갱신용으로 유지. **URL map은 손대지 않았다** — `defaultService`가 이미 모든 호스트를 Cloud Run 백엔드로 보내는 구조라 호스트 규칙 추가가 불필요했다. 애플리케이션 쪽은 두 곳이 걸렸다: **백엔드 `CORS_ORIGIN`에 새 도메인 2개 추가**(`api-00039-xhk`) — 이걸 안 하면 브라우저→API 호출이 전부 차단돼 **상담 접수가 통째로 안 된다**. 응답에서 `access-control-allow-origin` 헤더가 빠진 것을 실측으로 먼저 확인한 뒤 조치했다. 그리고 프론트 `AUTH_URL` → `https://bslawwin.co.kr`(`00088-6j7`) + 구글 OAuth 리디렉션 URI 추가(콘솔 작업). **`AUTH_URL`은 8/6 컷오버 때도 걸렸던 항목**이라 이번엔 사전에 목록에 넣어두고 처리했다.

### 5. 홈페이지 V2 — 색인·접근성 조치 (이슈 `#102`, `#91`)

- **알림에서 문의 상세로 직행** — 담당자가 구글챗 알림에서 바로 원문·답변 화면으로 들어갈 수 있도록 본문에 한 줄을 추가했다. 일반 상담은 `/admin/contact/{listindex}`, **전문센터 상담은 `/admin/ctlist/{listindex}`로 경로가 갈린다**(`ConsultService`의 `type` 분류와 같은 기준). 기준 주소는 `ADMIN_SITE_URL`로 두되 **미설정이면 운영 도메인을 쓰도록 기본값을 지정**해 Cloud Run에 env를 추가하지 않아도 동작하게 했다. 어드민 "테스트 전송"에는 이 줄이 나오지 않는다 — 실제 접수 건이 아니라 가리킬 상세 페이지가 없다. 한 스페이스를 여러 지사가 같이 쓸 때의 등록 방법도 대상 판정 주석에 명시했다. ### 7. 홈페이지 V2 — 표기 통일 및 대표 수치 (이슈 `#105`)

- **"해결 사례" → "수행 사례" 23곳** — 경영 요청. 승소한 것만 골라 보여준다는 오해를 줄이고 실제 수행 규모를 가리키는 표현으로 바꿨다. 메인 히어로 통계·검색 placeholder·CTA(`hero-cinematic.tsx`), 메인 사례 섹션·메타 설명(`page.tsx`), 사례 목록·상세 제목과 JSON-LD 라벨(`cases/page.tsx`·`cases/[id]/page.tsx`), 메가메뉴(`site-nav-data.ts`), 전문센터(`center-faq.ts`·`center-page-body.tsx`), **답변엔진용 경로 9곳**(`llms.txt/route.ts`), FAQ 구조화 데이터(`home-faq-jsonld.tsx`)까지 적용했다. 변호사 상세(`lawyer-stage.tsx`)는 라벨만 바꾸고 **건수는 개인 실집계를 유지**했다.
- **대표 수치를 기준연도와 함께** — **19,000건+ (2025년 기준)**으로 표기하고 기준 시점을 수치 옆에 회색·작은 글씨로 병기했다. **DB 값을 안 쓴 이유**가 핵심이다 — `/api/main-counts`의 `wincount`는 **홈페이지에 게시된 사례 수**(현재 3,308건)이고 실제 수행 건수는 그보다 훨씬 많은데, 게시 수만 내보내면 규모를 축소해 보이게 한다(전문센터 페이지에서도 같은 이유로 게시 건수 노출을 이미 내려둔 상태였다). 대신 **기준 시점 표기를 필수로 남겼다** — 근사치이자 특정 시점 집계라는 점이 화면에서 드러나지 않으면 과장 표기로 읽힌다. `frontend/src/lib/firm-stats.ts`를 신설해 값·기준 문구·라벨을 한곳에서 관리한다. 히어로·메인 사례 섹션·FAQ JSON-LD가 같은 값을 써야 하는데 흩어두면 한쪽만 고쳐져 수치가 어긋나므로, **도메인 하드코딩이 16곳에 퍼져 있던 것(`#104`)과 같은 실패를 반복하지 않으려는 조치**다. **누적 상담(52,700건+)은 종전대로 DB 값**이라 두 수치의 출처가 다르다는 점과 갱신 시 `PERFORMED_CASES`·`PERFORMED_CASES_BASIS`를 함께 고쳐야 한다는 제약을 주석에 명시했다. 검증은 `tsc --noEmit` 통과 + 배포까지이며, **표기 톤(회색 병기 위치·크기)의 실물 확인은 아직 받지 않았다.** (`f7b3e7e`)

### 8. 홈페이지 V2 — 메인 섹션 개편 설계 조사 (이슈 `#88`, 구현 미착수)

- **전문센터·지식센터 섹션 — 탭 축 결정** — 레거시 홈처럼 왼쪽에 분야 목록을 세우고 클릭하면 오른쪽 콘텐츠가 바뀌는 구성을 요청받았다. 현재 메인은 `히어로 → 변호사 → 사례 → 미디어 → 사무소 지도`로 **전문센터 7개가 상세 페이지로만 존재하고 메인에서 존재감이 없으며, 지식센터도 미디어 섹션 안에 섞여** 있다. 문제는 **전문센터(7개)와 상담폼 사건영역(8개)이 서로 다른 축**이라 무엇을 탭으로 쓸지였는데, **실제 사례 데이터를 세어보니 레거시 사이드바 체계와 사실상 동일한 10개**가 나왔다(`tbl_bbs.catearray`의 `KeyIndex:1`, `typeindex=1 AND useflag='Y'` 기준: 경제지능 826 / 일반형사 815 / 성범죄 805 / 민사·가사 289 / 음주·교통 265 / 행정·기업 148 / 손해배상 139 / 회생·파산 121 / 소년범죄 91 / 마약 73). 이걸 축으로 쓰는 것이 맞다고 판단했다. **부수 발견 — `center-data.ts`의 `caseCateIndex` 누락 3건**: `traffic`·`recovery`·`school` 세 센터가 비어 있어 **센터 상세의 "관련된 사건사례"가 그동안 안 채워지고 있었다**(traffic=3, recovery=10, school=70을 넣으면 된다. 이 작업과 독립적이라 먼저 채워도 즉시 효과). **제약 2개**: ① 가장 큰 두 분야(경제지능·일반형사)와 손해배상에 **전문센터가 없어** 탭은 세울 수 있지만 "센터 소개" 링크가 없다(사례 더보기만 걸어야 한다). ② **지식센터는 분야별로 나눌 수 없다** — `typeindex=2` 글에 `KeyIndex:1` 분야 태그가 **0건**이라 분야 필터가 원천적으로 불가능하므로 최신순 별도 섹션으로 가야 하고, 분야별로 묶으려면 기존 803건 재태깅이 선행돼야 한다. 구현은 `lawyers-tabs.tsx`가 이미 같은 탭 패턴(썸네일 스트립 + 선택 시 내용 교체)이라 재사용하면 톤이 맞고, 센터 상세의 관련 사례 블록이 `?cate=` 필터로 사례를 끌어와 데이터 경로도 이미 있다.
- **메인 섹션 스크롤 스냅(PPT 넘김) 요청 검토** — 히어로 → 변호사 → 사건들 → media까지 스냅하고 office부터는 자유 스크롤을 원하는 요청이다. **지금 구조는 스냅을 의도적으로 배제한 상태**이고 근거가 코드에 남아 있다 — `globals.css`에 "홈은 시네마틱 스크롤(scroll-snap 미사용)", `page.tsx` 헤더 주석에 "풀스크린 스냅 없음". 방향을 바꾸는 결정이므로 주석도 함께 갱신해야 한다. 선행 확인한 사실 셋: **Lenis 미사용**(코드에 흔적 0, 스무스 스크롤은 CSS `scroll-behavior`만 → **CSS scroll-snap과 충돌할 라이브러리가 없다, 유리한 조건**), **섹션에 고정 높이가 없다**(`min-h-screen`/`h-screen` 0건, 히어로만 `min-h-[88vh]`), **`section-dot-nav.tsx`가 이미 있으나 미사용**(스냅을 넣으면 되살려 현재 장면 표시에 쓸 수 있다). **핵심 난점은 높이**다 — PPT 넘김이 성립하려면 각 장면이 한 화면에 들어와야 하는데 변호사(썸네일 22명)·사건들(통계 + 카드 4장 + **카테고리 탭 추가 예정**)·media(3컬럼)가 화면을 넘긴다. 내용이 화면보다 길면 `mandatory` 스냅은 **읽던 중간이 잘리거나 스크롤이 튀고**, 모바일·세로 모니터에서 특히 심해 반응형 4기준 정책과 충돌한다. 그래서 **`proximity` + 앞 4개 섹션만 정렬**(요청의 "office부터 스냅 끊김"과도 맞는다), **`100svh` 기준 재구성**, `scroll-padding-top: 5rem`(고정 헤더)과의 상호작용 확인, `prefers-reduced-motion`에서 스냅 해제, `SectionDotNav` 복원을 제안했다. **작업 순서는 ① `caseCateIndex` 3건 → ② 카테고리 탭·지식센터 섹션 → ③ 스냅** 순이어야 한다 — 섹션 내용이 확정된 뒤 높이를 맞추는 순서여야 두 번 일하지 않는다. 미결정 사항(탭 10개 한 줄 노출 여부, 카드 3장 vs 4장, 센터 없는 3개 분야 처리, 스냅 적용 범위)은 이슈에 남겼다.

### 9. 사건관리 앱 — 수기일정 Drive 링크 첨부 파일명·형식

- **Drive 링크로 첨부한 파일이 "첨부 파일"로만 표시되던 버그** — 수기일정에 Drive 링크로 파일을 첨부하면 **복사본의 이름·형식을 조회하지 않아** 캘린더 첨부에 `"첨부 파일"` 리터럴만 들어가고 목록의 `file_name`도 비어 있었다. **PC 업로드 경로만 파일명을 채우고 있던** 상태다. `google_drive.get_file_meta()`로 Drive 파일의 `name`/`mimeType`을 조회하고, `add_file_attachment_to_event()`가 `mime_type` 파라미터를 받아 첨부 객체에 실어 **캘린더가 형식에 맞는 아이콘을 표시**하게 했다. Drive 링크 첨부 시에는 `webViewLink`에서 복사본 ID를 뽑아 메타를 조회하고 그 이름·형식을 `row.file_name`과 캘린더 첨부에 함께 사용한다. **기존 이벤트의 "첨부 파일" 표기는 소급 수정되지 않는다**(백필 별도). (`bf21b4e`)

**금일 종합:** **오전과 오후의 작업 방향이 정반대가 된 날이다.** 오전에는 V2를 운영으로 두고 전환 추적을 되살리는 작업(서울 컨테이너 게시, 광주 분석)을 하고 있었는데, 오후에 `www`가 레거시로 롤백되면서 그 전제가 사라졌다. 그래서 남은 시간은 **되돌리기와 옮기기**에 들어갔다 — 롤백 자체는 DNS 한 줄이지만, 그 뒤에 붙는 일이 훨씬 많았다. **가장 값이 컸던 발견은 도메인이 16개 파일에 하드코딩돼 있었다는 것**이다. 새 도메인에 V2를 올려도 `robots.txt`가 `Disallow: /`이고 canonical이 이전 도메인을 가리켜 **색인이 원천적으로 불가능한 상태**였고, 그중 canonical이 결정적이었다 — robots만 열어도 소용이 없다. 이걸 `lib/site.ts` 한 곳으로 모으면서 **정적 생성 페이지가 모듈 상수를 빌드 시점에 굳힌다**는 점 때문에 런타임 env로는 부족해 build-arg까지 내려야 했던 것이 이번의 실무적 교훈이다. 같은 교훈이 오후 마지막 작업에서 한 번 더 나왔다 — 대표 수치를 `firm-stats.ts` 한 곳으로 모은 이유가 정확히 "도메인이 16곳에 퍼졌던 실패를 반복하지 않기"였다. **전환 추적 쪽은 롤백에도 성과가 남았다.** 서울을 복구하려다 **네이버 전환 태그 11개가 2개월간 전부 일시중지**였다는 것을 찾았고, 광주를 보다가 **링크 클릭 트리거에 `Form URL` 조건이 걸려 원래부터 발화하지 않았다**는 것 — 즉 리뉴얼이 원인이 아닌 부분이 있었다는 것 — 을 확인했다. 그래서 지사별로 트리거를 고쳐 나가는 대신 **전환 5종을 전부 코드에서 발화하도록 바꿔** GTM이 화면 구조를 참조하는 구조 자체를 걷어냈고, 결과적으로 남은 세 지사 작업이 동일한 절차로 단순해졌다. **데이터 이관은 성격이 달랐다.** 42건이라는 건수는 작지만 시간대 9시간 차·번호 충돌·IPv6 컬럼 길이가 각각 다른 층의 문제였고, 특히 시간대는 **레거시 마이그레이션이 한국시간을 UTC 라벨만 붙여 옮겼다는 과거 사실**을 기존 행 3개로 대조해야 드러났다. 마지막으로 남긴 리스크 정리가 실제로는 가장 중요한 산출물일 수 있다 — **신·구 도메인이 같은 내용이면 노출이 2배가 되지 않고 신규 도메인이 밀린다**는 점은 색인을 여는 조치의 기대치 자체를 바꾸는 사실이라 대행사와 먼저 맞춰야 한다. 금일 2개 repo에 걸쳐 커밋 9건, 이슈 신규 2건·진행 코멘트 9건.
