### 2. 홈페이지 V2 — GSC 색인 17.8만 미색인 분석 (이슈 `#102`)

- **사유별 분류로 조치 대상 확정** — 컷오버(8/6) 후 색인 9만 / 미색인 17.8만(178,397건)이었다. 사유별로 뜯어 **실제 조치가 필요한 것 2건**, **이미 해소돼 재크롤만 기다리는 것 13,450건**(NOINDEX 13,397 + 5xx 53 — GSC가 본 시점이 컷오버 당일과 레거시 IIS 시절이다), 나머지는 정상 분류로 판정했다. 리디렉션 7,342건과 중복 591건은 라이브에서 직접 두드려 301 정상 동작·canonical 정상임을 확인했다.
- **필터·페이지 조합 주소 크롤 차단** — "적절한 표준 태그가 포함된 대체 페이지" 45,544건 샘플이 전부 `/{지역}/cases?lawyer=102&cate=66`, `/{지역}/knowledge?page=22` 모양이었다. 지역과 필터가 곱해져 **사실상 무한히 생성되는 주소가 4만5천여 개 크롤되는 동안 실제 글이 색인되지 못하고** "크롤링됨 - 미색인" 9.6만·"발견됨 - 미색인" 1.3만으로 밀려 있었다. 표준 주소 지정은 색인 단계에서만 작동해 크롤 자체를 막지 못하는 것이 원인이므로, `robots.ts`에서 목록 화면의 카테고리·변호사·페이지 조합 주소를 차단하고 답변엔진용 크롤러 규칙에도 같은 목록을 적용했다. 상세글은 전부 사이트맵에 실려 있어 페이지 넘김을 막아도 발견 경로는 끊기지 않는다. - **살아 있는 글이 옛 주소에서 404 나던 버그** — `/suwon/newsdetail?index=7871`이 301로 `/suwon/news/7871`까지 가서 404였다. 7871번 글은 살아 있고 `typeindex=2`(지식센터)라 `/knowledge/7871`에 있다 — 레거시 시절 뉴스로 발행됐다가 V2 이관 때 재분류된 글이라 `legacy-redirects.ts`의 액션명 매핑(`newsdetail → news`)이 목적지를 맞히지 못한다. 미들웨어는 DB를 볼 수 없어 그 단계에서는 해결이 불가능하다. `lib/bbs-section.ts`를 새로 두고 **상세 페이지가 글을 읽은 뒤 종류가 경로와 다르면 404 대신 실제 경로로 영구이동(308)** 하도록 사건·지식·후기·뉴스 4개 상세 화면에 동일 적용했다. 이동 시 지사 접두사를 유지해 지역 주소가 풀리지 않게 했고(`/seoul/news/7871 → /seoul/knowledge/7871`), **비공개(`useflag=N`)로 내린 글은 그대로 404를 유지**해 되살아나지 않게 했다 — 404 샘플 10건 중 8건이 이 경우로 404가 정상이었다. 없는 글을 목록으로 보내는 방식은 구글이 soft 404로 처리해 더 나빠지므로 채택하지 않았다. (`0a548eb`)
- **대문자가 섞인 옛 지사 주소 404** — 레거시 IIS는 주소 대소문자를 구분하지 않아 대문자가 섞인 주소도 정상 동작했는데, `legacy-redirects.ts`가 지사 이름 부분만 대소문자를 그대로 비교해 그런 주소가 전부 404로 빠지고 있었다. 지사 이름도 소문자로 맞춰 인식하고 이동 대상은 항상 소문자 주소로 보내며, 지사 이름만 있는 주소도 소문자로 이동하게 했다. 이미 소문자인 정상 주소는 이동시키지 않아 무한 리다이렉트가 생기지 않는다. (`28859de`)

### 8. 사건관리 앱 — 수발신문서·열람/등사 기능

- **수발신문서 첨부에 Drive 폴더 추가** — 파일 여러 개를 모아둔 폴더 전체를 첨부하고 싶은 경우가 대응되지 않았다. 폴더를 링크로 첨부할 수 있게 해 **폴더 내용이 나중에 바뀌어도 링크가 항상 최신을 가리키고, 파일 수십 개가 대장에 쏟아지지 않게** 했다. 파일 선택과 버튼을 분리했다(Drive 파일 / Drive 폴더 / PC 업로드) — 결과가 다르고(파일은 사건 폴더로 사본이 복사되지만 폴더는 링크만 남는다), 한 Picker에서 폴더 선택을 켜면 폴더를 열려다 선택되는 오조작이 잦아 기존 파일 선택 동선까지 망가진다. 폴더 Picker에는 공유드라이브 뷰도 추가했다 — `SUPPORT_DRIVES` 기능 플래그는 Picker 전체의 공유드라이브 지원을 켜는 것이고 실제로 목록에 띄우려면 뷰의 `setEnableDrives(true)`가 필요해 그동안 내 드라이브만 보였다. 기존 내 드라이브 뷰는 그대로 둬 사건 폴더 선택(`CaseFormPage`)에는 회귀가 없다. **백엔드 변경 없음** — `_sync_drive_files`가 폴더 URL을 이미 복사 대상에서 건너뛰고(`extract_file_id`가 None), 메일 첨부는 원래 MIME 첨부가 아니라 링크 목록이라 폴더 링크도 그대로 나간다. 저장 payload는 실제 파일을 폴더보다 앞에 정렬해, 백엔드가 첫 첨부를 대표 링크(`drive_url`)로 잡아 목록 Drive 배지가 폴더를 가리키는 것을 막았다. ### 9. 사건관리 앱 — 크롤러 웜서비스 자가복구 (이슈 `#269`)

- **고착된 브라우저를 스스로 재기동** — 웜 컨테이너(`minScale=1`)에서 요청 사이 CPU가 회수되면 기동 시 한 번 띄워둔 Chromium이 고착돼 `page.goto`가 `networkidle`에 도달하지 못하고 30초 타임아웃이 났다(8/10 `/crawl-single` **요청 18건 전부 500**). 타임아웃 시 브라우저를 새로 띄우고 1회 재시도하도록(`_restart_browser`) 하고, 동시 요청이 중복 재기동하지 않도록 lock + stale 비교로 가드했다. 최종 실패 시에는 uvicorn 기본 500 대신 **503 + 사용자용 안내 문구**를 반환하고, 굳은 브라우저에서 `page.close()`가 매달리지 않도록 5초 제한을 뒀다. 탭 열기~크롤 구간을 `_open_and_crawl`로 분리해 재시도 경로에서 재사용한다. 서비스에는 `--no-cpu-throttling`도 함께 적용(리비전 00061), 본 코드는 00062로 배포했다. (`01b6db9`)

Cloud Run 로그에 nginx worker 로그가 찍힌 것으로 컨테이너가 **uvicorn이 아니라 nginx**임을 확인했다 — `gcloud run deploy --source=.`가 루트 `Dockerfile`(프론트+백 통합, uvicorn)이 아니라 `frontend/Dockerfile`(nginx 정적 서빙)을 집어 빌드했다. 레포에 Dockerfile이 9개 있고 배포 로그는 "Building using Dockerfile"이라고만 찍혀 어느 것인지 알 수 없었다. **프론트 파일만 바뀐 배포에서 백엔드가 통째로 사라진 것**이 소스가 아니라 이미지가 다르다는 힌트였다. 조치는 ① 이전 리비전(`lawwin-case-00136-g8p`)으로 트래픽 100% 롤백해 즉시 복구, ② 루트 Dockerfile을 명시적으로 빌드한 뒤 `--image`로 배포해 정상화(`00138-dmq`, `/health` → `{"status":"ok"}`, `/api/notifications` → 401 JSON). 재발 방지로 **`--source=.` 금지 + 빌드·배포 2단계 + 배포 후 검증**을 이슈에 절차로 남겼다(이번에 검증을 하지 않아 장애를 늦게 잡았다). 이슈 `#298`.

**금일 종합:** 계획된 기능 작업보다 **운영에서 터진 것을 잡는 데 시간이 더 들어간 날**이다. 사건관리 API 27분 다운과 홈페이지 6분 39초 500은 원인이 전혀 다르지만(잘못된 이미지 배포 / Cloud SQL 커넥터 순간 장애) 증상이 같은 방식으로 사람을 속였다 — 앞의 것은 화면 에러가 엉뚱한 파일을 가리켰고, 뒤의 것은 제보가 "버튼을 누를 때"로 들어왔다. 둘 다 **화면에서 보이는 실패 지점과 실제 원인이 다른 층에 있었고**, 로그를 층별로 대조해야 드러났다. 공통 교훈도 겹친다 — **"배포·기동이 됐다"가 "제대로 떠 있다"를 보장하지 않는다.** 앞의 것은 배포 후 검증이 없어 27분을 흘려보냈고, 뒤의 것은 기동 실패를 흡수할 재시도가 없어 수 초짜리 네트워크 장애가 6분 다운으로 증폭됐다. 그래서 조치도 같은 방향으로 갔다: 배포는 이미지 명시 2단계 + 사후 검증으로, 기동은 재시도 + 실패해도 죽지 않기로. 계약 등록 500도 뿌리가 비슷하다 — 스키마·마이그레이션은 들어왔는데 모델만 빠져서 **DB만 봐서는 정상으로 보이는** 상태였고, 그래서 사람이 눈으로 확인하는 대신 정합성 검사를 붙여 기동 로그에서 잡게 했다. 껍데기 기초사실은 "실패해도 앞 단계가 남는다"는 같은 결의 문제였고, 롤백과 목록 제외를 동시에 넣어 새로 생기는 것과 이미 쌓인 것을 함께 막았다. 색인 쪽은 성격이 다르다 — 미색인 17.8만이라는 숫자 자체보다 **사유별로 뜯어 조치 필요 2건과 재크롤 대기 1.3만건을 갈라낸 것**이 실질이었고, 크롤 예산을 먹던 필터 조합 주소 4만5천여 개를 막은 것이 이후 색인의 조건을 바꾼다. 금일 2개 repo에 걸쳐 커밋 16건.
