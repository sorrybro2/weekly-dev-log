# 주간 업무 회고 (9월 2주차)

> 이번 주는 월~금 5일 전부 작업(9/7~9/11). 커밋 86건(머지 8건 포함) — 사건관리 앱 49건, CRM 17건, 사내 포털 16건, 홈페이지 V2 4건, 인프라 repo 0건. 신규 이슈 22건, 이슈 코멘트 53건. 주의 축은 셋이었다 — **세 코드베이스에 흩어져 있던 같은 인증 결함을 같은 주에 정리한 것**, 화면 갱신 방식을 놓고 **자기 근거를 세 번 다시 재서 결론을 뒤집은 것**, 그리고 **로컬에 없는 계층에서만 터지는 장애를 다섯 건 규명한 것**이다.

## 1. 주요 업무 성과 (Key Achievements)

**이번 주의 시작은 지난주 회고의 마지막 줄이었다.** 9월 1주차 향후 과제에 "`prompt=consent` 조치를 CRM·사건관리에도 확장"이라고 적어 둔 것을 수요일부터 실제로 집행했고, 금요일에는 세 앱(사내 포털·사건관리·CRM)을 **같은 날 사일런트 인증(`prompt=none`)으로 통일**했다. 서로 다른 언어와 프레임워크로 짜인 세 제품이 "브라우저에 구글 세션이 있는지 모르는 채 구글로 넘긴다"는 동일한 전제를 공유하고 있었고, 그 대가로 세션 없는 사용자는 우리 로그인 화면을 한 번도 보지 못한 채 구글 페이지에 떨어졌다. 두 번째 축은 **화면 갱신 방식**이었는데, 이 주제 하나로 월요일부터 금요일까지 결론이 세 번 바뀌었다 — 월요일에 웹소켓을 "월 $5 대 $21"이라는 근거로 보류시켰고, 화요일에 그 $5가 **요청 수만 센 값**임을 발견해 다시 재다가 gzip을 빼먹어 또 틀렸고(월 130만원이 나왔다), 수요일에는 egress 단가 자체가 `$0.12/GB`로 잘못 적혀 있던 것(실제 한국행 Premium tier `$0.19/GiB`)과 60명 기준을 확인하며 **보류 결정을 통째로 뒤집어 SSE 전면 전환**을 했다. 같은 주 금요일 CRM에서는 반대로 **SSE를 기각**했는데, 두 앱의 인프라 구조가 달라 같은 계산이 성립하지 않기 때문이다. 세 번째 축은 **운영에만 존재하는 계층**이다 — SSE가 로컬에서 완벽히 동작하는데 운영에서만 붙지 않던 원인 3건(gzip 압축 대기, `is_disconnected` 오작동, Firebase Hosting 버퍼링), 사내 포털 이관 후 `0.0.0.0:8080`이 만든 결함 3연속, 그리고 마지막에 드러난 **Firebase Hosting의 쿠키 제거**까지 다섯 건이 전부 로컬에 없는 계층에서 났다. 그 사이 사내 포털을 Vercel에서 Cloud Run으로 옮겨 월 $20 고정비를 무료 한도 안으로 넣었고, CRM에는 회생팀 요구(상태 체계 재정의, 채권자수·진행내역 컬럼)를 반영했다.

- **인증: 세 앱의 같은 전제를 걷어내고 사일런트로 (9/10~9/11, 이슈 `#11`·`#12`·`#524`)**

    - **원인이 한 줄씩이었다:** CRM은 `prompt: 'consent'`, 사건관리는 `prompt=select_account`. 값은 다르지만 **"기존 구글 세션을 무시하고 화면을 띄워라"는 같은 지시**다. 제거하니 동의 이력이 있는 사용자는 화면 없이 콜백으로 되돌아온다 (`c7be844`·`f835fa8`)
    - **로그인 버튼 클릭도 제거:** JWT가 없으면 버튼을 기다리지 않고 즉시 구글로 보낸다. 사건관리는 StrictMode 이중 실행을 피해 판단을 렌더 전 모듈 스코프로 뺐다 (`94f62f1`)
    - **로그아웃 가드는 선택이 아니라 필수 — 두 앱에서 같은 함정:** 가드가 없으면 로그아웃 직후 로그인 화면이 곧바로 재인증을 걸어 **로그아웃이 영구히 불가능**해진다
    - **🔴 자체 버그 1건, 30분 내 재배포:** CRM 자동 로그인 게이트를 `lastLoginEmail != ''`로 걸었는데 이 키는 **이 기능 배포 이후의 로그인에서만** 생긴다 → 기존 사용자 전원이 차단된 채 한 차례 배포됐다. 힌트일 뿐인 값을 필수 조건으로 쓴 실수 (`c997877`)
    - **금요일 — `prompt=none`으로 세 앱 통일:** 구글이 화면을 일절 띄우지 않고 즉답한다(세션 있으면 code, 없으면 `error=login_required`). iframe 사일런트 인증은 `X-Frame-Options`·3자 쿠키로 막히지만 **최상위 리다이렉트는 두 제약 모두 비대상** (`c1c0cbf`·`7f4d92d`·`8f8a010`·`2c83ada`)
    - **"거절은 실패가 아니다"를 세 곳 같은 표로:** `login_required`류를 오류 문구 없이 통과시키고, 사유별로 버튼이 계정 선택을 건너뛸지 결정. 계정 선택을 유지하는 예외 2개(로그아웃 직후·인증 실패 복귀)도 세 앱 동일 (`9c7155b`)
    - **탭 복귀 재시도 — 채택 후 같은 날 철회:** `visibilitychange`로 재시도를 붙였다가(`d1e6385`) 띄워놓고 보니 **탭을 옮겼다 왔다는 이유만으로 화면이 구글로 날아갔다.** 사용자가 누르지 않은 화면 전환을 만들지 않는 쪽으로 선회 (`4839051`)
    - **8시간 세션아웃 유지 확인:** 토큰 갱신 엔드포인트가 없어 8시간마다 반드시 구글을 왕복한다. 실질 재인증 주기는 우리 8시간이 아니라 **구글 워크스페이스의 4시간 세션 정책**이 정한다는 것을 코드 근거로 확인

- **실시간 갱신: 폴링 → 변경 가시화 → SSE 전면 전환 (9/7~9/9, 이슈 `#186`·`#518`)**

    - **⭐ 월요일 — 기술 대신 인지를 올렸다:** 웹소켓은 Cloud Run이 연결 유지 시간을 활성 단가로 과금해 "14초를 월 3~9만원과 중계 인프라로 사는 거래"라 판단해 보류. 대신 폴링 범위를 넓히고 **새 행(초록)·바뀐 행(주황)** 을 색으로 표시 (`a346600`·`d9606cd`·`1124aaf`)
    - **CRM에서 먼저 검증하고 사건앱으로 옮겼다:** CRM이 폴링조차 0건이라 여기서 만들며 **릴리즈 빌드에서만 표 행이 안 그려지던 잠복 버그**와 강조 깜빡임을 털어낸 뒤 설계만 이식 (`b6f4e0c`·`76c29b8`·`9e91ce6`·`cc1f815`)
    - **화요일 — 6화면 확대·완료·머지:** 법원진행내역·미수금·상담료(목록+대기열)·열람등사·문서대장·결재함. **크롤러가 채우는 화면**이 이 이슈의 정중앙이었다 (`576f482`·`bef5820`·`629e022`)
    - **🔴 근거 숫자가 두 번 틀렸다:** `#186`의 "월 $5"는 요청 수만 센 값 → 응답 크기로 재니 월 130만원 → 그것도 `GZipMiddleware`를 빼먹어 틀림 → 세 번째 실측으로 **월 $20~25** 확정. 주기를 20초로 통일하고 실측 표와 판단 규칙을 `lib/polling.ts` 주석에 박았다 (`4a82f9a`)
    - **⭐ 수요일 — 보류 결정을 뒤집었다:** 단가가 `$0.12/GB`로 잘못 적혀 있었고(실제 `$0.19/GiB`, 서울은 Tier 2), 60명이 20초마다 각자 4개를 조회하면 **폴링도 이미 업무시간 내내 활성 단가**다. 즉 웹소켓 보류 근거는 폴링도 내고 있던 비용이었다 → 실시간 전환이 오히려 싸다

    - **업무시간 예열창 08:30~19:30:** 야간·주말 인스턴스 해제로 월 약 $13 절감. **`--min-instances`가 리비전 레벨이면 토글마다 SSE 연결이 전원 끊기므로** 반드시 서비스 레벨이어야 했다 (`efa7dda`·`18ca42c`·`8b014c7`)

- **사내 포털: Vercel → Cloud Run 이관, 월 $20 → $0 (9/11, 이슈 `#11`·`#13`·`#14`)**

    - **고정비를 걷어냈다:** Vercel Pro $20/월 중 실제 컴퓨트는 $0.84였고 나머지는 이미 GCP에 내는 것을 한 번 더 사는 플랫폼 요금. Hobby는 상업적 이용 금지라 더 싼 등급이 없었다. 서울 리전 기준 84명 × 하루 8회는 무료 한도의 요청 3%·메모리 16% (`4a33434`)
    - **DB가 없어서 가능했던 선택:** 세션은 JWT 쿠키, 조직도는 30KB JSON 하나. 사건관리앱은 Cloud SQL을 상시 물고 있어 같은 계산이 성립하지 않는다는 것을 이슈에 근거로 남김
    - **저장소를 3중 어댑터로:** `ORG_BUCKET`이면 GCS, `BLOB_READ_WRITE_TOKEN`이면 Vercel Blob, 없으면 로컬 파일. **Vercel 경로를 걷어내지 않고 남겨** 되돌릴 여지를 뒀다
    - **🔴 `0.0.0.0:8080`이 세 번 연달아:** standalone 서버가 헬스체크용으로 `0.0.0.0`에 바인딩해 `redirect_uri`가 새어나갔다. **앱은 멀쩡히 뜨고 로그인만 전부 실패**하는 형태라 세 번 다 발견이 늦었다 (`4a33434`·`240d733`·`d3d8b55`)
    - **⭐ 마지막 원인은 호스트가 아니었다:** 진입점을 정규 호스트로 모은 뒤에도 `InvalidCheck: pkceCodeVerifier` 500이 남았고, 재현으로 **Firebase Hosting이 `__session` 외 요청 쿠키를 전부 제거**한다는 것이 확정됐다(공식 문서에 명시된 동작). 쿠키 묶음을 비공개 GCS 스냅샷에 두고 브라우저에는 **256비트 임의 식별자만** 내보내는 브리지로 해결 (`eb980c0`)
    - **저장소 오류를 익명으로 만들지 않음:** 404만 "없음"으로 보고 나머지는 던진다 — GCS 장애가 조용히 로그아웃으로 둔갑하면 안 되므로

    - **회생 상담 접수 창구를 본사로 단일화:** 헤더 지사 선택을 따라가지 않게 처리하고 폴백을 남김 (`a313dd2`)
    - **상담봇 스펙 확정:** 검색 점수 합산 규칙·본문 분할 단위(300~800자 문장 경계 + 100자 겹침)·품질 측정 지표, 지시문 차단 3층 (`282e244`)

- **운영·보안 조치 (커밋 없음 또는 인프라)**

    - **🔴 공휴일 API 키 두 번째 유실 — 시한폭탄:** 키가 없으면 앱이 죽지 않고 **빈 공휴일 목록으로 조용히 폴백**해 도과알림이 순수 달력 계산이 된다. `holidays_2026`이 캐싱돼 있어 올해는 정상이고 **연도가 바뀌는 순간 틀어진다.** 묶음 env가 아니라 전용 시크릿으로 분리해 "빠뜨리면 배포가 실패하는" 구조로 (`3d6f805`)
    - **KISA 보안권고 1048·1049 영향도 점검:** PostgreSQL CVE 6건·Linux Kernel 1건 — 운영 Cloud SQL이 이미 16.14(해결 버전)이고 직접 운영하는 리눅스 호스트가 없어 **조치 불필요.** 근거를 양쪽 repo 이슈에 기록
    - **SSE 운영 로그 점검:** 최근 24시간 연결 620건 중 즉시끊김 **0건**, 553건이 timeout(3600초)을 꽉 채움. 7일간 에러 1건은 Cloud SQL 네트워크 리셋으로 백오프가 1초 뒤 자동 복구 — **설계된 복구 경로가 설계대로 동작한 사례**

## 2. 기술적 도전 및 트러블슈팅 (Technical Challenges & Troubleshooting)

- **"로컬에서는 완벽한데 운영에서만 안 되는" 장애가 한 주에 다섯 건 나왔고, 전부 로컬에 없는 계층이었다:** ① `GZipMiddleware`가 `minimum_size` 판단을 위해 첫 청크를 물고 기다리는데 SSE 신호는 12~60바이트라 **응답 헤더조차 나가지 않았다**(프론트가 `Accept-Encoding: identity`를 보내도 Cloud Run 프론트엔드가 정규화해 무력). ② `is_disconnected()`가 첫 호출부터 `True`라 스트림이 한 줄만 남기고 200으로 종료 — **액세스 로그만 보면 "매달렸다"로 오해**하고 애플리케이션 로그를 봐야 "끝난 것"임이 드러난다. ③ Firebase Hosting(Fastly)이 스트리밍을 버퍼링해 도메인 경유는 응답 자체가 없었다. ④ Cloud Run standalone의 `0.0.0.0` 바인딩. ⑤ Firebase Hosting의 쿠키 제거. **공통점은 진단 순서였다** — 셋 다 코드를 아무리 봐도 안 나오고, "로컬에 없는 계층이 무엇인가"를 먼저 세워야 좁혀졌다.

- **같은 함정(`= []` 기본값)이 사흘 연속 다른 얼굴로 나왔다:** 월요일엔 호출부의 기본값이 매 렌더 새 배열을 만들어 **사건상세를 무한 렌더로 죽였고**, 화요일엔 문서대장·상담대기열·법원진행 세 곳에서 **첫 데이터 도착 순간 목록 전체가 "새 행"으로 물들었고**, 수요일엔 사건상세 전 섹션이 새로고침만 해도 강조됐다. 훅은 `undefined`를 "아직 기준 없음"으로 보도록 설계됐는데 기본값이 그 설계를 무력화한 것이다. **기본값을 안 준 `records`만 정상이었던 게 단서였다.** 세 번째에 가서야 호출부 규약을 훅 문서주석에 못박았다(`860b701`) — 같은 함정을 두 번 고치고 나서야 재발 방지를 코드에 남긴 셈이다.

- **⭐ 자기 근거를 세 번 다시 재고 결론을 뒤집었다:** 월요일의 "폴링 월 $5"는 **요청 수만 센 값**이었고, 화요일에 응답 크기로 다시 계산하니 월 130만원이 나왔는데 그것도 **gzip을 빼먹어** 틀렸고, 세 번째 실측($20~25)으로 확정한 뒤 그 표를 `lib/polling.ts` 주석에 박았다. 그런데 수요일에 **egress 단가 자체가 틀려 있던 것**(`$0.12/GB` → 실제 `$0.19/GiB`)과 60명 기준을 확인하자 보류 결론 자체가 무너져 SSE로 전면 전환했고, **전날 근거를 박아 넣은 그 파일을 다음 날 삭제**했다. 숫자를 네 번 만진 셈인데, 매번 틀린 지점이 달랐다는 게 요점이다 — 빈도만 보고, 크기를 빼고, 압축을 빼고, 단가를 잘못 적었다.

- **같은 문제에 두 앱이 정반대 결론을 낸 것이 오히려 근거의 검증이었다:** 사건관리는 SSE로 전면 전환했고 CRM은 같은 주에 SSE를 기각했다. 갈린 이유는 **인프라 구조**다 — 사건관리는 Cloud SQL을 상시 물고 `min-instances 1`로 이미 활성 단가를 내는 60명 규모라 실시간이 오히려 싸고, CRM은 활성 구간이 34%뿐이라 연결을 열어두면 100%로 올라간다. "실시간이 좋다/나쁘다"가 아니라 **그 앱의 과금 구조가 답을 정한다**는 것을 양쪽에 근거로 남겼다.

- **채택한 기능을 같은 날 철회한 판단:** 탭 복귀 재시도는 "다른 탭에서 구글에 로그인하고 돌아오는 순간"을 잡는 유일한 트리거였고 가드도 3개(탭당 1회·3초 이상 숨었을 때만·이미 시도한 경우만) 붙였지만, 실제로 띄워보니 **사용자가 누르지 않은 화면 전환**을 만들고 있었다. 세션이 없으면 아무것도 누른 적 없이 구글 페이지에 남겨진다. 대신 버튼의 계정 선택창을 걷어내 **클릭 0회가 아니라 "사용자가 의도한 1회"** 로 정리했다. 만들 수 있다는 것과 있어야 한다는 것은 다르다.

- **무증상 실패가 이번 주에도 세 건:** 공휴일 API 키 유실(연도가 바뀌어야 틀어지는 시한폭탄, 게다가 **두 번째**), 미수금 1,076건 증발(총 건수만 보면 정상으로 보인다), 폴링 게이팅이 코드상으로만 존재(측정하기 전엔 꺼진 줄 알았다). 셋 다 **에러가 없는 형태**라 증상을 기다려서는 영영 안 나오고, 각각 전수 조사·화면 대조·요청 수 측정으로만 드러났다. 공휴일 키는 실패 방식("env를 다시 만들면서 한 줄이 빠진다")에 맞춰 **전용 시크릿**으로 옮겨 구조적으로 막았다.

- **앞의 설명이 남아 있는 증상을 설명하지 못하면 그 설명이 틀린 것이다:** 사내 포털 로그인은 `0.0.0.0` → 절대 URL → 호스트 정규화까지 세 번 고쳤는데도 500이 남았다. 매번 "이번엔 맞다"고 생각했고 매번 증상이 남았다. 마지막에 운영 `/api/auth/csrf` 응답 쿠키를 재전송해보는 **재현**으로 진짜 원인(Firebase Hosting의 쿠키 제거)이 나왔고, 작업 기록에 적어뒀던 Safari 쿠키 경합 추정은 입증되지 않아 폐기했다. 이번 주에 하나만 배운 것을 꼽으면 이쪽이다.

## 3. 총평 및 향후 과제 (Wrap-up & Next Steps)

> **"같은 결함이 세 곳에 있었고, 내 근거는 네 번 틀렸다 — 확인만이 남는 한 주"**

이번 주 커밋의 절반 이상(49건)이 사건관리 앱에 들어갔지만, 성격으로 보면 **한 문제를 여러 코드베이스에서 동시에 정리한 주**였다. 인증이 그랬다 — 사내 포털에서 찾아낸 `prompt` 파라미터 문제를 지난주 회고의 향후 과제로 남겨뒀고, 이번 주에 CRM·사건관리로 확장했으며, 금요일에는 세 앱을 사일런트 인증으로 통일하면서 **거절 사유별 버튼 동작 표까지 같은 모양으로 맞췄다.** 언어도 프레임워크도 다른 세 제품이 같은 결함을 공유했다는 사실 자체가 이 조직에서 인증이 각자 구현돼 왔다는 뜻이고, 그래서 다음에 새 앱이 생기면 같은 일이 또 반복된다 — 그 점이 이번 주에 정리되지 않은 채 남았다. 갱신 방식은 반대로 **하나의 답을 강요하지 않는 것**이 결론이었다. 사건관리는 SSE, CRM은 폴링 + gzip으로 갈렸고 근거는 각 앱의 과금 구조였다. 그 과정에서 내가 세운 숫자가 네 번 틀렸는데(빈도만 셈 → 크기 누락 → 압축 누락 → 단가 오기), 값이 큰 것은 마지막에 맞춘 숫자가 아니라 **틀릴 수 있다는 전제로 매번 다시 잰 습관**이었다고 본다. 실제로 보류 결정을 뒤집은 것도, 이슈 본문에 적힌 "초기값만 바꾸면 됨"을 의심해 미수금 1,076건 증발을 찾은 것도 같은 자리에서 나왔다. 가장 아팠던 것은 **공휴일 API 키가 두 번째로 유실된 것**이다 — 한 번은 실수지만 두 번은 구조이고, 그래서 값을 채우는 대신 빠뜨리면 배포가 실패하는 형태로 옮겼다. 반대로 가장 조심한 것은 사내 포털 쿠키 브리지인데, **저장소 오류를 조용한 로그아웃으로 만들지 않는 것**과 세션 강제 폐기를 제공하지 않는다는 한계를 문서에 명시한 것이 그 판단이다.

**향후 과제:**

- **🔴 CRM 로그아웃 차단이 아직 브라우저 영구다:** 금요일에 인증 실패 차단만 탭 단위로 바꾸고 **로그아웃 차단은 localStorage에 그대로 뒀다**(`9c7155b`). 이 선택 때문에 한 번이라도 로그아웃한 브라우저는 구글 세션이 살아 있어도 주소창 진입만으로는 들어갈 수 없다 — 실제로 9/14 운영 로그에서 확인됐다. 차단 수명을 탭 단위로 내리고 이미 각인된 플래그를 청소하는 조치가 필요하다
- **Firebase Hosting 캐시로 배포가 최대 1시간 늦게 도달한다:** `index.html`에 `max-age=3600`이 내려가 CRM 배포 검증 때마다 강력 새로고침이 필요했다. `firebase.json` headers로 `index.html`만 no-cache 분리
- **사건관리 SSE가 run.app에 직접 붙어 있다:** Firebase Hosting 버퍼링 회피를 위한 임시 구조라 크로스 오리진이 남는다. 근본 해결은 도메인을 Cloud Run 매핑으로 이전하는 것이며 DNS·인증서 작업이 필요
- **미수금 서버 페이지네이션:** 이번엔 상한을 3,000으로 올려 막았지만 **3,000건을 넘으면 같은 방식으로 다시 사라진다**. 클라이언트 페이지네이션 구조 자체를 바꿔야 함
- **공휴일 `holidays_2027` 확인:** 캐시 덕분에 올해는 정상이므로 **연도 경계 전에** 키가 실제로 동작하는지 확인해야 실효가 있다
- **CRM 로그인 `invalid_grant` 500 1건 관찰:** 회생 컬럼 배포 직후 1건 발생 후 정상화됐으나 반복 여부 확인 필요
- **DataTable 카드 모드 강조 바 미표시:** `rowClassName`이 `<td>`를 겨냥하는데 카드엔 `<td>`가 없다. 페이지가 이미 `isMobile`을 아는 상태라 `target`을 넘기면 한 줄로 해결
- **사내 포털 세션 스냅샷의 한계:** 강제 폐기 수단이 없어 이전 스냅샷도 만료 전까지 유효하다. 기존 JWT와 같은 성질이지만, 계정 사고 시 대응 수단이 없다는 점은 남는 리스크
- **인증 구현이 앱마다 흩어져 있다:** 이번 주에 같은 결함을 세 번 고쳤다. 새 앱이 생기면 네 번째가 나온다 — 공용 인증 모듈이든 체크리스트든 형태를 정할 시점

> **보고 범위 메모** — `AGENTS.md`의 대상 저장소 목록에 여전히 `BS_MAINBOARD`(`lawwin-info/main-board`)가 없고, GitHub 이슈 수집 대상 목록에는 `lawwin-info/bs_crm`도 빠져 있다. 이번 주 CRM 이슈 7건·메인보드 이슈 7건이 그 목록 밖에서 나왔고 커밋도 33건(전체의 38%)이다. 9월 1주차 회고에서 같은 지적을 남겼으므로 두 저장소 모두 목록에 추가가 필요하다. 이 회고는 임의로 포함해 집계했다.
