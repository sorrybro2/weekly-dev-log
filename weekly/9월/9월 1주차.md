# 주간 업무 회고 (9월 1주차)

> 이번 주는 월~금 5일 중 4일 작업(8/31~9/4, 화요일 9/1 커밋 0건). 커밋 51건 — 사내 포털 22건, 홈페이지 V2 17건, 사건관리 앱 9건, CRM 3건, 인프라 repo 0건. 신규 이슈 23건, 이슈 코멘트 30건. 주의 축은 셋이었다 — **제품 하나를 새로 세운 것**(사내 포털로 Google Sites 대체), 사람 정보와 수납 기록의 **"진실을 어디에 둘지" 정한 것**, 그리고 **자기 근거·경고 문구·숫자를 그대로 믿지 않고 다시 재본 것**이다.

## 1. 주요 업무 성과 (Key Achievements)

**이번 주에 가장 많이 한 일은 "만들기"가 아니라 "기준을 정하기"였다.** 월요일 오후부터 수요일까지는 **사내 포털**을 새로 세웠다 — 기존 Google Sites 포털은 조직도를 PDF 썸네일로 박아 둔 구조라 편집·검색·연동이 전부 불가능했고, Next.js 앱으로 대체해 조직도·사내 앱·일정을 한 화면에 모았다. 그 과정에서 값이 가장 나간 것은 화면이 아니라 **원인 규명 두 건**이었다: `prompt=consent`를 넘기고 있어 구글이 세션 유무와 무관하게 매번 동의 화면을 띄우고 있었다는 것(이것이 "앱마다 로그인 딸깍"의 범인이었고, 같은 파라미터가 사내 앱 전반에 쓰이고 있어 다른 앱에도 같은 조치가 필요하다), 그리고 `position: fixed`가 transform 걸린 조상 아래에서는 뷰포트 기준이 아니라는 것. 수요일의 축은 **진실의 위치를 나눈 것**이다 — 포털이 손으로 관리하던 이름·내선·직위를 CRM(구글 어드민 동기화본)에 넘기고 배치·배지·순서만 남겼고(88명 × CRM 377명 대조, 매칭 실패 0), 반대편 CRM에는 지금껏 받아 놓고 버리던 관리자 권한·조직단위 계층을 저장해 편집 권한을 **수기 이메일 목록 없이** 판정할 근거를 만들었다. 목요일에는 같은 성격의 일을 회계 쪽에서 했다 — 예약금과 상담료를 한 행에 합쳐 담던 구조를 **행 2개로 분리**해 "행 1개 = 영수증 1장"을 성립시켰다. 계기는 구글시트 AR_DB가 한 행에 결제 한 세트만 담아 **예약금의 입금일·결제방법이 내보낼 때 사라지던 실제 사고**였다. 금요일은 만든 것이 가장 적고(커밋 3건) 재본 것이 가장 많았다 — AI 상담봇 「초기 대응 안내 31건」 목록의 근거가 **공급 통계(우리가 처리한 사건 분포)라는 것을 스스로 의심**해 레거시 상담 6,204건을 직접 집계했고, 보정에는 실패했지만(86%가 분야 미태깅) 설계 판단 세 가지가 실측으로 검증됐다. 같은 날 미수금 8월 차액 **10,836,000원을 1원 단위까지 원인별로 분해**하고, 조사를 전 기간으로 넓혀 **DB 자체의 미수금 중복 27쌍 43,818,000원**을 따로 찾았다. 운영 쪽에서 가장 아팠던 것은 **8/11 롤백 이후 3주간 무증상으로 죽어 있던 접수 알림 링크**였고(알림은 정상 발송, 링크만 404), 판단이 가장 무거웠던 것은 Cloud SQL 보안 경고 7항목 중 **멀티리전을 하지 않기로 한 것**이다 — 한국 리전이 서울 하나뿐이라 복제본이 일본에 놓이며 상담자 개인정보 국외이전이 된다.

- **사내 포털: Google Sites 대체 신규 구축 (8/31~9/2)**

    - **왜 새로 만드나:** 기존 포털은 조직도를 PDF 뷰어에 박아 둔 썸네일이라 편집·검색·연동이 전부 불가능했다. 초기 구축부터 파비콘·로그인·대시보드 2단 구성까지 하루에 세움 (`9b8fee0`·`cb04bc2`·`18d74a7`·`6286560`)
    - **DB 없이 간다:** 조직도를 JSON 스냅샷으로 관리(Vercel Blob / 로컬 파일). 저장할 때마다 변경 내역과 함께 버전이 쌓인다 — 조직도는 쓰기 빈도가 극히 낮고 이력이 중요한 데이터라 테이블을 파는 비용이 값을 못 한다
    - **원본 PDF에서 좌표째 추출:** 스크린샷 OCR 대신 39차 배포본 PDF의 텍스트를 좌표와 함께 뽑아 88명을 옮겼다. 손으로 옮겼던 1차 전사의 오탈자 8건(문월성→문필성, 법조→협조 등)이 그 과정에서 드러남 (`a0f37dc`)
    - **그림과 명부를 분리:** 조직도 그림은 한 사람이 다섯 박스에 나온다(대표·이사회·총괄·회생·서울). 명부에서는 한 번만 싣고, **표시 순서가 곧 중복 제거 우선순위**가 되게 함. 사무소를 루트로 두고 권역 묶음을 없앰 (`18eb602`)
    - **실 소속을 이름의 위치로 판정:** `정보실 (대전)` → 대전, `재무실 (서울)` → 서울. 괄호를 읽는 규칙이라 새 실이 생겨도 그대로 먹는다 (`3013e09`)
    - **구성원 클릭 → 상세 + 통화:** 대표번호로 연결한 뒤 내선을 눌러 주는 `tel:0421234567,,7012` 형식. 구글 프로필(사진·이메일)까지 카드에 붙임 (`92d2642`)
    - **대외비 처리:** 조직도 PDF가 `public/`에 있으면 로그인 없이 URL만으로 받아진다 → `reference/`로 이동

- **사내 포털: 로그인 클릭 제거와 인증 원인 규명 (8/31, `53336b3`)**

    - **원인은 내 설정이었다:** `prompt=consent`를 넘기고 있어 구글이 **세션 유무와 무관하게 매번 동의 화면**을 띄웠다. 이것이 "앱마다 로그인 딸깍"의 범인이었고, 걷어내니 구글 세션이 있으면 그냥 들어가진다
    - **실제 인증 URL로 검증:** 추측으로 닫지 않고 CSRF 토큰을 받아 authorize URL을 직접 뜯었다 — `prompt` 없음, `hd` 지정됨, `access_type=offline` 유지 확인
    - **조용한 재인증의 함정:** `prompt`를 빼면 refresh token이 다시 오지 않는다 → 최초 동의 때 받은 값을 덮어쓰지 않도록 방어를 함께 넣음
    - **`hd`는 차단 수단이 아니다:** 계정 선택창 힌트일 뿐이라 도메인 검증은 서버에서 해야 한다는 점을 분리해 둠

- **홈페이지 V2: Cloud SQL 보안 경고 7항목 판단 (9/3, 이슈 `#107`)**

    - **삭제 보호가 꺼져 있었다:** 클릭 한 번에 운영 DB와 **백업 7일치가 함께** 영구 삭제될 수 있던 상태 → 활성화
    - **평문 접속을 허용하고 있었다:** DB 비밀번호 본체가 평문으로 흐르던 구간을 `ENCRYPTED_ONLY`로 차단하고, 평문이 실제로 거부되는 것까지 실측. Cloud Run이 커넥터 소켓 경유임을 **먼저 확인한 뒤** 실행해 운영 무영향을 사전 확증
    - **비밀번호 정책 적용:** 인스턴스 정책(최소 12자·복잡도·재사용금지) + 사용자별 정책. **만료·실패잠금은 미설정**이라 운영 정지 위험이 없음을 실측 확인
    - **멀티리전은 하면 안 되는 항목:** 한국 GCP 리전이 서울 하나뿐이라 복제본이 일본에 놓여 **상담자 PII 국외이전**이 된다 → 미실행. 경고를 없애려다 법적 리스크가 생기는 항목
    - **HA·pgaudit 2건은 보류:** SCC는 ISO·PCI 벤치마크 기준이고 당사는 인증 대상이 아니다. IAM 소유자를 2명 구성(박준수 실장 추가)해 단일 소유자 위험도 함께 해소
    - **SSL 강제의 부작용을 같은 날 잡음:** 마이그레이션 스크립트 12개가 접속 실패로 깨졌고, 실측으로 확인해 런북에 반영 (`2d9b5d7`)

## 2. 기술적 도전 및 트러블슈팅 (Technical Challenges & Troubleshooting)

- **"코드는 맞는데 화면이 틀린" 종류가 한 주에 세 건 나왔다:** ① 구성원 카드가 200px 떨어져 뜨던 것은 좌표 계산이 아니라 **`position: fixed`가 등장 애니메이션 때문에 transform 걸린 조상 기준으로 잡히고 있던 것**이었다(body 포털로 해결). ② 메인 첫 화면에서 글자가 배경보다 늦게 뜬 것은 **motion이 서버 HTML에 투명 상태를 박아 내려** 글자가 홈 자바스크립트 전체를 기다린 것이었다. ③ 조직도 내보내기가 백지로 저장된 것은 `getViewportForBounds`의 padding이 픽셀이 아니라 **비율**이라 `24`를 넘겨 배율이 1/49로 뭉개진 것이었다. **셋 다 좌표나 값을 아무리 고쳐도 안 잡혔을 문제**로, 렌더 경로와 API 계약을 의심하는 쪽으로 방향을 틀어야 나왔다.

- **구글 API의 용어를 문서로 확인하지 않으면 코드만 봐서는 안 나온다:** 사내 일정 필터가 공유 캘린더 일정을 전부 "내 일정"으로 통과시키고 있었는데, 원인은 **구글 캘린더의 `self`가 "로그인한 사람"이 아니라 "이 일정이 실린 캘린더"를 뜻한다**는 것이었다(`388e923`). 반대로 같은 성격의 확인이 큰 작업을 덜어준 경우도 있다 — 도메인 프로필(사진·이메일)을 읽으려면 Admin SDK 도메인 위임이 필요하다고 알고 있었는데, **People API의 `listDirectoryPeople`은 본인 권한으로 같은 도메인 프로필을 읽는다**는 것을 확인해 서비스 계정 도메인 위임 설정을 당장은 피했다. **문서를 읽는 30분이 설정 작업 하루를 없앤 경우와 버그 하루를 만든 경우가 같은 주에 있었다.**

- **자기 근거를 자기가 깬 것이 이번 주 산출물 중 가장 값이 컸다:** 두 건이다. ① 사내 포털에서 "앱마다 로그인을 눌러야 한다"는 불편의 범인이 **내가 넘기고 있던 `prompt=consent`**였다 — 남의 설정이나 구글 정책을 찾다가 자기 코드에서 나왔고, 추측으로 닫지 않고 authorize URL을 직접 뜯어 확인했다. ② AI 상담봇 안내 31건 목록의 배분 근거를 **해결사례 분포**로 잡았는데, 그건 「우리가 처리한 사건」이지 「사람들이 물어본 말」이 아니다. 상담 6,204건을 직접 집계해 보정을 시도했고 **실패했지만**(86% 미태깅), 그 실패가 오히려 **어휘 분산이 극심해 키워드 매칭이 불가능함**(최다 표현 0.5%)을 실측으로 증명해 pgvector 결정을 뒷받침했고, **가장 많이 묻는 것이 우리가 답하지 않기로 한 「결과」**라는 사실까지 드러냈다. 목록을 그대로 썼으면 영영 몰랐을 것이다.

- **무증상 실패가 이번 주에 네 건 나왔고 뿌리가 하나였다:** 접수 알림 링크가 **3주간 404**(알림은 정상 발송돼 눌러 봐야 안다), 썸네일 7건 유실(증분 동기화가 DB 행만 옮긴다), 「업무분야」 표기 변경이 **이틀간 미배포**(배포가 커밋보다 2시간 55분 앞서 있었다), 검색어 로깅 0건. 네 건을 개별로 고친 뒤 **공통 원인을 따로 이슈로 세운 것**(`#131` — Cloud Scheduler 비활성, `@Cron` 없음, `.github/` 없음)이 마무리였다. 증상 넷은 전부 "사람이 기억해야만 돌아가는 구조"의 표면이었고, **표면을 다 고쳐도 다음 것이 또 나온다**는 판단이었다.

- **경고 문구를 없애려다 리스크가 생기는 항목을 골라냈다:** Cloud SQL 보안 경고 7건 중 4건만 조치하고 3건은 근거를 남겨 미실행·보류했다. 특히 **멀티리전은 한국 GCP 리전이 서울 하나뿐이라 복제본이 일본에 놓여 상담자 PII 국외이전이 된다** — 경고 문구만 보고 실행했다면 되돌리기 어려운 판단이었다. HA·pgaudit는 SCC가 ISO·PCI 벤치마크 기준이고 당사는 인증 대상이 아니라는 이유로 보류했다. 반면 조치한 것들은 **먼저 무영향을 확증한 뒤** 실행했다(Cloud Run이 커넥터 소켓 경유임을 확인 후 SSL 강제, 만료·실패잠금 미설정 확인 후 비밀번호 정책 적용). **다만 SSL 강제로 마이그레이션 도구 12개가 깨진 것은 그 사전 판단의 누락**이었고, 같은 날 실측으로 잡아 런북에 반영했다.

- **회계 단위와 입력 동선이 애초에 다르다는 것을 구조로 인정했다:** 예약금·상담료를 한 행에 합쳐 두던 것을 행 2개로 분리하면서, **DB는 영수증 단위 / API·화면은 상담 단위**라는 이원 구조를 의도적으로 세웠다. 직원은 한 화면에서 둘을 함께 처리하므로 목록 건수가 53건→72건으로 바뀌면 안 됐고, 시트만 행 단위로 내보내야 했다. 위험은 마이그레이션 순서에 있었다 — **구코드가 원본 컬럼과 새 행을 둘 다 세면 시트 금액이 2배**가 되므로 `029 → 신규코드 배포 → 030`을 못박고 원본 컬럼을 롤백 여지로 남겼다.

- **네 방향이 동시에 어긋나 어느 숫자도 단독으로는 신뢰할 수 없었다:** 미수금 조사에서 나온 것은 차액 하나가 아니라 결함 넷이었다 — 시트→앱 역방향 미반영(57%), **앱에서 메모 한 줄만 고쳐도 시트 금액이 조용히 사라지는 경로**, 취소 건이 구조적으로 시트에 반영될 수 없는 것, 시트 중복 이중계상. 그리고 8월 조사를 전 기간으로 넓히자 **시트가 아니라 DB 자체에 중복 27쌍(43,818,000원)**이 나왔다. 여기서 멈춘 판단이 중요했다 — 자동 생성 경로가 `UNIQUE`로 막혀 있어 무관함을 먼저 지워 원인 후보를 좁혔고, **분납·별건 수임으로 같은 날 같은 금액을 두 번 받는 전례**(`#458`)가 있어 영수증 대조 전에는 중복으로 단정하지 않았다. 전 과정을 읽기 전용으로만 수행했다.

- **되돌린 사유를 기록하지 않은 것이 이번 주 유일한 미기록 결함이다:** 상담료 목록에 예약금 하위 행을 표시하는 작업(`#463`, `ffbdac7`)을 **28분 뒤 되돌렸는데**(`14aae1a`) 그 사유가 커밋·이슈 어디에도 남지 않았다. 재작업 시 판단 근거가 없어 같은 시도를 반복하게 되는 종류의 누락이다. 참고로 구현 자체는 `DataTable`의 `renderExpandedRow`가 `colSpan` 전체 폭이라 컬럼 정렬이 안 되는 점을 피해 셀 안 둘째 줄로 짠 것이었다.

## 3. 총평 및 향후 과제 (Wrap-up & Next Steps)

> **"만들기보다 기준을 정하는 데 시간을 쓴 한 주 — 그리고 그 기준을 내가 먼저 깬 한 주"**

이번 주 커밋의 절반 가까이가 새 제품(사내 포털 22건)에 들어갔지만, 정작 오래 남을 산출물은 화면이 아니라 **경계를 그은 결정들**이다. 사람 정보는 이름·내선·직위를 CRM에 두고 배치·순서만 포털에 남겼고, 수납 기록은 DB를 영수증 단위로 쪼개면서 화면은 상담 단위로 유지했다. 둘 다 **"변경 주체와 빈도가 다른 데이터를 한곳에 두면 반드시 어긋난다"**는 같은 판단에서 나왔고, 전자는 `employeeKey`·`gws_id`로, 후자는 `fee_group_id`로 이었다. 그리고 이번 주의 성격을 가장 잘 보여주는 것은 **자기 근거를 두 번 깬 것**이다 — 로그인 딸깍의 범인이 내가 넘긴 `prompt=consent`였고, 상담봇 안내 목록의 근거가 공급 통계였다. 두 번째 건은 검증에 **실패**했는데(86% 미태깅) 그 실패가 설계 판단 세 가지를 오히려 실측으로 확정해 줬다는 점에서, 이번 주에 가장 값이 나간 작업이 **아무것도 만들지 않은 금요일**이었다는 결론이 된다. 반대로 가장 아팠던 것은 접수 알림 링크가 **3주간 무증상으로 404**였다는 사실이다 — "운영 도메인 고정값"이라는 전제를 코드 기본값에 박아 두면 도메인 정책이 바뀔 때 아무 로그 없이 조용히 깨진다. 같은 성격의 무증상 실패가 네 건 모여 **자동화가 전무하다는 하나의 뿌리**(`#131`)로 수렴한 것이 금요일의 마무리였고, 미수금 조사도 결국 **네 방향이 동시에 어긋나 어느 숫자도 단독으로는 못 믿는 상태**를 숫자로 세운 것이 실질이었다. 판단을 멈춘 곳도 분명히 있다 — 중복 27쌍은 분납·별건 수임일 수 있어 영수증 대조 전에는 단정하지 않았고, Cloud SQL 멀티리전은 경고를 없애는 대신 국외이전을 만드는 항목이라 하지 않았다. **고칠 수 있는 것과 고치면 안 되는 것을 가른 것이 이번 주 판단의 절반이다.**

**향후 과제:**

- **미수금 영수증 대조가 모든 후속의 선행 조건:** DB 중복 27쌍 43,818,000원(`#477`)은 분납·별건 수임 가능성이 남아 있어 대조 없이는 정리할 수 없다. 전부 수기 입력 행이므로 입력 경로 점검도 함께
- **시트 역방향 덮어쓰기 경로 차단이 가장 급하다:** 앱에서 **메모 한 줄만 고쳐도 시트 금액이 빈칸으로 덮어써지는** 6건(`#474`)은 아직 사고가 나지 않았을 뿐 대기 중이다. 경고도 로그도 없어 사고가 나도 원인 추적이 어렵다
- **취소 건 시트 반영은 구조 변경이 필요:** 취소 시 `AR_key`를 만들 수 없어 push가 스킵되는 것(`#476`)은 우회가 아니라 키 설계를 손대야 한다
- **자동화 체계 도입 (`#131`):** Cloud Scheduler 활성화 또는 GitHub Actions 도입. 이번 주 무증상 실패 네 건이 전부 이 뿌리에서 나왔으므로 개별 증상보다 우선순위가 높다
- **상담 DB 이원화 병합 (`#130`):** 계획은 이미 있고 안 돌렸을 뿐이나 **PK 충돌 시 V2 상담이 소리 없이 사라진다** — 충돌 여부 확인 전 `--apply` 금지를 유지할 것
- **검색어 로깅 (`#129`):** 히어로 검색바 입력을 지금부터 쌓지 않으면 나중에도 데이터가 없다. 상담봇 의도 분류의 실측 근거로도 필요
- **AI 상담봇 — 대표 결정 3건과 리전 확인:** `aiplatform.googleapis.com`이 **실측 비활성**이고 서울 리전 Gemini 가용성이 미확인이라 이것이 분기점이다. 그 외 **만 14세 확인 게이트**를 명세에 추가하고, 마케팅이 시안 두 번째 시나리오(「범위 밖」 처리)를 반드시 보게 할 것 — 이것이 예외가 아니라 주력 경로임이 실측으로 확인됐다
- **Cloud SQL 접속 경로 복구 (`#126`):** 금요일 확인의 상당 부분이 접속이 막혀 우회 경로로 이뤄졌다. 다음 조사 전에 정상화 필요
- **`#463` 되돌림 사유 기록:** 28분 만에 되돌린 판단 근거가 어디에도 없어 재작업 시 같은 시도를 반복하게 된다. 이슈에 사유를 소급 기록할 것
- **`prompt=consent` 조치를 다른 앱에도 확장:** 포털에서 걷어낸 이 파라미터가 CRM·사건관리 앱 인증 URL에도 같은 형태로 박혀 있다(CRM은 `consent`, 사건관리는 `select_account`). 세션이 있어도 매번 화면을 띄우는 원인이 동일하므로 양쪽에 같은 조치가 필요하다. 단 **`prompt`를 빼면 refresh token이 다시 오지 않는다**는 포털에서 확인한 함정과, 로그아웃 직후 자동 재인증을 막는 가드가 함께 들어가야 한다

> **보고 범위 메모** — `AGENTS.md`의 대상 저장소 목록에 `BS_MAINBOARD`(`lawwin-info/main-board`)가 없다. 이번 주 최다 커밋처(22건, 전체의 43%)이고 8/31·9/2 일일보고에서도 같은 지적을 남겼으므로 목록 추가가 필요하다. 이 회고는 임의로 포함해 집계했다.
