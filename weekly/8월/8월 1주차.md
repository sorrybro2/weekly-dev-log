# 주간 업무 회고 (8월 1주차)

> 이번 주는 월~금 5일 모두 작업(8/3~8/7). 전반(월·화)은 사건관리 앱 베타테스트 대응, 후반(수·목·금)은 홈페이지 V2 도메인 컷오버와 그 후속. 커밋 148건 — 사건관리 앱 45건, 홈페이지 V2 103건, CRM·인프라 repo 0건.

## 1. 주요 업무 성과 (Key Achievements)

**두 제품을 같은 주에 각각 실사용자 앞으로 내보낸 한 주.** 월·화는 사건관리 앱 **베타테스트 개시**에 붙어 실계정에서 터진 것들을 걷어냈고, 수·목·금은 홈페이지 V2를 **`www.lawwin.co.kr` 실서버로 전환**하고 실트래픽에서 드러난 것들을 잡았다. 두 흐름이 같은 성격의 문제를 반복해서 냈다 — **화면은 정상인데 실제로는 엉뚱한 곳을 가리키고 있는** 종류다. `user` 롤이 사건을 아예 못 만들고 있던 것, `super_admin`이 전사 권한을 가진 채 자기 지사에 갇혀 있던 것, 결재 요청을 안 했는데 결재함에 조용히 쌓이던 것(컬럼 기본값), 어드민 로그인 콜백이 `run.app`에 붙을 상태였던 것, 홈페이지 상담이 **전부 본사로 기록**되고 있던 것, CRM으로 나가는 상담이 **테스트 서버로 24건 전부 실패**하고 있던 것 — 전부 UI로는 확인이 안 되고 로그·DB·env를 대조해서야 드러났다. 컷오버 자체는 다운타임 0으로 끝냈으나, 그 과정에서 전날 "리전 지원 확인됨"이라고 내린 판단이 오판이었음이 실측으로 드러나(asia-northeast3은 Cloud Run 도메인 매핑 미지원, 501) 로드밸런서 + 인증서 관리자로 경로를 바꿨다. 사용자 눈에 보이는 축은 **모바일**이었다 — 화요일에 사건관리 6개 화면을 좁은 폭에서 쓸 수 있게 만들고(카드 모드에 정렬이 아예 없었다), 금요일에 홈페이지의 겹친 시각 효과들을 걷어냈다. 그 밖에 홈페이지 상담 접수 알림을 신설하고(레거시에도 없던 기능), 레거시 URL 404 11개 패턴을 301로 채우고, DB 참조 자산 7,797건을 전수 대조해 이미지 제보를 근거로 닫고, 컷오버 누락분이던 GTM을 어드민 관리 방식으로 도입했다. 성능·보안 쪽으로는 프론트 OOM(하루 198건)을 실측해 스펙을 올렸고, 어드민 인증 API의 **직원 이메일 열거·비밀번호 무제한 대입** 구멍을 막았으며, 컨테이너 빌더를 교체해 빌드를 3분 4초 → 2분 23초로 줄였다.

- **사건관리 앱: 베타테스트 대응 — 롤 권한 · 담당사건 재설계 · 모바일 · 결재 흐름 (8/3~8/4, 8/7)**

    - **롤 권한 정합성 — 실계정에서만 드러난 것들(8/3):**

        - `search/employees`·`search/offices`가 `contracts:read`를 요구해 `user` 롤에서 **담당자 드롭다운이 통째로 비고 사무소명 대신 조직 키(`2a2da3a2`)가 노출**되던 것을, 반환값이 이름뿐이라는 점을 근거로 `cases:read`로 완화함
        - 사건 등록 1단계가 '계약 선택'인데 `GET /contracts`가 `contracts:read` 전용이라 **일반 사원은 사건을 아예 만들 수 없었다** — `contracts:read` 또는 `cases:write`로 열고 `require_any_permission` 헬퍼를 신설함
        - `revenue_org_groups`가 **조회까지** super_admin 전용이라 그 외 역할에서 대전/청주·인천/부천 묶음이 낱개로 갈라지던 것을, 조회 차단과 편집 차단을 분리해 해소함(편집만 super_admin)
        - 프론트가 목록 조회에 JWT 소속을 항상 실어 보내 **super_admin의 전사 열람이 무력화**되고 소속이 NULL인 계정은 0건이 나오던 것을 수정함
        - 계정 팝오버를 신설해 **소속 사무소와 역할을 화면에서 확인**할 수 있게 함 — 목록 건수가 이상할 때 원인이 대개 그 계정의 접근 사무소인데 확인할 방법이 없었다

    - **담당사건을 "내 일감" 관점으로 재설계(#195 → #214, 8/3):**

        - 아침에 트리를 목록 기반으로 교체하고 저장 뷰·필터를 붙였다가(#195), **담당사건에서 표의 컬럼(주담당·부담당·지사)은 전부 "나"라서 정보량이 0**이라는 판단으로 목록/트리 토글을 없애고 트리 하나로 일원화함(#214)
        - 목록형에만 있던 필터를 `lib/caseFilters.ts` + `CaseFilterPopover`로 뽑아 전체 사건 목록과 담당사건이 **같은 함수**를 쓰게 함
        - 트리를 기일 중심으로 재구성함 — 행에 `사건번호 · 사건명 · 다음 기일`, 긴급도는 왼쪽 색 레일 하나로만, 범위 칩 3개·검색·임박순 정렬·**이번 주 기일 있는 폴더만 자동 펼침**
        - 폴더 배지·자동 펼침·행 레일·범위 칩의 기준을 '이번 주(7일 내·결과 미입력)' 하나로 통일함 — 예전엔 배지만 '다가오는 기일 전체'를 세서 **배지가 붙은 폴더가 접혀 있는 모순**이 보였다

    - **모바일에서 쓸 수 없던 화면 6개 정리(#240, #243, #244, 8/4):**

        - 모바일 카드 리스트에는 표 헤더가 없어 **컬럼을 눌러 정렬할 방법이 아예 없었다** → 정렬 가능 컬럼을 컬럼 정의에서 자동으로 뽑는 `MobileSortMenu`를 신설하고, 사건목록의 정렬 상태를 페이지로 승격해 표와 카드가 같은 값·같은 비교 함수를 쓰게 함
        - 폭이 제각각인 필터 컨트롤이 아무렇게나 감겨 라벨이 잘리던 것을 그리드로 묶고(상담료 3칸·계약목록 2열), 번호 9칸 + 이전/다음 + 「총 N건」이 390px에서 한 줄에 안 들어가던 페이저를 화면 폭에 맞춰 접음
        - 월 선택과 시작~종료 달력이 **동시에 떠 있어 무엇이 조회 기준인지 알 수 없던** 것을 「기간 지정」 토글로 갈랐고, 모드만 켜고 날짜를 비우면 월 조회를 유지해 **빈 범위가 서버로 나가지 않게** 처리함
        - 시스템 설정 4개 영역을 한 페이지 앵커 스크롤에서 라우트 분리로 바꿔 `scrollToSection`·IntersectionObserver·activeId 로직을 소멸시킴

    - **결재·메일 흐름의 실제 사고 정리(#210, #216, #233, #237):**

        - 결재 요청을 안 했는데 결재함에 쌓이던 원인은 체크박스도 프론트도 아니라 **컬럼 기본값**이었다 — `approval_status`의 server_default가 '대기'라 등록만 해도 대기 상태가 됐고, 알림은 가드에 막혀 안 나가서 **조용히** 쌓였다(#216)
        - 삭제 성공 후에도 체크 선택에 남아 **없는 문서로 결재요청이 나가던** 것을 선택에서 제거하고, 404는 건너뛰고 그 외 실패건만 남겨 재시도하게 함(#237)
        - 문서의 `approver_key`가 등록 시점 스냅샷이라 **사건 주담당이 바뀌면 옛 변호사로 요청**이 가고 목록 툴바는 자동 매핑을 써서 같은 문서인데 결재자가 서로 달랐던 것을, 요청 전(미발송·보류)이면 자동 매핑값을 기본으로 쓰게 정리함
        - 열람등사 메일에서 담당 자리에 `employee_key`가 찍히던 것을 이름으로, 제목 대괄호를 값 자체에 담아 미리보기와 실제 발송을 일치시키고, 사건번호가 뒤 일련번호(`1864`)만 들어가던 것을 정식 헬퍼로 바꿈(#210) — 금요일에 발송 미리보기·실제 발송·목록 API·결재요청 메일까지 `formatCaseNumber`로 전면 통일해 `2026노1864` 풀네임이 되게 마감함
        - 수발신방법 드롭다운이 한 번 고르면 다시 열리지 않던 것(열기가 `onFocus`에만 걸려 포커스가 남은 재클릭이 씹혔고, 열려도 고른 값으로 목록을 걸러 항목 하나만 남았다)을 `mousedown` 토글 + 전체 목록으로 수정함(#233)

    - **기일 충돌 판정 정확화(8/3):**

        - `CURRENT_DATE`가 DB 세션 타임존(운영 Cloud SQL은 UTC)을 따라 **한국시간 00~09시엔 어제로 잡혀** 지난 기일까지 충돌로 끌어올리던 것을 KST로 고정함
        - 크롤 결과에서 사라진 기일이 삭제가 아니라 비활성으로 남아 옛 기일 때문에 계속 빨갛게 뜨던 것과, '변론종결'·'기일변경'처럼 결과가 찍혀 조율할 게 없는 기일을 제외함
        - 목록 SQL의 `is_conflict`가 **언제나 `FALSE` 상수**인데 이름만 그럴듯해 오해를 부르던 것을 걷어냄

- **홈페이지 V2: 도메인 컷오버와 실서버 후속 (8/5~8/7)**

    - **컷오버 실행 — 다운타임 0(8/5 준비, 8/6 실행):**

        - 전날 "리전 지원 확인됨"이라 판단했던 Cloud Run 도메인 매핑이 **asia-northeast3에서 아예 제공되지 않는다는 것이 실측으로 드러나**(501 UNIMPLEMENTED) 글로벌 외부 로드밸런서 + Certificate Manager로 경로를 바꿈 — 결과적으로 인증서를 **전환 전에** 발급해둘 수 있어 다운타임이 0이 됐다
        - 코드 변경은 0건이었으나 런타임 env 하나(`AUTH_URL`)가 `run.app`으로 고정돼 **어드민 로그인 콜백이 엉뚱한 도메인에 붙을 상태**였고 이걸 먼저 바꿔야 했다
        - `www.lawwin.co.kr`·`lawwin.co.kr` 모두 ALB 고정IP(35.186.226.100)로 서빙되고 검증 스크립트 15/15 PASS(noindex 해제·HSTS·robots·레거시 301·주요 페이지 200)
        - 컷오버 다음 날 apex → www 301이 실제로 반영됐는지 재확인함(경로·쿼리 보존, PKCE 오류 로그가 조치 시점 이후 0건)

    - **지사별 URL 체계 정리(8/6):**

        - 지역을 1년짜리 쿠키로 기억해 접두사 없는 경로를 그 지역으로 307 보내고 있어 **`lawwin.co.kr`로 들어가도 전국판에 도달할 방법이 없던** 것을, 쿠키를 제거하고 URL 첫 세그먼트로만 지역을 판정하도록 바꿈
        - 담당 변호사·목록 복귀·뉴스 탭·페이지 이동·검색·경로표시·정책 링크 등 **접두사가 새는 링크를 30여 개 파일에서 전수 수정**함
        - 푸터 사업자정보가 서울로 남던 것을 보고 있는 지사 값으로 바꿈 — 상호·사업자등록번호는 **분사무소마다 별도 등록된 표시사항**이라 본사 값 대체는 부정확한 표시가 된다
        - 폐지 지사(목포·제주)를 경로에서 걷어내고 각각 광주·홈으로 301 처리함(색인·백링크가 남아 404 대신 301), 메인 지도가 따로 들고 있던 숨김 목록을 없애 공개 목록과 기준을 통일함

    - **상담 접수 — 알림 신설부터 지점 정확성까지(8/5~8/7):**

        - 홈페이지 상담이 접수돼도 담당자가 알 방법이 없다는 지사 제보(#5)에 대해 **지사별 구글챗 스페이스 알림**을 신설함(레거시에도 없던 기능). 웹훅 목록을 env가 아니라 `system_settings` 테이블에 둬 **재배포 없이** 등록·수정·활성 토글·테스트 전송이 되게 하고, 등록 가능 주소를 `chat.googleapis.com`으로 고정하고 조회 시 `key`·`token`을 마스킹함(URL 자체가 크리덴셜)
        - 담당자 요청으로 카드 → 일반 텍스트로 형식을 바꾸고(모바일에서 접히지 않고 연락처 복사가 쉽다), 회생·파산 접수는 접수 지사 훅과 회생·파산센터 훅이 **모두** 수신하게 함
        - 소년·학폭센터 상담이 레거시에 없던 센터라 카테고리 자체가 없어 **일반 온라인 상담으로 접수**되던 것을 멱등 SQL로 카테고리를 신규 등록해 해소하고, 회생·파산은 표시명으로 조인해 **문구만 다듬어도 전담 알림이 누락될 구조**였던 것을 센터 데이터에 조인 키를 명시해 끊음
        - 금요일에 **가장 큰 누락을 발견**함 — 상담 신청 폼이 지점 값을 전혀 보내지 않아 **모든 접수가 본사로 기록되고 알림도 본사로만** 가고 있었다. 폼 맨 위에 접수 지점 필수 선택을 넣고 고르지 않으면 제출을 막았으며, 헤더에서 고른 지점이 폼·하단 상담바까지 따라가게 함. 하단 상담바가 전국판에서도 첫 지사를 자동 선택해 **고르지 않은 지사로 접수되던** 동작은 비워 두게 바꿈
        - 회신이 불가능한 입력(전화번호 형식·자리수·없는 국번, 이름 자모·반복, 도배 본문, 5분 내 동일 재접수)을 접수 단계에서 거절하고, 연락처는 숫자만 입력해도 하이픈이 자동으로 들어가게 함(서울 `02`는 국번 자릿수에 따라 위치가 달라진다)

    - **회생 변제금계산기 개편(8/7):**

        - 인정 생계비 기준표가 2025년 고시에 머물러 1인 가구를 1,337,067원으로 계산하던 것을 2026년 고시(1,538,543원)로 교체함 — 생계비가 오르면 가용소득이 줄어 **월 변제금 추정치가 낮아지고**, 변호사 확인 값과 일치한다
        - 모바일에서 입력·결과·상담폼이 한 화면에 쌓여 화면 두세 개 높이가 되던 것을 **① 정보 입력 → ② 연락처 → ③ 추정 결과** 3단계로 자르고, 좌우 2단을 버려 단일 컬럼 가운데 정렬로 바꿈
        - "상담 신청을 해야 결과가 보이게" 하자는 안을 검토했으나 **결과를 개인정보와 교환하는 구조는 카드 헤더의 약속과 어긋나고 결과를 못 본 문의가 섞여 리드 품질을 떨어뜨린다**고 판단해 채택하지 않음 — 폼을 결과 앞에 두되 "결과만 먼저 볼게요" 스킵 링크를 항상 노출하고, 접수 완료 화면에도 추정 결과를 함께 실었다
        - 공용 프리미티브(`StepPane`·`StepNav`·`StepIndicator`)와 `stepped` 옵트인 prop을 만들되 **회생만 켜고 나머지 5개 센터는 기존 배치를 유지**함

    - **SEO · 콘텐츠 노출(8/5~8/7):**

        - 레거시 URL을 전수 점검해 404 나던 **11개 패턴**(전문센터 `*contact` 6개, 변제금 예측, `/Center` 인덱스, 지역 민사, 상담 비밀번호·상세)을 301에 채우고, 레거시 IIS가 무시했던 대소문자를 정규화함(`/Center/Recovery`가 404였다)
        - 구 sitemap에 색인된 `?tk=N` 뉴스 탭 32건(지사 8곳 × 4탭)이 전부 미디어 탭으로 뭉개지던 것을 탭 경로로 승격하고, 목적지가 요청 경로와 같으면 리다이렉트하지 않도록 미들웨어에 무한루프 가드를 넣음
        - 썸네일 미지정 게시물에 본문 첫 이미지를 자동 사용해 **대표 이미지 커버율을 869건 → 3,162건(95.9%)** 으로 올림(본문 전문을 가져오지 않고 DB가 첫 이미지 주소만 잘라 주도록 처리)

        - 히어로 통계의 정의 목록 마크업이 어긋나 있어 **접근성 감사와 에이전트형 브라우징의 유일한 실패 항목이 같은 원인**이던 것을 잡고, 단어마다 `span`으로 쪼개져 공백 없이 읽히던 헤드라인에 `sr-only` 읽기용 문장을 붙임

    - **어드민 · 추적 · 보안(8/6~8/7):**

        - 컷오버 누락분이던 GTM을 도입함 — 레거시처럼 `headtag`에 스니펫을 통째로 저장하지 않고 **컨테이너 ID만 저장하고 스니펫은 코드가 생성**해 어드민이 임의 스크립트를 심을 수 없게 하고, 경로 → 컨테이너 결정 규칙을 레거시와 동일하게 재현함
        - 어드민 인증 API(`/api/admin/auth/*`)에 가드가 없어 **URL만 알면 임의 이메일의 재직 여부·권한·소속 지사를 조회**할 수 있었고(직원 이메일 열거) 비밀번호 검증도 외부에서 무제한 대입이 가능했던 것을 공유 시크릿으로 잠금(fail-closed)

        - 서버 타임존이 UTC라 00~09시에 날짜가 하루 전으로 보이던 것을 KST 공용 유틸로 통일함(어드민·상담게시판·CSV 파일명까지)

## 2. 기술적 도전 및 트러블슈팅 (Technical Challenges & Troubleshooting)

- **"동작한다"와 "올바른 곳에 도달한다"는 다른 문제 — 한 주에 네 번:** 이번 주 가장 값이 큰 발견 네 건이 모두 **UI로는 확인이 불가능한 종류**였다. ① 홈페이지 상담이 접수는 되는데 **지점 값을 안 보내 전부 본사로 기록**되고 있었다(지사별로 영업하는 구조에서 지사가 자기 문의를 못 받는 것과 같다). ② CRM으로 나가는 상담 forward가 **24건 전부 실패**하고 있었다 — 성공 0건. ③ 결재 요청을 안 했는데 결재함에 쌓이고 있었다(원인은 컬럼 기본값). ④ 어드민 로그인 콜백이 `run.app`을 가리키고 있었다. 네 건 모두 화면상으로는 아무 이상이 없어서, Cloud Run 로그와 DB 적재 내역, env를 대조해서야 드러났다. 공통 교훈은 **"성공 응답을 받았다"가 "의도한 대상에 반영됐다"를 뜻하지 않는다**는 것이다.

- **CRM 전달 24/24 실패 — 대상이 테스트 서버였다:** "홈페이지에서 상담이 안 들어온다"는 보고를 받아 조사했다. 접수 자체는 정상이었고(최근 7일 53건, 계산기·센터 간이폼 포함 전 경로가 정상 적재) CRM forward만 전부 실패했다 — 타임아웃 16건 + 404 8건, 성공 0건. 실패 로그 구간의 접수 건수와 실패 로그 수가 **정확히 일치**했다. 원인은 운영 백엔드의 `CRM_HP_REQUEST_URL`이 **테스트 CRM(다른 프로젝트)** 을 가리키고 있었던 것이고, 운영 CRM은 30일간 그 요청을 한 번도 받은 적이 없었다. 404와 타임아웃이 섞인 것도 설명된다 — 테스트 CRM엔 그 라우트가 없고(404), 인스턴스가 0으로 내려가 있으면 콜드스타트가 4초 abort를 넘긴다(16건). 대체 경로였던 챗 딥링크마저 env 미설정으로 비활성이라 **두 경로가 모두 죽어 있었다.** 접수는 DB가 source of truth이고 fire-and-forget이라 유실은 없었다. CRM 서버 간 전달을 되살리는 대신 구글챗 딥링크로 대체하기로 결정하고 플래그를 내렸다.

- **에러 하나 보고 그 뒤 제약이 없다고 결론낸 오판:** 컷오버 전날 Cloud Run 도메인 매핑을 시도했을 때 **소유 확인 에러가 먼저 떠서** 그것만 해결하면 된다고 판단했다. 실제로는 `asia-northeast3`이 도메인 매핑을 **아예 지원하지 않았다**(501 UNIMPLEMENTED) — 리전 제약이 앞선 에러에 가려져 있었다. 로드밸런서 + Certificate Manager로 갈아탄 것이 결과적으로 더 나았다. 도메인 매핑은 DNS가 Google을 먼저 가리켜야 발급이 시작돼 HTTPS 오류 구간이 생기는데, Certificate Manager는 DNS authorization으로 **전환 전에** 발급을 끝낼 수 있어 다운타임이 0이 됐다.

- **같은 뿌리(타임존)가 두 제품에서 각각 터짐:** 사건관리에서는 `CURRENT_DATE`가 DB 세션 타임존(운영 Cloud SQL은 UTC)을 따라 **한국시간 00~09시엔 어제로 잡혀** 지난 기일까지 충돌로 끌어올리고 있었고, 홈페이지에서는 서버 렌더 날짜가 UTC라 같은 시간대에 **날짜가 하루 전으로** 보였다. 증상이 전혀 달라 별개로 접수됐지만 원인은 하나였다. 양쪽 모두 KST를 명시적으로 고정하는 쪽으로 정리했다.

- **권한을 "엔드포인트가 무엇을 반환하는가" 기준으로 다시 잡음:** `user` 롤에서 담당자 드롭다운이 비고 사무소명이 조직 키로 노출된 것은, 이름만 반환하는 검색 엔드포인트에 `contracts:read`가 걸려 있었기 때문이다. 더 심한 것은 **사건 등록 1단계가 계약 선택인데 그 조회가 `contracts:read` 전용**이어서 일반 사원이 사건을 아예 만들 수 없었던 것이다. 권한을 기능 이름이 아니라 **반환 데이터의 민감도** 기준으로 재배치하고 `require_any_permission` 헬퍼를 만들었다. 반대 방향의 오류도 있었다 — `super_admin`은 전사 열람 권한이 있는데 프론트가 목록 조회에 JWT 소속을 항상 실어 보내 자기 지사에 갇혀 있었고, 소속이 NULL인 계정은 0건이 나왔다. **권한은 백엔드에만 있는 게 아니라 프론트가 무엇을 보내는지까지가 권한**이었다.

- **원인이 코드가 아니라 컬럼 기본값이던 사례:** 결재 요청을 하지 않았는데 결재함에 문서가 쌓였다. 체크박스 상태와 프론트 호출을 먼저 의심했지만 둘 다 정상이었고, 실제 원인은 `approval_status`의 **server_default가 '대기'** 라 등록만 해도 대기 상태가 되는 것이었다. 알림은 별도 가드에 막혀 나가지 않아서 **조용히** 쌓였다 — 알림이 갔다면 훨씬 빨리 발견됐을 문제다.

- **효과를 겹쳐 쌓은 결과, 대개 빼는 쪽으로 해결됨:** 금요일 모바일 문제 대부분이 같은 형태였다. 누끼 PNG(배경 지운 프로필)에 **카드 배경색과 어두운 그라데이션**을 씌워 인물이 아니라 그 막이 보였고, 반투명 배경 + 배경 흐림이 겹쳐 카드 안 글자가 뿌옇게 읽혔고, `will-change`를 상시 걸어 요소가 항상 별도 합성 레이어로 분리되면서 버튼 글자가 평상시에도 뭉개졌다. 가장 성격이 뚜렷한 건은 **키보드가 올라오면 화면이 흐려지는** 문제였다 — 히어로 안에 검색바가 있어서 모바일에서 탭하면 visual viewport가 줄고 브라우저가 페이지를 스크롤하는데, 스크롤 연동 페이드가 그걸 스크롤로 읽어 **타이핑 중에 화면을 흐리게** 만들었다. 넷 다 효과를 제거하는 쪽으로 해결했고, 부수적으로 스크롤 전환에서 `opacity`를 아예 걷어내면서 **모션이 실패하면 섹션이 통째로 사라지던 위험(7월의 회귀 이슈)이 구조적으로 재현 불가능해졌다** — 이전 수정은 하한을 0에서 0.5로 올려 완화한 상태였다.

- **제보를 근거로 닫기 위해 7,797건을 전수 대조:** "이미지가 로딩되지 않는다"는 제보에 대해 변호사 프로필 78건, 성공사례 썸네일 857건, 전 게시물 본문·첨부의 **고유 URL 7,797건**을 전수 대조해 현재 깨진 건이 0건임을 확인했다. 동시에 과거 원인 두 개를 규명했다 — ① GCS 이관 **이후** 레거시에 올라온 파일이 버킷에 없었던 것(736개·393MB 복구), ② CKEditor가 쓴 대문자 `/Uploads`가 소문자만 매칭하는 rewrite를 못 타 404. 둘 다 **증분 동기화마다 재발하는 조건**이라 감사·복구·경로 정규화 절차를 매뉴얼에 남겼다.

- **정렬·기준을 하나로 정하자 그것을 덮고 있던 층들이 드러남:** 담당사건 트리에서 폴더 배지·자동 펼침·행 레일·범위 칩이 각자 다른 기준을 쓰고 있어 **배지가 붙은 폴더가 접혀 있는 모순**이 보였다(배지만 '다가오는 기일 전체'를 셌다). 기준을 '이번 주(7일 내·결과 미입력)' 하나로 통일하자 모순이 사라졌다. 같은 성격으로 홈페이지에서는 전화 팝오버·푸터·지역 스위처·상담 지점 선택이 각자 다른 지사 목록을 들고 있어 폐지·비노출 지사가 어떤 화면에는 남아 있었다 — 기준을 한 곳으로 모았다.

- **표기 정책이 하루에 세 번 바뀐 이유:** 집계 수치 노출을 전면 보류했다가 메인·전문센터만 복원했다가 최종적으로 **반올림 + `건+`** 표기로 정리했다. 단위도 갈랐다 — 메인은 수기 입력값이라 100 단위, 전문센터는 DB 실측이라 10 단위(실측값에 큰 올림을 걸면 원본을 넘어선다). 이 과정에서 화면 표시값(5,567건·52,741건)과 DB 실측(3,280건·5,976건)의 격차를 확인해 근거 자료 확인 필요 사항으로 남겼다. 금요일에는 사무소 개수 노출까지 보류했다.

## 3. 총평 및 향후 과제 (Wrap-up & Next Steps)

> **"두 제품을 실사용자 앞에 내놓고, 화면으로는 보이지 않는 것들을 걷어낸 한 주"**

전반과 후반이 다른 제품이었지만 한 주로 묶어 보면 같은 작업이었다. 월·화의 사건관리 앱은 베타테스트로 실계정이 들어왔고, 수·목·금의 홈페이지 V2는 컷오버로 실트래픽이 들어왔다. 그리고 양쪽에서 나온 가장 값이 큰 발견은 전부 **UI로 확인할 수 없는 것들**이었다 — 상담이 전부 본사로 기록되고 있었고, CRM으로 나가는 24건이 하나도 도달하지 않고 있었고, 결재 요청을 안 했는데 결재함에 쌓이고 있었고, 일반 사원은 사건을 아예 만들 수 없었다. 코드를 읽어서가 아니라 로그·DB·env를 실제 값과 대조해서 나온 것들이고, "성공 응답을 받았다"를 "의도한 대상에 반영됐다"로 읽었던 지점이 공통 원인이었다. 컷오버 자체는 다운타임 0으로 끝났지만 전날 판단이 오판이었음을 인정하고 경로를 바꾼 것이 오히려 결과를 좋게 만들었다 — **에러 하나를 해결하면 된다고 결론내면 그 뒤의 제약이 가려진다**는 것을 리전 제약으로 배웠다. 판단을 되돌린 사례가 이번 주에 네 번 있었다: 담당사건을 목록형으로 갔다가 트리로 일원화한 것, 도메인 매핑에서 로드밸런서로 바꾼 것, 집계 표기를 보류·복원·반올림으로 정착시킨 것, 계산기에서 결과 게이팅을 검토했다가 리드 품질을 이유로 접은 것. 마지막 건은 기술 판단이 아니라 **전환 수보다 약속 일관성을 택한** 제품 판단이었다. 사용자 눈에 보이는 쪽은 모바일이었고, 대개 무언가를 더하는 대신 **겹쳐 쌓인 효과를 빼는** 방향으로 해결됐다.

**향후 과제:**

- **CRM 대체 경로 마무리:** `CRM_REQUEST_INBOX_URL` 설정(운영 요청함 경로 확인 필요)으로 챗 알림의 당사자 등록 딥링크를 살리고, 누락된 상담 24건 처리 방식 결정. 알림 채널이 구글챗 하나로 줄어든 데 대한 운영 합의도 필요 — 챗 메시지는 흘러가므로 놓친 건은 홈페이지 어드민 문의 관리에만 남는다
- **컷오버 런북 보강:** "외부 연동 대상이 테스트 서버를 가리키는지" 항목을 추가. 이번 CRM 건과 지난주 GTM 누락이 같은 계열이므로 **env의 `*-test-*` 호스트 전수 점검**을 절차로 만들 것
- **GTM 전환 신호 구현:** 컨테이너는 올라갔지만 `dataLayer` push가 하나도 없어 **전환 신호가 아직 안 나간다**. 클릭 전환(카톡·톡톡·예약·전화)과 상담 접수 완료 전환을 붙이고, 레거시 AW 8계정·네이버 wcs 3계정 중 현재 운영 중인 것을 확정해야 한다. 미입력 컨테이너 ID(목포 1곳, 센터 5곳)도 마케팅팀 확인 필요
- **계산기 실물 확인 및 확장 판단:** 단일 컬럼 폭(576px)이 데스크톱에서 적절한지 실물 확인, 나머지 5개 센터도 단계형으로 갈지 결정. `funnel` 값이 붙어 있어 폼 위치에 따른 전환율 비교가 가능하다
- **사건관리 베타테스트 후속:** 이번 주 잡은 롤 권한·담당사건 트리·모바일 정렬이 실사용에서 의도대로 도는지 확인. 특히 권한은 백엔드와 프론트가 함께 결정하는 구조라 역할별 재검증이 필요
- **표시 집계값 근거 확인:** 화면 수치와 DB 실측의 격차(5,567 vs 3,280 / 52,741 vs 5,976)에 대한 근거 자료 확보 — 광고·표시 규정과 직결되는 사안
