# 주간 업무 회고 (8월 2주차)

> 이번 주는 월~금 5일 모두 작업(8/10~8/14). 커밋 69건 — 사건관리 앱 34건, 홈페이지 V2 25건, CRM 10건, 인프라 repo 0건. 지난주 컷오버한 `www.lawwin.co.kr`이 경영 판단으로 레거시로 **롤백**되면서 주 전체의 축이 한 번 뒤집혔고, 나머지는 운영 장애 3건 대응과 예약금 파이프라인 신설, 메인 랜딩 재설계였다.

## 1. 주요 업무 성과 (Key Achievements)

**지난주에 내보낸 것을 되돌리고, 되돌린 자리에서 다시 세운 한 주.** 화요일 오후 `www.lawwin.co.kr`이 레거시 IIS로 롤백됐다 — SEO 노출과 AI 인용이 끊겼다는 광고대행사 보고가 근거였고 경영 판단이었다. 그래서 오전에 하고 있던 전환 추적 복구의 전제가 사라졌고, 남은 시간은 **되돌리기(DNS 원복)와 옮기기(V2를 `bslawwin.co.kr`로 이전)** 로 들어갔다. 그 과정에서 이번 주 가장 값이 큰 발견이 나왔다 — **도메인이 16개 파일에 하드코딩돼 있어 새 도메인에 V2를 올려도 색인이 원천적으로 불가능한 상태**였다(robots가 `Disallow: /`, canonical이 이전 도메인). 운영 장애는 세 건이었다. 월요일 **사건관리 API 27분 전면 다운**(배포된 컨테이너가 uvicorn이 아니라 nginx였다), 같은 날 **홈페이지 6분 39초 전면 500**(Cloud SQL 커넥터 순간 타임아웃을 앱이 흡수하지 못해 기동 실패로 증폭), 그리고 목요일 **첨부 문서 4건 유실** — 이 마지막 건은 **수요일에 추적성을 높이려고 넓힌 감사 로그가 만든 사고**였다. 세 건 모두 "배포·기동이 됐다"가 "제대로 떠 있다"를 뜻하지 않는다는 같은 교훈으로 수렴했다. 계획된 축은 둘이었다. ① **상담 예약금 파이프라인** — 수요일에 CRM·사건관리 앱 양쪽에 전용 컬럼을 신설하고(그동안 직원 자유 메모 필드에 결제 문구로 섞여 있었다), 목요일에 결제 상태까지 분리해 "예약금만 받고 상담료는 미입금"인 건을 표현할 수 있게 했으며, 금요일에 양쪽 캘린더 표기 포맷을 통일했다. ② **홈페이지 메인 랜딩 재설계** — 목요일에 분야 탭·변호사 슬라이드를 세우고, 금요일에 레거시의 fullPage.js + GSAP 조합을 라이브러리 없이 재이식해 **한 화면씩 넘기는 다섯 장면 장표**로 만들고 히어로 로고를 three.js 실물 3D로 세웠다. 그 작업 중 **사이트 전체 한글에 폰트가 적용된 적이 없었다는 것**을 발견했다(자기 참조 CSS 변수 한 줄). 그 밖에 GSC 미색인 17.8만 건을 사유별로 뜯어 조치 필요 2건을 구현했고, 감사 로그 대상을 6개 → 22개로 늘린 뒤 남은 구멍 두 개(raw SQL 삭제 미적재, 업무 동작 이름 미기록)를 다음 날 모두 메웠으며, 롤백으로 이원화된 상담 42건을 레거시로 이관했다.

- **홈페이지 V2: 도메인 롤백과 새 도메인 이전 (8/11, 이슈 `#104`·`#84`)**

    - **롤백 수행:**

        - 가비아 A 레코드를 ALB 고정IP(`35.186.226.100`)에서 레거시 IIS(`139.150.69.177`)로 되돌림. 되돌리기 전에 레거시 서버를 실측해 확인함 — HTTPS 200, 응답 0.12~0.17초, 인증서 2027-03-06까지 유효, robots 전면 허용
        - 롤백 근거는 대행사 보고(메인키워드 노출 하락·AI 인용 중단)와 경영 판단이었고 기술 판단이 아니었으므로, **원복 가능한 형태로** 남겨 두는 데 중점을 둠

    - **V2를 `bslawwin.co.kr`로 이전:**

        - Certificate Manager 인증서 신규 발급 + 인증서 맵 항목 2개, A 레코드 2개. **URL map은 손대지 않았다** — `defaultService`가 이미 전 호스트를 받고 있어 건드릴 이유가 없었다
        - Cloud Run·ALB·Certificate Manager·GCS 인프라를 새 도메인이 **그대로 재사용**하게 해 이전 비용을 DNS·인증서로만 한정함
        - 백엔드 `CORS_ORIGIN`에 새 도메인 2개를 추가함 — 응답 헤더 누락을 먼저 실측했고, 이걸 안 고치면 **상담 접수가 죽는다**
        - 프론트 `AUTH_URL` 교체와 구글 OAuth 리디렉션 추가로 어드민 로그인 콜백을 새 도메인에 맞춤

    - **색인이 안 되던 근본 원인 제거:**

        - `https://www.lawwin.co.kr`이 **16개 파일에 하드코딩**돼 있어 새 도메인으로 들어와도 `robots.txt`가 `Disallow: /`, canonical이 이전 도메인, `X-Robots-Tag: noindex` 상태였다. 그중 **canonical이 결정적**이다 — robots만 열어도 색인은 안 된다
        - `lib/site.ts`를 신설해 `SITE_URL` 하나로 모았고, 다음에 도메인이 바뀌면 빌드 설정 한 줄만 고치면 되게 함
        - **런타임 env만으로는 부족했다** — 정적 생성 페이지가 모듈 상수를 빌드 시점에 굳히므로 Dockerfile ARG + build-arg로도 같은 값을 주입해야 했다
        - 구글·네이버 재등록까지 마치고, **네이버 소유확인 토큰은 도메인마다 다르다**는 점을 확인해 새 토큰을 추가하되 기존 토큰도 배열로 남겨 되돌릴 여지를 유지함
        - 사이트맵 실측 — 7,298 URL / 630KB / 도메인 불일치 0 / 중복 0

    - **상담 42건 레거시 이관(커밋 없음, 운영 조치):**

        - 롤백으로 접수 창구가 이원화돼 V2에만 남은 42건을 레거시로 넘겼다. 시간대 9시간 차·번호 충돌·IPv6 컬럼 길이 초과 세 가지가 각각 다른 층의 문제였고 보정·재발급·NULL 처리로 해소, **중복 0건**으로 검증
        - 테스트 9건 제외 기준을 `username`이 정확히 `테스트`인 행으로 한정함 — 본문에만 '테스트'가 있는 건은 실명 문의자일 수 있다

- **홈페이지 V2: 운영 장애와 색인 (8/10, 이슈 `#103`·`#102`)**

    - **6분 39초 전면 500 → 자체 회복 구조로 전환:**

        - Cloud SQL 커넥터가 순간적으로 타임아웃했는데 `PrismaService`가 `$connect()`를 재시도 없이 한 번만 호출하고 예외를 그대로 올려 Nest 부팅이 깨졌고, Cloud Run에서 그것은 곧 `exit(1)` → 기동 실패 → 그 인스턴스로 간 요청 전부 500이었다. **수 초짜리 네트워크 장애를 6분짜리 다운으로 증폭시킨 구조**
        - 같은 시각 DB는 정상이었음을 확인함(checkpoint·autovacuum 정상, 재시작·유지보수 없음) — 죽은 구간은 백엔드 → 커넥터
        - 0.5초에서 8초까지 5회 재시도하고, 다 소진해도 예외를 던지지 않고 기동을 이어가 DB 복구 시 자동 연결되게 바꿈
        - GTM 컨테이너 조회 실패가 `catch {}`로 삼켜져 **장애 시간 동안 추적 코드 없이 페이지가 나간 것조차 기록이 없던** 것을 오류 로그로 남기게 함

    - **GSC 미색인 17.8만 건 분석 및 조치:**

        - 사유별로 뜯어 **조치 필요 2건 / 이미 해소 1.3만 건(재크롤 대기) / 정상 분류**로 갈랐다. 숫자 자체보다 이 분리가 실질이었다
        - 크롤 예산이 필터 조합 주소로 소진되던 것을 차단함 — 지역 × 카테고리 × 변호사 × 페이지로 사실상 무한 생성되는 **4만5천여 개**. 표준 태그는 색인 단계에서만 작동해 크롤 자체를 막지 못하는 것이 원인이었다
        - 뉴스로 발행됐다가 지식센터로 재분류된 글이 옛 주소에서 404 나던 것을 실제 경로로 영구이동시킴(지사 접두사 유지, 비공개 글은 404 유지)
        - 레거시 IIS가 무시했던 대소문자를 지사 이름 부분에서만 그대로 비교하고 있던 것을 정규화함

    - **전환 추적·AEO (8/10~8/11, 이슈 `#84`):**

        - 전환의 실제 신호인 `consult_submit`을 **접수 성공 시점에만** 발사하도록 붙임(지사·센터·접수 위치·경로 동반, 상담 폼 4곳이 공유하는 전송 함수 한 곳에). 동의 미체크·연락처 오류·서버 오류는 전환으로 잡히지 않는다
        - 서울 컨테이너를 게시하고 광주를 분석하던 중 **네이버 전환 태그 11개가 2개월간 전부 일시중지** 상태였음을 발견함(공통 수집만 살아 방문은 잡히고 전환만 0)
        - 광주는 링크 클릭 트리거에 `Form URL` 조건이 걸려 **리뉴얼과 무관하게 원래부터 미발화**였다 — 즉 원인의 일부는 리뉴얼이 아니었다
        - 지사마다 트리거 조건이 제각각이라 복제가 불가능하다는 판단으로 **전환 5종을 전부 코드 발화로 통일**함(카톡·톡톡·예약까지 `dataLayer`로). GTM이 CSS 선택자·주소를 직접 보던 구조가 전환이 통째로 끊긴 원인이었고, 남은 세 지사 작업이 "트리거 5개 + 태그 연결"로 동일해졌다
        - 크롤 차단 3줄을 대행사 요청으로 원복함(크롤 예산보다 랭킹 회복 우선) — 재차단 방법은 주석으로 보존
        - 네이버 랜딩 진단의 "Alt 속성 누락"을 실측해 **변호사 썸네일 32장**이 원인임을 특정하고 조치함. 원래 비운 건 감싸는 `<button>`에 `aria-label`이 있어서였고 낭독 결과는 그대로다
        - 무브랜드 분야 질의 근거를 `llms.txt`에 세우고(9개 분야 × 지역) 홈 문답을 5개 → 9개로 늘림. 전문분야 등록 인원 집계를 단일 모듈로 모아 `llms.txt`와 홈 문답이 같은 숫자를 쓰게 함

- **사건관리 앱: 운영 장애와 데이터 정합성 (8/10, 이슈 `#298`)**

    - **API 27분 전면 다운:** 배포된 컨테이너가 uvicorn이 아니라 nginx였다 — `gcloud run deploy --source=.`가 루트 Dockerfile 대신 `frontend/Dockerfile`을 집어 빌드했다. 화면은 `NotificationCenter`에서 터졌지만 실제로는 `/api/*`가 전부 SPA `index.html`을 반환하고 있었다. 즉시 이전 리비전으로 롤백하고 **`--source` 금지 · 명시적 이미지 빌드 후 배포**하는 2단계로 절차를 고정함
    - **계약 신규 등록 500:** 스키마·마이그레이션만 머지되고 SQLAlchemy 모델 컬럼(`is_acquaintance`)이 빠져 생성 API가 통째로 실패하고 있었다. 누락분을 반영하고, 같은 유형 재발 방지로 **쓰기 스키마 필드가 모델 컬럼의 부분집합인지 검사**하는 정합성 체크를 붙임(기동 시 경고 로그 + 수동 CLI, 현재 23쌍 통과)
    - **껍데기 기초사실 정리:** 계약·사건 저장이 실패해도 먼저 만든 matter가 남아 재시도마다 누적되던 것(3회 실패 → 3개)을 catch 롤백으로 막고, 실체 1건이 검색에 4건으로 뜨던 것을 목록에서 제외함(활성 1,173 → 1,170). 정리용 옵션을 따로 남김
    - **크롤러 웜서비스 요청 18건 전부 500:** 웜 컨테이너에서 CPU가 회수되면 Chromium이 고착되던 것을, 타임아웃 시 브라우저 재기동 후 1회 재시도하고 최종 실패는 503 + 안내 문구로 바꿈
    - **복수 지사 조회가 일반 사용자에게 무시되던 것:** `organization_keys`를 super_admin일 때만 읽어 대전/청주처럼 묶인 지사 요청이 통째로 버려지던 것을 접근 범위와 교집합으로 좁힘. 법원사건진행내역에 지사 칩 탭을 추가해 다른 목록들과 기준을 맞춤

- **CRM + 사건관리 앱: 상담 예약금 파이프라인 (8/12~8/14, 이슈 `#313`·`#320`·`#327`)**

    - **특이사항 필드를 쓰지 않기로 한 판단이 전제였다:** 예약금은 CRM에서만 받는 선입금인데 그동안 특이사항(`consultation_detail3`)에 결제 문구로 섞여 있었다. **값이 있는 320건 중 결제 문구는 31건뿐**이고 나머지는 입실시각·연락처 같은 직원 자유 메모라, 앱이 그 필드를 자동으로 쓰기 시작하면 사람이 적은 내용과 경합한다 — **수치를 먼저 세어보고 결정한 것이 이후 작업 전체의 전제**가 됐다
    - **양쪽 DB에 같은 이름으로 신설:** `reservation_fee_amount`·`consultation_fee_amount` (NULL은 미입력, 0은 금액 없음). `deposit_*`을 쓰지 않은 이유는 이 코드베이스에서 `deposit_date`·`depositor`가 **입금**을 뜻해 선입금과 의미가 섞이기 때문. FDW 포린테이블까지 노출을 맞춤
    - **입력 주체를 한쪽으로 고정:** 예약금은 CRM 입력, 상담료는 사건관리 앱 입력 — CRM 폼에서 상담료는 읽기 전용
    - **결제 상태 분리(다음 단계):** 금액만 보관하던 상태에서는 **예약금만 받고 상담료는 미입금인 건**을 표현할 수 없었다. CRM에 미입금 컬럼·체크박스를 신설하고, 앱에 `reservation_` 접두어 결제 컬럼 10개를 추가함(마이그레이션 027, `ADD COLUMN IF NOT EXISTS`로 재실행 안전, 프로덕션 적용 + **백필 9건**)
    - **백필로 과거 데이터의 뜻을 보존:** 컬럼이 없던 시절의 예약금은 "항상 받은 돈"으로 집계됐으므로 금액이 있는 기존 건을 **입금완료로 채워** 의미가 바뀌지 않게 함
    - **캘린더 제목이라는 공유 자원 관리:** 금액 구간을 정규식으로 걷어내고 다시 붙여 재저장에도 중복이 쌓이지 않게 하고, 제목 꼬리에 앵커링해 특이사항 본문의 직원 문장은 건드리지 않게 함. 금요일에 양쪽 표기 포맷을 통일하고 CRM 입력 UI를 체크박스에서 스위치로 교체
    - **AR_DB 합치기 규칙 명시:** 시트는 한 행에 결제정보 한 세트라 — 금액=예약금+상담료 / 입금액=**입금완료된 쪽만** / 완납=예약금 있으면 양쪽 다 완료 / 결제방법·입금일은 상담료 우선
    - **양방향 연동은 예약금 블록만:** 상담료까지 양방향이면 **일부만 입금된 건을 기록할 수 없다**. 블록 노출 판정을 모달 열 때 한 번만 하도록 바꿈(편집 중 0으로 지우면 블록이 사라져 재입력이 불가능했다)

    - **대상 6개 → 22개:** 상담료를 실수로 "처리 취소"한 건을 추적할 수단이 아예 없다는 것이 드러나 확대함 — 서버 로그엔 사용자·본문이 없고 Cloud SQL은 pgaudit 미설정이라, 결국 `updated_at` 역순 조회로 손으로 특정해야 했다. 전체 29개 테이블을 전수 분류(감사 22 + 의도적 제외 7, 누락 0)

    - **전날 보고에 "남은 구멍 2개"로 적어둔 것을 둘 다 메움(`#325`):** ① raw SQL 삭제가 안 잡히던 것 — 누적 1,148건 중 delete가 **1건뿐**이었던 수치가 곧 구멍의 크기였고, `record_manual()`을 **같은 세션·같은 트랜잭션**에 적재하도록 신설함(별도 세션이면 롤백된 삭제가 "지웠다"로 남아 감사 로그가 거짓말을 한다) ② 사건·계약·수발신문서 삭제가 전부 소프트 삭제라 `update`로만 남아 삭제를 찾을 수 없던 것에 업무 동작 이름을 주입함(**그동안 채워진 행이 0건**이었다)
    - 감사 화면이 행마다 2~3줄로 접혀 훑기가 안 되던 것을 6열 → 9열로 쪼개고 `table-fixed` + 셀별 truncate로 1행 1줄 고정, 전문은 툴팁·펼침 패널로 옮김

    - **오조작 방지·공통 UX:** 기록신청 목록에서 드롭다운을 고르는 즉시 저장되던 것을 사건·의뢰인·관할을 보여주는 확인창으로 차단하고, 법원사건진행내역에서 필터를 바꿔도 이전 날짜 선택이 남아 엉뚱한 날이 잡히던 것을 수정. 사이드패널·드로어 ESC 닫기를 공용 훅으로 신설함(중첩 시 맨 위 하나만, 수정 중이면 차단)

## 2. 기술적 도전 및 트러블슈팅 (Technical Challenges & Troubleshooting)

- **"배포·기동이 됐다"가 "제대로 떠 있다"를 뜻하지 않는다 — 한 주에 세 번:** 월요일 사건관리 API 27분 다운은 **배포된 컨테이너가 uvicorn이 아니라 nginx**였고(`--source=.`가 프론트 Dockerfile을 집었다), 같은 날 홈페이지 6분 39초 500은 **기동 실패한 인스턴스가 요청을 전부 받고 있던** 것이었으며, 목요일 첨부 4건 유실은 **감사 로그를 남기려는 코드가 업무 트랜잭션을 롤백시킨** 것이었다. 세 건 모두 배포·기동 직후에는 아무 신호가 없었고, 화면에서 보이는 실패 지점이 실제 원인과 다른 층에 있었다. 조치도 같은 방향으로 모였다 — 배포는 이미지 명시 2단계 + 사후 검증으로, 기동은 재시도 + 실패해도 죽지 않기로, 감사 로그는 실 DB 행 검증 후에만 확대하기로.

- **도메인이 16개 파일에 하드코딩돼 있었고, 런타임 env로는 고칠 수 없었다:** 새 도메인에 V2를 올렸는데 색인이 시작되지 않았다. 원인은 `robots.txt`가 `Disallow: /`, canonical이 이전 도메인, `X-Robots-Tag: noindex` — **한 곳이 아니라 16곳**이었다. 그중 **canonical이 결정적**이라는 점이 중요하다(robots만 열어도 검색엔진은 원본이 다른 도메인이라고 읽는다). `lib/site.ts` 한 곳으로 모으는 것으로 끝날 일이었는데, 배포해도 값이 바뀌지 않았다 — **정적 생성 페이지가 모듈 상수를 빌드 시점에 굳히기 때문**이다. 런타임 env에 더해 Dockerfile ARG + build-arg로 같은 값을 주입해야 비로소 반영됐다. 같은 교훈이 그날 마지막 작업에서 한 번 더 나왔다 — 대표 수치를 단일 모듈로 모은 이유가 정확히 "16곳에 퍼졌던 실패의 반복 방지"였다.

- **추적성을 높이려는 조치가 업무 데이터를 잃게 만든 역설:** 수요일에 감사 대상 테이블을 6개 → 22개로 늘렸다. 목요일에 그 확대가 `document_logs`와 `document_log_files`를 동시에 대상으로 만들면서, 한 요청에서 insert+update가 겹치면 `executemany` 파라미터 키 집합이 행마다 달라져 **flush가 깨지고 요청 트랜잭션 전체가 롤백**됐다. 피해가 컸던 이유는 버그 자체보다 **실패 지점의 위치**였다 — Drive 업로드가 이미 끝난 뒤 커밋이 터지므로 파일은 남고 대장에는 첨부가 없는 어긋난 상태가 만들어졌다. 그리고 **첨부 실패 안내가 원인을 묻지 않고 전부 "사건 폴더가 없다"로 표시해 오진을 유도한 것**이 원인 규명을 하루 늦췄고, 그 사이 문서 4건이 유실됐다. 좋은 안내 문구는 UX가 아니라 **장애 대응 시간**의 문제라는 것을 값을 치르고 확인했다.

- **감사 로그가 거짓말을 하지 않게 만드는 조건:** 확대 다음 날, 전날 보고에 적어둔 "남은 구멍 2개"를 메웠다. 누적 1,148건 중 **delete가 1건뿐**이었던 이유는 세션 훅이 ORM 객체 상태만 보기 때문이었고(raw SQL로 지운 행은 흔적이 없다), 사건·계약·문서 삭제가 전부 소프트 삭제라 `update`로만 남아 삭제를 **찾을 수 없었다**. 여기서 설계상 핵심은 ORM 밖 변경을 적재하는 `record_manual()`을 **같은 세션·같은 트랜잭션**에 넣은 것이다 — 별도 세션으로 적재하면 롤백된 삭제가 "지웠다"로 남아 감사 로그 자체가 거짓 기록이 된다. 확대할 때 **뺀 것에 사유를 남긴 것**도 같은 성격의 결정이었다(`refresh_token` 평문 노출, UI 상태 노이즈).

- **판단을 두 번 뒤집었고, 뒤집은 쪽이 맞았다:** ① 재판부 저장 실패를 처음엔 스키마 길이 제한으로 500을 422로 바꾸는 방향으로 잡았는데, 크롤러가 넣는 같은 이름의 컬럼은 이미 TEXT이고 실제 값이 50자를 예사로 넘긴다는 것(초과 29건, 최대 72자)을 확인하고 **폭을 넓은 쪽에 맞추는 것으로 뒤집었다**. "에러를 친절하게 만드는 것"과 "값이 들어가게 하는 것"은 다른 문제이고, **같은 개념의 컬럼이 테이블마다 폭이 다른 것 자체가 원인**이라는 진단이 더 위였다. ② 목요일에 섹션 스냅을 철회했는데 같은 날 저녁 같은 자리를 다시 요청받았다. 철회할 때 재발 방지 근거를 코드 주석으로 박아둔 덕에 **"브라우저 스냅에 위임"과 "전환을 직접 제어 + 되감기 모션"이 다른 물건**임을 표로 대조해 기록할 수 있었고, 다음 날 후자로 구현했다.

- **수치를 먼저 세고 나서 설계를 정한 사례:** 예약금을 어디에 저장할지 정할 때, 기존 특이사항 필드를 재사용하는 안이 가장 싸 보였다. 그런데 그 필드에 값이 있는 320건을 실제로 세어보니 **결제 문구는 31건뿐**이고 나머지는 입실시각·연락처 같은 직원 자유 메모였다. 앱이 그 필드를 자동으로 쓰기 시작하면 사람이 적은 내용과 경합한다는 것이 분명해져 전용 컬럼 신설로 갔고, 이 판단이 이후 이틀 작업(입력 주체 고정, 캘린더 제목 정규식 앵커링, 결제 상태 분리, 백필)의 전제가 됐다. 컬럼 이름도 데이터를 근거로 골랐다 — 이 코드베이스에서 `deposit_*`은 이미 **입금**을 뜻해 선입금과 섞인다.

- **타입체크가 런타임 사고를 막아준 사례:** 프로덕션 빌드가 두 번 깨져 배포가 두 차례 밀렸다. 두 번째는 미사용 import였지만 첫 번째는 성격이 달랐다 — `useMemo`가 `useState` 선언보다 위에 놓인 TDZ 위반이었고, **의존성 배열은 렌더 시점에 평가되므로** 그대로 배포됐다면 `ReferenceError`로 계약 사이드패널이 아예 렌더되지 않았을 것이다. dev(vite)는 타입체크를 하지 않아 로컬에서는 보이지 않는 전형이었다. 왜 그 위치로 올리면 안 되는지를 주석으로 남겼다.

- **브라우저 없이 외부 서비스 설정 오류를 판정함:** 새 도메인에서 상담 접수가 되지 않았다. 배포 청크에서 reCAPTCHA 사이트키를 확인한 뒤 구글 앵커 엔드포인트에 오리진 파라미터를 바꿔 질의해 `Invalid domain for site key`를 받아냈다 — 실제 브라우저로 폼을 제출해보지 않고도 원인을 특정할 수 있었고, 조치 후 같은 방법으로 양쪽 도메인 토큰 발급까지 확인했다. 도메인 이전 체크리스트에 빠져 있던 **여섯 번째 항목**(SITE_URL·INDEXABLE_HOSTS·AUTH_URL·CORS_ORIGIN·소유확인 다음)이었다.

- **자기 참조 CSS 변수 한 줄이 전 사이트 한글 폰트를 무력화하고 있었다:** 메인 재설계 중 폰트를 손대려다 `--font-sans: var(--font-sans)`를 발견했다. 자기 참조라 해석되지 않아 `html { @apply font-sans }`가 무효였고, Geist는 라틴 서브셋만 받아와 한글 글리프가 없어 **한글 전체가 접속자 OS 기본 폰트로** 렌더되고 있었다. 기기마다 다른 글꼴로 나가고 있었던 셈이라 디자인 논의보다 앞단의 문제였고, 라틴·숫자는 Geist, 한글은 Noto Sans KR로 떨어지도록 스택 순서에 의도를 담아 정리했다.

## 3. 총평 및 향후 과제 (Wrap-up & Next Steps)

> **"지난주에 내보낸 것을 되돌리고, 어제 한 조치가 오늘의 사고가 되는 연쇄를 끊은 한 주"**

이번 주의 성격은 두 개다. 하나는 **되돌림**이다. 지난주 다운타임 0으로 성공시킨 컷오버가 화요일 오후 경영 판단으로 롤백됐다. 기술적으로 실패한 것이 아니라 SEO 노출·AI 인용이라는 다른 기준이 앞선 것이었고, 그래서 오전에 하던 전환 추적 복구의 전제가 통째로 사라졌다. 되돌리기 자체는 DNS 한 줄이지만 뒤에 붙는 일이 훨씬 많았다 — 새 도메인 이전, 인증서, CORS, OAuth, 소유확인, 그리고 **상담 42건 이관**. 이 과정에서 나온 발견(도메인 16곳 하드코딩, canonical이 결정적, 정적 생성은 빌드 시점에 값을 굳힌다)은 롤백 여부와 무관하게 남는 자산이다. 다른 하나는 **연쇄**다. 수요일에 추적성을 높이려고 감사 로그를 6개 → 22개로 넓혔고, 목요일에 그 확대가 업무 트랜잭션을 롤백시켜 문서 4건을 잃게 했고, 같은 날 그 감사 로그로 다른 사고(사건번호 잔존)의 순서를 역추적했다. 조치가 사고를 만들고 그 조치가 다른 사고를 밝히는 순환이었다. 여기서 배운 것은 **확대는 그 자체로 위험 변경**이라는 것 — 22개 전부를 실 DB 행으로 검증한 뒤 커밋했음에도, 검증하지 않은 조합(두 대상 테이블이 한 요청에서 함께 바뀌는 경우)이 남아 있었다. 판단을 뒤집은 두 건(재판부 컬럼 폭, 섹션 스냅)은 모두 **철회할 때 근거를 코드에 남겨둔 것**이 다음 판단을 빠르게 만들었다. 특히 스냅은 철회 당일 저녁 재요청을 받았는데, 주석 덕에 "같은 물건이 아니다"를 표로 대조해 기록하고 다음 날 다른 방식으로 구현할 수 있었다. 마지막으로 이번 주 발견 중 가장 조용했던 것은 **사이트 전체 한글에 폰트가 적용된 적이 없었다**는 것이다 — 자기 참조 변수 한 줄 때문에 모든 방문자가 자기 OS 폰트로 이 회사 홈페이지를 보고 있었고, 아무도 오류로 신고하지 않았다.

**향후 과제:**

- **새 도메인 색인 안정화:** 신·구 도메인이 같은 내용이면 노출이 2배가 되지 않고 **신규 도메인이 밀린다** — 이 사실을 대행사와 먼저 맞춰야 색인을 여는 조치의 기대치가 정해진다. V2 클린 URL 7,050건 404, GTM이 도메인을 구분하지 않아 데이터가 혼입되는 문제도 함께 정리 필요
- **도메인 이전 체크리스트 정본화:** 이번에 reCAPTCHA 허용 도메인이 여섯 번째 누락 항목으로 드러났다. SITE_URL(빌드 인자)·INDEXABLE_HOSTS·AUTH_URL·CORS_ORIGIN·소유확인·reCAPTCHA **6곳**을 런북에 고정하고, 지난주 CRM 건과 같은 계열인 **env의 테스트 호스트 전수 점검**도 절차로 넣을 것
- **전환 추적 잔여 3개 지사:** 서울은 게시 완료, 광주는 작업공간에 미게시 보존 상태. 전환 5종을 코드 발화로 통일해 남은 작업이 "트리거 5개 + 태그 연결"로 동일해졌으므로 광주·부천·인천을 같은 절차로 마감. 미입력 컨테이너 ID(목포 1곳, 센터 5곳)는 마케팅팀 확인 필요
- **감사 로그 남은 범위:** raw SQL 대량 UPDATE 14곳은 여전히 감사 대상 밖이다. "취소된 상담료가 어느 계약에 물려 있었는지"를 끝내 복구하지 못한 것이 이 구멍의 실제 비용이었다
- **메인 랜딩 실물 확인:** 장표·3D를 브랜치로 올린 상태이므로 실물에서 다듬은 뒤 `main` 반영 판단. 장표 경계(세로 800px)와 모션 감소 사용자 동작을 기기별로 확인 필요
- **예약금 파이프라인 운영 확인:** 컬럼·백필·캘린더 표기까지 넣었으므로 실제 접수 흐름에서 CRM 입력 → 앱 집계 → AR_DB 합치기가 의도대로 도는지 확인. 특히 **일부만 입금된 건**의 표기가 양쪽에서 일치하는지
