# 주간 업무 회고 (8월 3주차)

> 이번 주는 화~금 4일 작업(8/18~8/21, 월요일 8/17은 광복절 대체공휴일로 커밋 0건). 커밋 71건 — 홈페이지 V2 58건, 사건관리 앱 11건, CRM 2건, 인프라 repo 0건. 신규 이슈 12건, 이슈 코멘트 54건. 주의 축은 셋이었다 — **"네이버에 안 보인다"와 "광고 전환이 안 잡힌다"는 현업 신고를 계측 층까지 내려가 원인으로 바꾼 것**, 메인 홈 전면 재구성과 실물 다듬기, 그리고 그 배포 직전에 발견한 **어드민 권한 구멍 3종** 차단이다.

## 1. 주요 업무 성과 (Key Achievements)

**한 주 내내 같은 종류의 일을 했다 — 보고된 증상을 그대로 고치는 대신, 그 증상이 어느 층에서 만들어졌는지 실측으로 내려간 것.** 화요일은 "리뉴얼 홈페이지가 네이버에서 안 보인다"였고, 제출 상태는 전부 정상이었다(사이트맵 7,317 URL·중복 0, Yeti 가 robots 와 sitemap 을 실제로 읽어간 기록까지 확인). 크롤러 로그까지 내려가 보니 원인이 세 겹이었다 — **Yeti 요청 225건 중 116건(52%)이 이미지**였고, 이 도메인이 원래 2016~2023년 부산사무소 사이트라 **색인된 구 URL 수천 건이 전부 404**였으며, 사이트맵은 읽어가면서 그 안의 주소를 따라오지 않고 있었다. 금요일은 같은 구조의 더 큰 건이었다. 8/11 롤백 사유로 통용되던 "SEO·광고 성과 하락"을 지표로 대조하니 서울 광고는 **클릭이 12% 차이인데 전환만 7배 차이**였다 — 성과 하락이 아니라 **계측 소실**이었고, 레거시 지사별 js 16개 중 13개가 네이버 전환을 직접 쏘고 있는데 V2 에는 그 코드가 0건이라는 것이 물증이었다. 그 역할을 V2 코드로 옮겨 배포하고 전송 요청 본문까지 뜯어 검증했다. 수·목요일의 축은 **메인 홈 전면 재구성**이었다. 대행사 시안대로 히어로·붉은 유틸 바·분야 표·변호사 슬라이드를 다시 짜고 장표형 스크롤을 세운 뒤, 목요일 하루를 통째로 실물·실기기 확인에 썼다 — 거기서 **카카오톡 인앱 브라우저에서 홈이 스크롤조차 안 되던 것**이 나왔다. 그리고 수요일, 배포 직전에 어드민 지사 잠금을 구현하다 **잠그려던 계정이 오히려 전 지사로 열려 있던 것**을 발견해 막았다. 그 밖에 8월 초 상담 10건 유실 사고의 코드 측 원인(무음 실패)을 제거하고 대체 발송 안전망을 넣었으며, 사건관리 앱은 "모바일에서 저장 버튼을 누를 수 없다"는 한 증상을 네 갈래 원인으로 분해해 공통 레이어에서 해결했고, CRM 은 구글 어드민 개명이 DB 에 반영되지 않던 버그를 운영 데이터로 재현·수정해 배포했다.

    - 대행사 요청은 코드가 아니라 대부분 **DB 작업**이었다(레거시 지사 홈 head 는 전부 `tbl_company` 에서 나온다). 컬럼↔태그 대응표를 만들고, 뷰가 읽지 않는 `Meta_Title` 을 title 로 승격하면 9개 지사가 퇴화한다는 이유로 승격을 막았다

    - 라이브 실측으로 **`og:site_name` 과 `og:title` 이 같은 문구로 두 번 노출되던 것**과 상대경로 `og:image` 로 공유 미리보기가 빠지던 것을 함께 잡고, 배포 후 16개 항목을 요청안과 대조 검증

## 2. 기술적 도전 및 트러블슈팅 (Technical Challenges & Troubleshooting)

- **"제출은 정상인데 안 보인다" — 실패가 로그에 안 남는 층까지 내려가야 원인이 나온다:** 화요일 색인 조사는 제출 상태 점검에서 끝날 수도 있었다(사이트맵 제출됨, 중복 0, robots 허용, Yeti 가 실제로 읽어감 — 전부 정상). 한 층 더 내려가 Cloud Logging 의 크롤러 요청을 집계한 뒤에야 **네이버가 배정된 요청량의 절반을 이미지 최적화 주소에 쓰고 있다**는 것이 보였다. 금요일 전환 조사도 같은 모양이었다 — GTM 콘솔만 보면 태그가 멀쩡히 살아 있는데, 실제 발신자는 GTM 이 아니라 레거시 지사별 js 였다. **두 건 모두 "정상으로 보이는 계측 화면"이 원인을 가리고 있었고, 로그와 게시본이라는 다른 출처를 열어야 진실이 나왔다.**

- **계측의 경계를 다시 그었다 — 네이버 전환은 코드가, GA4·구글Ads 는 GTM 이:** 전환을 GTM 으로 되잡는 안이 당연해 보였지만, V2 지사 페이지에는 **11개 지사의 카톡·톡톡·예약 링크가 모두 들어 있다**(푸터·지사 목록). 레거시에 없던 구조라 `Click URL 에 kakao 포함` 같은 조건은 V2 에서 타 지사 클릭까지 자기 전환으로 집계한다 — URL 조건을 유지하는 한 못 고친다. 반면 코드는 호출 지점이 어느 지사 화면인지 이미 안다. 그래서 **돈이 걸린 네이버 전환은 코드가 보장하고, 라벨을 대행사가 자주 바꾸는 구글Ads 는 GTM 이 중계**하도록 경계를 정했다. 구글Ads 를 코드로 옮기지 않은 이유(`gtag.js` 로더와 계정 7개를 프론트가 짊어지게 되고 라벨 변경이 배포를 요구한다)도 함께 기록했다.

- **잠그려던 계정이 오히려 열려 있었다 — 권한 기본값의 방향:** 지사 잠금을 구현하며 발견한 두 구멍은 **둘 다 "정보가 없을 때 열어주는" 방향**이었다. 구글에서 지사를 특정하지 못한 계정, 열람 지사 목록이 빈 배열인 계정이 모두 전 지사 열람으로 처리되고 있었다. 권한은 **막히면 바로 항의가 오지만 잘못 열리면 아무도 모르게 샌다** — 그래서 소속이 없으면 인가를 거부하고 어느 값을 채워야 하는지 로그로 남기는 쪽으로 정했다. 서버단 차단으로 구현한 이유도 같다(화면에서 콤보만 좁히면 주소창 수정으로 뚫린다). 조직키를 단일값으로 다루던 것을 실제 다중값으로 정정한 것은 범위가 더 넓다 — 사건관리 앱과 CRM 이 **같은 값을 읽으므로 잘못 잡으면 세 시스템의 지사 범위가 함께 어긋난다.**

- **브라우저가 조용히 버리는 것들 — 세 건이 같은 주에 나왔다:** ① 카카오톡 인앱에서 홈이 멈춘 것은 `dvh` 를 모르는 브라우저가 **높이·이동 선언만 버리고 입력 제어와 감추기는 살려 둔** 결과였다(부분 실패가 완전 실패보다 나쁜 전형). `matchMedia` 로는 "이 단위를 아느냐"를 물을 수 없어 CSS `@supports` 와 JS `CSS.supports` 양쪽에 같은 게이트를 걸어야 했다. ② 모바일 검색 팝업이 안 보이던 것은 헤더의 `backdrop-filter` 가 `fixed` 자손의 기준 상자를 가로채 판이 헤더 높이 안에 눌린 것이었다. ③ 사건관리 앱 모달이 실기기에서만 잘리던 것은 주소창이 뷰포트를 먹어 `90vh` 가 실제 표시 영역보다 컸기 때문이다. **셋 다 데스크톱 반응형 모드에서는 재현되지 않는 종류**였고, 실기기·실물 확인에 하루를 쓴 것이 값을 했다.

- **증상마다 방어를 덧붙이는 것보다 원 구조로 돌아가는 편이 짧았다:** 장을 넘기다 푸터로 떨어지는 경로가 넷이었다(휠 한 칸 더·터치 튕김·스크롤바 직접 잡기·포커스 이동). 하나씩 막는 대신 문서 스크롤 여유 자체를 없애는 1차 방어를 넣었는데, 레거시를 다시 열어보니 **푸터가 마지막 장 안에 들어 있었다.** 같은 구조로 바꾸자 1차에서 넣은 방어 세 개(`scrollbar-gutter`·`scrollTo` 보정·마지막 장 잠금 해제)가 전부 필요 없어졌고 이음선·왕복 덜컹거림·새로고침 어긋남이 생길 자리 자체가 사라졌다. **레거시를 "옮길 대상"이 아니라 "이미 답을 낸 참조"로 읽은 것이 이번 주 두 번 통했다** — 전환 조사에서도 레거시 js 16개가 답이었다.

- **판단을 세 번 뒤집었고 그중 하나는 내 근거였다:** ① 목요일에 '메인 홈페이지' 링크를 정본 절대주소로 바꾸면서 **보고 있던 지점은 유지**하도록 했는데, 금요일에 그러면 지사 화면에서 빠져나갈 통로가 없어 링크가 아무 일도 하지 않는 것처럼 보인다는 지적을 받아 지점을 떼는 쪽으로 뒤집었다(주석의 "⚠️ 지점은 유지한다"를 반대 취지로 다시 씀). ② 폰 히어로 배경을 첫 장 고정으로 바꿨던 근거 둘이 실측과 달라 되살렸고, "각인 겹침은 이미지 재크롭이 필요해 코드로는 못 한다"고 적어 둔 것도 비율을 재서 닫았다. ③ 서울 wa 키 오타를 판정하며 **"네이버 키는 `s_` + 12자 규격"이라고 단정했는데 근거가 약했다** — 관측한 키 4개가 전부 12자였다는 것을 규격처럼 적은 것이라, 공식 문서에 길이 규정이 없음을 확인하고 스스로 철회한 뒤 콘솔 실측(등록 목록 21행)으로 다시 확정했다. **틀린 근거로 맞는 결론에 도달한 것을 그대로 두지 않은 것**이 이 건의 실질이다.

- **도구를 하나 만들자 조사 속도가 바뀌었다:** GTM 조사는 콘솔을 사람이 한 화면씩 넘겨야 하는 작업이라 컨테이너 13개를 보는 데 하루가 걸릴 일이었고, 무엇보다 **콘솔은 작업공간 초안을 보여줘 게시본과 착각할 수 있다**(8/14 광주에서 실제로 그 사고가 났다). 게시본이 `gtm.js` 로 공개 배포된다는 성질을 이용해 파싱 스크립트를 만들자 그날 안에 17개를 전수로 훑었고, wa 공통키 공유·오타 키·죽은 트리거가 연달아 나왔다. **116줄짜리 스크립트가 만든 것은 속도가 아니라 "지금 라이브인 것"이라는 기준선이었다.**

- **바이트 단위 제약이 SEO 작업을 막고 있었다:** 수원 head 개편은 문구를 넣기만 하면 되는 일로 보였는데 저장이 실패했다. `KoName` 이 `nvarchar` 가 아닌 `varchar(50)` 이라 한글 1자가 CP949 2바이트로 계산돼 31자 타이틀이 56바이트가 된 것이다. 어드민 폼으로 해도 같은 오류가 난다. 축약으로 우회할 수 있었지만 **서울이 이미 49바이트라 현행 폭에서는 어느 지사도 SEO 문구를 더 늘릴 수 없다**는 것이 확인돼 컬럼 확장으로 갔다. `sp_helpindex` 로 해당 컬럼이 어느 인덱스에도 없음을 먼저 확인해 메타데이터 전용 변경임을 보장한 뒤 실행했다.

## 3. 총평 및 향후 과제 (Wrap-up & Next Steps)

> **"'안 보인다'와 '안 잡힌다'의 원인이 전부 계측 층에 있던 한 주"**

이번 주에 받은 두 개의 현업 신고는 문장으로는 서로 달랐지만("네이버에서 안 보인다", "광고 전환이 떨어졌다") 원인의 위치는 같았다 — **일이 실제로 일어나는 층과 우리가 들여다보던 화면이 어긋나 있었다.** 사이트맵 제출 화면은 정상이었지만 크롤러 로그에서는 예산의 절반이 이미지로 새고 있었고, GTM 콘솔에서는 전환 태그가 멀쩡했지만 실제 발신자는 레거시 지사별 js 였다. 두 건 모두 **다른 출처를 열어본 뒤에야** 원인이 나왔고, 그래서 이번 주 산출물 중 가장 오래 쓰일 것은 조치가 아니라 게시본 X-ray 도구와 전환 매핑표 같은 **기준선**일 것이다. 특히 롤백 원인 규명은 성격이 다르다 — 8/11 롤백은 "성과가 나빠졌다"는 이해로 봉인돼 있었는데, 클릭은 그대로인데 전환만 7배 빠졌다는 것이 확인되면서 **컷오버의 정의 자체가 "도메인 전환"에서 "13개 파일의 전환 로직 이관"으로 바뀌었다.** 다시 컷오버할 때 같은 실패를 반복하지 않을 근거가 생긴 것이 이번 주의 가장 큰 값이다. 다른 축인 메인 홈은 만들고(수) 실물에서 부수는(목) 이틀 구성이었는데, 부수는 날에 나온 것들이 더 무거웠다 — 카카오톡 인앱에서 홈이 통째로 죽어 있던 것을 아무도 신고하지 않았다는 사실이 특히 그렇다. 그리고 배포 직전에 발견한 어드민 권한 구멍은 이번 주 유일하게 **"보고된 적 없는 문제"** 였다. 잠그는 기능을 만들다 잠금 대상이 이미 열려 있던 것을 발견한 셈이라, 기능 개발이 감사 역할을 한 경우다.
